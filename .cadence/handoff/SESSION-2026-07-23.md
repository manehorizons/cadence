## Carry-forward gotchas
- **`gh` commands can silently target the wrong branch across a worktree/primary-checkout boundary.** While an `EnterWorktree` session is active, the bash cwd was observed snapping back to the worktree path after `cd`-prefixed commands into the primary checkout ran successfully. `gh pr create` with no explicit `--head` infers the branch from cwd — this combination caused a real mistake (PR #283 merged the wrong, already-merged branch as a no-op instead of the intended one). Always pass `--head <branch>` explicitly to `gh pr create`/`gh pr merge` when working across that boundary in the same session; never rely on inferred cwd branch context.
- **`gh pr merge --delete-branch`'s failure mode goes further than previously known.** When the local post-merge checkout step fails (because `main` is checked out elsewhere, e.g. the primary checkout) — the known `gh-pr-merge-local-checkout-failure` pattern — the REMOTE branch delete is *also* skipped this time, not just the local one. Always verify with `git ls-remote --heads origin` after any `--delete-branch` merge and manually delete any stray remote branch found.
- **Squash-merged commits are never literal ancestors.** `git merge-base --is-ancestor <original-commit> main` reports false even when the commit's content is fully merged (squash merges intentionally discard original parentage). Verify via content diff (`git diff <original-commit> main -- <files>` should be empty) before treating a worktree/branch as safe to discard — ancestry checks give a false "not merged" alarm.
- PR #281's squash commit accidentally swept in an unrelated, previously-unpushed handoff-stamp commit from the *prior* session (its branch was forked from local `main`, which had that commit as an unpushed ancestor, rather than from `origin/main`).
