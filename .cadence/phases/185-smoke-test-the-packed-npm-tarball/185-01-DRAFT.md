# 185-01 — Smoke-test the packed npm tarball

## Objective

`scripts/publish-proof.mjs` already publishes the 3 packages to an ephemeral
local verdaccio, clean-installs them, and asserts both bins run — but its
post-install check only invokes `--help`. Extend it to actually exercise the
real DRAFT→BUILD→SETTLE loop (`cadence init` → `cadence draft new` → mark the
task DONE → `cadence settle run --auto`, offline `mock` provider) against the
installed CLI inside that clean temp project, so a broken published artifact
(missing dist files, bad bin shebang/dispatch, ESM resolution failure) is
caught by the reversible proof before a release ships it, not just that
`--help` prints. Stays the existing operator-invoked script; not wired into
CI in this phase.

## Acceptance Criteria

### AC-1: the reversible proof exercises the real loop, not just --help
Given the three packages are published to the ephemeral verdaccio and
installed into the clean temp project (as today)
When `node scripts/publish-proof.mjs` runs its post-install checks
Then it additionally runs `npx cadence init`, `npx cadence draft new`, marks
the resulting task DONE via `npx cadence build task ... --status=DONE`, and
`npx cadence settle run --auto` inside that clean temp project — each step
exiting 0 — before printing `PUBLISH-PROOF: PASS`

**As built:** the real DRAFT→BUILD loop transition requires an explicit
`npx cadence draft approve <phase> <num>` between `draft new` and `build
task` (confirmed against `services/draft-approve.ts` — `build task` refuses
without it), so the shipped sequence is 5 steps, not 4. This AC's prose was
written before that requirement was traced; the actual sequence is the
source of truth (`exerciseLoopSteps()` in `scripts/publish-proof.mjs`,
covered by `packages/core/tests/scripts/publish-proof.test.ts`'s "AC-1 step
sequence" tests).

### AC-2: a broken published artifact fails the smoke test loudly
Given one step of the new init→draft→settle exercise fails (simulated via a
unit test around the new loop-exercise helper — not against the real npm
registry)
When that step is run
Then the script throws/exits non-zero with the failing step's captured
stdout/stderr, in the same `must()` failure format the script already uses,
rather than silently passing because only `--help` was checked

### AC-3: teardown stays unconditional even when the loop exercise fails
Given the new init→draft→settle exercise throws partway through (e.g.
settle refuses)
When the script's `finally` block runs
Then verdaccio's process tree is still killed and all OS-temp dirs are still
removed, matching the existing reversible-proof guarantee

## Tasks

- files: `scripts/publish-proof.mjs`
- action: implement `exerciseLoop(proj)` running `npx cadence init`, `npx cadence draft new`, `npx cadence build task <id> --status=DONE`, `npx cadence settle run --auto` inside the clean-installed temp project, using the existing `must()`/`run()` pattern for each step; call it after the current bin `--help` checks and before the `PASS` log line
- verify: `node scripts/publish-proof.mjs` completes and its final log line confirms the loop ran (e.g. "... loop: init->draft->settle: PASS")
- done: AC-1

### T2: Make exerciseLoop() failures surface like existing must() failures, teardown-safe
- files: `scripts/publish-proof.mjs`
- action: reuse `must()` for every step of `exerciseLoop()` so a broken step throws with captured stdout/stderr and is caught by the outer `try`, letting the existing `finally` teardown still run
- verify: fault-injecting a broken step (e.g. pointing at a corrupted temp project) exits non-zero with that step's captured output, and verdaccio/OS-temp teardown still happens
- done: AC-2

### T3: Add a focused test for exerciseLoop()'s step sequence and failure/teardown behavior
- files: `packages/core/tests/scripts/publish-proof.test.ts` (new, mirroring `packages/core/tests/scripts/release-integrity.test.ts`), `scripts/publish-proof.mjs` (additive only — see action)
- depends: T1, T2
- action: `release-integrity.mjs` is importable-and-testable because it guards its side-effecting `main()` behind `if (process.argv[1] && import.meta.url === pathToFileURL(process.argv[1]).href)` and exports pure functions directly; `publish-proof.mjs` currently has neither guard and runs its whole `try/finally` body at module load. Apply the same guard to `publish-proof.mjs` (wrap the existing top-level `try/finally` body in a `main()` function, call it only under the same import.meta.url guard) and export a pure function describing `exerciseLoop`'s step sequence (e.g. the list of `[cmd, args, label]` tuples it runs) so a test can import the module without triggering a real verdaccio/npm run and assert the exact sequence + failure/must() semantics. This is an additive wrapper only — do NOT change T1/T2's already-verified `exerciseLoop` step logic, `must()`/`run()` semantics, or teardown ordering; only restructure for importability
- verify: `pnpm --filter @manehorizons/cadence-core test -- publish-proof` passes locally; `node scripts/publish-proof.mjs` (run directly, real end-to-end) still passes exactly as before, proving the guard didn't change runtime behavior
- done: AC-3
