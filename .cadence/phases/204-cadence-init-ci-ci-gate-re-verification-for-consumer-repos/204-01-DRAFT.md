# 204-01 — cadence init --ci: CI-gate re-verification for consumer repos

## Objective

Ship cadence verify phase (state-independent, phase-scoped re-derivation of whether a settled phase's AC coverage still holds) and cadence init --ci (a GitHub Actions workflow scaffold + branch-protection recipe that calls it), closing rec-20260709-003.

## Acceptance Criteria

### AC-1: coverage re-derivation is phase-scoped and collision-safe
Given a phase settled with cadence verify phase's inputs (DRAFT.md, SUMMARY.json) present, including a repo where a different phase has an identically-numbered AC test
When cadence verify phase <phase> <num> re-derives coverage scoped to that phase's own DRAFT task files against the current working tree
Then it reports drift for any previously-executed AC whose linked test was deleted or gutted after settle, without requiring any active loop state, and without a false negative caused by another phase's colliding AC number

### AC-2: changed discovery scopes correctly
Given a base ref and HEAD where zero or more .cadence/phases/*/*-SUMMARY.json files were added, modified, renamed, or deleted
When cadence verify phase --changed --base <ref> runs
Then it discovers exactly the phases whose SUMMARY.json was added/modified/renamed (excluding deletions via --diff-filter=ACMR), and reports "nothing to verify" (exit 0) only when the diff genuinely computed and was empty

### AC-3: git-diff failure is loud, not silent
Given --changed is used with an unfetched base ref, a shallow clone, or an invalid --base value
When the git diff computation fails
Then the command exits 2 with a distinct, loud stderr message, never silently treated as "nothing changed"

### AC-4: malformed inputs fail loud and distinct
Given a phase's SUMMARY.json is missing, malformed JSON, or schema-invalid, or its DRAFT.md is missing or unparseable
When cadence verify phase is run against that phase
Then it produces a distinct stderr message per failure case and exits 2

### AC-5: test-command re-run is separate from coverage drift
Given verification.testCommand is configured
When cadence verify phase runs (default), or is run with --no-test-run
Then the test-command re-run reports pass/fail as a line distinct from coverage drift (exit 1 on failure), is skipped entirely under --no-test-run, and the output/docs state plainly that this line is suite-wide, not attributed to the specific AC whose test failed

### AC-6: exit codes and --json are pinned
Given verify phase is invoked with various argument combinations
When neither [phase] [num] nor --changed is supplied, or --json is requested
Then the neither-supplied case exits 2 as a usage error rather than a silent no-op, and --json emits { mode, results, testRun } under one schema for both single-phase and --changed multi-phase invocations, with exit codes pinned to 0 clean / 1 drift-or-test-failure / 2 usage-or-input error

### AC-7: init --ci scaffolds a working workflow
Given a consumer repo with a lockfile-detectable package manager
When cadence init --ci runs
Then it writes .github/workflows/cadence-verify.yml with a working --changed --base invocation and a real (not placeholder) install + test command, and refuses (nonzero exit, no file written) if that path already exists

### AC-8: init --ci prints, never executes, the branch-protection recipe
Given cadence init --ci has just written the workflow file successfully
When it finishes
Then it prints the branch-protection gh api recipe, substituting the real owner/repo when resolvable from origin, and never calls the GitHub API itself

## Boundaries

- DO NOT change `gates/engine.ts`, the tier×profile gate matrix, or any Zod schema (`SummaryZ`/`DraftZ` are read-only in this phase).
- DO NOT make `cadence verify phase` read or require `.cadence/state.json` — it must work with no active loop state.
- DO NOT add support for GitLab, CircleCI, or any non-GitHub CI provider (YAGNI — this repo's own dogfood target is GitHub Actions only).
- DO NOT re-run `structural-verifier` or `boundary-scan` against historical phase artifacts — only coverage + test-command re-derivation are in scope.
- DO NOT attempt per-AC attribution of which AC's test failed within a whole-suite test-command failure — that's a documented limitation (AC-5), not a gap to close here.
- DO NOT have `cadence init --ci` call the GitHub API (branch protection) itself — print the `gh api` recipe only, never execute it.
- DO NOT add an overwrite/`--force` flag for an existing `.github/workflows/cadence-verify.yml` — hard refusal only, matching `draft new`'s existing-file precedent.
- DO NOT add a new runtime dependency (no YAML library, no safe-regex library, no subprocess-management library) — string-literal YAML rendering and `node:child_process`/`node:fs` only.
- DO NOT redefine a local `git(cwd, args)` test helper in any new test file — reuse the shared `runGit` export added to `cadence-testkit` in T2 (this repo's duplicate-detection tooling blocks a second copy).
