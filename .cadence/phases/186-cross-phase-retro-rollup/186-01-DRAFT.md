# 186-01 — Cross-phase retro rollup/trend view

## Objective

Add a read-only `cadence retro` CLI command that scans every settled phase's post-settle retro artifact (`.cadence/phases/*/*-RETRO.json`, from the Phase 174 retro-artifact feature) and produces a cross-phase rollup: how many phases carry friction, which gate bypasses and rough-task statuses recur, and which code-review/security-audit/boundary-scan finding categories repeat across phases — so an operator or CI can answer "is there anything across recent settles worth looking into" without manually grepping phase directories. Fulfils rec-20260712-002; the dependent rec-20260712-003 (feeding retro friction back into Praxis recommendation scoring) is explicitly out of scope.

## Acceptance Criteria

### AC-1: Pure rollup computation across phase retros
Given N phase directories under `.cadence/phases/` each containing a `<draftId>-RETRO.json` matching `RetroDigestZ`
When `computeRetroRollup` is called with the parsed digests (each tagged with its phase/draft id)
Then it returns a `RetroRollup` aggregating: total phases scanned, phases with non-empty friction, gate-bypass frequency counts, rough-task status frequency counts, and finding-category counts (codeReview/securityAudit/boundaryScan), each sorted by descending frequency

### AC-2: Recurring-only signal, not just totals
Given a rollup where some friction item (e.g. a bypassed gate name) appears in only one phase and another appears in 3+ phases
When the rollup is computed
Then items occurring in only one phase are grouped separately from items recurring in 2+ phases, so the recurring "worth investigating" signal isn't buried under one-time noise — this is the rec's "surfaces recurring workflow friction" intent, not merely a flat count

### AC-3: CLI wiring, terminal + JSON output
Given a repo with `.cadence/phases/*/*-RETRO.json` artifacts present
When `cadence retro` is run
Then it prints a terminal-rendered rollup by default, and valid JSON via `--format json`, following the same format-flag and exit-code conventions as `cadence intelligence stats`

### AC-4: Empty/missing-artifact handling
Given a repo with no `.cadence/phases/` directory, or phases present but none containing a `*-RETRO.json`
When `cadence retro` is run
Then it prints a clear "no retro artifacts found" message (never an empty JSON object that could be misread as data) and exits 0 — mirrors the `intelligence stats`/`audit` "No intelligence ledgers present" precedent

### AC-5: Malformed/missing individual artifact tolerance
Given one phase directory whose `*-RETRO.json` fails `RetroDigestZ` validation or is unreadable, among several otherwise-valid ones
When `cadence retro` is run
Then that single phase is skipped with a stderr notice (best-effort introspection never throws) and the rollup still computes over the remaining valid phases

### AC-6: Docs stay in sync
Given the new command changes the CLI's registered command set
When the doc-content test suite runs
Then `docs/reference/commands.md` documents `cadence retro` (flags, behavior, and that it writes no files — read-only) and the command-count/marker-block assertions pass

## Boundaries

- Do NOT implement rec-20260712-003 (retro friction feeding back into Praxis recommendation scoring) — that's a separate, explicitly-dependent rec; out of scope here.
- Do NOT touch the settle-time retro-write path (`packages/core/src/services/retro.ts`'s `writeRetroArtifacts`/`runRetroOffer`, or `settle.ts`) — this phase only reads existing artifacts, never writes or mutates them.
- Do NOT add a GitHub-issue-filing or notification side effect to the rollup — it stays read-only diagnostics, matching `intelligence stats`/`audit`/`recommend`'s pattern.
- Do NOT change `RetroDigestZ`'s existing schema or fields — only additive new types for the rollup output.
- Do NOT add migration/backfill tooling for historical RETRO artifacts that don't validate against the current schema — AC-5's best-effort skip is the only handling in scope.
