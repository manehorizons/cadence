# 211-00 — CLAUDECODE-aware messaging for anthropic provider + host-cli suggestion

## Objective

When `deep-verify`'s provider is `anthropic`, its credential (`ANTHROPIC_API_KEY`) is missing, AND the process is running inside a live Claude Code session (`CLAUDECODE=1`), `cadence doctor`'s `verification-readiness` check and `cadence activate`'s key-missing message currently print the same generic "key missing, export it" text as any other missing-key case — even though the user is, in this specific detectable situation, very likely to be confused about why their Claude Code login didn't already satisfy this. Both surfaces should additionally name the confusion directly and proactively suggest `host-cli` as the provider that reuses the session's own Claude Code auth with zero separate key, sibling to the runtime fallback-warning wording already shipped in phase 209.

## Acceptance Criteria

### AC-1: `cadence doctor`'s verification-readiness check is CLAUDECODE-aware
Given `deep-verify`'s effective provider is `anthropic`, its credentials are
missing (`assessReadiness(...).keyPresent === false`), and `env.CLAUDECODE ===
'1'` — so `checkVerificationReadiness`
(`packages/core/src/doctor/run.ts` ~707-714) takes the real-provider-missing-
key branch,
When `checkVerificationReadiness` builds the `warning` `DoctorCheck`,
Then its `detail`/`remediation` text — in addition to the existing "deep-
verify is set to 'anthropic' but its credentials are missing" wording —
states that a Claude Code login does not supply `ANTHROPIC_API_KEY` (`anthropic`
calls the Anthropic SDK directly and needs a separately API-billed key) and
proactively suggests `cadence activate --provider host-cli` as the way to
reuse this session's own auth instead, verified by a test in
`packages/core/tests/doctor/verification-readiness.test.ts` asserting the new
clause is present when `CLAUDECODE=1` is passed in the injected `env` (the
`AC-1` token inside an asserting `it()` block). When `env.CLAUDECODE` is unset
or the provider isn't `anthropic`, the check's output is byte-identical to
today (no regression to the existing four tests in that file).

### AC-2: `cadence activate`'s key-missing message is CLAUDECODE-aware
Given `cadence activate` resolves to `provider: anthropic` with
`keyMissing: true` (`runActivate`, `packages/core/src/cli/commands/
activate.ts` ~84-122) and `env.CLAUDECODE === '1'`,
When `renderText`/`renderJson` (`packages/core/src/activate/render.ts`) render
the `keyMissing` branch,
Then the human text — in addition to today's "⚠ ANTHROPIC_API_KEY is not set
… export ANTHROPIC_API_KEY=…" lines — states the same Claude-Code-login-
doesn't-satisfy-this distinction and suggests `cadence activate --provider
host-cli`, and `renderJson`'s output carries an additional field surfacing
that the suggestion applies (so a `--json` caller can detect it
programmatically) — verified by tests in
`packages/core/tests/activate/render.test.ts` asserting both the new text
(text mode) and the new field (json mode) when the passed-in result signals a
Claude Code session, with the existing "export ANTHROPIC_API_KEY" substring
still present. When the session flag is absent/false or the provider isn't
`anthropic`, `renderText`/`renderJson` output is byte-identical to today's
(no regression to the existing four tests in that file).

## Constraints

- Detection: reuse the already-documented, already-cited `CLAUDECODE=1`
  session signal (`packages/core/src/verify/host-cli-client.ts`'s
  `SELF_INVOCATION_ENV_VAR`/`isSelfInvocation`, itself sourced from
  https://code.claude.com/docs/en/env-vars). Add ONE new exported, shared
  helper (e.g. `isClaudeCodeSession(env)`) in `packages/core/src/activate/
  assess.ts` — already the shared module between `doctor` and `activate` — 
  rather than duplicating the env-var-name literal a third place. Do not
  refactor `host-cli-client.ts`'s existing self-invocation guard to depend on
  it; that guard serves a different purpose (spawn-time deadlock avoidance)
  and is out of scope here.
- `renderText`/`renderJson` are pure (no direct `env` read) — the Claude-Code
  signal must be computed by the caller (`runActivate`, which already reads
  `env`) and threaded in as a new field on `ActivationResult`, mirroring how
  `ping` is already threaded in as an optional field.
- Do NOT touch the phase-209 `verifier-factory.ts` fallback-warning literal,
  the phase-210 `docs/providers.md` callout, or `config-explain/build.ts`'s
  `provider-no-key` warning — all three are out of scope (already shipped or
  belong to a different surface not named in this recommendation).
- Do NOT add CLAUDECODE detection to any `local`/`host-cli`/`mock` branch of
  either surface — this is anthropic-specific, matching phase 209's scope
  boundary.
- Best-effort convention: neither surface may throw if `env` lacks the var —
  absence must read as "not a Claude Code session", not an error.
- Keep both surfaces' existing byte-exact/regex-matched substrings
  (`ANTHROPIC_API_KEY`, `export ANTHROPIC_API_KEY`) intact so the current four
  tests per file stay green untouched.

## Open Questions

- **Exact wording (bikeshed).** Doctor's remediation and activate's stderr
  text should each stay to 1-2 terse sentences (matching phase 209/210's
  tone) and explicitly name `cadence activate --provider host-cli` as the
  concrete next step. Human to approve final sentences before/at DRAFT
  review.
- **JSON field name for AC-2.** Proposed: `claudeCodeHostCliSuggested:
  boolean` on `renderJson`'s output, included only when applicable (mirrors
  the existing conditional-field convention for `ping`). Open to a different
  name at DRAFT time.
