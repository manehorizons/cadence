# 258-01 — JS/TS coverage scanner: model regex literals in the span mask

## Objective

`packages/core/src/verify/coverage-profiles/mask.ts`'s `classify()` state
machine has no concept of a JS/TS regex literal. A raw or escaped paren or
backtick inside a `/regex/` corrupts `strategies.ts`'s depth-aware paren
matcher (misreads the file's remaining structure) and `mask.ts`'s
string-delimiter handling (a stray backtick flips template-literal mode),
desyncing span detection for the rest of the file — reproduced live in phase
251 (`packages/core/tests/docs/phase251-ledger.test.ts`, worked around there
by avoiding `.toMatch(/regex/)` in favor of `.toContain('string')`, not
fixed at the source). Teach `classify()` a regex-literal lexical category so
these characters are correctly masked, without silently misclassifying a
division expression as a regex. Where the two are genuinely ambiguous, fail
loudly via `cadence verify coverage --explain` rather than guessing — this
profile's existing false-positive-averse invariant (`strategies.ts`: an
unresolved boundary yields no span, never a best-guess span) extends to the
new regex category, it does not get relaxed for it.

**Scope correction found during BUILD (T4's repo-wide sweep, independently
spot-checked against the real built scanner before accepting):** the defect
surface is wider than "parens or backticks." `mask.ts`'s `classify()`
registers `'`, `"`, **and** `` ` `` all as JS/TS string delimiters (see
`js-ts.ts`'s `syntax.strings`), so **any** of the three inside an
unrecognized regex literal — not just a paren or a backtick — desyncs the
state machine. Cleanest exhibit: `packages/core/tests/quickstart.test.ts`'s
`/legalMoves|position:\s*['"]?draft-new/i` contains no paren or backtick at
all, only a `'` inside a `['"]?` character class, and alone drops the
scanner from 3 real test blocks to 0. **T2 must implement a genuine
regex-literal mode** (parallel to the existing `'string'`/`'comment'` modes
in `classify()`'s `Mode` union) that protects every character inside the
regex — parens, quotes, backticks, everything — until the real closing `/`,
not a narrow special-case for only parens/backticks. This is what "teach
`classify()` a regex-literal lexical category" already meant; this note
exists so no implementer narrows it back down to the original bug report's
literal wording.

**Design decision, made at DRAFT time, binding for BUILD:** per the source
handoff's own ordered evaluation (parser-already-in-graph →
narrowly-scoped-parser-dependency → masker-only heuristic →
fail-loudly-on-ambiguity), `packages/core` carries no JS/TS parser as a
runtime dependency today (checked `packages/core/package.json`:
`@anthropic-ai/sdk`, `cadence-types`, `@modelcontextprotocol/sdk`,
`commander`, `zod` — no parser), and this repo's zero-runtime-dependency
bias means adding one needs the operator's explicit sign-off, not a
DRAFT-time assumption. This phase implements the **masker-only heuristic**
(a context-sensitive `/`-disambiguation directly in `classify()`): never
misread division as regex correctness-wise, and where genuinely ambiguous,
fail loud per T3/AC-4 instead of reaching for a dependency. If T2 discovers
the heuristic cannot hold the line without unacceptable false positives,
**stop and report — do not silently add a parser dependency mid-BUILD.**

## Acceptance Criteria

### AC-1: regex literals containing parens no longer corrupt call-expression depth tracking
Given a dedicated fixture in **this phase's own new test file** (not
`packages/core/tests/docs/phase251-ledger.test.ts`, which stays untouched —
another phase's artifact) replicating phase 251's exact defect shape: an
`it()`/`test()` block whose assertion uses `.toMatch(/regex containing an
unescaped or escaped paren/)`
When `cadence verify coverage` scans that fixture
Then the block's call-expression span resolves to its real closing paren,
and the assertion inside is correctly counted as coverage (evidenced by an
asserting block carrying the token `258-01/AC-1`)

### AC-2: regex literals containing backticks no longer falsely toggle template-string masking
Given a dedicated fixture in this phase's own new test file containing an
`it()`/`test()` block whose assertion uses `.toMatch(/regex containing a
backtick/)`
When `cadence verify coverage` scans that fixture
Then the backtick inside the regex is not treated as opening or closing a
template literal, and all code following the regex in the file is
classified correctly (not swallowed into a false string span), evidenced by
an asserting block carrying the token `258-01/AC-2`

### AC-3: division expressions are never misclassified as regex literals
Given a JS/TS fixture containing a division expression immediately following
an identifier, a number literal, or a closing `)`/`]`/`}` (e.g. `a / b`,
`arr[0] / 2`, `fn() / 2`)
When `classify()` runs over the file
Then the `/` is treated as a division operator, not a regex-literal opener,
and subsequent code is classified normally — this must hold across every
division case in T1's corpus, not just one, evidenced by an asserting block
carrying the token `258-01/AC-3`

### AC-4: syntax outside T2's documented preceding-token vocabulary fails loudly, never silently
T2's heuristic is explicitly **not** a total classifier — it documents a
bounded, enumerated set of preceding code-mode token categories (specific
operators, keywords, brackets) that resolve `/` to regex-eligible or
division-eligible. This is a deliberate scope boundary, not an attempt to
cover 100% of valid JS/TS grammar.
Given a fixture whose preceding-token context is, by construction,
outside T2's documented enumerated set (T2's own PR names which category
and why it was left out)
When `cadence verify coverage --explain` runs against that fixture
Then it reports a diagnosable message naming the unrecognized
preceding-token context, instead of silently guessing regex-or-division or
silently zeroing out coverage credit with no explanation — evidenced by an
asserting block carrying the token `258-01/AC-4`

### AC-5: no regression, and no AC receives assertion credit from outside a real test block
Given the existing JS/TS coverage-profile test suite, phase 166/167/169's
own fixtures, and a new regression-assertion block in this phase's test file
that re-scans every fixture from T1's corpus after the fix
When the full test suite runs after the fix
Then every existing JS/TS coverage test still passes unchanged, phase
166/167/169's byte-for-byte parity for regex-free files is unchanged, and
the new regression assertion (carrying the token `258-01/AC-5`) confirms no
span in T1's corpus is produced outside a real test block
