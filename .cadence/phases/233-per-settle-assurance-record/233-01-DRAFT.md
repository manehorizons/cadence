# 233-01 — Per-settle assurance record

## Objective

With verifier identity persisted (phase 232), compute one **assurance record**
per settle: a derived, whole-run answer to "how strongly was this settle
actually verified?", composed from the per-gate verifier identities plus the
existing per-AC evidence-class ranking (`ai-verified > executed > assertion >
mention > unverified`). The record is *derived and reported*, not a new gate
— it adds no refusal and no bypass flag. Its job is to make a settle whose
gates all ran under `mock` visibly different, in the durable record, from one
verified for real. This phase is also where the spec's first binding tripwire
is evaluated: if the derivation cannot be expressed without gate-specific
special-casing, this phase stops here and phases 234–237 are abandoned.

## Acceptance Criteria

### AC-1: every settle carries a derived assurance record
Given a settle completes (gates have run, provenance persisted, per-AC
evidence classes computed)
When the SUMMARY is constructed
Then it carries an assurance record derived from the gate provenance array
and the per-AC evidence-class array

### AC-2: mock and real-provider settles are distinguishable
Given two otherwise-identical phases — one settled with every
verifier-capable gate running under the `mock` provider, one settled with a
real-provider-shaped fixture
When each produces its assurance record
Then the two records differ

### AC-3: the derivation is gate-agnostic (binding tripwire)
Given the assurance-record derivation function
When it is implemented
Then it is a pure function of the provenance array and the evidence-class
array with no gate-specific special-casing — if this cannot be achieved, stop
after this phase and abandon phases 234–237 per the spec's binding tripwire,
recording the outcome in this phase's SUMMARY decisions

### AC-4: settle's pass/refuse outcome is unchanged
Given the full settle gate sequence with the assurance-record step added
When compared to the pre-phase-233 settle path
Then every gate's pass/refuse verdict and existing refusal reasons are
byte-for-byte unchanged — the record is reported, never gating

### AC-5: the record is tamper-evident
Given a settled SUMMARY carrying an assurance record
When the record is edited post-settle
Then phase 223's settle-time content-hash attestation (`cadence summary
verify`) detects the tampering, exactly as it does for any other covered
field

## Boundaries

- DO NOT add a new gate, a new refusal path, or a bypass flag — the record is
  derived and reported only.
- DO NOT change `GATE_ORDER` or any gate's pass/refuse verdict.
- DO NOT special-case any individual gate name or id inside the derivation
  function — this is exactly what AC-3's tripwire tests. If it proves
  unavoidable, stop and record the outcome per the binding tripwire instead
  of working around it.
- DO NOT start phase 234 (kernel/verifier/consumer boundary) work in this
  phase — it is explicitly gated on this phase settling with AC-3 met.
