# 232-01 — Gate provenance carries verifier identity; SUMMARY schemaVersion 2

## Objective

Stop discarding verifier identity at persistence. Enrich `GateProvenanceZ` with
the verifier family and model that actually ran the `code-review` and
`security-audit` gates, threading the already-computed `provider`/`model`
(currently used only for logging and convergence sidecars) through to the
persisted provenance entry instead of dropping them. This is a SUMMARY shape
change, so bump `SummaryZ.schemaVersion` from the literal `1` to `1 | 2`:
writers emit `2`, readers accept both, and a pre-parse probe reads the raw
`schemaVersion` before Zod validation so an unrecognized *higher* version
reports "written by a newer Cadence" rather than a corruption error. Zero
`GATE_ORDER` changes, no gate behavior changes, no new refusals — purely, the
record stops lying by omission.

## Acceptance Criteria

### AC-1: code-review provenance names its verifier
Given a settle where the `code-review` gate has run
When the SUMMARY is persisted
Then the gate's `GateProvenanceZ` entry records the verifier family (and
model, when the verifier reports one) that actually ran it, so a `mock`-family
run and a real-provider run are distinguishable in the SUMMARY

### AC-2: security-audit provenance names its verifier
Given a settle where the `security-audit` gate has run
When the SUMMARY is persisted
Then the gate's `GateProvenanceZ` entry records the verifier family (and
model, when reported) that actually ran it, matching AC-1's shape

### AC-3: schemaVersion 2 is additive, not breaking
Given a new settle completes
When its SUMMARY is written
Then `schemaVersion` is `2`; and given a pre-existing SUMMARY with
`schemaVersion: 1`, when it is read by the updated reader, it still parses
unchanged

### AC-4: a newer SUMMARY reports its own currency, not corruption
Given a SUMMARY file whose raw `schemaVersion` is higher than any version this
build's `SummaryZ` recognizes
When it is read (via `cli/commands/summary.ts` and `verify/phase-replay.ts`)
Then the reader reports a distinct "written by a newer Cadence" diagnostic
rather than a generic parse/corruption error

### AC-5: gate behavior is byte-for-byte unchanged
Given the full settle gate sequence
When this phase's changes are applied
Then `GATE_ORDER`, every gate's pass/refuse verdict, and existing refusal
reasons are unchanged — this phase adds no gate and changes no outcome

## Boundaries

- DO NOT add a letter grade or a derived assurance ordinal — that is Phase
  233's per-settle assurance record, out of scope here.
- DO NOT change `GATE_ORDER`, any gate's pass/refuse semantics, or introduce a
  new refusal path.
- DO NOT touch `DeepVerifyMetaZ` or `deep-verify`'s existing provenance shape
  — it already persists `provider`/`model` correctly; this phase closes the
  gap only for `code-review` and `security-audit`.
- DO NOT special-case any gate other than `code-review`/`security-audit` in
  the registry's provenance-merge step — this phase's scope is exactly the
  two gates named in `rec-20260727-001`.
- DO NOT bump `packages/core/package.json`'s published version or touch
  `CHANGELOG.md`/the `CLAUDE.md` version line — that happens at release-cut,
  not in this phase.
