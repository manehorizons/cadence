# 58-01 — MCP server surface (cadence mcp serve)

## Objective

Add `cadence mcp serve` — a local **stdio** MCP server, in-process in `core`, that
exposes a curated read+write tool set so any MCP-capable host (Claude Desktop,
Cursor, generic agents) can drive the DRAFT→BUILD→SETTLE loop without a bespoke
adapter. This is a **third surface** on the single engine (CLI · Claude-Code
hooks · MCP); it covers the imperative loop only — ambient edit-time gates need
host hooks and are out of MCP's reach.

## Acceptance Criteria

### AC-1: serve handshake + exact tool discovery
Given a repo with an initialized `.cadence/`
When an MCP client connects to `cadence mcp serve` over stdio and lists tools
Then the handshake completes and the advertised tools are **exactly** the curated set
(`cadence_progress`, `cadence_status`, `cadence_recommend`, `cadence_draft_new`,
`cadence_draft_check`, `cadence_draft_approve`, `cadence_build_task`,
`cadence_settle`, `cadence_spec_new`, `cadence_spec_approve`) — and excluded
commands (`init`, `config`, `doctor`, `install`, `handoff`, `resume`) are **not**
advertised.

### AC-2: read tools return structured loop state
Given an initialized repo with a known loop position
When the client calls `cadence_progress`, `cadence_status`, and `cadence_recommend`
Then each returns a structured result carrying the same data the corresponding CLI
command computes (next action; loop position + active phase/draft; ranked
recommendations) — and none mutates `.cadence/` state.

### AC-3: write tools drive the loop end-to-end
Given an idle initialized repo
When the client calls `cadence_draft_new` → `cadence_draft_check` →
`cadence_draft_approve` → `cadence_build_task` (status `DONE`) → `cadence_settle`
in sequence
Then the loop advances IDLE→DRAFT→BUILD→SETTLE→IDLE with the same `.cadence/`
state writes (`state.json` + regenerated `STATE.md`, phase artifacts) a CLI run
would produce.

### AC-4: command-boundary gates fire over MCP
Given a draft that violates a structural-coherence rule
When the client calls `cadence_draft_check` (and, separately, `cadence_settle` on a
phase that fails a gate)
Then the tool result reports the gate failure exactly as the CLI command would —
the MCP surface runs the same command-boundary gate stack, it does not bypass it.

### AC-5: typed errors become MCP error results, not crashes
Given an **uninitialized** directory (no `.cadence/`)
When the client calls any write tool
Then the server returns an MCP error tool result (`isError: true`) whose message
carries the `NotInitializedError` reason **plus remediation** ("run `cadence init`
first") — the server process stays up and keeps serving subsequent calls.

### AC-6: `--repo` scopes the server to a target repo
Given two initialized repos A and B
When `cadence mcp serve --repo <A>` is launched from an unrelated cwd and a tool is called
Then all reads/writes target repo A's `.cadence/` (not the cwd, not B); with no
`--repo`, the server operates on its launch cwd.

### AC-7: the MCP SDK is lazy-loaded off the CLI hot path
Given the `@modelcontextprotocol/sdk` dependency on `core`
When an ordinary CLI command runs (e.g. `cadence progress`)
Then the MCP SDK module is **not** loaded — it is imported only inside the
`mcp serve` action, so non-MCP invocations pay no SDK load cost.

## Constraints

- **stdio transport only.** No HTTP/SSE/remote, no auth, no multi-tenancy. A
  remote surface is a future additive follow-up, explicitly out of scope.
- **In-process, in `core`, no new package.** `core` gains `@modelcontextprotocol/sdk`
  (runtime, lazy-imported) and a `mcp` subcommand registered in
  `cli/register.ts`. Server + tools live under `packages/core/src/mcp/`.
- **Service-function reuse for the curated commands only.** Each exposed command's
  logic is factored into a pure `async fn(repoRoot, args): Promise<Result>` that
  returns structured data; the existing CLI action call-then-renders, the MCP tool
  handler call-then-serializes. The other ~14 commands are untouched. No
  argv-replay through Commander; no subprocess-per-call.
- **Same state backend.** Writes go through the existing atomic `state.json` +
  `STATE.md` path; never hand-roll state writes. No new locking (single stdio
  client, single repo).
- **Each tool gets a hand-written input schema** (zod → JSON Schema) and a
  description; write-tool descriptions note the ambient-gate caveat.
- **TDD with `@manehorizons/cadence-testkit`.** MCP integration tests use the SDK's
  in-memory transport against an ephemeral repo — deterministic, offline, mock
  verifier; no subprocess, no network. Each AC referenced by its `AC-N` token in
  test text (test-coverage gate contract).
- **Deliverables beyond code:** (a) annotate `DESIGN.md` D5 recording MCP as a
  supported third surface (imperative-only; ambient gates need host hooks; not
  multi-host adapter pluralism — the anti-goal still holds); (b) a "Driving CADENCE
  over MCP" docs page (setup snippet, tool table, ambient-gate caveat) + a
  `cadence mcp serve` entry in `docs/reference/commands.md`; (c) a changeset —
  **minor** bump on `core` (+ `types` if new shared types land).

## Open Questions

- Should `cadence_spec_new` / `cadence_spec_approve` ship in v1, or wait until the
  core loop tools prove out? Default assumption: **ship them** — SPEC is part of
  the loop and the marginal cost over the other write tools is low.
- Is a doc-presence test for the D5 amendment worth wiring to an `AC-N` token, or
  is the amendment better treated as a review-checked deliverable? Default: keep it
  a **constraint/deliverable**, not a gated AC, to avoid a brittle doc-grep test.
