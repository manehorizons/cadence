# 132-01 — init --dry-run fit check

## Objective

Give `cadence init` a `--dry-run` mode that resolves everything a real init
would resolve and **prints a fit-check preview while writing nothing** — so an
adopter can run it inside an existing repo and see the detected project name,
gate profile, layout, test globs, verification/provider status, host surface,
and the exact files/dirs init would create, *before* touching the tree. Lowers
the perceived risk of running `init` in a populated repo. Source:
rec-20260619-005 (onboarding/trust lane — same lane as `doctor`/`activate`; no
new DESIGN.md D-number).

Design: extract a pure `planInit(cwd, opts, env)` → `InitPlan` that composes the
already-pure resolution helpers (`deriveName`, `detectTestGlobs`,
`suggestGateProfile`/`resolveGateProfile`, preset + activation + host decisions)
into a single inspectable plan, plus a `renderInitPlan(plan)` renderer. `--dry-run`
short-circuits the init action *before any write* and prints the rendered plan.
The real write path is **left byte-for-byte unchanged** — `--dry-run` is purely
additive; this phase does not refactor the write path to consume the planner.

## Acceptance Criteria

### AC-1: pure `planInit` builds an inspectable plan with no I/O
Given a working directory and a set of init options + env
When `planInit(cwd, opts, env)` runs
Then it returns an `InitPlan` capturing the resolved project name (and its
source: flag / package.json / dirname), preset, gate profile (and whether it
was explicit or git-suggested), layout (monorepo vs single-package), test globs,
verification provider + whether real verification would be on, host surface
(`.claude/` present + the would-wire decision), and the ordered list of paths
init would create — and it performs **no filesystem writes, no `process.exit`,
and is deterministic** given its inputs (cwd inspection is read-only)

### AC-2: `--dry-run` on a fresh repo previews and writes nothing
Given a repo with no `.cadence/`
When `cadence init --dry-run` runs
Then it prints the rendered fit-check (showing name, gate profile, layout, test
globs, provider status, host surface, and the would-write file list), creates
**no `.cadence/` directory and writes no files**, and exits 0

### AC-3: `--dry-run` on an already-initialized repo previews instead of refusing
Given a repo that already contains `.cadence/`
When `cadence init --dry-run` runs
Then it still prints the fit-check (resolved settings) and clearly states that a
real `init` would refuse because `.cadence/` is already initialized — and it
still writes nothing and exits 0 (it does **not** exit 2 the way a real init
does)

### AC-4: the preview reflects the resolution flags
Given resolution-affecting flags
When `cadence init --dry-run` runs with them
Then the preview honors them: `--gate-profile strict` shows `strict`;
`--activate` with `ANTHROPIC_API_KEY` present shows real verification on
(`anthropic`, deep-verify) while `--activate` without the key shows the
stay-on-mock note; and `--demo` lists the seeded demo phase DRAFT in the
would-write paths

### AC-5: documented and discoverable
Given the new flag
When the docs are updated
Then `--dry-run` is documented under `init` in `docs/reference/commands.md`,
surfaced in `docs/quickstart.md` as a "preview before you commit" step, and the
flag carries a `--dry-run` description in the `init` command registration

## Boundaries

- DO NOT change the real init write path's behavior or output — `--dry-run` is
  additive and short-circuits before any write; the happy path stays
  byte-for-byte unchanged. Do not refactor the write path to consume `planInit`
  in this phase.
- DO NOT touch the disk, spawn the host install, or call `process.exit` in the
  dry-run path — host wiring is reported as a would-wire *decision* only.
- DO NOT add `cadence init --json` in this phase — the `InitPlan` object makes it
  trivial later, but it is a separate surface and out of scope here.
- DO NOT change the standalone `--claude-md` path; when combined with
  `--dry-run`, the dry-run preview of the full scaffold takes precedence.
- DO NOT have `planInit` read or write any cadence state — it only inspects the
  cwd read-only (package.json, `packages/`, `.claude/`, git history), exactly as
  today's helpers already do.
