# 235-01 — Criteria-anchored review verifier: input + anchor ladder

## Objective

Give the code-review verifier sight of what the phase committed to. `CodeReviewInput` is `{ files, diff }` (`packages/core/src/verify/code-review.ts:22`) and `gates/code-review.ts:38` calls `verify({ files: touched, diff })` while holding the entire `Draft` on `ctx.draft` (`gates/types.ts:184`) — so the reviewer grades code against general good practice, never against the DRAFT's acceptance criteria. Extend the input with acceptance criteria, boundaries and task→AC refs; classify each finding by the strength of the criterion it anchors to through the anchor ladder (`executable > structured > declared > undeclared`, §7.1), derived from measured DRAFT and gate-provenance facts rather than verifier self-report; and emit an explicit criteria-gap finding where the diff does work no criterion covers, tripping the existing `evidenceFloor` per D2 rather than adding a second refusal primitive. `GATE_ORDER`, the HIGH-finding refuse contract, and every previously settled artifact are unchanged.

## Acceptance Criteria

### AC-1: The review verifier can see the phase's criteria
Given `CodeReviewInput` is `{ files, diff }` and the gate already holds the full `Draft` on `ctx.draft` but passes none of it through
When the input contract is extended and the gate populates it
Then `CodeReviewInput` carries the DRAFT's acceptance criteria (`id`, `name`, `given`, `when`, `then`), its `boundaries[]`, and task→AC refs (`Task.id`, `files`, `verify`, `done`, `status`), and a test asserts a non-empty criteria payload reaches the verifier for a DRAFT with ACs

### AC-2: The anchor ladder classifies findings by criterion strength
Given §7.1's four tiers — `executable`, `structured`, `declared`, `undeclared` — and D5's requirement that the ladder be a peer schema to `AcEvidenceZ` rather than a reuse of it
When a finding is anchored
Then it carries `{ kind: 'ac' | 'boundary' | 'none', ref?, tier }`, the tier is derived from measured DRAFT facts (non-empty `given`/`when`/`then` for `structured`; prose-only AC or a `boundaries[]` string for `declared`), and the ladder is declared as its own schema alongside `AcEvidenceZ`

### AC-3: `executable` is derived from real gate provenance, not assumed
Given the `executable` tier requires both that the AC is referenced by a task whose `verify` is a runnable command and that `build-test-must-pass` actually ran, and phase 232 ships per-gate provenance
When an AC is referenced by a task with a runnable `verify` but `build-test-must-pass` did not run in this settle
Then the anchor resolves to `structured` or lower and never to `executable`, proven by a test that holds the DRAFT constant and varies only the provenance

### AC-4: Unanchored findings above the floor surface as criteria gaps
Given a diff introducing a defect that no acceptance criterion and no boundary covers, and D2's rule that gap findings reuse the existing refusal path with no second refusal primitive (as built, `dec-20260729-005`: D1/§6 say "severity floor" while D2 names `evidenceFloor`; those rank different things — `gates.evidenceFloor` is an `AcEvidence` tier, findings carry `high|medium|low` severity, and no mapping between them exists. D2 is read as forbidding a *new* primitive and a *new* config knob, so gap findings are emitted into the stream `code-review` already refuses on)
When review runs
Then a criteria-gap finding is emitted naming the uncovered work, it is distinguishable in the result from an ordinary anchored finding, and its gap count and severity distribution are declared unconditionally per D3 regardless of whether the floor stops the settle

### AC-5: Declaring the criterion converts the gap into an anchored finding
Given the DRAFT from AC-4 is amended to declare a criterion covering that work
When review re-runs over the same diff
Then the same defect is emitted as an anchored finding at the tier its new criterion earns, and no criteria-gap finding is emitted for it

### AC-6: A trivial unanchored finding does not block, and weak anchors are marked weak
Given §6 Slice 3's adversarial corpus — a trivial unanchored finding, and anchor-shopping via a vague AC such as "the API should be secure" that could absorb any finding
When review runs over that corpus
Then the trivial unanchored finding does not refuse settle, and an anchor earned only at `structured` or `declared` is recorded as weak rather than carrying the same authority as an `executable` anchor

### AC-7: Gate semantics, gate order, and existing artifacts are unchanged
Given hard constraints §9.2 and §9.5
When the criteria-anchoring lands
Then `GATE_ORDER` is unchanged, the HIGH-finding refuse and convergence contract of `code-review` is unchanged for findings that would have been emitted before, a previously settled SUMMARY still parses, and no existing test is loosened to accommodate the change

## Boundaries

- DO NOT give findings a stable `id`, a `disposition`, or an expiring `waiver` — that is phase 236, and it is gated on `rec-20260727-007` (shared fingerprint primitive extracted from Déjà). DO NOT write a bespoke fingerprint to make findings survive refactors.
- DO NOT route findings to the recommendation ledger and DO NOT extend `RecommendationSourceZ` with a `review` member — phase 236.
- DO NOT criteria-anchor `spec-review`, `ui-spec-review`, or `plan-review`. Scope is the code-review verifier only (`dec-20260729-003`, resolving §10 open question 3).
- DO NOT add a second refusal primitive or a second floor — D2 is locked: gap findings trip the existing `evidenceFloor`.
- DO NOT change `GATE_ORDER`, and DO NOT change any gate's pass/refuse semantics for finding classes that existed before this phase.
- DO NOT import kernel internals from a verifier — tripwire T2 says fix the contract, never grant the exception.
- DO NOT converge the two divergent `Finding` types (the persisted schema's `critical` versus the verifier's `high|medium|low`); §7.2 assigns that to the finding-identity slice.
- DO NOT make any schema change non-additive: new fields are `.optional()` or `.default(...)` so every pre-existing artifact keeps parsing.
- DO NOT write a test that calls a real provider, and DO NOT loosen an existing test to accommodate the change.
- DO NOT add a runtime dependency, and DO NOT move any package.
