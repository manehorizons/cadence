# 235-01 — Criteria-anchored review verifier: input + anchor ladder

## Objective

The code-review verifier cannot see what the phase committed to. `CodeReviewInput` is
`{ files, diff }` (`packages/core/src/verify/code-review.ts:22`), and the gate discards
everything else it holds — `ctx.draft` is a full `Draft` at `gates/types.ts:184`, yet
`gates/code-review.ts:38` calls `verify({ files: touched, diff })`. The reviewer therefore
grades code against general good practice rather than against the DRAFT's acceptance
criteria. Extend the input with acceptance criteria, boundaries and task→AC refs, and
classify every finding by the strength of the criterion it anchors to via the anchor ladder
(`executable > structured > declared > undeclared`), emitting an explicit **criteria-gap**
finding where the diff does work no criterion covers.

## Acceptance Criteria

### AC-1: The review verifier can see the phase's criteria
Given `CodeReviewInput` is `{ files, diff }` and the gate already holds the full `Draft` on
`ctx.draft` but passes none of it through
When the input contract is extended
Then `CodeReviewInput` carries the DRAFT's acceptance criteria (`id`, `name`, `given`,
`when`, `then`), its `boundaries[]`, and task→AC refs (`Task.id`, `files`, `verify`, `done`,
`status`), and `gates/code-review.ts` populates them from `ctx.draft` — proven by a test
asserting a non-empty criteria payload reaches the verifier for a DRAFT with ACs.

### AC-2: The anchor ladder classifies findings by criterion strength
Given §7.1 defines four tiers, strongest → weakest — `executable` (the AC is referenced by a
task whose `verify` is a runnable command **and** `build-test-must-pass` actually ran),
`structured` (non-empty `given`/`when`/`then`), `declared` (prose-only or empty G/W/T, or a
`boundaries[]` string), `undeclared` (no citable criterion)
When a finding is anchored
Then it carries `{ kind: 'ac'|'boundary'|'none', ref?, tier }`, each tier is derived from the
measured DRAFT/provenance facts above rather than from verifier self-report, and the ladder is
a **peer** schema to `AcEvidenceZ`, not a reuse of it.

### AC-3: `executable` is derived from real gate provenance, not assumed
Given the `executable` tier's second condition is that `build-test-must-pass` actually ran,
and phase 232 shipped per-gate provenance carrying verifier identity
When an AC is referenced by a task with a runnable `verify` but `build-test-must-pass` did
not run in this settle
Then the anchor resolves to `structured` (or lower), never `executable` — proven by a test
that holds the DRAFT constant and varies only the provenance.

### AC-4: Unanchored findings above the floor surface as criteria gaps
Given a diff introducing a defect that no acceptance criterion and no boundary covers
When review runs
Then a **criteria-gap** finding is emitted naming the uncovered work, and it is distinguishable
in the result from an ordinary anchored finding.

### AC-5: Declaring the criterion converts the gap into an anchored finding
Given the DRAFT from AC-4 is amended to declare a criterion covering that work
When review re-runs over the same diff
Then the same defect is emitted as an **anchored** finding at the tier its new criterion earns,
and no criteria-gap finding is emitted for it.

### AC-6: A trivial unanchored finding does not block, and weak anchors are marked weak
Given the adversarial corpus in §6 Slice 3 — a trivial unanchored finding, and
"anchor-shopping" (a vague AC such as "the API should be secure" that could absorb any finding)
When review runs
Then the trivial unanchored finding does **not** refuse settle, and an anchor earned only at
`structured` or `declared` is recorded as weak rather than being reported with the same
authority as an `executable` anchor.

### AC-7: Gate semantics, gate order, and existing artifacts are unchanged
Given hard constraints §9.2 and §9.5
When the criteria-anchoring lands
Then `GATE_ORDER` is unchanged, the existing HIGH-finding refuse/convergence contract of
`code-review` is unchanged for findings that would have been emitted before, previously
settled SUMMARY files still parse, and no existing test is loosened to accommodate the change.

## Constraints

- **Scope is the code-review verifier only** (operator decision, 2026-07-29, resolving §10
  open question 3). `spec-review`, `ui-spec-review` and `plan-review` are **not**
  criteria-anchored in this phase; file a follow-up recommendation so the generalization is
  recorded rather than silently dropped.
- **Finding identity is phase 236, not this phase.** No stable `id`, no `disposition`, no
  expiring `waiver`, no ledger routing, no `RecommendationSourceZ` extension. Phase 236 is
  additionally gated on `rec-20260727-007` (shared fingerprint primitive extracted from Déjà);
  do not build a bespoke fingerprint here to make findings survive refactors.
- **No kernel internals imported** (tripwire T2, phase 234's contract). If routing criteria to
  the verifier appears to need a kernel internal, fix the contract — never grant the exception.
- No `GATE_ORDER` changes; no change to any gate's pass/refuse semantics for pre-existing
  finding classes (§9.5).
- Additive, backward-compatible schema changes only: new fields get `.default(...)` /
  `.optional()`; every pre-existing artifact must keep parsing.
- Tests use the `mock` provider only. The mock code-review verifier must stay deterministic
  and offline; extending its rule set to exercise anchoring is in scope.
- **Tripwire T3 (binding, §8).** If this runs beyond a couple of focused sessions, revert —
  overrun is the diagnosis, not a schedule problem. Record the outcome in the SUMMARY if it
  trips.
- **Settle with the branch build** — `node packages/core/bin/cadence.cjs settle run --auto`,
  not the globally installed CLI (operator decision, 2026-07-29, per `rec-20260729-001`). Both
  report `1.51.1`, so the shadowing is invisible from `--version` alone.

## Open Questions

- **Q1 — Does the anchor ladder feed `evidenceFloor`, or get its own floor? (§10 q5.)**
  D2 forbids a second *refusal primitive*, which is not the same as forbidding a second
  *floor*. Leaning per the design doc: one floor, with anchor tier as an input to evidence
  derivation. **Resolve before drafting the task that emits gap findings**, since AC-4's
  "above the floor" wording depends on it.
- **Q2 — Where does the criteria payload get assembled?** `gates/code-review.ts` reading
  `ctx.draft` directly is the smallest change, but a shared pure builder is likely warranted
  if phases 236+ or the deferred generalization to the other three review verifiers will
  reuse it. Prefer the pure-core/impure-shell split; do not build verifier-agnostic
  generality speculatively (operator scoped this to code-review only).
- **Q3 — `Finding` type convergence (§7.2 convergence note).** The persisted schema has
  `critical` but the code-review verifier emits only `high|medium|low`. §7.2 assigns this
  convergence to the finding-identity slice. **Assumed out of scope here** unless anchoring
  cannot be expressed without it; if it turns out to be a blocker, say so rather than
  quietly widening the phase.
- **Q4 — Does a criteria-gap finding carry a severity at all,** or is it a distinct result
  channel? AC-4 requires only that it be distinguishable from an anchored finding. Decide at
  DRAFT time and record the choice.
