# 248-01 — Honest bypassed-verifier provenance for code-review/security-audit throws

## Objective

A code-review or security-audit **verifier throw** (the call itself
failed — revoked key, network blip — not a findings-based bypass of a
completed review) bypassed via `--allow-code-review-failure` /
`--allow-security-audit-failure` / `--force` records an honest
`status: 'skipped'` provenance entry naming the flag and the failure —
never a bare `status: 'ran'` with empty identity. Out of scope: the
existing findings-bypass path (real HIGH/CRITICAL findings waved through
on a *completed* verifier call) keeps recording `status: 'ran'` with a
real `verifierIdentity` — that call did return, so `'ran'` is accurate
there; only the never-returned case is dishonest.

## Context

**Source:** `rec-20260801-004`, joined to the finding-durability cluster via
`ev-20260802-011`. Verified live at `main@59a2116e`.

**Verified: both catch blocks set no flags on a bypassed throw today.**
`code-review.ts:253-261` and `security-audit.ts:72-80` are structurally
identical — on a caught throw, if a bypass flag (`--force`, or the
gate-specific `--allow-*-failure`) is set, both simply
`return { outcome: 'pass' }` with no `flags` at all. `registry.ts`'s
dispatch loop falls through to its final `else` branch
(`gates.push({ gate, status: 'ran', ...verifierIdentityProvenance(res) })`)
since none of the named branches match, and `verifierIdentityProvenance`
(registry.ts:127) returns `{}` when `res.flags?.verifierIdentity` is
absent. The persisted `SUMMARY.gates[]` entry reads
`{ gate: 'code-review', status: 'ran' }` — indistinguishable from a clean
real-provider pass.

**Revision note on the source handoff's T1 premise.** The originating
handoff (`docs/handoffs/cadence-handoff-finding-durability-remainder.md`,
Part 3, T1) instructed verifying `deep-verify.ts`'s throw path on the
assumption "the two review gates mirror that pattern" — i.e. that
`registry.ts` already has working machinery to convert a bypassed throw's
`flags.verifierFailure` into an honest `skipped` status, and this phase
only needs to make the two review gates *set* that flag. Verified:
`deep-verify.ts:110-137` does set `flags.verifierFailure = { message,
provider: failedProvider }` on a bypassed throw, sourcing
`failedProvider` from `ctx.config?.verifier?.provider ?? 'mock'` (model
similarly from `ctx.config?.verifier?.model`, included only if present).
**But a full read of `registry.ts`'s dispatch loop found no branch reads
`res.flags?.verifierFailure` at all** — the only named branches are the
self-guard predicate, `build-test-must-pass`'s two branches (no-test-command
and bypass), `boundary-scan`'s bypass branch, and `test-coverage`'s bypass
branch. So `deep-verify.ts`'s own bypassed-throw case *also* currently
falls through to the generic `else` and records `status: 'ran'` with empty
identity — the identical bug class this phase fixes, via a parallel code
path that was never wired up. The handoff's premise was accurate about the
flag *shape* `deep-verify.ts` sets, but not evidence that `registry.ts`
already turns it into honest provenance — that machinery does not exist
yet; this phase builds it for the first time. Scoped deliberately to
`code-review`/`security-audit` only, per `rec-20260801-004`'s own `files:`
list and AC-5's gate pairing — seed `deep-verify.ts`'s identical gap as a
separate follow-up rather than silently widening scope (see Open
Questions).

**Verified: the config field paths exist and default safely.**
`config.codeReview.provider` and `config.securityAudit.provider` are
top-level siblings of `config.verifier` in `CadenceConfig`
(`packages/types/src/config.ts:303`, `:329`), both defaulting to
`'mock'` in `DEFAULT_CONFIG` (`config.ts:582-586`) when the section is
absent — the direct `codeReview`/`securityAudit` analogues of
`deep-verify.ts`'s `ctx.config?.verifier?.provider ?? 'mock'` fallback.

**Verified: the existing bypass-ladder branches generalize cleanly, no
special-casing needed.** `verifierIdentityProvenance` reads only
`res.flags?.verifierIdentity`, never `verifierFailure`. A new branch that
spreads `...verifierIdentityProvenance(res)` exactly like the four
existing bypass-ladder branches do will safely resolve to `{}` on a
caught-throw result, because the catch block never sets
`flags.verifierIdentity`. This is what makes AC-3/AC-4 achievable by
reusing the exact existing registry pattern rather than inventing a
bespoke one.

**Correction from independent review (2026-08-02): `flags.verifierFailure`
is NOT an inert provenance channel — reusing it is wrong.** `registry.ts:209`
merges every gate's `flags` into `acc.flags` unconditionally
(`mergeInto`, a plain `Object.assign`) before the outcome check.
`services/settle.ts` reads `acc.flags.verifierFailure` and forwards it
into `collectAnomalies`, which `notify/collect.ts:125-134` turns into an
anomaly `{ type: 'verifier-failure', message: \`deep verifier failed:
${message}\` }`. `settle.ts`'s `anomalyToGateBypass` (~166-201)
**hardcodes** that anomaly type to `{ gate: 'deep-verify', flag:
'--allow-verifier-failure' }`, which is then unconditionally printed
(`settle.ts:~1039-1041`) and persisted into `SUMMARY.gateBypasses`
(`types/summary.ts:261`). If code-review/security-audit set this same
field, the result is a **false, durable bypass record** claiming
deep-verify was bypassed via a flag the operator never passed — in the
phase whose entire purpose is provenance honesty. Worse: because
`mergeInto` is a plain object assign and `deep-verify` (gate 8) runs
immediately before `code-review` (gate 9) in `GATE_ORDER`, a settle where
*both* throw-and-bypass would have code-review's `verifierFailure`
silently clobber deep-verify's real one — a regression this SPEC would
introduce if implemented naively. **The two review gates must set a
distinct new `GateFlags` field instead** — `reviewVerifierFailure:
{ message: string; provider?: string }` — that `notify/collect.ts` does
not read. `deep-verify.ts`'s own `verifierFailure` field, and its `model`
handling, are untouched by this phase; note also that `verifierFailure`
itself carries no `model` field (`gates/types.ts:248`:
`{ message: string; provider?: string }`) — `deep-verify.ts` never
threads a model through it, only through the unrelated `deepVerifyMeta`.
An earlier draft of this Context section incorrectly implied
`verifierFailure` carries a model; it does not, and the new
`reviewVerifierFailure` field should not invent one either.

## Acceptance Criteria

### AC-1: A bypassed code-review throw records an honest skipped status
Given the code-review verifier throws and a bypass flag (`--force` or
`--allow-code-review-failure`) is set
When settle completes
Then the persisted `SUMMARY.gates[]` entry for `code-review` is
`status: 'skipped'` with a `skipReason` that names the actual flag used,
states a verifier failure was bypassed, and includes the underlying error
message and the configured provider (sourced via
`ctx.config?.codeReview?.provider ?? 'mock'`) — never `status: 'ran'`.
When both `--force` and `--allow-code-review-failure` are set, the
`skipReason` names `--allow-code-review-failure` — matching `registry.ts`'s
own existing bypass-ladder precedent (`build-test-must-pass`/
`boundary-scan`: name the gate-specific flag when it was explicitly set,
`--force` only when it alone triggered the bypass). Additionally, stderr
prints a loud notice on the bypass (mirroring the existing findings-bypass
notice at `code-review.ts:159-161`, e.g. `code-review:
--allow-code-review-failure set; proceeding past a verifier failure
(<message>).`) — a bypassed throw must not fall silent, per this repo's
own no-quiet-fallback convention.

### AC-2: Un-bypassed throw behavior is unchanged (regression pin)
Given the code-review or security-audit verifier throws and no bypass flag
is set
When settle runs
Then the exit code is 1, the exact stderr reason string is unchanged —
`code-review: verifier failed — ${message}. Pass --allow-code-review-failure
to continue.` (or the `security-audit` equivalent naming
`--allow-security-audit-failure`) — and `res.flags` remains `undefined` on
this un-bypassed refuse return, exactly as already pinned by the existing
gate tests (`tests/gates/code-review.test.ts`,
`tests/gates/security-audit.test.ts`). This means `reviewVerifierFailure`
must be set only inside the bypassed branch, never unconditionally in the
catch block.

### AC-3: No verifier identity is fabricated
Given a bypassed throw (either gate)
When the persisted `SUMMARY.gates[]` entry for that gate is inspected
Then it has no `provider` field and no `model` field; the configured-
provider name appears only inside the `skipReason` string, never as a
structured identity field — a clean identity for a call that never
returned is a lie. The covering test must drive an actual bypassed throw
through the gate and assert both the absence of `provider`/`model` AND
the presence of the `skipped`/`skipReason` entry (AC-1) in the same
assertion — a test that only checks the absence of `provider`/`model`
would pass unmodified against today's `main` (which sets no flags at all
on this path) and would prove nothing about this phase's fix.

### AC-4: The gate stays excluded from verifierRollup (pin as correct semantics)
Given a bypassed throw
When `deriveAssuranceRecord` computes `verifierRollup` (which groups
strictly by `gates[].provider !== undefined`)
Then this gate's entry continues to be excluded — true today only because
the catch block sets no flags at all, and true after this phase because
AC-3 keeps `provider` unset. As with AC-3, the covering test must drive
an actual bypassed throw and assert `verifierRollup` excludes it in the
same run that also asserts the new `skipped` status is present — not a
standalone check against an unmodified pass/refuse path — so a future
change to `verifierIdentityProvenance` or the new branch can't silently
regress it into an over-report.

### AC-5: Security-audit is fixed identically (symmetry)
Given the security-audit verifier throws under the same conditions
(`--force` or `--allow-security-audit-failure`)
When settle completes
Then AC-1 through AC-4 hold identically for `security-audit` (including
AC-1's flag-naming precedence and stderr-notice requirements), using
`ctx.config?.securityAudit?.provider ?? 'mock'` as the configured-provider
source and the `security-audit` gate name throughout. The two catch
blocks are structurally identical today (verified); the fix must stay
symmetric — no divergent behavior between the two gates.

## Constraints

- Gates signal via a **new, distinct** `GateFlags` field —
  `reviewVerifierFailure: { message: string; provider?: string }` —
  structurally parallel to `verifierFailure` but a separate field, never
  reused. No `model` sub-field (matches `verifierFailure`'s own actual
  shape, not the wider shape an earlier draft of this SPEC incorrectly
  assumed).
- **Must not alter `SUMMARY.gateBypasses` or trigger any
  `notify/collect.ts` anomaly emission.** Today, a bypassed code-review/
  security-audit throw sets no flags and produces neither. After this
  phase, the same must hold — achieved structurally by `collect.ts` never
  reading `reviewVerifierFailure` (it only reads `verifierFailure`,
  untouched by this phase).
- Consumed by **one** new `registry.ts` branch checking
  `res.flags?.reviewVerifierFailure` — since only `code-review` and
  `security-audit` will ever set this field, no gate-name disjunction is
  needed in the branch condition (simpler than the `verifierFailure`
  approach an earlier draft proposed). Follows the existing multi-branch
  bypass-ladder style (`build-test-must-pass` / `boundary-scan` /
  `test-coverage`) for the branch's shape.
- No `GATE_ORDER` change.
- No change to either gate's pass/refuse *decision* logic — the existing
  `if (!bypassFlag) return refuse` branching is untouched. The bypassed
  `return { outcome: 'pass' }` branch gains two things, both additive and
  both scoped inside that branch only (never on the refuse return, per
  AC-2): a `flags: { reviewVerifierFailure }` field, and one new stderr
  line (mirroring the existing findings-bypass notice's style) — no other
  statement in either catch block changes.
- `deep-verify.ts` and `notify/collect.ts` are explicitly **not** touched
  by this phase (see Open Questions) — `deep-verify.ts`'s own,
  already-wired `verifierFailure` gap is a separate, unscoped concern.
- `ctx.config?.codeReview?.provider ?? 'mock'` /
  `ctx.config?.securityAudit?.provider ?? 'mock'` are the only new config
  reads; no schema change — both fields already exist and already default
  in `DEFAULT_CONFIG`.
- `docs/concepts.md`'s `gates[]` provenance narrative (phase-by-phase,
  ~106-132) gets a paired edit describing this new skipped-status case,
  per this repo's doc-drift discipline.

## Open Questions

- Should `deep-verify.ts`'s identical registry-side gap (a bypassed
  `--allow-verifier-failure` throw also currently records `status: 'ran'`
  with empty identity, since no registry branch reads `flags.verifierFailure`
  today) be filed as a follow-up recommendation now, or folded into this
  same phase? **Recommendation: file a follow-up rec, don't fold it in.**
  With the distinct-field fix (`reviewVerifierFailure`, not a reused
  `verifierFailure`), this is no longer a "guard that exists just to
  exclude deep-verify" — the new field is structurally invisible to
  `deep-verify.ts` and to `collect.ts`, so there is nothing to guard
  against. `deep-verify.ts`'s own gap (its *own* `verifierFailure` field
  never reaching an honest `skipped` status either) is a genuinely
  separate fix, since `verifierFailure` is load-bearing for the anomaly/
  `gateBypasses` pipeline in a way a naive copy of this phase's approach
  would need to account for — worth its own SPEC. `rec-20260801-004`
  explicitly scoped to `code-review`/`security-audit` only; filing the
  deep-verify follow-up as the phase's first post-settle action, alongside
  promoting `rec-20260801-004` to shipped, in the same settle commit.
