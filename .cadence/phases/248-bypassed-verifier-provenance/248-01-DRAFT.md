# 248-01 — Honest bypassed-verifier provenance for code-review/security-audit throws

## Objective

A code-review or security-audit **verifier throw** (the call itself
failed — revoked key, network blip — not a findings-based bypass of a
completed review) bypassed via `--allow-code-review-failure` /
`--allow-security-audit-failure` / `--force` records an honest
`status: 'skipped'` provenance entry naming the flag and the failure —
never a bare `status: 'ran'` with empty identity. Out of scope: the
existing findings-bypass path (real HIGH/CRITICAL findings waved through
on a *completed* verifier call) keeps recording `status: 'ran'` with a
real `verifierIdentity` — that call did return, so `'ran'` is accurate
there; only the never-returned case is dishonest.

## Acceptance Criteria

### AC-1: A bypassed code-review throw records an honest skipped status
Given the code-review verifier throws and a bypass flag (`--force` or
`--allow-code-review-failure`) is set
When settle completes
Then the persisted `SUMMARY.gates[]` entry for `code-review` is
`status: 'skipped'` with a `skipReason` that names the actual flag used,
states a verifier failure was bypassed, and includes the underlying error
message and the configured provider (sourced via
`ctx.config?.codeReview?.provider ?? 'mock'`) — never `status: 'ran'`.
When both `--force` and `--allow-code-review-failure` are set, the
`skipReason` names `--allow-code-review-failure` — matching `registry.ts`'s
own existing bypass-ladder precedent (`build-test-must-pass`/
`boundary-scan`: name the gate-specific flag when it was explicitly set,
`--force` only when it alone triggered the bypass). Additionally, stderr
prints a loud notice on the bypass (mirroring the existing findings-bypass
notice at `code-review.ts:159-161`, e.g. `code-review:
--allow-code-review-failure set; proceeding past a verifier failure
(<message>).`) — a bypassed throw must not fall silent, per this repo's
own no-quiet-fallback convention.

### AC-2: Un-bypassed throw behavior is unchanged (regression pin)
Given the code-review or security-audit verifier throws and no bypass flag
is set
When settle runs
Then the exit code is 1, the exact stderr reason string is unchanged —
`code-review: verifier failed — ${message}. Pass --allow-code-review-failure
to continue.` (or the `security-audit` equivalent naming
`--allow-security-audit-failure`) — and `res.flags` remains `undefined` on
this un-bypassed refuse return, exactly as already pinned by the existing
gate tests (`tests/gates/code-review.test.ts`,
`tests/gates/security-audit.test.ts`). This means `reviewVerifierFailure`
must be set only inside the bypassed branch, never unconditionally in the
catch block.

### AC-3: No verifier identity is fabricated
Given a bypassed throw (either gate)
When the persisted `SUMMARY.gates[]` entry for that gate is inspected
Then it has no `provider` field and no `model` field; the configured-
provider name appears only inside the `skipReason` string, never as a
structured identity field — a clean identity for a call that never
returned is a lie. The covering test must drive an actual bypassed throw
through the gate and assert both the absence of `provider`/`model` AND
the presence of the `skipped`/`skipReason` entry (AC-1) in the same
assertion — a test that only checks the absence of `provider`/`model`
would pass unmodified against today's `main` (which sets no flags at all
on this path) and would prove nothing about this phase's fix.

### AC-4: The gate stays excluded from verifierRollup (pin as correct semantics)
Given a bypassed throw
When `deriveAssuranceRecord` computes `verifierRollup` (which groups
strictly by `gates[].provider !== undefined`)
Then this gate's entry continues to be excluded — true today only because
the catch block sets no flags at all, and true after this phase because
AC-3 keeps `provider` unset. As with AC-3, the covering test must drive
an actual bypassed throw and assert `verifierRollup` excludes it in the
same run that also asserts the new `skipped` status is present — not a
standalone check against an unmodified pass/refuse path — so a future
change to `verifierIdentityProvenance` or the new branch can't silently
regress it into an over-report.

### AC-5: Security-audit is fixed identically (symmetry)
Given the security-audit verifier throws under the same conditions
(`--force` or `--allow-security-audit-failure`)
When settle completes
Then AC-1 through AC-4 hold identically for `security-audit` (including
AC-1's flag-naming precedence and stderr-notice requirements), using
`ctx.config?.securityAudit?.provider ?? 'mock'` as the configured-provider
source and the `security-audit` gate name throughout. The two catch
blocks are structurally identical today (verified); the fix must stay
symmetric — no divergent behavior between the two gates.

## Boundaries

- Do NOT touch `deep-verify.ts` or `notify/collect.ts` — the distinct-field
  approach (T1) means neither needs to change; if a task finds itself
  editing either file, stop and reconsider the approach against the SPEC.
- Do NOT change either gate's pass/refuse decision logic — only the
  bypassed-and-`pass` return branch of each catch block gains the new
  `flags` field and stderr line (T2/T3); the refuse branch is untouched
  (AC-2).
- Do NOT alter `SUMMARY.gateBypasses` or trigger `notify/collect.ts`
  anomaly emission for a code-review/security-audit throw-bypass.
- Do NOT add a `model` field to `reviewVerifierFailure` — it does not
  exist on `verifierFailure` either (T1).
- Do NOT change `GATE_ORDER`.
- Do NOT touch the existing findings-bypass path (real HIGH/CRITICAL
  findings on a *completed* verifier call) — it correctly keeps
  `status: 'ran'` with a real `verifierIdentity`; out of scope per the
  Objective.
