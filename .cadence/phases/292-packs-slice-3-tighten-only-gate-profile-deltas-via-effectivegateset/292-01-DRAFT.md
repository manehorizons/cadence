# 292-01 — packs slice 3 -- tighten-only gate-profile deltas via effectiveGateSet

## Objective

Make a pack's declared gates[].add deltas actually enforce: union pack-contributed gates into effectiveGateSet()'s output at every real call site (not just resolve them), reflect enabled packs' contribution in cadence config explain's current-tier row while the tier×profile matrix table stays raw, and regression-test that a non-additive manifest shape is rejected at parse time -- completing Packs Slice 3 per docs/packs-design.md §4b/§7 and rec-20260822-011.

## Acceptance Criteria

### AC-1: Pack-contributed gates enforce at every effectiveGateSet call site
Given a pack with a `gates[].add` delta matching the active (profile, tier) cell, enabled in `config.packs.enabled`
When `effectiveGateSet` is computed at any of its 9 existing call sites (`draft-check`, `draft-approve`, `build-task` ×2, `settle`, `hooks/handlers.ts` ×3, `notify/loop-violation.ts`)
Then the pack's added gate is present in the resulting `GateSet.gates` for every call site whose caller supplies a real resolved-packs set; `effectiveGateSet` requires a `resolvedPacks: ResolvedPack[]` parameter with no default (a missed call site is a compile error, not a silent gap); `gatesFor` itself stays unchanged (pure/sync, still the two raw matrix-builder callers in `doctor/run.ts` and `config-explain/build.ts` untouched by this parameter).

### AC-2: Call sites that don't need pack-awareness say so explicitly
Given the call sites that only perform a gate-membership check unrelated to a pack's additive scope, or where resolving packs' filesystem I/O is unjustified on that path
When `resolvedPacks` is threaded through
Then each such site passes `[]` explicitly with an inline comment recording the decision, and behavior at that site is unchanged from before this phase.

### AC-3: config explain's current-tier row reflects enabled packs; the matrix table stays raw
Given one or more enabled packs contributing `gates[].add` for the active (profile, tier) cell
When `cadence config explain` runs
Then the current-tier row's gate list includes the pack-contributed gates (threaded in via `ExplainContext`, `buildExplanation` stays pure/no I/O); the full tier×profile matrix table continues to render raw `gatesFor` output for every row including the current tier's own matrix row; a divergence between the current-tier row and its matching matrix row is surfaced to the operator rather than left silent.

> **As-built amendment (whole-branch review, 2026-08-23):** this AC's wording presupposed two separate renderings -- a standalone current-tier row and a distinct matrix row for that same tier -- that could visibly diverge from each other. The actual CLI output is a single "Gates that fire, by tier" table with one row per tier; there is no second, separate rendering of the current tier's matrix-only gate list to diverge from. `buildExplanation`'s data model still keeps the distinction internally (`TierGateView.gates` is pack-augmented only for `current: true`; `packContributedGates` names exactly what a pack added), and every OTHER tier's row is still unaugmented raw `gatesFor` output -- so the design intent (§4b: "the current-tier row ... reflects packs ... the matrix table stays raw") is satisfied. The divergence surfaces via the dedicated `packs-augment-current-tier` warning, not via a second row to compare against. Text-mode `renderTierBlock` does not yet visually distinguish a pack-contributed gate from a DELTAS gate within the current row itself (both look identical inline; only the warning below explains it) -- left as-is for this phase, matching the AC's actual (satisfied) intent rather than its overly specific plan-time assumption about renderer shape.

### AC-4: A non-additive gate delta is rejected at manifest parse time, not silently dropped
Given a pack manifest whose `gates[]` entry contains an unrecognized key (e.g. `remove`, `override`, or `set`) alongside or instead of `add`
When `resolvePacks` validates that manifest
Then resolution returns the existing `{ error }` branch for that pack (schema validation failure), never a partially-applied or silently-truncated gate delta -- regression-tested against `PackGateDeltaZ`'s `.strict()` behavior specifically, not just the manifest's top-level strictness.

## Boundaries

- DO NOT touch `gatesFor`'s signature or purity -- packs must not reach the matrix-builder callers (`doctor/run.ts`'s reachability scan, `config-explain`'s matrix table) except via the deliberate current-tier exception in AC-3.
- DO NOT add a `remove`/`override`/`set` key to `PackGateDeltaZ` or `PackManifestZ` -- I-3 (`dec-20260822-019`) is structural, not just behavioral.
- DO NOT fix doctor's reachability-scan divergence (T5) in this phase even if it turns out to be real -- file it instead, per `dec-20260820-003` precedent.
- DO NOT expand into registry/remote pack sources (`source: 'registry' | 'remote'`) -- out of scope, deferred per `docs/packs-design.md`.
- DO NOT change how `effectiveProfile`/DRAFT-tier resolution works -- pack gates union onto the output of that resolution, never interact with it (I-5).
