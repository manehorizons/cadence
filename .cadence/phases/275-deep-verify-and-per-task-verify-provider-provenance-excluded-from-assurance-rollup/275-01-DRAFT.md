# 275-01 — deep-verify and per-task-verify provider provenance, excluded from assurance rollup

## Objective

Close rec-20260808-007's provenance gap (v1.57's Phase V): `deep-verify` and
`per-task-verify` currently persist no verifier-provider identity into
`SummaryZ.gates[]` at all, unlike `code-review`/`security-audit`. Add a
structurally separate `observedProvider`/`observedModel`/`taskId` field set
to `GateProvenanceZ` — distinct from the existing `provider`/`model` fields
that `deriveAssuranceRecord`'s `verifierRollup` fold reads — so both gates'
real provider identity becomes visible without being picked up by the fold
that feeds `assurance.overall`. `deriveAssuranceRecord` only ever reads
`.provider`/`.model`; it requires zero code changes for the new fields to be
invisible to it, which is the actual safety property (see AC-3). This
preserves the exact rationale `dec-20260808-008`/`dec-20260811-002`
protected: this repo's `perTaskVerifier.provider`/`verifier.provider` are
already `host-cli`, so naively adding baseline persistence would silently
move `overall` toward `strong` on ordinary settles with no review gate
having run.

**Coverage-token convention**: this repo's `.cadence/config.json` sets
`coverageScheme: "phase-qualified"`, `coverageMode: "assertion"`,
`gates.evidenceFloor: "assertion"`. Every new `it()`/`test()` title this
phase adds MUST use the qualified `275-01/AC-N` token form (matching every
existing test in this repo, e.g. `274-01/AC-4:`, `263-01/AC-4:`), sitting
inside an asserting block — a bare `AC-N` token is dropped before dedup
under this repo's scheme (`coverage.ts`) and would leave this phase's own
settle unable to clear its evidence floor.

## Evidence

- Confirmed live (2026-08-13): `deep-verify.ts` writes provider/model only
  into `deepVerify[]`/`deepVerifyMeta`, never into a `gates[]` entry — matches
  the rec.
- **Correction to the rec's own evidence**: rec-20260808-007 says
  "per-task-verify.ts persists no provider identity anywhere (zero matches
  for verifierIdentity/result.provider in the file)". That grep was a false
  negative — `PerTaskVerifyRecord.provider`/`.model`
  (`packages/core/src/build/record.ts:16-22`) have existed since Phase 39.7
  and `per-task-verify.ts` populates them today (`provider: verdict.provider`).
  The grep searched for the literal string `result.provider`, but this
  file's local variable is named `verdict`, not `result` — a naming
  mismatch, not a missing feature. The real gap is narrower than the rec's
  title implies: per-task-verify's identity already exists in
  `PROGRESS.json`'s per-task records, it just never reaches
  `SummaryZ.gates[]`/`assurance`. This phase's per-task-verify half is
  "surface already-persisted identity into the SUMMARY," not "add
  persistence."
- `registry.ts`'s `verifierIdentityProvenance()` (the mechanism that already
  populates `code-review`/`security-audit`'s `gates[]` provenance) is
  deliberately keyed by `GateFlags.verifierIdentity` presence alone, never by
  gate name — confirmed by direct read. `deriveAssuranceRecord`'s
  `verifierRollup` fold is equally gate-agnostic by design (its own doc
  comment: "never inspects `gate.gate`"), with an existing test tripwire.
  This DRAFT's design (a new, separate `observedVerifierIdentity` flag /
  `observedProvider`/`observedModel` field pair, mirrored through the same
  generic-by-flag-presence pattern) preserves both invariants rather than
  introducing gate-name branching into either function.
- Consumer check (2026-08-13, corrected after independent review): TWO
  places read `gates[].provider` outside `deriveAssuranceRecord` itself, not
  one — `summary-render.ts`'s "## Assurance" section AND
  `parse/summary-writer.ts:56-60`, which does the identical
  `g.provider === v.provider && g.model === v.model` join independently.
  Both cross-reference an *already-computed* `verifierRollup` entry back
  into `gates[]` to build a display label; neither scans `gates[]` directly
  for provider identity, so both are naturally blind to entries carrying
  only `observedProvider`. This is why a separate field name (not a boolean
  flag alongside the existing `provider`/`model`) is the safer shape:
  `deriveAssuranceRecord`'s fold structurally cannot see `observedProvider`
  without new code being written to read it.
- `GateProvenanceZ` has no `taskId` field today. `per-task-verify` executes
  once per task (potentially under different providers if config changes
  mid-build), so surfacing its identity as one collapsed entry per distinct
  `(provider, model)` pair would silently discard which task ran under which
  provider — the same "silent collapse loses evidence" shape this session
  already spent Phase W reconciling for `scanTestCoverage`'s AC-token dedup
  bug (rec-20260809-001/rec-20260812-004). This DRAFT adds an optional
  `taskId` to `GateProvenanceZ` so per-task-verify can emit one entry per
  task execution instead.
- **Type gap found by independent review**: `settle.ts` threads
  `progress: ProgressJson` using the type at `gates/types.ts:30-36`, which
  has NO `perTaskVerify` field — a different, narrower same-named interface
  than `build/record.ts:24-36`'s, which does. T4 needs
  `progress.tasks[id].perTaskVerify`; T1 must add
  `perTaskVerify?: PerTaskVerifyRecord` to `gates/types.ts`'s `ProgressJson`
  (confirmed no import cycle: `build/record.ts` imports nothing from
  `gates/types.ts`).
- **Settle-flow insertion point** (independent review): `gates` first comes
  into existence at `settle.ts:1573`
  (`const { acc, refused, gates } = await runSettleGates(ctx);`) and flows
  unchanged into 5 separate SUMMARY-writing call sites — 4
  `writeRefusedSettleSummary(...)` (lines 1576, 1585, 1619, 1636) plus
  `finalizeAndCloseSettle(...)` (line 1648). T4 extends `gates` exactly once,
  immediately after line 1573, before any branch, so all 5 paths see
  per-task-verify's entries uniformly regardless of how this settle
  resolves — per-task-verify already ran during BUILD, independent of this
  settle's own outcome.
- **Bypassed-refuse status choice** (independent review flagged this as
  needing an explicit decision, not silence): a `PerTaskVerifyRecord` can
  carry `verdict: 'refuse', bypassed: true` — per `per-task-verify.ts`'s own
  logic, an UNbypassed refuse halts the record write entirely (never reaches
  `PROGRESS.json`), so every refuse-shaped record that could exist in
  practice already has `bypassed: true`. Decision: T4 records `status: 'ran'`
  uniformly for every `PerTaskVerifyRecord` found (`pass`/`concerns`/
  `refuse`-bypassed alike), matching `dec-20260809-004`'s existing precedent
  that a bypassed real finding keeps `status: 'ran'` rather than being
  relabeled `skipped` — the audit trail for *that* a bypass happened lives
  in `gateBypasses[]`, a distinct mechanism this phase does not extend (see
  Boundaries). This phase's own scope is provider-identity surfacing, not
  bypass auditing.
- `packages/core/tests/services/settle.test.ts:2365` pins
  `summary.gates?.map(g => g.gate)` to exactly `GATE_ORDER` — this phase
  deliberately breaks that invariant whenever per-task-verify ran (its
  fixture never sets `perTaskVerify`, so the existing test stays green
  unmodified). AC-4's own test must positively assert the *new* shape
  (`GATE_ORDER.length + N` per-task entries) rather than only checking
  absence of regression.

## Acceptance Criteria

### AC-1: deep-verify's GateResult carries observed verifier identity on every return path
Given deep-verify runs to any of its three outcomes that already call
`meta(...)` today (per-AC-pass, per-AC-fail, or the verifier-transport-
-failure catch branch specifically under `--allow-verifier-failure` — NOT
the bare-refuse sub-path with no bypass flag, which calls no `meta()` and
gets no flags today, out of scope)
When the gate function returns its `GateResult`
Then `result.flags.observedVerifierIdentity` is populated with the provider
that actually ran (and model, when present) on all three in-scope paths —
proven by a direct unit test per path, not by inspecting a settled SUMMARY

### AC-2: registry.ts maps observed identity onto GateProvenanceZ, gate-name-agnostically
Given a gate's `GateResult` carries `flags.observedVerifierIdentity`
When `registry.ts` assembles that gate's `gates[]` entry
Then the entry carries `observedProvider` (and `observedModel`, when
present), via a new helper mirrored on `verifierIdentityProvenance()`'s
existing pattern — keyed by flag presence only, proven by a test using a
synthetic/mock gate result so the assertion cannot pass by coincidentally
matching `deep-verify`'s specific name

### AC-3: deriveAssuranceRecord's rollup and overall are structurally unaffected by observedProvider/observedModel
Given a `gates[]` array containing entries with `observedProvider`/
`observedModel` set and `.provider`/`.model` absent
When `deriveAssuranceRecord` computes `verifierRollup` and `overall`
Then `verifierRollup` contains no entry derived from those fields and
`overall` does not change between an otherwise-identical input with and
without them present — a direct unit test of the pure function's output
(no source change to `assurance-record.ts` itself is expected; the test
proves the *existing* fold already cannot see the new fields), the
load-bearing safety property this phase exists to prove

### AC-4: per-task-verify's already-persisted identity is surfaced into the SUMMARY's gates[], one entry per task execution, on every settle path
Given one or more tasks recorded a `PerTaskVerifyRecord` (carrying `provider`,
optional `model`, `verdict`, and optional `bypassed`) during BUILD
When settle assembles the SUMMARY, on either the success path or a refused
path (settle can refuse for reasons unrelated to per-task-verify, e.g. a
failing AC)
Then one `gates[]` entry per task's `PerTaskVerifyRecord` is present with
`gate: 'per-task-verify'`, `status: 'ran'`, `taskId` set to that task's id,
`observedProvider`/`observedModel` set, and `.provider`/`.model` left
absent — proven by a settle-service test with 2+ tasks carrying different
per-task-verify providers (including one `refuse`+`bypassed: true` record),
asserting the exact resulting `gates[]` length (`GATE_ORDER.length + N`)
and content on BOTH a successful settle and a refused settle

### AC-5: the new schema fields are additive and content-hash-safe
Given `observedProvider`, `observedModel`, and `taskId` are added to
`GateProvenanceZ`
When a hand-built legacy `gates[]` entry (lacking all three fields) is
hashed, then round-tripped through `SummaryZ.parse`, then re-hashed
Then the pre-parse and post-parse hashes are identical (mirroring
`summary-provider-selection-schema.test.ts`'s existing non-tautological
round-trip pattern for the sibling `providerSelection` field exactly — NOT a
self-referential round-trip that already has the fields baked in on both
sides) — additionally sanity-checked by parsing one real, historical,
settled `<id>-SUMMARY.json` fixture from this repo's own `.cadence/phases/`
corpus through the updated schema and confirming
`verifySummaryContentHash` still reports `MATCH` (mirroring
`summary-hash.test.ts`'s real-fixture pattern)

## Boundaries

- DO NOT modify `deriveAssuranceRecord`'s fold to explicitly check/skip
  `observedProvider`/`observedModel`/`taskId` — the safety property is that
  it never reads those field names at all, proven by T1's test on the
  *existing* code, not by adding a new exclusion branch.
- DO NOT add gate-name branching to `registry.ts`'s new helper or to
  `deriveAssuranceRecord` — both must stay keyed by flag/field presence only,
  matching the existing `verifierIdentityProvenance()`/rollup-fold pattern.
- DO NOT add a `.default(...)` to `observedProvider`/`observedModel`/
  `taskId`, and DO NOT bump `schemaVersion` — this is an additive,
  content-hash-safe schema change per `providerSelection`'s precedent.
- DO NOT touch `code-review`/`security-audit`/`spec-review`/`ui-spec-review`/
  `plan-review`'s existing `provider`/`model`/`providerSelection` persistence
  — this phase adds a new parallel field set, it does not change the
  existing one.
- DO NOT collapse per-task-verify's per-task entries into a distinct-pair
  rollup (that is `verifierRollup`'s job, one layer up) — `gates[]` is the
  raw provenance layer and must carry one entry per task execution via
  `taskId`, matching this session's own Phase W finding on
  `scanTestCoverage`'s dedup-collapses-evidence bug.
- DO NOT synthesize `gateBypasses[]` entries for a bypassed per-task-verify
  refuse — that is a distinct, out-of-scope audit-trail question from this
  phase's provider-identity scope; a bypassed refuse keeps `status: 'ran'`
  in `gates[]` (see Evidence), and whether `gateBypasses[]` should also
  cover per-task bypasses is left for a future rec if wanted.
- DO NOT add rendering for `taskId`/`observedProvider`/`observedModel` in
  `summary-render.ts`/`summary-writer.ts` in this phase — deliberately
  deferred, not an oversight; a rendered SUMMARY.md will show N generic
  "per-task-verify: ran" lines with no visible identity until a future
  phase adds display support.
- DO NOT add a standalone "full test suite passes" AC — fold the suite run
  into each task's own `verify:` line (phase 273's carry-forward gotcha;
  matches `rec-20260811-008`'s documented pattern of command-output-shaped
  ACs being structurally unverifiable by deep-verify).
- `docs/concepts.md` documents each prior phase's `gates[]` schema evolution
  by name (lines 108, 112, 147 as of this writing) — T1 or T3's implementer
  should add a one-line mention of `observedProvider`/`observedModel`/
  `taskId` there to match convention, though no mechanical test enforces
  this specific pairing.
