# 100-01 — Add a 'shipped' terminal status to the recommendation lifecycle

## Objective

Give a recommendation whose work has landed a truthful terminal home — a new
`shipped` status (set via `recommendation promote`, with an optional freeform
provenance reference) — so the ledger stops showing delivered work as
`candidate` and shipped recs drop out of the active `recommend` surface.

## Context

The rec lifecycle (`RecommendationStatusZ`) is
`candidate | accepted | deferred | rejected | converted`. `converted` is the only
positive-terminal state, but reaching it requires `cadence recommendation convert`
to create a real `.cadence/phases/<id>/` dir. A rec fixed directly (e.g.
rec-20260610-001, the phase-id ceiling fix shipped as v1.22.1 via PR #70) has
nowhere terminal to go and stays `candidate` forever. This phase is itself the
conversion of **rec-20260611-001** and is the first phase numbered ≥ 100 (the
ceiling fix that unblocked it).

## Acceptance Criteria

### AC-1: `shipped` is a valid recommendation status
Given the recommendation status schema
When a recommendation is parsed/validated with `status: 'shipped'`
Then it validates, and `shippedRef` is an accepted optional freeform string field;
unknown statuses are still rejected.

### AC-2: promote to `shipped` from an active status
Given a recommendation in `candidate`, `accepted`, or `deferred`
When `recommendation promote <id> --status=shipped` runs
Then the rec's status becomes `shipped` and `updatedAt` advances.

### AC-3: `converted → shipped` is allowed (the one sanctioned exception)
Given a recommendation in `converted`
When `recommendation promote <id> --status=shipped` runs
Then the transition succeeds (a converted phase that later shipped reaches true
completion), even though `converted` is otherwise terminal.

### AC-4: `shipped` is terminal
Given a recommendation already in `shipped`
When any `recommendation promote <id> --status=…` runs
Then it is refused with a terminal-status error (you cannot promote out of
`shipped`).

### AC-5: optional provenance reference, guarded
Given `recommendation promote <id> --status=shipped --ref="PR #70 / v1.22.1"`
When it runs
Then `shippedRef` is stored verbatim; AND supplying `--ref` with any status other
than `shipped` is refused; AND `--status=shipped` without `--ref` is allowed
(old recs need no ref).

### AC-6: `shipped` recs leave the active surface
Given a `shipped` recommendation
When the ledger is partitioned for `cadence recommend`
Then the rec is excluded from `ranked`/`parked` exactly like `converted`/`rejected`
(it no longer pollutes the active backlog).

### AC-7: provenance is rendered
Given a `shipped` recommendation with a `shippedRef`
When the recommendation detail is rendered (RECOMMENDATIONS.md / detail view)
Then a `- shipped: <ref>` line appears, mirroring the existing
`convertedToPhaseId` line.

## Boundaries

- DO NOT change `convert` / `convertedToPhaseId` semantics, or add a new
  top-level command — `shipped` is set through the existing `promote`.
- DO NOT make `shippedRef` structured or validated beyond a non-empty string
  (freeform by design; no parsing into PR/commit/version).
- DO NOT reorder existing statuses or change the terminal behavior of
  `rejected`/`converted` — the only new edge is `converted → shipped`.
- Out of scope for code (operator follow-up after settle): retro-marking the
  ~10 shipped-but-`candidate` recs (incl. rec-20260610-001) as `shipped`.
- No DESIGN.md D-number — additive extension of the existing rec lifecycle.
