# 109-01 — init --demo: pre-filled first phase in the real repo

## Objective

Add `cadence init --demo`, which after scaffolding `.cadence/` seeds a real,
ready-to-approve demo phase (objective + AC-1 + task T1) into the user's own
repo using the same toy template the `tutorial` sandbox uses — so a newcomer
runs `approve → done → settle` and watches a real gate pass in their repo, with
no hand-edit.

## Acceptance Criteria

### AC-1: `init --demo` leaves a ready-to-approve demo phase
Given a fresh repo with no `.cadence/`
When the user runs `cadence init --demo`
Then `.cadence/phases/01-demo/01-01-DRAFT.md` exists and the loop position is
DRAFT (the demo phase is the active draft).

### AC-2: the seeded DRAFT needs no hand-edit
Given the DRAFT written by `init --demo`
When it is inspected
Then it contains a non-placeholder Objective, at least one acceptance criterion
(AC-1), and at least one task (T1) linked to AC-1.

### AC-3: the toy template is shared with `tutorial` (one source)
Given the demo-draft template
When both `cadence init --demo` and `cadence tutorial` render it
Then both consume a single shared renderer (no duplicated template literal), and
`tutorial`'s rendered draft is unchanged (byte-identical to its prior text).

### AC-4: init without --demo is unchanged
Given a fresh repo
When the user runs `cadence init` (no `--demo`)
Then no demo phase is scaffolded (`.cadence/phases/` has no `01-demo`) and the
loop position stays IDLE.

### AC-5: the seeded loop settles clean end-to-end
Given a repo initialized with `cadence init --demo`
When the user runs `draft approve 01-demo 01`, `done T1`, then
`settle run --ac AC-1=pass`
Then the loop settles (exit 0) and a SUMMARY is written for the demo phase.
