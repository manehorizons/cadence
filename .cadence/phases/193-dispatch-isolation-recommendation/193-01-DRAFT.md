# 193-01 — Recommend worktree isolation for mutation-scoped dispatch tasks

## Objective

Today `cadence dispatch plan` gives no per-task signal about whether a
dispatched task should run in an isolated worktree — isolation is decided
purely by human/skill-level convention (the `phase-build` skill's whole-phase
worktree step), with zero backing in the dispatch plan itself. Per
rec-20260718-002 (from the same 2026-07-18 incident that motivated phase
192), add a pure `recommendIsolation(task)` heuristic — `'worktree'` when a
task declares one or more `files:`, `'none'` when it declares none — and
surface it both in `cadence dispatch plan --json`'s per-task output and in
the packet's own rendered text, so an orchestrator dispatching subagents
sees the recommendation whichever surface it reads. No DRAFT/Task schema
change: existing DRAFT.md files keep parsing exactly as before.

## Acceptance Criteria

### AC-1: `--json` output carries the recommendation
Given a dispatch plan computed via `cadence dispatch plan --json`
When the JSON is emitted
Then each task entry in every wave includes a `recommendedIsolation` field
set to `'worktree'` when that task declares one or more `files:`, or `'none'`
when it declares none

### AC-2: the rendered packet states the recommendation
Given a task rendered through `renderPacket`
When the packet text is produced
Then it includes an explicit isolation-recommendation line matching the same
heuristic as AC-1 (worktree vs. none), phrased as advisory guidance for the
dispatching orchestrator, not as an enforced mechanism

### AC-3: purely additive, no schema or wave-planning change
Given the existing `Task`/`Draft` zod schemas and `computeWaves` wave-leveling
logic
When this feature is implemented
Then neither the schemas nor `computeWaves` change, and a pre-existing
DRAFT.md with no knowledge of isolation still parses and dispatches exactly
as before

### AC-4: docs describe the new field and heuristic
Given `docs/reference/commands.md` documents `cadence dispatch plan`'s
`--json` shape and Behavior
When the docs are read after this change
Then they describe the `recommendedIsolation` field and the files-presence
heuristic that computes it

## Boundaries

- DO NOT add an `isolation` field to the `Task`/`Draft` zod schemas (`packages/types/src/plan.ts`) — this phase implements the pure-computation heuristic only, not an author-overridable field. A schema field is out of scope; revisit only if the heuristic proves too coarse in practice.
- DO NOT change `wave-planner.ts` / `computeWaves` — isolation is orthogonal to wave ordering.
- DO NOT change or weaken the prohibition-boilerplate content `renderPacket` already emits (added in phase 192).
- DO NOT implement actual enforcement (e.g. auto-creating worktrees, refusing dispatch without one) — this is advisory output only, matching the packet's existing pattern of prose guidance rather than mechanism.
