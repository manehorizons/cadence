# 162-01 — Codex first-run bootstrap

## Objective

Make Codex a first-class onboarding target so a new user can run one setup path
before launching Codex and have Cadence commands, hooks, and project
instructions available on the first useful Codex session.

## Acceptance Criteria

### AC-1: Codex bootstrap is reachable from the core setup flow
Given a repo that is not yet wired for Codex
When the user runs the documented Codex bootstrap path from the Cadence CLI
Then Cadence installs the Codex host adapter hooks and prompt commands through the existing host installer and prints the required "approve hooks / start Codex" next step

### AC-2: Codex receives project instructions via AGENTS.md
Given `cadence init` writes managed agent instructions for host use
When Codex is the chosen or detected host target
Then the repo contains a managed `AGENTS.md` Cadence block with the same loop guidance as `CLAUDE.md`, preserving user content outside markers

### AC-3: doctor can verify and repair Codex readiness
Given a repo that may be missing one or more Codex readiness artifacts
When the user runs the relevant `cadence doctor` check or fix
Then Cadence reports whether `.codex/hooks.json`, `$CODEX_HOME/prompts/cadence-*.md`, `AGENTS.md`, and the `cadence` command are ready, and exposes safe fixes for the artifacts Cadence owns

### AC-4: onboarding docs make first-run ordering explicit
Given a new user following the quickstart or host adapter docs
When they choose the Codex surface
Then docs tell them to run the Codex bootstrap before opening Codex for the first time and explain the fallback: if prompts are not loaded yet, ask Codex to run the `cadence` CLI directly

## Tasks

### T1: Add a Codex setup path to the core CLI
- files: `packages/core/src/cli/commands/init.ts`, `packages/core/src/start/menu.ts`, `packages/core/tests/cli/init.test.ts`, `packages/core/tests/cli/start.test.ts`
- action: add a Codex bootstrap entry point such as `cadence init --host codex` or `cadence setup codex` that shells out to `npx -y @manehorizons/cadence-host-codex install` without importing host code into core
- verify: focused CLI tests prove the Codex host installer is invoked, non-TTY behavior does not hang, and existing Claude auto-wire behavior remains intact
- done: AC-1

### T2: Generalize managed agent instruction generation for AGENTS.md
- files: `packages/core/src/init/claude-md-template.ts`, `packages/core/src/cli/commands/init.ts`, `packages/core/tests/cli/init*.test.ts`
- action: extract the managed Cadence block so it can render into `CLAUDE.md` and `AGENTS.md`; add a Codex-targeted init path that creates or updates `AGENTS.md` while preserving marker-less user files
- verify: tests cover create, regenerate, and preserve behavior for `AGENTS.md`
- done: AC-2

### T3: Add Codex readiness checks to doctor
- files: `packages/core/src/doctor/run.ts`, `packages/core/src/doctor/fix.ts`, `packages/core/tests/doctor/*.test.ts`
- action: detect missing or stale Codex hooks, prompts, `AGENTS.md` managed block, and unavailable `cadence` binary; wire safe fix actions for Cadence-owned files/installers
- verify: doctor tests cover all-ready, missing hooks, missing prompts, missing `AGENTS.md`, and missing binary cases
- done: AC-3

### T4: Update user-facing docs
- files: `docs/quickstart.md`, `docs/host-adapters.md`, `packages/host-codex/README.md`, `README.md`
- action: document the pre-Codex first-run bootstrap command, explain why a new Codex session is required for prompt loading, and include the CLI fallback wording
- verify: docs tests pass and the quickstart has a direct Codex path before the generic host adapter details
- done: AC-4

## Boundaries

- DO NOT make Codex prompt commands project-scoped unless Codex itself supports project-level prompt directories.
- DO NOT commit machine-absolute `--local` host installer paths.
- DO NOT import host adapter packages into `@manehorizons/cadence-core`; keep host wiring as subprocess invocation.
- DO NOT remove or weaken the existing Claude Code setup behavior.
