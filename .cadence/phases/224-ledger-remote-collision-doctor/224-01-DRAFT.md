# 224-01 — cadence doctor: detect cross-session ledger id collisions before push

## Objective

`mintId` (`packages/core/src/intelligence/store/ids.ts` / `ledger.ts`) computes
the next `rec-YYYYMMDD-NNN` / `ev-YYYYMMDD-NNN` / `dec-YYYYMMDD-NNN` /
`as-YYYYMMDD-NNN` id purely from the local ledger on disk — it has no
visibility into ids minted by another unpushed branch/worktree/session. This
phase closes the gap with detection, not prevention (a central id-issuing
service is against this repo's offline/zero-runtime-dependency design; a
higher-entropy id format is a disruptive convention change) — a new `cadence
doctor` check, `ledger-remote-collision`, that fetches the tracked upstream
branch (reusing the existing `checkRemoteFreshness` fetch plumbing) and diffs
local's new-since-merge-base ledger ids (recommendations, evidence, decisions,
assumptions) against the upstream's new-since-merge-base ids, warning loudly
on any overlap. Matches the existing "refuse + suggest, never silently
mutate" doctor convention (`worktree-phases`, `orphaned-evidence`).

## Acceptance Criteria

### AC-1: doctor detects a genuine cross-session ledger id collision
Given local and the tracked upstream branch have diverged since their common
merge-base, and both sides independently minted the same recommendation,
evidence, decision, or assumption id for different content
When `cadence doctor` runs
Then the `ledger-remote-collision` check reports `warning` severity, naming
the colliding id(s), which ledger each belongs to, and remediation to
re-mint the local-only entry under a new id before pushing

### AC-2: check degrades safely when remote comparison isn't possible
Given any of: no git repository, no upstream configured, a failed fetch, a
detached HEAD, or no discoverable merge-base with the upstream ref
When `cadence doctor` runs
Then the `ledger-remote-collision` check reports `ok` (never `error`, never an
unhandled throw), with a detail explaining why the comparison could not be
made — matching the best-effort convention of `worktree-phases` /
`orphaned-evidence` / `recommendation-shipped-drift`

### AC-3: implementation is covered by tests
Given the `ledger-remote-collision` check implementation is complete
When the relevant test suite runs
Then unit tests cover the pure id-diff logic and each degrade-safely path
from AC-2 using an injected stub gatherer (offline, deterministic), AND at
least one test exercises the real git-fetch/merge-base path end-to-end
against a genuine local-repo + bare-origin pair (mirroring
`packages/core/tests/handoff/remote-freshness.test.ts`) that reproduces an
actual id collision

## Tasks

### T1: Implement the `ledger-remote-collision` doctor check
- files: `packages/core/src/doctor/run.ts`
- action: add a `LedgerIdSnapshot` shape (`recommendations`/`evidence`/
  `decisions`/`assumptions` id arrays); a pure `findLedgerRemoteCollisions(local,
  mergeBase, origin)` that returns `{subject, id}` pairs present in both
  local's and origin's new-since-merge-base sets; an impure
  `gatherLedgerRemoteCollisionSnapshot(root)` that reuses
  `checkRemoteFreshness` (`../handoff/remote-freshness.js`) for the
  fetch+branch+upstream-existence check, then (only when `checked`) resolves
  `git merge-base HEAD @{u}` and reads ledger ids at HEAD (local filesystem,

  `readAssumptionLedger`/`readIntelligenceDecisionLedger` readers — includes
  archived recs), at the merge-base commit, and at `@{u}`, both via `git show
  <ref>:<path>` (through the existing `gitBestEffort` helper from
  `../git/worktrees.js`; a missing file at a ref parses to an empty id set,
  never a thrown error); and the `DoctorCheck`-returning
  `checkLedgerRemoteCollision(root, gather = gatherLedgerRemoteCollisionSnapshot)`
  wired into `runDoctor`'s checks array (after `orphaned-evidence`) — mirrors

## Boundaries

- DO NOT touch `packages/core/src/intelligence/store/ids.ts` or `ledger.ts` —
  `mintId` itself is out of scope; this phase adds detection only, not a
  change to how ids are minted.
- DO NOT add a `--fix` auto-repair for this finding — a ledger id collision
  needs a human to pick which side re-mints; it stays classified `manual`
  (fixId `null`) like `worktree-phases`/`verification-readiness`.
- DO NOT change `checkRemoteFreshness`'s existing behavior or signature —
  reuse it as-is; if it needs a new capability, that's a separate phase.
- DO NOT expand this check to assumptions/decisions/evidence content-diffing
  (e.g. detecting same-id-different-title) beyond the id-overlap signal
  itself — id overlap after divergence from a common merge-base is already a
  sufficient and unambiguous signal per the rec's own evidence.
