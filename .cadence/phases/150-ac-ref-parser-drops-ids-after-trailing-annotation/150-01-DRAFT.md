# 150-01 — AC-ref parser drops ids after trailing annotation

## Objective

Found while dogfooding phase 149 (issue #135): a task's `done:` field lists
comma-separated AC ids (e.g. `done: AC-1, AC-2, AC-3, AC-4`). Both
`packages/core/src/status.ts` and `packages/core/src/notify/collect.ts`
independently define a byte-identical private `parseAcRefs(done: string):
string[]`:

```ts
function parseAcRefs(done: string): string[] {
  return done
    .split(',')
    .map((s) => s.trim())
    .filter((s) => /^AC-\d+$/.test(s));
}
```

The exact-match filter `/^AC-\d+$/` silently drops any comma-token that has
trailing text after the id — e.g. `done: AC-1, AC-2, AC-3, AC-4 (core
logic)` parses to `['AC-1', 'AC-2', 'AC-3']`, silently dropping AC-4 with no
error. `cadence status`/`cadence progress` then show that AC as permanently
`pending` even when a task claims to cover it and a real test references it
— a legibility trap with no diagnostic pointing at the actual cause (a stray
annotation in the DRAFT).

Fix: replace the strict whole-token match with a per-token *prefix* match
that tolerates trailing text after the id, and de-duplicate the two
byte-identical private copies into one shared, tested helper (both are the
same defect; fixing only one leaves the other silently broken). New home:
`packages/core/src/parse/ac-refs.ts`, exporting `parseAcRefs`, imported by
both `status.ts` and `notify/collect.ts` in place of their private copies.

## Boundaries

- DO NOT loosen the `AC-\d+` id format itself (no fuzzy/case-insensitive
  matching) — only tolerate trailing text after a valid prefix.
- DO NOT touch `draft-parser.ts`'s raw `done` field extraction — this phase
  is scoped to the downstream `parseAcRefs` consumers only.
- DO NOT refactor anything else in `status.ts`/`notify/collect.ts` beyond
  swapping the import.
