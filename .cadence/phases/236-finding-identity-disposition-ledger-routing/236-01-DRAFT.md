# 236-01 — Finding identity, disposition, and Finding-type convergence

## Objective

Give findings a stable identity so they can be tracked across settles instead of re-detected as new every time. Add {id, target, disposition, waiver} to the persisted Finding schema per dec-20260730-001: id is a pure anchor-derived content hash over (file, anchor.kind, anchor.ref, severity, normalized message) — no fingerprint primitive, no new runtime dependency, never derived from a line number. Widen AnchorZ.kind with 'invariant' (unused by any producer yet — phase 237 scope). Converge the two independently-declared Finding types (packages/types/src/summary.ts's 4-severity FindingZ and packages/core/src/verify/code-review.ts's local 3-severity Finding/FindingSeverity) onto one, per the source design doc's local D9 ('one Finding type, discriminated by target'). Extend RecommendationSourceZ with a 'review' member so a future routing phase can carry real provenance. Scope is deliberately schema-and-computation only: this slice does NOT implement findings-to-ledger auto-routing (creating Recommendation + Evidence entries from findings during settle, source doc section 7.3) — that behavioral piece is split to a follow-on phase, recorded as an inline roadmap amendment.

## Acceptance Criteria

### AC-1: Finding gains a stable identity, target, and disposition
Given the persisted Finding schema (FindingZ) has only severity, message, and an optional line/anchor
When a Finding is validated with id, target: 'artifact'|'verification', disposition: 'open'|'accepted'|'waived'|'fixed'|'superseded', and (only when disposition==='waived') a waiver: { expiry }
Then all fields parse successfully, and a pre-phase-236 Finding record with none of these fields present still parses unchanged — the new fields are additive and optional

### AC-2: Anchor kind widens to include 'invariant'
Given AnchorZ.kind currently accepts only 'ac'|'boundary'|'none'
When AnchorZ.kind is widened to also accept 'invariant' per source doc section 7.2
Then an anchor with kind 'invariant' parses successfully, and every existing 'ac'/'boundary'/'none' anchor continues to parse and resolve identically to before this change

### AC-3: Code-review findings get a computed, refactor-stable id at anchor time
Given a code-review finding tagged with its resolved section-7.1 anchor via anchorFindings
When the settle's code-review gate builds its summaryPatch
Then each finding also carries a stable id — a pure content hash over (file, anchor.kind, anchor.ref, severity, normalized message), computed with no new runtime dependency and never derived from a line number — plus target: 'artifact' and disposition: 'open'; the same finding recomputed from the same (file, anchor, severity, message) inputs after an edit that only shifts its line number yields the identical id

### AC-4: The two divergent Finding types converge into one
Given today's two independently-declared Finding shapes — the persisted-schema FindingZ (severity critical|high|medium|low) and the code-review verifier's local Finding/FindingSeverity (high|medium|low only)
When the verifier module is updated per the source doc's local D9 ('one Finding type, discriminated by target')
Then packages/core/src/verify/code-review.ts no longer declares its own divergent Finding/FindingSeverity — it uses the shared cadence-types Finding — and every pre-existing code-review test (mock walker, Anthropic-response mapping, criteria-gap tagging) keeps passing unchanged

### AC-5: RecommendationSourceZ gains a 'review' member
Given RecommendationSourceZ currently enumerates manual|code-analysis|impact|cadence|session
When it is extended with a 'review' member
Then a Recommendation record with source: 'review' parses successfully, and every existing source value still parses

## Boundaries

- DO NOT implement findings-to-ledger auto-routing — creating `Recommendation` + `EvidenceZ(kind: 'cadence-artifact')` entries from findings during settle (source doc section 7.3). That is real behavioral/I-O work split to a follow-on phase; this slice only extends `RecommendationSourceZ` so that future phase has correct provenance to route with.
- DO NOT build a disposition-management CLI or mutation surface (waive/accept/fix/supersede commands). This slice only computes fresh identity and a default `open` disposition at detection time.
- DO NOT compute or attach `id`/`target`/`disposition` for security-audit findings in this slice. They already share the converged `Finding` schema — the new fields simply stay absent on them — and wiring identity computation into `gates/security-audit.ts` is out of scope.
- DO NOT build a fingerprint primitive, and DO NOT extract anything from Déjà — `dec-20260730-001` rejected that route on the record.
- DO NOT change `GATE_ORDER`, and DO NOT change any gate's pass/refuse semantics for finding classes that existed before this phase.
- DO NOT make any schema change non-additive: every new field is `.optional()`, and every pre-existing SUMMARY/recommendations artifact must keep parsing.
- DO NOT criteria-anchor `spec-review`, `ui-spec-review`, or `plan-review` — unrelated to this phase, `dec-20260729-003` still holds.
- DO NOT write a test that calls a real provider, and DO NOT loosen an existing test to accommodate the change.
- DO NOT add a runtime dependency, and DO NOT move any package.
