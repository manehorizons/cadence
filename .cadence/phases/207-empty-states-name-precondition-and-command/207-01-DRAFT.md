# 207-01 — Empty states and refusals must name the precondition, nearest candidates, and unblocking command

## Objective

Every empty-result or refusal message emitted by the intelligence-layer CLI surface (`recommend`, `milestone propose`, `recommendation promote`/`convert`/`list`, `retro`) states why it's empty, the concrete unmet precondition, the nearest-miss candidate(s) from the already-loaded ledger, and the exact command that would change the outcome — computed through one shared, reusable helper rather than duplicated per site.

## Acceptance Criteria

### AC-1: Shared nearest-candidate helper exists
Given `resolveIdleLedgerHints` in `packages/core/src/cli/commands/next.ts` (lines 41-104) already computes ranked/filterable ledger candidates using `partitionLedger` + `scoreRecommendation` from `packages/core/src/intelligence/recommend.ts`
When phase 207 is implemented
Then that computation is extracted into a shared, tested module importable by any CLI command, and `next.ts` is refactored to consume it with no behavior change to `cadence next`'s existing output

### AC-2: `cadence milestone propose` empty result is enriched
Given zero recommendations meet the milestone-eligibility bar (status=accepted + readiness in {ready-for-milestone, ready-for-cadence-spec}) — currently `services/milestone-propose.ts:23` prints only the bare count
When `cadence milestone propose` runs with zero eligible recommendations
Then stdout states the eligibility precondition in concrete terms, lists the nearest-miss candidate(s) with what each is missing, and prints the exact `cadence recommendation promote <id> --status=... --readiness=...` command to fix the closest one

### AC-3: `cadence recommend` empty result is enriched
Given zero recommendations exist, or none score above the actionable threshold — currently `intelligence/render-recommend.ts:22` prints only `No actionable recommendations.`
When `cadence recommend` runs with an empty or all-filtered-out result
Then the rendered output distinguishes "none exist" from "none actionable," and when candidates exist but are filtered out, names the nearest one and the unblocking command

### AC-4: Recommendation lookup-not-found errors are consolidated and enriched
Given the four near-duplicate `recommendation ${id} not found` sites in `intelligence/store/recommendations.ts` (lines 101, 183, 321, 351)
When any of them fires
Then they route through one message-building function that also suggests the nearest-ID match (if any) against the loaded ledger, plus the exact `cadence recommendation list` command to browse

### AC-5: Promote/convert status-refusal messages name the unblocking command
Given promote/convert refusals in `intelligence/store/recommendations.ts` (lines 187, 239, 245, 253, 260, 278, 411) already name the concrete blocking status
When any of these refusals fires
Then the existing concrete-status text is retained and joined with the exact command that would transition the recommendation to an eligible status

### AC-6: Retro rollup disambiguates "no phases" vs "zero friction"
Given `parse/render-retro-rollup.ts:41` currently emits one message (`${totalPhases} phase(s) scanned, no friction to report.`) for both zero-phases-scanned and phases-scanned-with-no-friction
When `cadence retro` runs
Then the two cases render distinct messages, and the zero-phases case names the precondition (no settled phases yet) plus the command to check current loop position

### AC-7: Guidance invariant is documented
Given this phase establishes a uniform bar for empty/refusal messaging across the intelligence layer
When phase 207 ships
Then `docs/concepts.md` (or the most fitting existing reference doc) documents the four-part invariant (why / concrete precondition / nearest candidates / exact command) as the guidance bar for future intelligence-layer commands, and the phase's DRAFT or SUMMARY carries an audit checklist of the 7 sites covered by this phase (AC-2 through AC-6, with AC-4/AC-5 each covering multiple call sites)

## Boundaries

- DO NOT change `cadence next`'s ranking/scoring output — this phase only extracts the existing computation into a shared module.
- DO NOT change the `--json` / `--format=json` schema of `recommend`, `recommendation list/promote`, or `milestone propose` — enrichment is additive to human-readable rendering only.
- DO NOT write a second scoring/ranking implementation — every enrichment site reuses `intelligence/nearest-candidate.ts` (T1) or, for AC-4's ID lookup, a small self-contained prefix-match helper (not a general fuzzy-match library).
- DO NOT expand scope beyond the 7 sites enumerated in AC-2 through AC-6 — no speculative sweep of other CLI surfaces.

## Audit checklist (AC-7)

Site-by-site closure record for the guidance invariant this phase establishes
(documented in `docs/concepts.md`, "Empty-result and refusal messages").
Counts below reflect what T1-T5 actually shipped, not this DRAFT's original
per-site guesses where the two differ.

- [x] AC-2 — `cadence milestone propose` empty-eligibility result — done, see
  T2. Two rounds: the first enriched `milestoneProposeService`
  (`services/milestone-propose.ts`), which is MCP-tool-only and does not
  back the real `cadence milestone propose` CLI command; a review caught
  this. A fix round wired the actual CLI command
  (`cli/commands/milestone.ts`) through the same exported
  `buildEmptyResultMessage`, keyed on `ledger.milestones.some(m => m.status

  markdown always renders the full historical ledger, so an empty *new*
  proposal isn't the same as an empty ledger). Lesson for future phases:
  verify which code path actually backs a CLI command before enriching a
  function that merely looks like it does — a function reachable from both
  CLI and MCP can silently diverge if only one caller is fixed.

- [x] AC-4 — recommendation not-found consolidation — done, see T4. 5 call
