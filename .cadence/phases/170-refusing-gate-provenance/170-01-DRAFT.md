# 170-01 — Refused settle persists gate provenance + SUMMARY

## Objective

When a settle gate refuses, persist a structured record of exactly which gate refused and why, alongside every gate's status up to that point — today the refusing gate is silently dropped from the gates provenance array and no SUMMARY is written at all on the refusal path, leaving zero durable evidence besides an ephemeral stderr line.

## Acceptance Criteria

### AC-1: Refusing gate appears in provenance
Given a settle run where a gate impl returns { outcome: 'refuse' }
When runSettleGates halts on that gate
Then the returned gates array includes an entry for the refusing gate with status 'refused', in addition to every earlier gate's ran/skipped entry

### AC-2: Refusal reason is captured on the gate result
Given any of the 9 settle-dispatched gates (draft-read, structural-verifier, boundary-scan, build-test-must-pass, test-coverage, interactive-verdict, deep-verify, code-review, security-audit) refuses
When it returns { outcome: 'refuse' }
Then the result carries a reason string matching the message it writes to stderr, and registry.ts surfaces that reason on the refused gate's provenance entry

### AC-3: A refused settle persists a SUMMARY
Given cadence settle run halts because a gate refused
When the command exits with exitCode 1
Then <draft>-SUMMARY.json and .md are written under .cadence/phases/<phase>/, containing the populated gates array (through and including the refusing gate) and taskResults derived from current BUILD progress, where previously nothing was written on this path

### AC-4: Schema stays additive and back-compat
Given pre-existing SUMMARY.json records whose gates entries only ever used status ran or skipped
When parsed against the updated GateProvenanceZ
Then they still validate unchanged — the new 'refused' status and optional reason field are additive, no existing field changes shape

## Boundaries

- Do NOT add 'errored' or 'bypassed' to GateProvenanceZ.status — no code path produces a graceful 'errored' outcome today (an uncaught gate exception still propagates to settleService's outer try/catch, a separate and larger problem not covered by this phase's acceptance bar), and 'bypassed' is already tracked via the existing GateBypassZ/gateBypasses mechanism; duplicating it here is redundant.
- Do NOT add the optional `--collect-all` diagnostic mode mentioned in rec-20260711-008's suggested fix — fail-fast-refuse-and-persist satisfies the stated acceptance bar on its own; a "keep running all gates after a refusal" mode is a separate, larger feature (how do dependent gates behave when an earlier one refused?) and is out of scope here.
- Do NOT add duration/provider metadata to GateProvenance — not required by the acceptance bar and would need new per-gate timing instrumentation across all 9 impls, a distinct scope expansion.
- Do NOT change `loopPosition` or `activeDraft` on a refused settle — the loop must remain exactly where a human can retry; only SUMMARY persistence changes.
- Do NOT touch the 4 DRAFT/BUILD-only gates (`coherence-check`, `approve`, `plan-review`, `per-task-verify`) — they are excluded from `SettleGate` and never appear in settle's `gates` provenance array; their refusal paths are out of scope.
