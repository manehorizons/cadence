# 139-01 — Default install enforces what the tutorial demonstrates

## Objective

Close the gap between what `cadence tutorial` demonstrates (real enforcement)
and what a fresh `cadence init` delivers (a comment-only `AC-1` mention
settling green with no test runner executed): default new inits to
`coverageMode: 'assertion'`, derive a real `verification.testCommand` from
the target repo's `package.json#scripts.test` + detected package manager,
and make `build-test-must-pass` print a loud, non-blocking stderr notice
instead of passing silently when no `testCommand` is configured. Source:
rec-20260701-001 (wave 2, "enforcement wedge"). Design:
`docs/superpowers/specs/2026-07-02-default-enforcement-design.md`.

Scope note: this only changes what a **new** `init` writes — existing
`.cadence/config.json` files are untouched. `coverageMode: 'assertion'`
applies to all three presets (`solo`/`team`/`production`) — coverage
truthfulness isn't a process-friction knob. rec-003 (SUMMARY provenance) and
rec-009 (sealed gates) are separate, later phases.

## Acceptance Criteria

### AC-1: coverage default flips to assertion mode for every preset
Given a fresh `cadence init` with no flags
When `.cadence/config.json` is written
Then `verification.coverageMode` is `'assertion'`, for `solo`, `team`, and
`production` alike

### AC-2: testCommand is derived from package.json + detected package manager
Given a target repo with a `package.json` `scripts.test` entry and a
lockfile (`pnpm-lock.yaml` / `yarn.lock` / `bun.lockb` / `package-lock.json`)
When `cadence init` runs
Then `.cadence/config.json`'s `verification.testCommand` is the correctly
package-manager-prefixed command (`pnpm test` / `yarn test` / `bun test` /
`npm test`, with `npm test` as the no-lockfile fallback)

### AC-3: no testCommand when nothing to derive
Given a target repo with no `scripts.test` entry (or no `package.json` at
all)
When `cadence init` runs
Then `verification.testCommand` is absent from the written config, matching
today's schema-optional behavior — no guessing, no placeholder command

### AC-4: --dry-run previews the derived testCommand identically
Given the same repo shapes as AC-2/AC-3
When `cadence init --dry-run` runs
Then the printed plan shows the same derived `testCommand` (or its absence)
that a real init would write, and nothing is written to disk

### AC-5: unconfigured testCommand gets a loud, non-blocking settle notice
Given `verification.testCommand` is unset
When `settle run` reaches the `build-test-must-pass` gate
Then the gate writes the `NO_TEST_COMMAND_NOTICE` to stderr and still
returns `pass` (no behavior change to pass/fail); when `testCommand` **is**
configured, no notice is printed and existing enforcement is unchanged

## Boundaries

- DO NOT touch existing `.cadence/config.json` files — this is an
  `init`-write-time default only, no migration.
- DO NOT change `build-test-must-pass`'s pass/fail semantics — the
  `ran: false` path stays a pass, only gains stderr output.
- DO NOT add a `cadence doctor` check, an interactive package-manager
  prompt, or touch rec-003/rec-009 — all explicitly out of scope for this
  phase.
- DO NOT let `detectTestCommand` throw — same never-throws discipline as
  `detectTestGlobs`/`deriveName`.
