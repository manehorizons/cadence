# 184-01 — AbortSignal/deadline/trace-id plumbing

## Objective

Thread an optional `AbortSignal` + `traceId` through the verifier call path,
starting with the surfaces rec-20260712-010's own evidence names
(`packages/core/src/gates`, `packages/core/src/verify/security-audit.ts`)
plus the shared `host-cli-client.ts` subprocess-spawn plumbing every
host-cli-backed verifier depends on. Purely additive: every new parameter is
optional, every existing call site keeps compiling and behaving exactly as
before when it omits them. Wired through end-to-end for one real gate
(`security-audit`) so the plumbing is provably connected, not orphaned
parameters nobody calls. Cross-links (without duplicating) the existing
headless-verifier guardrail recs rec-20260710-004 (batching/fallback-chain/
model-passthrough) and rec-20260710-006 (quota transparency/self-invocation/
CI fallback) — neither of those covers signal/deadline propagation.

## Acceptance Criteria

### AC-1: host-cli-client accepts an external AbortSignal
Given `hostCliJSON`/`spawnCapture` (`packages/core/src/verify/host-cli-client.ts`)
already has its own internal spawn-timeout timer (Phase 178 T3)
When a caller passes an optional `signal: AbortSignal` that later fires
before the subprocess settles
Then the spawned child is killed and the call rejects with a `HostCliError`
whose `reason` is `'aborted'` — distinct from the existing `'timeout'`
reason — and an optional `traceId` string, when passed, appears in the
existing structured logger's child context; omitting both keeps today's
behavior byte-identical

### AC-2: the `Verifier` interface and its local/mock implementations accept optional signal + traceId
Given `localChatJSON` (`packages/core/src/verify/local-client.ts`) calls
`fetch` directly and `Verifier.verify` (`packages/core/src/verify/verifier.ts`)
is the interface the `--deep` gate calls
When `Verifier.verify` gains an optional second parameter
`{ signal?: AbortSignal; traceId?: string }`
Then `LocalVerifier` forwards `signal` into the `fetch` call's `init.signal`
and `traceId` into its logger context; `MockVerifier` accepts the same
optional parameter but ignores it (pure, no I/O to cancel); every existing
caller that omits the parameter keeps compiling and behaving identically

### AC-3: SecurityAuditVerifier gets the same shape, wired through the real gate
Given `SecurityAuditVerifier` (`packages/core/src/verify/security-audit.ts`)
mirrors `Verifier`'s shape and the `security-audit` gate
(`packages/core/src/gates/security-audit.ts`) is its one real caller
When `SecurityAuditVerifier.verify` gains the same optional
`{ signal?, traceId? }` second parameter (Mock/Anthropic/Local
implementations each handling it per AC-2's pattern) and the
`security-audit` gate generates a per-run `traceId` (e.g. `crypto.randomUUID()`)
and passes it through on every real invocation
Then a test can observe the gate's generated `traceId` reaching the
verifier's `verify()` call — proving the parameter is genuinely connected
end-to-end for at least one gate, not just plumbed-and-unused

## Tasks

### T1: Thread signal + traceId through host-cli-client.ts
- files: `packages/core/src/verify/host-cli-client.ts`, `packages/core/tests/verify/host-cli-client.test.ts`
- action: add optional `signal?: AbortSignal` and `traceId?: string` to
  `HostCliJSONOptions`; in `spawnCapture`, listen for the signal's `abort`
  event (if provided) and, on fire, kill the child and reject with a new
  `HostCliError` reason `'aborted'` (add `'aborted'` to
  `HostCliErrorReason`), guarding against the same double-settle race the
  existing timeout timer already guards against (only one of
  timeout/abort/close/error may win); thread `traceId` into the
  `getLogger().child({...})` call already made in `callOnce`
- verify: `pnpm --filter @manehorizons/cadence-core test -- host-cli-client`
- done: AC-1

### T2: Thread signal + traceId through local-client.ts and the Verifier interface
- files: `packages/core/src/verify/local-client.ts`, `packages/core/src/verify/verifier.ts`, `packages/core/src/verify/mock-verifier.ts`, `packages/core/tests/verify/local-client.test.ts`, `packages/core/tests/verify/local-verifier.test.ts`, `packages/core/tests/verify/mock-verifier.test.ts`
- action: add optional `signal?: AbortSignal` and `traceId?: string` to
  `LocalChatJSONOptions`, forwarded into the `fetch(...)` call's init options
  and the logger context respectively; change `Verifier.verify`'s signature
  to `verify(input: VerifyInput, opts?: { signal?: AbortSignal; traceId?: string })`;
  `LocalVerifier.verify` forwards `opts` into its `localChatJSON` call;
  `MockVerifier.verify` accepts the optional second parameter and ignores it
- verify: `pnpm --filter @manehorizons/cadence-core test -- local-client local-verifier mock-verifier verifier-factory`
- done: AC-2

### T3: Mirror the shape onto SecurityAuditVerifier and wire the real gate
- files: `packages/core/src/verify/security-audit.ts`, `packages/core/src/gates/security-audit.ts`, `packages/core/tests/verify/security-audit.test.ts`, `packages/core/tests/gates/security-audit.test.ts`
- action: change `SecurityAuditVerifier.verify`'s signature to match AC-2's
  shape (`verify(input, opts?: { signal?; traceId? })`); `MockSecurityAuditVerifier`
  ignores `opts`; `AnthropicSecurityAuditVerifier`/`LocalSecurityAuditVerifier`
  forward it into their respective transport calls the same way `LocalVerifier`
  does; in `packages/core/src/gates/security-audit.ts`, generate a per-run
  `traceId` (`crypto.randomUUID()`) and pass `{ traceId }` on the real
  `verify()` call site; add a test that injects a fake verifier capturing
  the `opts` it received and asserts a `traceId` was actually passed
- verify: `pnpm --filter @manehorizons/cadence-core test -- security-audit`
- done: AC-3

## Boundaries

- DO NOT add a configurable gate-level deadline/timeout config field in this
  phase — that is real scope creep beyond "plumbing" (a config schema
  change, a new docs section, a policy decision about default values) and
  belongs in a follow-up recommendation, not this phase. Callers may pass an
  `AbortSignal` they construct themselves (e.g. via `AbortSignal.timeout(ms)`,
  a Node/web-standard API already available); this phase does not construct
  one on the gates' behalf.
- DO NOT touch `PerTaskVerifier`, `CodeReviewVerifier`, `PlanReviewVerifier`,
  or `SpecReviewVerifier` and their Mock/Anthropic/Local/HostCli
  implementations — the same pattern applies to them, but extending all four
  in one phase is out of scope; a future phase can repeat this pattern.
- DO NOT modify `.github/workflows/*`, `docs/security/*`,
  `scripts/check-audit-exceptions.mjs` (phase 182), or
  `docs/reference/{commands,config,exit-codes}.md` /
  `packages/core/tests/docs/*` (phase 183).
- DO NOT change any existing gate's or verifier's *behavior* when
  signal/traceId are omitted — every existing test must keep passing
  unmodified except where a signature literally changed (adding an optional
  parameter does not require updating existing call sites).
