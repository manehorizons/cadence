# 228-01 — Split settleService into named step functions

## Objective

`rec-20260725-007`: `settleService` (`packages/core/src/services/settle.ts:210-760`,
~555 lines) is a single function spanning at least 9 concerns — distinguished
only by inline `// Phase N` comments, not function boundaries — while its
public interface (`SettleArgs` in, `CommandResult` out) is already
right-sized and `cli/commands/settle.ts` is a clean thin adapter that does
not change. This phase extracts each remaining concern into its own
private, named step function within the same file, so `settleService`
becomes a short orchestrator that calls them in sequence. **This is a pure,
mechanical, behavior-preserving extraction — move code, thread the minimum
params/return values each step actually needs, change no logic, no test
file edits, no public signatures.** The full existing test suite (in
particular the `settle*.test.ts` behavioral suites) is the safety net and
must pass byte-for-byte unchanged.

Concern boundaries (verified by reading the full function; line numbers are
pre-refactor references, will shift as extraction proceeds — re-locate by
the anchor comment/variable named, not the raw number):

1. **Precondition + load** (`:216-236`): read state, check
   `loopPosition==='BUILD'` + active draft/phase (else `LoopViolationError`
   + early return), parse the active phase, read+parse the DRAFT.md, read
   the PROGRESS.json (or default `{ draftId, tasks: {} }`).
2. **Phase-collision backstop** (`:252-267`): the Phase 83
   `assertNoPhaseCollision` check + early return on refusal.
3. **Gate-set resolution + mock-verifier banner + soft-cap precondition**
   (`:269-298`): `effectiveGateSet`, the `deepWillRun` mock-provider banner,
   the auto×complex soft-cap refusal/warn.
4. **`SettleContext` construction** (`:300-425`): the large `ctx` object —
   memoized closures for coverage/draft-mtime/diff/verifiers, the `emit`/
   `runner`/`prompter`/`codeReviewSidecar`/`io` seams. This is the single
   highest-value extraction (self-contained, few external dependents besides
   `ctx` itself) — a `buildSettleContext(...)` factory returning
   `SettleContext`.
5. **Gate-loop refusal-path SUMMARY** (`:426-455`): already calls out to
   `runSettleGates(ctx)` (not this phase's concern) but the refused-SUMMARY
   write-and-return block inline here is extractable (uses
   `buildTaskResults`, already a top-level helper).
6. **AC-result derivation** (`:456-519`): the `--auto`/interactive merge
   logic (`interactiveVerify`, `deriveAcResults`, the offenders/`--force`
   refusal, the merged `acResults` build).
7. **Anomaly collection + notify + skill-audit check** (`:521-555`):
   `collectAnomalies`, `gateBypassesFromAnomalies` + stderr lines,
   `anomaly-notify` gate dispatch, `runSkillAuditCheck`.
8. **Evidence derivation + evidence-floor gate** (`:556-615`):
   `deriveAcEvidence` per AC, `checkEvidenceFloor`, the per-AC
   `--evidence-floor-bypass` exemption loop and refusal message.
9. **Summary build + write + retro digest + recommendation ship-promotion**
   (`:617-717`): `stateAtSettle` snapshot, `Summary` object construction,
   `computeSummaryContentHash`, the JSON/MD write, `buildRetroDigest` +
   `writeRetroArtifacts`, the `--ship-ref` / settle-pending recommendation
   advance.
10. **State commit to IDLE + retro offer** (`:719-750`): clearing
    `openDrafts`/`activeDraft`/`activeTask`/`loopPosition`/`tier`,
    `backend.commit(state)`, the post-commit `runRetroOffer` (deliberately
    *after* the commit — do not reorder relative to it, per the existing
    Phase 174 comment explaining why).
