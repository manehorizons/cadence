# 295-01 — host-hooks doctor check must verify completeness, not existence

## Objective

`cadence doctor`'s `host-hooks` check (`checkHostHooks`, `packages/core/src/doctor/run.ts`) currently passes as soon as `hasManagedCadence` finds any single non-stale `_managedBy: "cadence"` marker anywhere in `.claude/settings.json` — it answers "has CADENCE ever installed a hook here?", not "are the hooks CADENCE needs actually installed?". This repo is a live example of the gap: its committed `.claude/settings.json` is missing 2 of the 7 managed hook entries the installer (`packages/host-claude-code/src/install.ts`) writes (the `PostToolUse` `Skill` matcher and the entire `SubagentStart` event), yet `cadence doctor` has reported `host-hooks: ok` throughout. The missing `Skill` matcher is the direct cause of phase 294's finding (`skillAudit.invoked` never populates). This phase makes the check verify the actual expected set, not a single marker, while keeping the thing that installs hooks and the thing that verifies them from drifting apart silently (`packages/host-toolkit`'s expected-hooks list is the single source `install.ts` builds from; `core` holds its own copy since it cannot import host code, pinned against host-toolkit's by a dedicated drift test in `packages/host-claude-code`, which already depends on both).

## Acceptance Criteria

### AC-1: an incomplete install is named specifically
Given a `.claude/settings.json` fixture reproducing this repo's measured shape (a managed `PostToolUse` entry with the edit-tool matcher but no `Skill` matcher, and no `SubagentStart` entry at all)
When `cadence doctor` runs
Then `host-hooks` does not report `ok`, and the failure detail names both missing entries specifically (`PostToolUse` / `Skill` matcher, and `SubagentStart`) — not a generic "not managed" message

### AC-2: every missing entry is enumerated, not just the first
Given the AC-1 fixture (two independent gaps: one missing matcher on an existing event, one missing event entirely)
When the check runs
Then both gaps appear in the failure detail — the check does not stop at the first mismatch

### AC-3: a complete install is unaffected
Given a `.claude/settings.json` fixture with all 7 events' managed entries present and current (the full set `install.ts` writes)
When the check runs
Then it reports `ok` with the exact literal message `'CADENCE-managed hook entries are present in settings.json.'` — pinned as an explicit string assertion, not a fixture diffed by hand, so a future accidental wording change to the complete-case path is caught

### AC-4: non-managed hooks are untouched and unreported, on both the check and the fix path
Given a `.claude/settings.json` with a complete managed set plus a non-managed entry (mirroring this repo's real `deja hook user-prompt-submit` and third-party entries)
When the check runs, and separately when `cadence doctor --fix --wire-host` repairs an incomplete install
Then the non-managed entry is never named in the check's output, and survives the repair unchanged

### AC-5: the checker and the installer cannot silently drift apart
Given `packages/host-toolkit` holds the canonical expected-hooks list that `install.ts` builds its `desired` map from, and `packages/core`'s `doctor/host-hooks.ts` holds its own copy (core cannot import host-toolkit)
When a dedicated test in `packages/host-claude-code` (which already depends on both) compares the two
Then it passes today and is proven to actually fail if the two are made to disagree (verified during development, not committed) — the Slice-4 `COMMAND_GUIDANCE`-vs-`COMMANDS` precedent applied to this pair

### AC-6: severity, fixId, and the doc-sync pairing
Given an incomplete install is a fail-closed hazard for any settle that declares a required skill (D-AV/D-BA), not merely informational
Then `host-hooks`' failure severity is `error` (escalated from today's `warning`), `fixId` stays `host-install` (the existing `--fix --wire-host` path repairs completeness the same way it already repairs stale-scope), and `docs/reference/commands.md`'s doctor-check table row for `host-hooks` is updated in the same commit to describe the new severity and behavior. **Blast-radius finding, recorded rather than left implicit:** a repo with an existing (non-CADENCE) `.claude/settings.json` whose CADENCE wiring was declined already reported `host-hooks: warning` before this phase — `report.ok` was `true` (exit 0). After this phase that population reports `error` — `report.ok` becomes `false` (exit 1). This is a genuine, deliberate behavior change for that population, not a new detection of a previously-invisible problem (the signal already fired, only the severity/exit-code changes); nothing in this repo's CI or git hooks keys on `cadence doctor`'s exit code (verified), and a repo that never had `.claude/settings.json` at all, or used `install --no-hooks` (which skips writing the file entirely), is unaffected — `checkHostHooks`'s `!existsSync` early-return still reports `ok`/not-applicable.

### AC-7: cross-host scope is explicit, not silent
Given `checkCodexHooks` (`.codex/hooks.json`) shares the identical existence-only `hasManagedCadence` predicate and has the same class of gap, and `host-codex`'s expected hook shape genuinely differs (`apply_patch` matcher, different event names)
When `checkCodexHooks`'s existing tests run after this phase's changes
Then its behavior is provably unchanged — a single non-stale managed marker anywhere in `.codex/hooks.json` still reports `ok` (existence-only, not completeness) — pinning the deferral as a deliberate, tested state rather than an unfixed oversight; the deferral is additionally recorded as a filed recommendation, not only a passing test
