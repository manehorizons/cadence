# 181-01 — Define an MCP tool-trust envelope for 'cadence mcp serve' (origin + def-hash + capability scope + expiry)

## Objective

Confirmed: mcp/tools.ts explicitly bypasses the interactive draft/spec-approve prompt over MCP ('the tool call IS the approval', e.g. cadence_draft_approve, cadence_spec_approve) with no expiry/capability-scope/origin-binding/revoke logic anywhere in packages/core/src/mcp/*.ts. Document exactly what that grants and constrain it: bind approval to caller identity/transport origin and tool-definition hash, attach a capability class, and add expiry with revoke-on-version-change so a schema-stable but changed server can't retain silent trust.

## Acceptance Criteria

### AC-1: Approval-bypass MCP tools refuse without a valid trust envelope
Given an MCP client calls `cadence_draft_approve` or `cadence_spec_approve` —
the two tools where, per `tools.ts`, "the tool call IS the approval" and the
interactive TTY prompt the CLI would otherwise show is skipped — and the call
either presents no trust envelope, or presents one that fails any of: caller
identity/transport-origin binding, a hash of the tool's current definition
(name + description + inputSchema as registered in `TOOLS`) matching what the
envelope was granted against, a capability class that permits approval-bypass
calls (not just read-only ones), or a still-unexpired grant
When the tool's `run()` handler executes (before `draftApproveService` /
`specApproveService` touches `state.json` or the gate ladder)
Then the call is refused with a reason naming which envelope check failed —
using the project's existing refuse-loudly-and-suggest convention, never a
silent no-op — the loop stage is left unchanged, and no DRAFT/SPEC file or
`state.json` write occurs; separately, when the server's advertised tool
definition for a gated tool changes (e.g. its `inputSchema` or description
changes between CADENCE versions), any envelope granted against the old
def-hash is treated as invalid until a fresh grant is issued (revoke-on-
version-change), so a schema-stable-looking but behavior-changed server
cannot silently retain a prior caller's trust.

## Constraints

- Scope is the approval-bypass class of tools first (`cadence_draft_approve`,
  `cadence_spec_approve` today) — read-only tools (`cadence_progress`,
  `cadence_status`, `cadence_recommend`, `cadence_doctor`,
  `cadence_milestone_propose`) and ledger-write-but-not-loop-transitioning
  tools must not gain new friction from this work; the envelope is not a
  blanket auth layer bolted onto every registered tool.
- Zero-runtime-dependency bias applies (`CLAUDE.md`): envelope
  hashing/expiry/identity checks must be implementable with Node's built-in
  `crypto` plus what the MCP SDK's `StdioServerTransport`/`InMemoryTransport`
  already exposes — no new runtime dependency without the operator's
  explicit sign-off.
- Must not change `TOOL_NAMES` / the registered tool count, rename any
  existing tool, or alter the shape of a passing call's `CallToolResult` —
  only the refusal path for a failing envelope check is new surface.
- Not in scope: reintroducing an interactive TTY-style approval prompt over
  MCP itself (there is no TTY on a stdio transport) — the envelope
  constrains *who/what* may exercise the existing no-TTY-bypass pattern, it
  does not reverse the phase-58 decision that MCP calls can approve at all.

## Open Questions

- What does "transport origin" even mean for a stdio-transport MCP server
  with no network/HTTP layer (`server.ts`: `StdioServerTransport` in
  production)? Candidates: process ancestry of the spawning host, a
  caller-supplied identity token exchanged at MCP `initialize` time, or
  something else — needs research before DRAFT, not assumed here.
- Which of the 18 tools in `TOOLS` (`tools.ts`) fall into which capability
  class? At minimum "read-only", "ledger-write", and "loop-transitioning /
  approval-bypass" are implied by existing tool descriptions, but the full
  mapping isn't decided.
- Where does a granted envelope live — a new field in `state.json`, a
  separate file under `.cadence/`, or purely in-memory for the life of one
  stdio connection (so it can never survive a process restart)? Each has
  different implications for "expiry".
- Is expiry purely version-scoped (revoke-on-version-change, per the
  Objective) or does it also need a time-based TTL independent of version
  bumps? The milestone's source recommendation only evidences the
  version-change trigger.
