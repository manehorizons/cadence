# 181-01 — Define an MCP tool-trust envelope for 'cadence mcp serve' (origin + def-hash + capability scope + expiry)

## Objective

Confirmed: mcp/tools.ts explicitly bypasses the interactive draft/spec-approve prompt over MCP ('the tool call IS the approval', e.g. cadence_draft_approve, cadence_spec_approve) with no expiry/capability-scope/origin-binding/revoke logic anywhere in packages/core/src/mcp/*.ts. Document exactly what that grants and constrain it: bind approval to caller identity/transport origin and tool-definition hash, attach a capability class, and add expiry with revoke-on-version-change so a schema-stable but changed server can't retain silent trust.

## Acceptance Criteria

### AC-1: Approval-bypass MCP tools refuse without a valid trust envelope
Given an MCP client calls `cadence_draft_approve` or `cadence_spec_approve` —
the two tools where, per `tools.ts`, "the tool call IS the approval" and the
interactive TTY prompt the CLI would otherwise show is skipped — and the call
either presents no trust envelope, or presents one that fails any of: caller
identity/transport-origin binding, a hash of the tool's current definition
(name + description + inputSchema as registered in `TOOLS`) matching what the
envelope was granted against, a capability class that permits approval-bypass
calls (not just read-only ones), or a still-unexpired grant
When the tool's `run()` handler executes (before `draftApproveService` /
`specApproveService` touches `state.json` or the gate ladder)
Then the call is refused with a reason naming which envelope check failed —
using the project's existing refuse-loudly-and-suggest convention, never a
silent no-op — the loop stage is left unchanged, and no DRAFT/SPEC file or
`state.json` write occurs; separately, when the server's advertised tool
definition for a gated tool changes (e.g. its `inputSchema` or description
changes between CADENCE versions), any envelope granted against the old
def-hash is treated as invalid until a fresh grant is issued (revoke-on-
version-change), so a schema-stable-looking but behavior-changed server
cannot silently retain a prior caller's trust.

## Boundaries

- Do NOT gate `cadence_settle` in this phase — it's classified `SETTLE` (T1)
  but left ungated; extending the envelope to it is deferred to a follow-up
  recommendation, not silently folded in here.
- Do NOT add a new runtime dependency for hashing or crypto — `node:crypto`
  only (zero-runtime-dependency bias, `CLAUDE.md`).
- Do NOT persist grants in `state.json` — they live in a separate
  `.cadence/mcp-trust.json` file; `state.json`'s shape is not touched by
  this phase.
- Do NOT change `TOOL_NAMES`, rename any existing tool, or alter the
  `CallToolResult` shape of a passing (granted) call — only the refusal
  path for `APPROVAL_BYPASS` tools is new surface.
- Do NOT implement any network-origin/IP/process-ancestry binding — stdio
  has no such signal (confirmed: `StdioServerTransport` wraps only
  stdin/stdout; `AuthInfo`/`requestInfo` are HTTP-transport-only). The
  identity model is CLI-issued grants only, not client self-attestation.
- Do NOT reintroduce an interactive TTY-style approval prompt over the MCP
  transport itself — grants are issued out-of-band via the CLI, not via a
  prompt inside the MCP call.
