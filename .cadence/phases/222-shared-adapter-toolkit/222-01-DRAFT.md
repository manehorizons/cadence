# 222-01 — Extract the shared adapter toolkit for host-claude-code and host-codex

## Objective

Extract the logic that host-claude-code and host-codex currently duplicate —
routeHookEvent's dispatch algorithm, the slash-command catalog, install.ts's
managed-marker merge, and locate-self.ts — into a new published package,
`@manehorizons/cadence-host-toolkit`, both adapters depend on as
`workspace:*` (the same pattern they already use for `cadence-core` /
`cadence-types`). Also make core actually enforce `HostCapabilities` so a
capability gap like Codex's silent `agentId`/`agentType` drop is caught by a
test instead of discovered live.

## Acceptance Criteria

### AC-1: routeHookEvent's dispatch algorithm and the slash-command catalog live in one shared module
Given host-claude-code and host-codex each currently hand-roll their own copy
of routeHookEvent's 8-step dispatch algorithm and their own slash-command
catalog, and the two catalogs have already drifted (Codex silently lost its
dispatch dialogue)
When the shared toolkit module is extracted and both adapters' shim.ts /
event-map.ts import it instead of reimplementing it
Then both adapters exercise the identical routing algorithm and an identical
slash-command catalog through one shared implementation, and each adapter's
existing test suite continues to pass (parity fixtures updated only where the
extraction changes call shape, never behavior)

### AC-2: install.ts's managed-marker merge and locate-self.ts are shared, not cloned
Given install.ts's managed-marker merge logic and locate-self.ts are
byte-identical (or near-identical) between the two adapter packages today
When both are moved into the shared toolkit and each adapter's install.ts /
locate-self.ts becomes a thin wrapper around the shared implementation
Then a single shared test suite covers the merge / locate-self behavior once,
and both adapters' own tests continue to pass against the shared
implementation

### AC-3: core enforces HostCapabilities instead of only validating it in adapter tests
Given HostCapabilities is declared and validated by both adapters' own tests
but nothing in core ever reads it, so Codex silently drops agentId/agentType
with no capability flag and no notice
When core's dispatch path checks the relevant HostCapabilities flag before
relying on agentId/agentType, and Codex's declared capabilities are corrected
to accurately reflect what it supports
Then a test exercises a host lacking the capability and asserts core degrades
or notices loudly rather than silently proceeding as if the fields were
present, and Codex no longer silently drops agentId/agentType when they are
actually present

## Boundaries

- Do NOT change adapters' "translate lifecycle events only, never duplicate
  engine logic" contract (D11) — this is a pure logic extraction into a
  shared location both adapters call, not new engine logic in an adapter.
- Do NOT touch the MCP/CLI parity work shipped in phase 221
  (rec-20260725-003 / PR #304) — different subsystem.
- Do NOT change either adapter's public `HostAdapter` contract or the
  prompt-parity golden fixtures' asserted behavior — only their internal
  implementation.
- Do NOT add `@manehorizons/cadence-host-toolkit` as a runtime dependency of
  `cadence-core` — the dependency direction is adapters → toolkit, never
  core → host-adapter-specific code.
