# 149-01 — milestone close verb

## Objective

Close issue #135: a `cadence milestone close <id>` verb so an `exported`
milestone whose work has actually landed can leave the ledger as `closed`
instead of staying listed under "Exported" forever. The schema is already
ready for this — `MilestoneStatusZ` in `packages/types/src/intelligence.ts`
already enumerates `'closed'`, and `renderMilestonesMd` in
`packages/core/src/intelligence/render-milestone.ts` already has a working
"## Closed" section — but nothing ever sets the status. This phase adds the
one missing transition + CLI verb, following the exact shape of the existing
`accept`/`defer` verbs in `packages/core/src/intelligence/milestone.ts`
(`TransitionAction`, `applyTransition`, `runMilestoneTransition`) and
`packages/core/src/cli/commands/milestone.ts`.

Design decisions locked for this phase (don't relitigate — implement as specified):
- `close` is only legal from `exported` (not `proposed`/`accepted`/`deferred`/
  already-`closed`) — mirrors `accept`'s `['proposed']` / `defer`'s
  `['proposed', 'accepted']` allow-list pattern.
- `close` takes an optional `--ref <text>` (freeform provenance, symmetry with
  `recommendation promote --status=shipped --ref`), stored as a new optional
  `closedRef` field on `IntelligenceMilestoneZ`.
- Closing does NOT hard-block on the milestone's linked recommendations not
  all being `shipped` yet — it's a warn-but-allow advisory (consistent with
  this repo's general stance that intelligence-layer ledger tooling is
  advisory, not a loop gate). Print a warning naming any `recommendationIds`
  whose current status in the recommendation ledger is not `shipped`, but
  still perform the close.

## Acceptance Criteria

### AC-1: close transitions exported -> closed
Given a milestone in `exported` status
When the operator runs `cadence milestone close <id>`
Then the milestone's status becomes `closed` in
`.cadence/intelligence/milestones.json`, `updatedAt` is refreshed, and stdout
confirms the transition

### AC-2: close refuses from any other status
Given a milestone in `proposed`, `accepted`, `deferred`, or already `closed`
status
When the operator runs `cadence milestone close <id>`
Then the command refuses (non-zero exit, no ledger write) naming the
milestone's current status, mirroring the existing `accept`/`defer` refusal
message shape (`cannot close milestone in status <status>`)

### AC-3: --ref is stored and rendered
Given a milestone in `exported` status
When the operator runs `cadence milestone close <id> --ref "PR #NNN"`
Then `closedRef: "PR #NNN"` is persisted on the milestone and appears in the
"## Closed" section of `MILESTONES.md` (extend the existing renderer's closed
one-liner: `${m.id} — ${m.name}` becomes `${m.id} — ${m.name} (ref: ${m.closedRef})`
when present, unchanged when absent) and in `milestone list --json`

### AC-4: advisory warning on unshipped members
Given a milestone in `exported` status whose `recommendationIds` include at
least one recommendation whose current status (read from
`.cadence/intelligence/recommendations.json`) is NOT `shipped`
When the operator runs `cadence milestone close <id>`
Then the close still succeeds (AC-1's transition still happens) but stdout
also prints an advisory line naming the not-yet-shipped recommendation id(s)
— this must never throw or block even if the recommendation ledger is
missing/unreadable (best-effort, same defensive style as
`runAdvanceConvertedToSettlePendingForPhase`)

### AC-5: implementation is covered by tests
Given the feature implementation is complete
When `packages/core/tests/intelligence/milestone-close.test.ts` (new) and the
CLI test for the `milestone close` command run
Then AC-1, AC-2, AC-3, and AC-4 are each covered by a passing test that
asserts on real ledger file state, not just exit codes

## Boundaries

- DO NOT make `close` hard-block on unshipped recommendations — warn only.
- DO NOT touch `cadence milestone propose`/`export`/`premortem` logic.
- DO NOT add a `cadence milestone reopen`/`unclose` verb — out of scope,
  not requested by issue #135.
- DO NOT update `docs/reference/commands.md` in this phase unless time
  allows after T1-T4 are green — the DRAFT's scope is the verb itself; if
  docs are skipped, leave a note in the SUMMARY rather than silently
  omitting them.
