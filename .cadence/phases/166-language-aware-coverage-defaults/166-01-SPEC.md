# 166-01 — assertion coverageMode is JS/TS-only; silently breaks by default for non-JS test suites

## Objective

`findTestSpans` only recognizes JS/TS `it()`/`test()` syntax, but a fresh `cadence init` (Phase 139) defaults `verification.coverageMode` to `'assertion'` for every preset regardless of project language, so a pytest/Go/Rust/PHP project gets a permanently unsatisfiable `test-coverage` gate; this phase makes the gate diagnosable and safe-by-default for every language without adding any new language parsing (that's the follow-on `rec-20260711-002`).

## Acceptance Criteria

### AC-1: init defaults coverageMode based on detected project language
Given a fresh `cadence init` run in a project directory
When init detects the project's language from marker files (`package.json`→js/ts; `pyproject.toml`/`setup.py`/`requirements.txt`→python; `go.mod`→go; `Cargo.toml`→rust; `composer.json`→php; none found→unknown)
Then it writes `verification.coverageMode: 'assertion'` only when the detected language is js/ts (the only language with an existing assertion-mode span-finder); every other detected or unknown language writes `verification.coverageMode: 'mention'` and prints a stderr notice naming the detected language and explaining assertion mode isn't supported yet for it.

### AC-2: init writes language-aware default test-file globs
Given the same language detection as AC-1
When init writes the default test-file glob patterns for a fresh config
Then non-js/ts languages get sensible default globs for that language (python: `**/test_*.py`, `**/*_test.py`; go: `**/*_test.go`; rust: `tests/**/*.rs`, `**/*_test.rs`; php: `**/*Test.php`, `tests/**/*.php`) instead of today's TS-only `packages/**/*.test.ts`/`.tsx` defaults, so `mention`-mode coverage checking can actually find test files in a non-JS project.

### AC-3: test-coverage gate error distinguishes glob-miss from span-miss
Given the `test-coverage` gate fails to find assertion-mode evidence for an AC
When it renders its refusal message
Then it names which of two distinct causes applies — "no test files matched configured globs" vs. "test files matched but no assertion-shaped span found for AC-N" — each with its own suggested fix (adjust globs; or switch `coverageMode` to `mention` via `cadence config edit coverageMode` / `--allow-missing-coverage`) instead of today's single generic message.

### AC-4: doctor flags assertion mode paired with an unsupported language
Given `cadence doctor` runs against a project with `verification.coverageMode: 'assertion'`
When the detected project language (per AC-1's detection) is not js/ts
Then doctor reports a check naming the mismatch and suggesting `cadence config edit coverageMode`, mirroring doctor's existing loud-notice pattern for other misconfigurations.

## Constraints

- Additive, init-time only: never rewrites an existing `.cadence/config.json` — matches the Phase 139 precedent (only fresh `init` output changes).
- Language detection is best-effort and must never throw; any fs-read failure falls back to `unknown` → `mention` (Best-effort introspection never throws).
- No new runtime dependency — marker-file sniffing is plain fs reads, not a language-detection library (Zero-runtime-dependency bias).
- Does not add assertion-mode parsing support for any new language — that split is deliberate and recorded in `dec-20260711-001`; this phase only prevents the gate from being permanently unsatisfiable, it does not make `assertion` mode actually work for Python/Go/Rust/PHP (that's `rec-20260711-002`).
- Doc-sync: `docs/reference/config.md`'s `coverageMode` and default-globs documentation must be updated to describe the language-aware defaults, per the existing doc-content-test convention.

## Open Questions

- Mixed-language/monorepo detection: if multiple marker files are present (e.g. a JS frontend + Python backend in one repo), what should init do — pick by which marker sits at repo root, ask interactively, or default conservatively to `mention` whenever more than one language is detected?
- Should language detection be a reusable `detectProjectLanguage()` shared by both `init` (AC-1/AC-2) and `doctor` (AC-4), and if so where does it live — inside `packages/core/src/init/` or a new small module?
- Rust's idiomatic unit tests live inline in `src/*.rs` under `#[cfg(test)]`, not under a top-level `tests/` dir — should the default Rust glob include `src/**/*.rs`? That risks matching non-test source files under `mention` mode. May need a narrower default (`tests/**/*.rs` only) with the inline-test gap documented as a known limitation until `rec-20260711-002` lands real Rust parsing.
