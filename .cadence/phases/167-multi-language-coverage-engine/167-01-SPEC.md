# 167-01 — Shared-lexer multi-language assertion-coverage engine

## Objective

Generalize `findTestSpans` (`packages/core/src/verify/test-spans.ts`) from a hardcoded JS/TS-only scanner into one shared, string/comment-aware engine parameterized by a per-language profile (opener/assertion patterns, comment/string tables, block-boundary strategy: call-expression / brace-delimited / indentation-delimited / do-end-keyword), shipping built-in profiles for python, go, rust, and php alongside a re-expressed js/ts profile with per-file dispatch by extension, plus a `verification.coverageProfiles` config escape hatch so an unsupported language is never a dead end — making `assertion` coverageMode actually work beyond JS/TS, as sequenced in `dec-20260711-001` (part B, following phase 166's diagnose-fix).

## Acceptance Criteria

### AC-1: shared profile-parameterized engine re-expresses js/ts with unchanged behavior
Given the existing JS/TS assertion-span behavior covered by the current `findTestSpans` test suite
When the scanner is rebuilt as a shared string/comment-aware engine that takes a language profile (opener pattern, assertion pattern, comment/string syntax tables, block-boundary strategy) and js/ts becomes just one profile using the call-expression strategy
Then every pre-existing js/ts span-finding test passes unchanged against the new engine — identical spans for identical input — and the js/ts profile is registered in a single profile registry that dispatch (AC-6) and docs (AC-9) both read from.

### AC-2: built-in python profile (indentation-delimited)
Given pytest-style fixture files containing `def test_*` functions (module-level and class-based) with `assert` statements
When the engine scans them with the built-in python profile
Then an AC token inside an asserting test-function body yields a span bounded by indentation (the whole test function), tokens in comments/docstrings/strings yield no span, and a non-asserting test function yields no assertion-mode span.

### AC-3: built-in go profile (brace-delimited)
Given Go test fixtures with `func TestX(t *testing.T)` including table-driven tests and `t.Run` subtests, asserting via `t.Error*`/`t.Fatal*`/testify-style calls
When the engine scans them with the built-in go profile
Then an AC token inside an asserting test-function body (including inside a subtest closure or table entry) yields a brace-bounded span, and tokens in comments or string literals yield no span.

### AC-4: built-in rust profile (brace-delimited, attribute-aware)
Given Rust test fixtures with `#[test]` / `#[should_panic]` functions (including inside `#[cfg(test)] mod tests` blocks) asserting via `assert!`/`assert_eq!`/`assert_ne!`
When the engine scans them with the built-in rust profile
Then an AC token inside an asserting `#[test]` function yields a brace-bounded span whose opener detection is attribute-aware (the `#[test]` attribute marks the block, not just the `fn` keyword), and tokens in comments or string literals yield no span.

### AC-5: built-in php profile (Pest call-expression + PHPUnit method shape)
Given PHP test fixtures in both Pest style (`it(...)`/`test(...)` closures with `expect(...)`) and PHPUnit style (`public function testX` methods calling `$this->assert*`)
When the engine scans them with the built-in php profile
Then AC tokens inside either shape's asserting block yield correct spans for that shape, and tokens in comments or string literals yield no span.

### AC-6: per-file dispatch by extension, unknown shapes yield zero spans
Given a mixed-language repo whose configured test globs match `.test.ts`, `_test.go`, `test_*.py`, and an extension no profile claims
When assertion-mode coverage evidence is gathered across those files
Then each file is scanned with the profile registered for its extension, the unclaimed-extension file contributes zero spans (never a partial or wrong match — false-negative-over-false-positive is the invariant), and the same zero-spans rule applies inside any file where the profile does not positively recognize the block shape.

### AC-7: `verification.coverageProfiles` operator-extensible custom profiles
Given a `.cadence/config.json` defining a custom entry under `verification.coverageProfiles` (extensions, opener/assertion patterns, block-boundary strategy) for a language with no built-in profile
When config is loaded and assertion-mode coverage runs over matching files
Then the custom profile is validated at config-load time — a bad regex or missing required field refuses loudly with the offending field named and a suggested fix, never silently ignored — and a valid custom profile makes the otherwise-unsupported language's files yield real assertion spans via the shared engine.

### AC-8: coverage explain diagnostic
Given a project with assertion-mode coverage configured and a draft with ACs
When the operator runs the coverage explain dry-run (`cadence verify coverage --explain AC-N` shape per `dec-20260711-001`)
Then it prints, without mutating any state, which test files matched the globs, which profile scanned each file, every span found for the AC token, and for each span why it did or didn't satisfy assertion mode (e.g. token present but block not asserting), so a failing gate is diagnosable without reading engine source.

### AC-9: supported-language matrix doc kept honest by a doc-content test
Given `docs/reference/config.md` documents assertion-mode coverage support
When the built-in profile set changes
Then the docs carry a supported-language matrix (language, extensions, block strategy, recognized test/assertion shapes) and a doc-content test under `packages/core/tests/docs/` asserts the matrix matches the live profile registry, failing on any drift in either direction.

## Constraints

- Zero new runtime dependencies — the engine is a homegrown lexer/scanner; tree-sitter was explicitly rejected in `dec-20260711-001` as violating the zero-runtime-dependency bias. Not open for relitigation here.
- False-positive-averse throughout: an unrecognized shape always yields zero spans, never a partial match. False negatives have existing relaxation valves (`mention` mode, `--allow-missing-coverage`); false positives defeat the gate's purpose.
- Backward compatible: existing js/ts scanning behavior is unchanged (AC-1 parity), and `verification.coverageProfiles` is additive (`.optional()`/`.default()`) so pre-existing configs keep parsing.
- Tests are offline and deterministic: real-framework fixture files (pytest, Go table-driven + subtests, Rust `#[test]`/`#[should_panic]`, Pest, PHPUnit) checked into the test tree — no language toolchains invoked, no live providers.
- Custom-profile validation follows refuse + suggest: name the conflict, suggest the fix, never silently fall back.
- Doc-sync pairs: profile registry ↔ `docs/reference/config.md` matrix (AC-9 test); any new CLI surface (`--explain`) ↔ `docs/reference/commands.md`; config schema ↔ `docs/reference/config.md`.
