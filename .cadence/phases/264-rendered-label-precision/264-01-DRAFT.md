# 264-01 — Rendered label precision for verifier provenance

## Objective

Make the rendered provider label for mock precise and honest, at the display layer only, wherever it is shown to a human -- cadence summary render, the on-disk SUMMARY.md sidecar, cadence doctor, cadence config explain, and the phase-243 fallback banners -- including surfacing whether a mock result was a deliberately configured choice or an unannounced fallback (Phase L's providerSelection), through one single-sourced formatting function so the wording cannot drift across renderers, without touching the mock provider identity, the AssuranceRecordZ/GateProvenanceZ JSON schema, or contentHash verification.

## Acceptance Criteria



### AC-1: SUMMARY renderers share one precise mock label
Given a settled SUMMARY whose assurance.verifierRollup contains an entry with matching gates[] providerSelection data
When cadence summary render or the on-disk <id>-SUMMARY.md sidecar renders it
Then both render an identical, precisely-worded verifier line sourced from one shared function: naming what mock does and does not check when the entry's provider is mock; tagging configured/fallback/empty-diff when every matching gate agrees on one value (empty-diff applies to any provider, not only mock, since a real provider that judged an empty diff is the "looked like verification, judged nothing" case this release targets); rendering an explicit mixed tag rather than silently omitting one when matching gates disagree; and rendering no tag when no matching gate carries providerSelection at all

### AC-2: Historical summaries stay hash-stable with absent selection info
Given a historical SUMMARY.json predating Phase L, with no providerSelection anywhere in gates[] or assurance
When it is re-rendered through the updated summary renderers and re-verified
Then the rendered label carries no selection-mode tag (absent-means-absent), and cadence summary verify still reports MATCH for every existing file in .cadence/phases/ -- no schema field, default, or historical hash changes

### AC-3: doctor and config explain convey the same precision
Given a repo where a verifier seam is set to mock or has silently downgraded to it
When cadence doctor's verification-readiness check or cadence config explain renders that seam's status
Then both surfaces convey what mock does and does not check, sourced from the same shared capability wording added in this phase, alongside the existing MOCK_VERIFIER_NOTICE activation nudge which is left unedited

### AC-4: phase-243 banners stay loud and consistent
Given a verifier seam that silently downgrades to mock at selection or call time
When MOCK_FALLBACK_BANNER or buildDowngradeBanner fires on stderr
Then the banner keeps its existing loud framing and also references the same shared capability wording used by the other four surfaces, so no surface states the mock-capability fact differently from another

### AC-5: label never implies mock is adequate, and gate-outcome derivation is provably unmoved
Given the new rendered mock label text and the existing deriveAssuranceRecord logic
When the label is checked against a banned adequacy-implying word set (e.g. verified, passed, adequate, sufficient) and deriveAssuranceRecord is run over a fixed corpus of gate arrays from before this phase
Then the label never contains a banned word, and overall/hasRealVerifier/evidenceTally are byte-identical to their pre-phase output for that corpus

## Boundaries

- DO NOT modify `AssuranceRecordZ`, `GateProvenanceZ`, or `SummaryZ` — the JSON schema stays byte-identical; this phase is display-layer only per `docs/handoffs/HANDOFF-v1.56-verifier-honesty.md` §5 Phase M.
- DO NOT modify `deriveAssuranceRecord`'s grouping/derivation logic (`hasRealVerifier`, `overall`, `evidenceTally`, the `(provider, model)` rollup key) — join `providerSelection` in at render time only.
- DO NOT rename the `mock` provider identity or its JSON key (D-A, `docs/handoffs/HANDOFF-v1.56-verifier-honesty.md` §3).
- DO NOT add a corpus-wide "re-render every historical SUMMARY.json" sweep test — `summary-verify-sweep.test.ts` is already close to its CI timeout budget on 3 OSes (`rec-20260806-010`); use fixture-scale tests only.
- DO NOT edit `MOCK_VERIFIER_NOTICE`'s existing wording in place — add a new sibling constant for the neutral capability-fact framing. 4+ existing tests assert doctor/config-explain/banner output `.toContain(MOCK_VERIFIER_NOTICE.message)`, and its tone (an activation nudge) is deliberately distinct from the neutral SUMMARY-review fact this phase adds.
- DO NOT add per-verifier-family label variants (AC-verifier vs. code-review-family wording) — one umbrella capability statement covers both, per the scoping decision recorded before implementation.
