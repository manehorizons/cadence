# 51-01 — Documentation portal (Astro + Starlight)

## Objective

Build a standalone Astro + Starlight documentation portal at `website/` that projects the repo's canonical markdown plus generated typedoc API docs into one navigable, GitHub-Pages-deployed site — without touching the engine's pre-push gate.

## Acceptance Criteria

### AC-1: Standalone site builds
Given the new `website/` project (own package.json + lockfile, not a `packages/*` workspace member)
When `cd website && pnpm install && pnpm build` runs
Then `astro build` completes and produces `website/dist/` with the home page, and the root workspace/turbo/packages files are unmodified.

### AC-2: Canonical markdown is projected with no dead links
Given the allowlisted repo docs (README, DESIGN, docs/**, CONTRIBUTING, SECURITY, CODE_OF_CONDUCT, agents docs)
When the build-time `sync-docs` script runs as a prebuild
Then each doc renders under its mapped route with a `title` derived from its H1, every relative `.md` link is rewritten to a base-aware site route, and a link to an unpublished/missing `.md` fails the build loudly (root docs remain the single source of truth).

### AC-3: API reference is generated
Given the published packages that expose a public programmatic API
When the site builds with `starlight-typedoc`
Then an "API" sidebar section is generated covering `cadence-types` and `cadence-host-claude-code` (testkit excluded). DEVIATION (discovered in build): `@manehorizons/cadence-core` is CLI-only — its `src/index.ts` is an empty barrel (`export {}`), so it has no programmatic surface to document; it was dropped from the typedoc entry points to avoid an empty section + dead link. Core's surface (its CLI) is covered by Reference → Commands.

### AC-4: Pages deploy workflow exists and is isolated
Given a new `.github/workflows/docs.yml`
When it runs on push to `main` / dispatch
Then it tests the sync script, builds the site, and deploys to GitHub Pages, on paths independent of `ci.yml` (the engine gate never builds the site).

### AC-5: Sync transforms are unit-tested
Given the `transform.mjs` pure functions (extractTitle, rewriteLinks, toFrontmatter)
When `website`'s own vitest runs
Then title extraction, base-aware `.md` link rewriting (anchors/external/code-fence/non-md preserved), fail-loud-on-dead-link, and idempotency are covered and green.

- action: Plan Task 3 — add starlight-typedoc over the API-bearing packages (types + host-claude-code; core dropped as CLI-only); API sidebar group; dedicated rootDir-correct typedoc tsconfig; ignore generated output.

### T4: Deploy to GitHub Pages
- files: `.github/workflows/docs.yml`, `website/pnpm-lock.yaml`
- action: Plan Task 4 — test→build→deploy workflow with Pages permissions; commit website lockfile.
- verify: workflow YAML parses; paths/permissions present; independent of `ci.yml`. (Live deploy requires the one-time Settings→Pages→GitHub Actions toggle, flagged to operator.)
- done: AC-4

## Boundaries

- DO NOT modify `pnpm-workspace.yaml`, `turbo.json`, root `vitest.shared.ts`, or any `packages/**` source — `website/` is standalone and the engine pre-push gate stays untouched.
- DO NOT hand-edit anything under `website/src/content/docs/` except `index.mdx`; that tree is generated by `sync-docs`.
- DO NOT fork/duplicate canonical doc prose — the site is a build-time projection of the repo markdown (CLAUDE.md rule).
- DO NOT special-case a dead `.md` link in the sync script; either publish the target via `ROUTES` or fix the link in the source doc.
