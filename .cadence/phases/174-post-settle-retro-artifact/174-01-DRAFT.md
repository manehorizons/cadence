# 174-01 — Post-settle retro artifact + GitHub issue offer

## Objective

On every successful `cadence settle`, synthesize a friction digest from the SUMMARY data already assembled (gate bypasses, non-DONE tasks, code-review/security-audit/boundary-scan findings), write it as `<draftId>-RETRO.json`/`.md` alongside SUMMARY, and — only when there's friction and the run is interactive — offer to file a GitHub issue for it via `gh`. Full design: `docs/superpowers/specs/2026-07-12-post-settle-retro-artifact-design.md`. Full implementation plan: `docs/superpowers/plans/2026-07-12-post-settle-retro-artifact.md` (both local-only, gitignored — read them for exact code/signatures; this DRAFT is the loop-facing summary).

## Acceptance Criteria

### AC-1: retro artifact reflects settle friction
Given a successful `cadence settle` run
When it completes
Then `<draftId>-RETRO.json` and `.md` exist alongside `SUMMARY.json`/`.md` under `.cadence/phases/<phase>/`, containing gate bypasses, non-DONE tasks, and any code-review/security-audit/boundary-scan findings from that settle — or a "No friction detected this settle." form when there's none.

### AC-2: GitHub issue offer fires only for real friction on interactive runs
Given a friction-having digest and an interactive run (a real TTY or the `CADENCE_PROMPTER_SCRIPT` seam) with `gh` able to resolve the current repo
When settle finishes
Then the user is prompted, naming the resolved target repo, and on accept `gh issue create --repo <target>` runs followed by a best-effort `gh issue edit --add-label needs-triage`.
Given a clean digest, OR a non-TTY run with no `CADENCE_PROMPTER_SCRIPT` set, OR `gh` cannot resolve a target
When settle finishes
Then no prompt ever appears and no `gh` issue-creation call is made.

### AC-3: retro behavior is config-toggleable without disrupting settle
Given `cadenceConfig.retro.enabled === false`
When settle runs
Then neither the artifact nor the issue offer occurs, and settle otherwise behaves identically.
Given `cadenceConfig.retro.enabled` is true but `offerGithubIssue === false`
When settle runs
Then the artifact still writes but the issue offer never appears, even with friction.

### AC-4: retro failures never fail settle
Given an unexpected failure at any point in the retro artifact write or the GitHub issue offer (fs error, `gh` missing, spawn error, label-add failure)
When settle runs
Then settle still exits 0, the loop still reaches `IDLE`, and a stderr notice records what happened — never a thrown error that aborts the settle command.

## Boundaries

- DO NOT touch `rec-20260712-002` (cross-phase retro rollup) or `rec-20260712-003` (Praxis-scoring feedback loop) — explicitly out of scope, depend on this phase existing first.
- DO NOT build an enforced "retro required" gate — explicitly rejected by the originating `/cadence-scout` session as anti-YAGNI.
- DO NOT fire the retro artifact or offer on the refused-settle path (`settle.ts:395-424`) — successful settle only.
- DO NOT add a `--repo` config override for the issue target — resolving and confirming the real target via `gh repo view` is the whole mechanism.
- DO NOT hardcode `--label` on `gh issue create` itself — it fails issue creation outright on any repo without that label; the label is always a separate best-effort call after creation.
- DO NOT invent a "quiet decline on exhaustion" special case for `ScriptedPrompter` — it deliberately throws on exhaustion (house convention); scripted tests supply one more answer instead.
- DO NOT wire up `Summary.deferred`/`decisions` as live fields as part of this phase — both are dead fields nothing in the codebase populates today; that's separate, unrelated work.
