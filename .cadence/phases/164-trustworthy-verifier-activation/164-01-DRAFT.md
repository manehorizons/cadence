# 164-01 — Trustworthy verifier activation: broader key discovery + activation smoke test + committed provider config

## Objective

Look for a verifier key anywhere it legitimately lives (not just env var), run one real verification call on 'cadence activate' so real verification is proven not assumed, and let the provider choice (not the key) live in committed config so every teammate inherits real verification instead of silently defaulting to mock. Targets the known competitive risk that mock-default undercuts the enforcement wedge.

## Acceptance Criteria

### AC-1: Broader verifier key discovery
Given a verifier API key exists somewhere legitimate (e.g. OS keychain, a
`.env` file, or another conventional credential location) but is not exported
into the current process's environment
When cadence determines whether a real verifier is available (`cadence
activate`, `cadence doctor`)
Then it discovers the key from that legitimate location and treats a real
provider as available, without requiring the operator to manually `export`
it into their shell

### AC-2: Activation smoke test
Given an operator runs `cadence activate` with a discovered or supplied
verifier key
When activation completes
Then cadence has made one real verification call to the configured provider
and reports success/failure based on that live call's outcome, rather than
recording activation as successful merely because a key string was present

### AC-3: Committed provider config
Given a team repo already ran `cadence activate` and committed the resulting
provider configuration
When a second teammate clones the repo and has the same kind of key
available (env var, keychain, etc.) but has never run `cadence activate`
themselves
Then cadence uses the committed provider choice to run real verification for
that teammate too, instead of silently falling back to the mock provider

## As-built amendments

- T5 was added mid-BUILD (not part of the original DRAFT approval). T2's
  independent reviewer found that `assessReadiness`/`credsPresent`/
  `createVerifierFactory` gained an optional `cwd` param, but no real
  production call site (`doctor`, `activate`, `settle`, the draft/build
  gates, `spec approve`) actually passed it — each defaults to
  `process.cwd()`, which coincidentally matches for plain CLI usage but is
  wrong for `cadence mcp serve --repo <path>`. The plan-time assumption that
  T1+T2+T4 alone satisfied AC-1/AC-3 in production proved false; T5 closes
  that gap rather than letting the AC claim ship unproven.

## Boundaries

- Do NOT add OS keychain support (e.g. via `keytar`) in this phase — no
  runtime dependency for it exists today, and CLAUDE.md's zero-dependency
  bias requires explicit operator sign-off before adding one; broader
  discovery in this phase is process.env + a repo-root `.env` file only.
  Keychain support is a candidate for a follow-up recommendation.
- Do NOT extend the activation smoke test to the `local` provider — no
  existing ping pattern covers it; `local` stays `skipped` as it is today.
- Do NOT commit the discovered key value itself anywhere (config.json,
  logs, git) — only the provider *choice* is committed config.
- Do NOT change the `mock` provider's behavior or its loud stderr-notice
  fallback path when no key is discoverable anywhere.
- Do NOT touch `packages/core/src/verify/anthropic-verifier.ts`'s public
  constructor signature — only its internal default-key lookup changes.
