# 191-00 — Wire host-cli builders for the remaining 5 verifier families

## Objective

Wire a real `hostCli()` builder into the 5 verifier families that phase 165 left unwired (`spec-review`, `plan-review`, `code-review`, `security-audit`, deep-verify `Verifier`), so `provider: "host-cli"` in a consumer's config actually spawns the headless host CLI instead of silently falling back to `mock` — closing the gap discovered while investigating why `necro` (a downstream project) was rubber-stamping its spec-review gate despite configuring `host-cli`.

## Acceptance Criteria

### AC-1: spec-review gets a real host-cli builder
Given `.cadence/config.json` sets `specReview.provider: "host-cli"`
When `selectSpecReviewVerifier` resolves the verifier
Then it returns a `HostCliSpecReviewVerifier` instance (not a silent mock fallback) that spawns the configured host CLI via `hostCliJSON`, using the existing `SYSTEM_PROMPT`/`formatUserMessage`/`SpecReviewResponseSchema` already defined in `spec-review.ts`, and returns the same `SpecReviewResult` shape the `anthropic`/`local` providers return.

### AC-2: plan-review gets a real host-cli builder
Given `.cadence/config.json` sets `planReview.provider: "host-cli"`
When `selectPlanReviewVerifier` resolves the verifier
Then it returns a `HostCliPlanReviewVerifier` instance that spawns the host CLI via `hostCliJSON` using `plan-review.ts`'s existing prompt/schema, returning the same `PlanReviewResult` shape as `anthropic`/`local`.

### AC-3: code-review gets a real host-cli builder
Given `.cadence/config.json` sets `codeReview.provider: "host-cli"`
When `selectCodeReviewVerifier` resolves the verifier
Then it returns a `HostCliCodeReviewVerifier` instance that spawns the host CLI via `hostCliJSON` using `code-review.ts`'s existing prompt/schema, returning the same `CodeReviewResult` shape as `anthropic`/`local`.

### AC-4: security-audit gets a real host-cli builder
Given `.cadence/config.json` sets `securityAudit.provider: "host-cli"`
When `selectSecurityAuditVerifier` resolves the verifier
Then it returns a `HostCliSecurityAuditVerifier` instance that spawns the host CLI via `hostCliJSON` using `security-audit.ts`'s existing prompt/schema, threading the `{signal, traceId}` opts through to `hostCliJSON` the same way `LocalSecurityAuditVerifier` does (this family's `verify()` signature already carries those opts, unlike spec-review/plan-review/code-review/per-task), and returning the same `SecurityAuditResult` shape as `anthropic`/`local`.

### AC-5: deep-verify (`Verifier`) gets a real host-cli builder
Given `.cadence/config.json` sets `verifier.provider: "host-cli"`
When `selectVerifier` resolves the verifier
Then it returns a `HostCliVerifier` instance that spawns the host CLI via `hostCliJSON` using `anthropic-verifier.ts`'s existing exported `SYSTEM_PROMPT`/`formatUserMessage`/`VerifierResponseSchema`, threading `{signal, traceId}` opts through the same way `LocalVerifier` does, and returning the same `VerifyResult` shape (including `usage` when the transport reports it — `hostCliJSON` does not currently report token usage, so `usage` is correctly omitted, matching how `LocalVerifier` behaves when its transport doesn't report usage either).

### AC-6: `cadence doctor`'s verification-readiness check reflects reality
Given all 5 families now have a `hostCli` builder wired
When `cadence doctor` runs with `host-cli` configured for these families
Then the "verification-readiness" check's claim (`deep-verify uses host-cli with credentials present`) is actually true for `verifier`, not just checking config+auth presence while silently mock-falling-back underneath — verify this check's current implementation doesn't need a code change now that the underlying gap is closed (if it does, that's a bonus fix, not new scope).

## Boundaries

- Do not modify `createVerifierFactory`/`verifier-factory.ts`'s generic dispatch logic — it already handles `hostCli` correctly; only each family's own files change.
- Do not modify `host-cli-client.ts` (`hostCliJSON`, `HostCliError`, spawn/timeout/self-invocation logic) — it's the shared, already-correct transport.
- Do not add `{signal, traceId}` opts to `SpecReviewVerifier`/`PlanReviewVerifier`/`CodeReviewVerifier`/`PerTaskVerifier` interfaces — those families don't have them today (Phase 184 only touched `Verifier` and `SecurityAuditVerifier`); adding them is a separate, out-of-scope decision.
- Do not touch config schema (`packages/types/src/config.ts`) — `'host-cli'` is already a valid `VerifierProvider`.
- No real host-CLI subprocess spawns in any test — `fakeSpawn` only.
