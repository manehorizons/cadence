# 257-01 — Render findings in Markdown summaries

## Objective

Persisted codeReview and securityAudit findings on SummaryZ are never rendered by the Markdown summary writers (summary-writer.ts, summary-render.ts), so a refused settle or PR gives no visibility into the finding that caused the refusal without reading raw JSON; render both finding kinds in both renderers, redacted to the extent the existing redactSecrets utility supports, without changing byte-compatibility for historical summaries lacking findings.

## Acceptance Criteria

### AC-1: Both finding kinds render, deterministically
Given a SUMMARY.json carrying codeReview (as `{}`, as a file-key mapping to `[]`, or as a file-key mapping to a non-empty array) and/or securityAudit (as `[]` or a non-empty array) findings
When it is rendered to Markdown by either renderer, under a `## Findings` heading placed after `## Tasks` and before the gates heading (`## Gate provenance` in summary-writer.ts, `## Gates` in summary-render.ts), in that same position in both files
Then every persisted finding of both kinds appears (severity, message, line if present, id/target/anchor(kind,ref,tier)/disposition/waiver-expiry when present), codeReview findings grouped by file path (codepoint order) then severity (critical>high>medium>low) then id (original array order when id is absent, since security-audit findings never carry one per current schema), and the `## Findings` heading itself is omitted entirely when codeReview is absent/`{}`/all-empty-arrays and securityAudit is absent/`[]`

### AC-2: Refused settle shows its causing finding
Given a refused settle whose refusal was caused by a code-review or security-audit finding
When its refused-settle Markdown SUMMARY is rendered
Then the causing finding is visibly shown in that Markdown output, not only in the JSON sibling (note: `settle.ts`'s refused-snapshot path already calls the same `renderSummaryMd` as a normal settle, so this should fall out of AC-1's fix for free -- do not build a second render path for it)

### AC-3: Historical summaries stay byte-compatible
Given a historical SUMMARY.json with no codeReview/securityAudit fields (pre-phase-24.3/25.2 schema)
When it is re-rendered to Markdown
Then the output is byte-identical to its prior rendering (verified against a checked-in golden fixture, not a loose `toContain`/`toMatch` assertion) and `cadence summary verify <phase> <num>` still validates its contentHash for every existing summary under `.cadence/phases/` -- no default injects a findings field before hashing, and rendering must not participate in `computeSummaryContentHash`'s input at all (it hashes the parsed JSON, never the Markdown)

### AC-4: Finding text is redacted to the extent redactSecrets already supports
Given a finding message containing a credential-shaped string that `redactSecrets` (`packages/core/src/security/redact.ts`) already matches -- a PEM private key block, a JWT, an AWS access key, a GitHub token, an Authorization header, or a `key=`/`token=`/`password=`/`secret=`-style assignment
When it is rendered
Then the rendered Markdown has it redacted via the existing redactSecrets utility, same as other rendered surfaces (`gates/security-audit.ts`, `intelligence/finding-routing.ts`). Webhook URLs and bare local absolute paths are explicitly NOT covered by the current redactSecrets patterns and are out of scope for this AC -- widening redact.ts's shared patterns is a separate phase if ever needed, since it is consumed by four other call sites this phase does not otherwise touch.

## Boundaries

- Do NOT change `SummaryZ`/`FindingZ` schema fields -- this phase is rendering only, no new persisted data.
- Do NOT touch `computeSummaryContentHash` or any other contentHash logic -- Markdown rendering must derive from the already-hashed JSON, never the reverse.
- Do NOT implement disposition-mutation (accept/waive/fix/supersede) CLI surface -- still out of scope per phase 236/242's own boundary.
- Do NOT touch `assurance-record.ts`, the `overall: 'strong'` computation, or add any Assurance-section caveat text. The handoff's J.1 premise ("strong is structurally unreachable") is now factually superseded by phase 256's real settles reaching `strong` -- the actual defect (a diff-scoped gate can reach `strong` off an empty-diff false pass) is already tracked as `dec-20260806-001`/`rec-20260806-004` and is a separate, more subtle fix than a rendering caveat. Out of scope here entirely.
- Do NOT widen `packages/core/src/security/redact.ts`'s patterns (webhook URLs, local paths, etc.) -- it is shared by `gates/security-audit.ts`, `intelligence/finding-routing.ts`, `intelligence/store/recommendations.ts`, and `services/retro-feedback.ts`; widening it is a separate phase if ever justified.
- Do NOT merge `summary-writer.ts`'s and `summary-render.ts`'s other sections, or their deliberately divergent empty-section/refusal-`reason` rendering conventions, into one shared code path -- only the new Findings section is shared (via `findings-render.ts`).
- Do NOT add a `file` field to `FindingZ` for security-audit findings -- the current schema has no per-finding file for that gate; render what's actually persisted.
