# 203-01 — Milestone lifecycle has no un-defer/re-propose path once deferred

## Objective

`clusterMilestones()` (`packages/core/src/intelligence/milestone.ts`) treats any non-`proposed` milestone as a permanent survivor and permanently excludes its claimed `recommendationId`s from re-clustering. `applyTransition()`'s allowed-transitions table has no path out of `deferred` (accept only works from `proposed`, defer only from `proposed`/`accepted`, close only from `exported`). Once a milestone is deferred, bumping the underlying recommendation's readiness/status has no effect — the rec stays permanently claimed by the dead milestone entry. Add a CLI-driven `deferred -> proposed` transition so an operator has a real path to reopen a stuck milestone instead of hand-editing `milestones.json`.

## Acceptance Criteria

### AC-1: a deferred milestone can be reopened via CLI
Given a milestone is in `deferred` status
When the operator runs `cadence milestone reopen <id>`
Then the milestone transitions to `proposed`, the CLI prints the new status, and the change is reflected in `cadence milestone list`

### AC-2: reopen refuses from any non-deferred status
Given a milestone that is NOT in `deferred` status (`proposed`, `accepted`, `exported`, or `closed`)
When the operator runs `cadence milestone reopen <id>`
Then the command refuses loudly, names the milestone's current status in the error, and makes no state mutation

### AC-3: reopened milestone's recommendation re-enters re-clustering
Given a milestone was reopened (`deferred -> proposed`) via AC-1
When `cadence milestone propose` runs again
Then the milestone's claimed `recommendationId`s are eligible for re-clustering instead of being permanently excluded by `clusterMilestones()`

### AC-4: unknown milestone id refuses cleanly
Given an `<id>` that does not exist in `milestones.json`
When the operator runs `cadence milestone reopen <id>`
Then the command exits non-zero with a clear "no such milestone" stderr message, no state mutation

## Constraints

- Not unwinding the recommendation-restart workaround (archiving a stuck rec and recreating a fresh one) — that stays a valid escape hatch even after this fix.
- Not touching `accepted`/`exported`/`closed` milestone transitions — scope is limited to the `deferred` state's dead end.
- No direct `milestones.json` mutation as an implementation shortcut — go through the same `applyTransition()` path the other transitions use.

## Open Questions

- [operator] Requires understanding `applyTransition()`'s allowed-transitions table and `clusterMilestones()`'s claimed-`recommendationId`s exclusion logic in `packages/core/src/intelligence/milestone.ts`.
- [operator] Reopening a deferred milestone whose claimed `recommendationId` has since been re-claimed by a newer restart milestone (e.g. `rec-20260619-008` → `rec-20260720-002`) could let two milestone entries claim the same recommendation, breaking the dedup invariant `clusterMilestones()` relies on — AC-1/AC-3 must define what happens in this case (likely: refuse reopen if the recommendationId is already claimed by a different live milestone).
- [operator] A naive "always re-pool on readiness bump" rule could thrash accepted/exported milestones back into proposed if a recommendation's readiness is edited after work has already started — this spec deliberately scopes the fix to an explicit operator-invoked `reopen` command, not an automatic re-pooling rule, to avoid that failure mode.
