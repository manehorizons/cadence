# 251-01 — Conduction reachability check + finding-durability arc close-out

## Objective

Close out the finding-durability arc's ledger bookkeeping (phases 247–249,
shipped in v1.54.0), then add a `cadence doctor` check —
`conduction-reachability` — that reports, per gate (`code-review`,
`security-audit`) and per axis, whether this repo's current configuration
can produce a real-provider finding at all, since three independent,
verified blockers — two deliberately retained, one an ordinary config
default — currently make that structurally unreachable in the normal
(headless-agent) operating mode this repo runs in almost all the time.

## Context

**The arc is complete but has never carried water.** Phase 247 threaded
`codeReview`/`securityAudit` findings into refused SUMMARYs and added an
immutable per-attempt snapshot sibling; phase 248 gave bypassed
review-verifier throws an honest `status:'skipped'` record instead of a
bare `status:'ran'`; phase 249 routed the three post-gate refusal families
through the same writer. All of it persists complete records — of findings
that, in this repo's actual operating mode, are never produced, because
`code-review`/`security-audit` never run for real.

**Blocker 1 (profile), verified at this commit.** `packages/core/src/
gates/engine.ts`'s `DELTAS` matrix, `auto` profile, all three tiers:
`'quick-fix': ['anomaly-notify']`, `'standard': ['test-coverage',
'anomaly-notify', 'task-verify-required']`, `'complex': ['test-coverage',
'anomaly-notify', 'task-verify-required']` — `code-review` and
`security-audit` appear in **zero** `auto`-profile cells. `auto` is this
repo's own configured default (`.cadence/config.json`), a deliberate cost
decision, not an oversight. **The two gates are not symmetric even outside
`auto`**: `code-review` ∈ `{strict×standard, strict×complex,
standard×complex}` (3 cells); `security-audit` ∈ `{strict×complex}`
**only** (1 cell). A profile+tier override that surfaces `code-review`
(e.g. `standard`/`complex`) does not necessarily surface `security-audit`
— only `strict`/`complex` does. The check and its remediation text must
report these two gates separately, never collapsed into one verdict.

**Blocker 2 (session), verified at this commit.** `packages/core/src/
verify/host-cli-client.ts`: `SELF_INVOCATION_ENV_VAR` is `{ claude:
'CLAUDECODE' }` — a `Partial<Record<HostCliFamily, string>>` with exactly
one family keyed. `isSelfInvocation(family, env)` returns `true` whenever
that env var reads `'1'`, and the surrounding comment explains Codex is
**deliberately** left unguarded: its only documented session-indicator env
var is Seatbelt-sandbox-specific (macOS only, not universal even there),
and guessing at a family-wide signal risks the exact false-positive/
false-negative this guard exists to avoid — so today the self-invocation
guard covers Claude Code sessions only. When it fires,
`wrapWithFallback` (`verifier-factory.ts`) catches the resulting
`HostCliError(reason:'self-invocation')` and falls back to the `mock`
verifier provider rather than spawning a nested headless call.

**Blocker 3 (provider), found during this SPEC's authoring — not in the
original input doc, and load-bearing.** `.cadence/config.json` configures
`securityAudit.provider` as `mock`, while `codeReview.provider` is
`host-cli`. `seamProvider(config, seam)` (`packages/core/src/
activate/assess.ts`) reads exactly this field. This means: even with
blocker 1 cleared (`strict`×`complex` override) **and** blocker 2 cleared
(a real interactive terminal, no self-invocation), `security-audit` in
*this* repo still produces a **mock** finding, because its provider is
separately configured that way. This is an ordinary per-seam config
default, not a safety property — unlike blockers 1 and 2, changing it is
in scope for an operator to just do (`cadence activate` or a config edit),
not something this phase forbids. But a reachability check that only
evaluates blockers 1–2 and calls `security-audit` reachable whenever they
clear would be **wrong in this repo today** — the exact honesty failure
this phase exists to fix, reintroduced one layer up. The check must
evaluate all three axes per gate.

**The session axis is conditioned on provider — verified, and load-
bearing for AC-2.** `isSelfInvocation`'s guard only sits inside
`host-cli-client.ts`'s spawn path, reached from `verifier-factory.ts`'s
`host-cli` branch (`wrapWithFallback`); the `anthropic`/`local`/`mock`
branches return before ever calling it. So the self-invocation guard can
only block a gate whose own provider is `'host-cli'` — a gate configured
to `'anthropic'`/`'local'` is unaffected by a headless Claude Code
session (a different, non-self-invoking code path runs it for real), and
a gate configured to `'mock'` is already blocked on the provider axis
regardless of session. The check's session axis must therefore read as
"provider is `host-cli` **and** `isClaudeCodeSession(env)`," never
"`isClaudeCodeSession(env)` alone" — the latter would over-report a
blocker on a gate the guard was never going to touch, the same honesty
failure blocker 3 already forced onto the provider axis.

**Compounding, not independent, for `code-review` specifically.** Almost
every agent-driven settle in this repo runs inside a headless Claude Code
session (`CLAUDECODE=1`) under the default `auto` profile. Blocker 1 means
`code-review` usually isn't even in the gate set to run; blocker 2 means
that on the rarer occasion a profile override does include it, the same
session that would run it is exactly the session the guard exists to stop
from spawning a second one. Both are correct, retained behavior — see
Constraints. `security-audit` additionally carries blocker 3 in this
repo's live config. The gap is that nothing currently reports any of this,
so "no real finding has been produced yet" reads identically to "no real
finding *can* be produced under this configuration" — the unknown-vs-
unreachable distinction `rec-20260801-012` names.

**The DRAFT-level profile override mechanism, verified — and explicitly
out of scope for this check to consult.** `effectiveProfile()`
(`gates/engine.ts`): `draft.profile` (DRAFT frontmatter) wins over
`config.profile` (`.cadence/config.json`), which wins over the `'auto'`
fallback. This is the real lever an operator uses, and the check's
`remediation` text must name it precisely (`profile:` in DRAFT
frontmatter, not a CLI flag). But `cadence doctor` does not load an active
DRAFT today, and adding that plumbing is out of scope here — the check
evaluates **`config.profile` only** (the project default), not a
specific in-flight DRAFT's override. Documented limitation: if an
operator has already set a DRAFT-level override, the check may report
`warning` for a draft that has, in fact, already cleared blocker 1. The
`remediation` text stays correct regardless (it names the lever, not a
claim about every draft's current state). `effectiveProfile(config,
null)` — not bare `config.profile` — is the deliberate call here: it
carries the `'auto'` fallback for a config with no `profile` key at all.
Simplifying it to `config.profile` directly would silently break on that
config shape; keep the call as written.

**The session-axis predicate: reuse, do not touch the guard file, do not
add a third copy.** `isSelfInvocation` and `SELF_INVOCATION_ENV_VAR` are
module-private to `host-cli-client.ts`, which Constraints forbid
modifying. A second, functionally identical predicate already exists and
is exported: `isClaudeCodeSession(env: NodeJS.ProcessEnv): boolean` in
`packages/core/src/activate/assess.ts`, defined as `env.CLAUDECODE ===
'1'` — the exact same env var and comparison `isSelfInvocation('claude',
env)` uses. The new check reuses `isClaudeCodeSession` for its session
axis. This narrows the check's session-axis language to Claude Code
specifically (matching what `SELF_INVOCATION_ENV_VAR` actually covers
today — one family), not a generic multi-family claim. If
`SELF_INVOCATION_ENV_VAR` ever grows a second family, this check's session
axis should be revisited to match — noted, not solved, here.

**Ledger close-out precedent and its sharp edge (phase 249, same shape).**
`cadence intelligence audit`'s orphan count is a **known moving target**,
not a stable pass/fail signal: `computeIntelligenceAudit`
(`packages/core/src/intelligence/store/audit.ts`) builds its valid-rec-id
set from `recommendations[]` only, never consulting `archived[]` — so a
decision/evidence entry whose rec was legitimately archived (not lost)
reads as an orphan indistinguishable from a genuinely-vanished one.
`recommendation promote`'s `autoArchive: true` default means **every
phase that closes via the single-commit settle convention's normal path
(promote its source rec to `shipped`) generates new "orphans" by this
definition** — including this phase's own T1a promotion of
`rec-20260802-001`, which moves it from `recommendations[]` into
`archived[]` **in the same atomic write**. Phase 249 hit this directly
(documented in its own SPEC Context, filed as `ev-20260802-014` on
`rec-20260802-003`) and dropped a raw-count AC clause for exactly this
reason. This phase's T1c (re-measure post npm-scope-migration) inherits
the same shape: **record the number as evidence, do not assert a specific
value or a decrease** — the count is expected to have moved again by the
time this phase's own settle finishes, for reasons that have nothing to do
with orphan cleanup health.

**Coverage mode is `assertion`** (`.cadence/config.json`:
`"coverageMode": "assertion"`) — every AC below must be referenced by its
`AC-N` token inside an asserting `it()`/`test()` block, not a comment.
Ledger-state ACs (AC-1, AC-5, AC-6) are not code-behavior tests; the
in-repo precedent for asserting ledger/doc content directly is
`packages/core/tests/docs/readme-shakedown.test.ts` (`readFileSync` a
ledger/doc file, `expect(...).toContain/toMatch` against its content). It
transfers only partially: that test reads a **frozen** artifact, while
AC-1/AC-5/AC-6 assert against a live, continuously-mutating ledger that
every future phase's promote/archive churn can perturb. Keep these
assertions to what stays stable across that churn — **match on id +
status (+ `evidenceIds.length >= N` where explicitly not asserting an
exact count) only, never on exact array ordering or unrelated ledger
counts.** `evidenceIds` on the rec is an array of ids; evidence *bodies*
live in `.cadence/intelligence/evidence.json`, a separate file — don't
grep note text in the wrong one. `recommendation add`'s new id (T1b) is
minted at run time and unknowable now; DRAFT/BUILD match that
recommendation by title substring, not a hardcoded id.

**Doctor check contract, verified.** `packages/core/src/doctor/model.ts`:
`DoctorCheck = { name, status, severity, detail, remediation, fixId }`,
with `pass(name, detail)` and `fail(name, severity, detail, remediation,
fixId)` helpers. `runDoctor()` (`packages/core/src/doctor/run.ts`) pushes
each check's result into a `checks: DoctorCheck[]` array. **Correction to
the original input doc's assumption:** there is no existing precedent for
factoring a check into its own module — all 19 live `DoctorCheck`-
returning functions live inline in `run.ts`; `doctor/host-hooks.ts`
exports only predicates it calls, not a check itself. The closest existing
precedent for AC-3's injectable-seam requirement is already inline in
`run.ts`: `checkVerificationReadiness(root: string, env:
NodeJS.ProcessEnv = process.env)` — a default-parameter env seam on an
inline check function. `conduction-reachability` may follow that inline
pattern (simplest, matches every existing check) or introduce a new
per-check-module pattern as a deliberate choice — DRAFT decides, but must
state which and why, not assume a precedent that doesn't exist.

**Profile-axis and gate-name-space plumbing, verified clean.**
`gatesFor(tier: Tier, profile: Profile): GateSet` and `effectiveProfile`
are both exported from `gates/engine.ts` — no engine change needed for the
profile axis. `GateSet = { gates: Gate[], softCap: boolean }`
(`packages/types/src/profile.ts`); checking inclusion is
`gatesFor(tier, profile).gates.includes('code-review')` across
all three `Tier` values (`'quick-fix' | 'standard' | 'complex'`) to
answer "at any tier." **Gate names and seam names are different string
spaces — do not conflate them:** the `Gate` enum uses kebab-case
(`'code-review'`, `'security-audit'`, from `gates/engine.ts`/
`packages/types/src/profile.ts`); `VerifierSeam` (config/provider lookup,
`activate/assess.ts`) uses camelCase (`'codeReview'`, `'securityAudit'`).
The provider axis reads `seamProvider(config, 'codeReview' | 'securityAudit')`.

**Doc surface that must be paired-edited, verified.**

## Constraints

- **Do not modify** `isSelfInvocation`, `SELF_INVOCATION_ENV_VAR`, the
  spawn guard in `host-cli-client.ts`, or the `DELTAS` matrix in
  `gates/engine.ts`. This phase adds visibility only — blockers 1 and 2
  are deliberate, retained behavior (AC-5 records why). The session axis
  is implemented by reusing the already-exported `isClaudeCodeSession`
  from `activate/assess.ts` — no export needs adding to the forbidden
  file (see Context).
- **No escape hatch.** No flag, env var, or config option that lets
  `code-review`/`security-audit` run for real from inside a headless
  self-invoking session. That is exactly the safety property blocker 2
  protects. (Blocker 3 — the provider default — is not a safety property;
  an operator changing it via existing, already-sanctioned mechanisms like
  `cadence activate` is not an escape hatch and is not forbidden.)
- **`fixId: null` on the new check.** There is no safe auto-repair for any
  of the three axes — all three remediations are operator decisions (a
  profile override, a different execution context, a provider
  reconfiguration), not something `cadence doctor --fix` can apply.
- **T1 gates everything else.** Per the anti-skip contract: T1 (ledger
  close-out) must be `DONE` in `PROGRESS` before any T2+ (verification) or
  T3+ (implementation) task begins. AC-1 is deliberately first for the
  same reason.
- **Ledger writes commit in the same commit as the rest of the phase.**
  Two prior arc sessions stranded correct ledger work uncommitted in a
  worktree; do not repeat that.
- **Idempotency guards are report-back events.** If T1a/T1b/T1c's guard
  conditions don't hold as expected (e.g. `rec-20260802-001` already
  `shipped`), stop and reconcile — do not silently skip or re-run a
  mutating command that assumes the un-run state.
- **Out of scope, separate phases:** `rec-20260802-002` (SUMMARY.md
  renders no findings), `rec-20260802-004` (deep-verify's identical
  registry gap). Do not fold either in.
- **No orphan-count threshold.** Per Context, `cadence intelligence
  audit`'s count is a known-drifting metric (the `archived[]`-blind-spot
  gap in `computeIntelligenceAudit`, not yet fixed) — T1c records the
  number, it does not gate anything on it.
- **Ledger-assertion stability.** Per Context: AC-1/AC-5/AC-6's tests
  assert id + status (+ `evidenceIds.length >= N` where not asserting an
  exact count) only — never exact array ordering, never an unrelated
  count that future phases' normal ledger churn would break.
