# 251-01 — Conduction reachability check + finding-durability arc close-out

## Objective

Close out the finding-durability arc's ledger bookkeeping (phases 247–249,
shipped in v1.54.0), then add a `cadence doctor` check —
`conduction-reachability` — that reports, per gate (`code-review`,
`security-audit`) and per axis, whether this repo's current configuration
can produce a real-provider finding at all, since three independent,
verified blockers — two deliberately retained, one an ordinary config
default — currently make that structurally unreachable in the normal
(headless-agent) operating mode this repo runs in almost all the time.

### AC-2: The check reports reachability honestly, per gate, across all three axes
Given a `cadence doctor` run, taking exactly two inputs — `config`
(`.cadence/config.json`) and `env` (`NodeJS.ProcessEnv`), no tier or
active-DRAFT input (see Context on the `config.profile`-only scope) —
evaluating `code-review` and `security-audit` **separately** (never
collapsed into one verdict — see Context on why they're asymmetric)
When any of a given gate's three axes blocks it — **profile**
(`gatesFor(tier, profile).gates` excludes the gate at every `Tier` value,
for `profile = effectiveProfile(config, null)`), **provider**
(`seamProvider(config, seam)` is `'mock'`), or **session** (the gate's
own provider is `'host-cli'` **and** `isClaudeCodeSession(env)` is
`true` — the session axis never blocks a gate whose provider isn't
`host-cli`: the self-invocation guard sits inside `host-cli-client.ts`'s
spawn path, which an `anthropic`/`local`-configured gate never reaches,
and a `mock`-configured gate is already blocked on the provider axis
regardless)
Then the check reports `severity: 'warning'` for that gate with a `detail`
naming specifically which axis or axes block it (profile / provider /
session, any applicable combination); when all applicable axes clear for
a gate, that gate is reported reachable. The check's overall `status` is
`'ok'` only when both gates are reachable; `'warning'` otherwise, with
`detail` covering both gates' per-axis state so an operator can tell at a
glance which gate(s) and which axis(es) need attention.

### AC-3: Deterministic under the mock-only rule, no real terminal or provider needed
Given the check's two inputs — `config` (profile + per-gate provider) and
`env` (session) — are supplied through injectable parameters, not read
directly from `process.env`/live config inside the check's core logic;
the profile axis itself quantifies over all three `Tier` values
internally (the check takes no tier input), so scenarios below are
described by `profile` alone, never a profile×tier cell
When each combination below is exercised in a test
Then every combination is reachable and assertable without a real
provider, a real interactive terminal, or a mutated `process.env` —
matching this repo's existing `mock`-only test discipline. Exhaustive
enumeration of every profile × session × provider × gate combination is
not required; cover at minimum: (1) `profile: 'auto'` — both gates
profile-blocked (today's live default); (2) `profile: 'standard'` —
`code-review` profile-clear, `security-audit` still profile-blocked —
the one profile where the two gates' profile axis diverges (Context,
Blocker 1's 3-cells-vs-1-cell asymmetry), and the case that catches an
implementation that computes the profile axis once and wrongly reuses it
for both gates; (3) `profile: 'strict'`, `codeReview.provider:
'host-cli'`, session set — `code-review` session-blocked,
`security-audit` still provider-blocked regardless of session;
(4) `profile: 'strict'`, both providers non-`mock`, session clear — both
gates reachable; (5) `profile: 'strict'`, `codeReview.provider:
'anthropic'`, session set — `code-review` reachable despite session
being set, exercising the "session axis doesn't apply to a non-`host-cli`
provider" clause in AC-2.

### AC-5: The disposition is recorded as a decision, not implied
Given the phase settles
When `cadence decision add` is run, linked to `rec-20260801-012`
Then the entry records:
(a) the self-invocation guard is retained — it prevents unbounded nested
self-invocation, a real safety property, and removing it to farm findings
would trade that property for test data; (b) the `auto`-profile gate set
is unchanged — conduction is a deliberate, operator-initiated act, not
something that should happen incidentally; (c) `security-audit`'s
`mock`-provider default (blocker 3) is a separate, ordinary config
decision an operator can change independently of (a)/(b) — noted so a
future reader doesn't conflate it with the two retained safety/cost
decisions; (d) conduction is therefore a documented human-operator
procedure (AC-6), and this check exists so its absence is legible rather
than silent; (e) the trigger to revisit: if operator-run conduction proves
impractical enough that the corpus stays empty through the next arc,
reconsider a supervised, depth-limited escape hatch.

### AC-6: The operator procedure to produce a real finding is documented
Given the docs build
When the operator-procedure doc (in whichever existing doc namespace
covers operator runbooks — see Open Questions) and the
`conduction-reachability` check's own `remediation` text are read
Then the documented procedure states the exact steps,
**correctly distinguishing the two gates**: for `code-review`, override

that includes it (`standard`×`complex`, `strict`×`standard`, or
`strict`×`complex`); for `security-audit`, the override must be
`strict`×`complex` specifically (its only reachable cell) **and** its
provider must be reconfigured off `mock` (`cadence activate` or the
equivalent config edit — blocker 3). Both procedures continue: run
`cadence settle run` from a real interactive terminal (not a headless
agent session, so the self-invocation guard never fires), and confirm the
persisted SUMMARY records a non-`mock` provider for the gate — read
`SUMMARY.gates[]`'s `provider` field for the relevant gate entry (or the
`assurance.verifierRollup[]` entry), **not** `verifierIdentity` (that's a
`GateFlags` field internal to gate evaluation, not a SUMMARY key;
`registry.ts` lifts it onto `GateProvenance.provider`/`.model` before
persisting).
`rec-20260801-012` is promoted to reflect this recorded disposition
(readiness/status per its own current state at settle time — verify
before promoting; do not assume `candidate`).

  guard in `packages/core/src/verify/host-cli-client.ts`, or the `DELTAS`
  matrix in `packages/core/src/gates/engine.ts`. This phase adds
  visibility only. The session axis is implemented by reusing the
  already-exported `isClaudeCodeSession` from `packages/core/src/
  activate/assess.ts` — no export needs adding to the forbidden file.

  `security-audit` run for real from inside a headless self-invoking
  session. An operator reconfiguring `security-audit`'s provider off
  `mock` via existing, already-sanctioned mechanisms (`cadence activate`)
  is not an escape hatch and is not forbidden.

  auto-repair for any of the three axes.
- Do NOT begin T2+ before T1 is `DONE` in `PROGRESS`. Per the anti-skip
  contract, T1's guard firing (e.g. `rec-20260802-001` already `shipped`)
  is a report-back-and-reconcile event, not a silent skip.
- Do NOT leave ledger writes (T1, T5, T6's promotion) uncommitted in this
  worktree at session end — they land in the same commit as the rest of
