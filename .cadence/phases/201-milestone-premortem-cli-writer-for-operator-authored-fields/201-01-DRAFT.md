# 201-01 — Milestone premortem: CLI writer for operator-authored fields

## Objective

`cadence milestone premortem <id>` recomputes a milestone's pre-mortem deterministically
(`deepenPreMortem` in `packages/core/src/intelligence/milestone.ts`) from ledger heuristics.
`outOfScope` is intentionally excluded from that derivation and preserved verbatim across
refreshes (`outOfScope: milestone.preMortem.outOfScope`) because it's meant to be
operator-authored — but there is no CLI path to *set* it, only a raw hand-edit of
`.cadence/intelligence/milestones.json`. The same gap applies to `likelyFailureModes` and
`hiddenDependencies`: the deterministic refresh only derives heuristic-driven entries, with no
way for an operator to add their own judgment calls (closing rec-20260714-001, confirmed via
mil-rec-rec-20260619-008's pre-mortem walk-back on 2026-07-19).

Add repeatable `--add-out-of-scope`, `--add-likely-failure-mode`, and `--add-hidden-dependency`
options to `cadence milestone premortem <id>` that append operator-authored text. `outOfScope`
already survives refreshes verbatim; `likelyFailureModes`/`hiddenDependencies` do not (each
refresh fully replaces them with freshly-derived entries), so operator-added entries in those
two fields need the same survive-a-refresh guarantee `outOfScope` already has — mark them so
`deepenPreMortem` can pass them through alongside the freshly-derived deterministic entries on
every subsequent refresh, the same way `outOfScope` is preserved today.

## Acceptance Criteria

### AC-1: operator-authored likelyFailureModes/hiddenDependencies entries survive a later refresh
Given a milestone whose pre-mortem has an operator-authored entry in `likelyFailureModes` or
`hiddenDependencies` (added via the new CLI flags)
When `cadence milestone premortem <id>` is run again later with no `--add-*` flags (a plain
deterministic refresh)
Then that operator-authored entry is still present in the result, alongside whatever the
deterministic heuristics currently derive — matching the existing guarantee `outOfScope` already
has (see the `deepenPreMortem` test "outOfScope preserved verbatim, never written")

### AC-2: the CLI can append operator-authored pre-mortem entries, and refuses empty text
Given `cadence milestone premortem <id> --add-out-of-scope <text> --add-likely-failure-mode
<text> --add-hidden-dependency <text>` (each flag repeatable, e.g.
`--add-out-of-scope "text one" "text two"`)
When the command runs against a `proposed`/`accepted` milestone
Then each provided value is appended to the corresponding `preMortem` field and persisted to
`.cadence/intelligence/milestones.json`
And when any provided value is empty or whitespace-only, the command refuses with a clear
stderr message and non-zero exit before writing anything (matching the existing `milestone
close --ref` empty-value refusal pattern), for an unknown id, or for a milestone whose status
is neither `proposed` nor `accepted` (matching the existing `premortem <id>` refusal shape)

### AC-3: full test suite passes
Given the fix and new tests are in place
When `pnpm --filter @manehorizons/cadence-core test`, `typecheck`, and `lint` run
Then all exit successfully with no failures

## Boundaries

- DO NOT change `seedPreMortem` (the propose-time seeding path) — it has no prior milestone
  state to preserve from, and its "byte-frozen 4a" contract comment says not to route it through
  shared helpers casually.
- DO NOT change `driftRisks` — it stays fully deterministic; the recommendation scopes operator
  authorship to `likelyFailureModes`, `hiddenDependencies`, and `outOfScope` only.
- DO NOT add a way to *remove* or *edit* a previously-added operator entry in this phase — only
  append. Deletion/editing is a separate, undecided feature.
- DO NOT change the `premortem <id>` refusal shape for unknown id / wrong status — only add the
  new optional flags and their own validation on top.
- DO NOT touch `cadence milestone propose`, `accept`, `defer`, `export`, `status`, or `list`.
