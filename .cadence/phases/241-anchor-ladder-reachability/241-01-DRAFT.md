# 241-01 — Anchor-ladder reachability: gate provenance in SettleContext + first real end-to-end anchoring run

## Objective

Phase 235 shipped the full four-tier §7.1 anchor ladder as a pure resolver, but its top rung is dead in production. `gates/code-review.ts:80` calls `anchorFindings` with a literal `[]` for `gateProvenance`, because `SettleContext` exposes no prior-gate provenance to a `GateImpl` — the accumulator is a local `const gates: GateProvenance[]` inside `runSettleGates` (`gates/registry.ts:162`). The `executable` tier requires a `build-test-must-pass` entry with `status: 'ran'`, so from the live gate it can never be reached: every real finding caps at `structured`/`declared`/`undeclared`, and `executable` is exercised only by unit tests that inject provenance directly. `code-review` already runs ninth in `GATE_ORDER`, well after `build-test-must-pass` runs fifth, so the fact it needs is sitting in that array unread. Thread the in-flight provenance into the per-gate context as an immutable snapshot, consume it in the code-review gate, and prove the tier is reachable through the real settle path rather than only through injected test doubles. Closes `rec-20260729-002` (high) and `rec-20260729-007` (the same anchoring code has never once run against a real diff in a real settle, because `code-review` is absent from the `auto` / `standard × standard` gate set this repo settles under — this DRAFT declares `profile: strict` so the gate it changes actually fires on its own settle).

## Acceptance Criteria

### AC-1: A gate impl can read the provenance of gates that already ran this settle
Given a settle whose gate set includes `code-review`, where `build-test-must-pass` has already run and recorded a `status: 'ran'` provenance entry
When `runSettleGates` invokes a later gate's `GateImpl`
Then that impl receives, through its `SettleContext`, the provenance entries recorded so far this settle, including the `build-test-must-pass` entry, and a gate invoked before any provenance exists receives an empty collection rather than `undefined`

### AC-2: The provenance a gate sees is an immutable point-in-time snapshot
Given a gate impl that has read its provenance snapshot from `SettleContext`
When subsequent gates append their own entries to the registry's accumulator, or the gate attempts to mutate the collection it was handed
Then the gate's snapshot reflects only what had been recorded at its own invocation, and no mutation through that snapshot can reach or corrupt the registry's accumulator

### AC-3: The `executable` tier is reachable through the real settle path
Given a real settle at a profile whose gate set includes `code-review`, a DRAFT whose acceptance criterion is cited by a task with a non-empty `verify`, a diff that produces at least one code-review finding, and `build-test-must-pass` having genuinely run
When the code-review gate anchors that finding
Then the anchor resolves to tier `executable` and that tier is recorded in the persisted `SUMMARY.json`, with no test double substituting for the gate provenance the live registry produced

### AC-4: Absent, skipped, or refused test corroboration still caps the tier
Given the same settle shape as AC-3 but where `build-test-must-pass` recorded `skipped` (no test command, or bypassed) or `refused` instead of `ran`
When the code-review gate anchors the same finding against the same task-cited criterion
Then the anchor resolves no higher than `structured`, so corroboration is required rather than assumed, and threading real provenance cannot inflate a tier that the ladder's two-condition check does not earn

### AC-5: The shipped docs stop claiming the tier is unreachable, and this phase's own gate set includes code-review
Given phase 235 documented the `executable` tier as structurally unreachable from the live gate, and `docs/concepts.md` carries that disclosure
When phase 241 makes the tier reachable and settles under its own declared profile
Then the doc statement is corrected to match current code truth rather than left contradicting it, and the effective gate set resolved for this DRAFT's declared profile contains `code-review`

## Boundaries

- DO NOT fix `rec-20260729-003` (per-finding criterion attribution) or `rec-20260729-005` (boundary-relevance for anchors) here — both are deliberately disclosed phase-235 limitations with their own scope, and folding them in was explicitly declined when this phase was chosen.
- DO NOT change `GATE_ORDER`, gate-set membership in `engine.ts`, or the tier × profile matrix. This phase makes an existing tier reachable; it does not redefine which gates fire in which cell.
- DO NOT alter the anchor ladder's grading logic in `verify/anchor.ts`. The two-condition `executable` check and its documented residual gap stay exactly as phase 235 specified — this phase supplies the input it was always meant to receive, nothing more.
- DO NOT make `SettleContext`'s new field required, and DO NOT rebuild the context per gate in a way that discards the memoized `coverage()` / `diff()` / `draftMtimeMs()` closures — re-running the coverage scan once per gate would be a silent performance regression.
- DO NOT add a second refusal primitive, and DO NOT change which findings refuse a settle. `highs`/`pass` semantics are phase 24.3 contract and stay untouched.
- DO NOT add a runtime dependency, and DO NOT touch the `anthropic` or `local` verifier providers. Tests stay on `mock`.
- DO NOT claim the end-to-end run proves more than it does: the `mock` verifier only flags added `console.log(` lines, so this phase's own diff is expected to produce zero findings and its own SUMMARY will show an empty `codeReview` map. The `executable`-tier evidence comes from T3's fixture diff, not from phase 241's own diff — say so in the SUMMARY rather than implying the phase self-demonstrated the tier.
