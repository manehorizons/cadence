# 212-01 — Retro friction feeds back into Praxis recommendation scoring

## Objective

Add a `cadence retro feedback` command that closes the loop from post-settle retro friction (phase 174 artifacts, phase 186 rollup) back into Praxis recommendation scoring: it matches recurring friction against affected recommendations, records each match as an auditable evidence.json entry, and scoreRecommendation gains a new transparent frictionPts term so recommendations tied to real recurring pain rank higher — idempotent and operator/CI-triggered rather than silent.

## Acceptance Criteria

### AC-1: Recurring friction is matched to related recommendations
Given a `.cadence/phases/**/*-RETRO.json` corpus containing recurring friction (a bypass gate, rough-task status, or finding category appearing in ≥2 distinct phases, per `computeRetroRollup`'s `recurring` bucket)
When `cadence retro feedback` runs
Then for each recurring friction entry it finds candidate recommendations whose `affectedAreas` or `affectedFiles` overlap with that friction's key/context, and reports the matches it intends to record

### AC-2: Matched friction is recorded as evidence, idempotently
Given a recurring friction entry has been matched to recommendation R
When `cadence retro feedback` runs (first time, and again on a subsequent run with no new friction)
Then it writes exactly one new `evidence.json` entry linked to R's `evidenceIds` describing the friction (gate/category, phase count), and a second run for the same friction/recommendation pair writes zero additional entries (no duplicates)

### AC-3: Friction evidence measurably raises a recommendation's Praxis score
Given recommendation R has N linked friction-evidence entries (0 ≤ N ≤ cap)
When `scoreRecommendation(R)` is computed
Then the score includes a new, separately-labeled `frictionPts` `ScoreTerm` proportional to N (capped), visible in `cadence recommend`'s per-recommendation term breakdown, and R with friction evidence scores strictly higher than an otherwise-identical recommendation with none

### AC-4: The command is loud and non-silent about what it did or skipped
Given a set of recurring friction entries and their candidate recommendation matches
When cadence retro feedback runs and processes each entry
Then it prints, per friction entry, whether it matched and wrote evidence, matched but was already recorded (skipped), or found no matching recommendation

## Tasks

### T1: Friction-matching + idempotent evidence writer
- files: `packages/core/src/services/retro-feedback.ts`, `packages/core/tests/services/retro-feedback.test.ts`
- action: implement `matchFrictionToRecommendations(rollup, recommendations)` (pure, matches recurring-bucket entries' gate/task-status/finding-category keys against a recommendation's `affectedAreas`/`affectedFiles`) and `recordFrictionEvidence(...)` which, for each match, checks whether an identical-key friction evidence entry is already linked to that recommendation and, if not, writes one via `addEvidenceToRecommendation`'s ledger-write pattern (running friction text through `redactSecrets()` first)
- verify: unit tests cover a match, a non-match, and a second run producing zero new evidence entries for an already-recorded match
- done: AC-1, AC-2

### T2: Wire frictionPts into scoreRecommendation
- files: `packages/core/src/intelligence/recommend.ts`, `packages/core/tests/intelligence/recommend.test.ts`
- depends: T1
- action: add a new `frictionPts` `ScoreTerm` to `scoreRecommendation`, derived from the count of friction-evidence entries linked to that recommendation (weighted, capped — e.g. weight 1.5, cap 3), additive to the existing 7 terms; a recommendation with zero friction evidence must score identically to today
- verify: unit test asserts a recommendation with N>0 linked friction-evidence entries scores strictly higher than an otherwise-identical recommendation with none, and that N=0 leaves `raw`/`score` unchanged from pre-phase-212 behavior
- done: AC-3

### T3: `cadence retro feedback` CLI command
- files: `packages/core/src/cli/commands/retro.ts`, `packages/core/tests/cli/retro.test.ts`
- depends: T1, T2
- action: add a `feedback` subcommand under `cadence retro` that runs `scanRetroArtifacts`/`computeRetroRollup`, calls T1's matcher/writer, and prints one line per recurring friction entry: matched-and-wrote-evidence, matched-but-already-recorded (skipped), or no-matching-recommendation — plus a `--json` variant of the same result; never mutate `evidence.json` without a corresponding printed line
- verify: CLI test exercises a fixture RETRO.json corpus and asserts both the printed per-entry summary and the resulting `evidence.json` contents
- done: AC-4

## Boundaries

- DO NOT change scanRetroArtifacts/computeRetroRollup (phase 186) — this phase only consumes their output.
- DO NOT persist the rollup itself to disk — `cadence retro feedback` recomputes it on each run, matching the existing on-demand `cadence retro` behavior.
- DO NOT run the feedback loop automatically inside `cadence recommend` or `cadence settle` — it stays an explicit, separately-invoked command.
- DO NOT match against one-off friction (rollup's `oneOff` bucket) — recurring only.
- DO NOT add a new runtime dependency.
