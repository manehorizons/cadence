# 246-01 — Finding-identity dedup under real-provider message drift

## Objective

Decide, on evidence rather than assumption, whether finding-identity dedup
under real-LLM-provider message drift (rec-20260801-010) needs code now —
and since the evidence says no, record that decision durably with a
concrete, pre-registered trigger, rather than leaving it open-ended or
building something speculative to feel productive.

## Context

Phase 245 (`0d6aea6d`) narrowed `computeFindingId`'s hash to
`(file, normalized message)` only — `anchor` and `severity` are
**deliberately excluded** because they legitimately change across settles
for the same underlying defect (`packages/core/src/verify/finding-identity.ts:53-60`).
`normalizeMessage` does no semantic normalization, so a real LLM-backed
verifier (anthropic/local/host-cli) re-wording the same underlying defect
across settles still mints a new id, and phase 242's `deriveRoutingCandidates`
(keyed on `Finding.id`) misses the duplicate.

**Revision note (2026-08-01).** The first draft of this SPEC proposed
in-loop telemetry (grouping findings sharing `(file, anchor.kind, anchor.ref,
severity)` but differing message, as a "near-miss" signal). An independent
fresh-context review, verified empirically before accepting it, found that
approach broken in both directions and the premise it was built on wrong:

1. **Zero observed instances.** Across all 257 `.cadence/phases/*/*-SUMMARY.json`
   in this repo, only 5 carry a `codeReview` key and **none contain a single
   persisted finding** (verified by script, 2026-08-01). Phase 242's
   auto-routing has never fired in production. The dedup defect is reasoned
   from reading the code, not measured from a real occurrence — instrumenting
   a stream that has never once produced data ships an instrument for
   nothing.
2. **The proposed grouping key was inverted.** Requiring `anchor`/`severity`
   to *match* while message differs uses precisely the two fields phase 245
   excluded *because* they legitimately vary for one recurring defect — so it
   would filter out real drift pairs while merging genuinely distinct
   findings that happen to share a file/severity/anchor slot.
3. **It measured the wrong axis.** The drift is cross-settle; the proposed
   telemetry only grouped within one settle batch. Detecting real drift needs
   a prior settle's finding text, which `deriveRoutingCandidates` never
   receives (`alreadyRoutedIds` is a `ReadonlySet<string>` of hashes only,
   `packages/core/src/intelligence/finding-routing.ts:271-276`) and is not
   allowed to fetch — the module deliberately has no ledger-store import
   (`finding-routing.ts:11-19`), matching the house pure-core/impure-shell
   split. Threading prior-finding text in would be a boundary change, not
   observability.
4. **Asymmetric failure cost, unchanged.** Bounded fuzzy-matching still has a
   real false-merge risk ("could silently swallow a distinct finding as a
   duplicate — worse than the current failure mode, which only produces
   recoverable duplicate noise" — rec-20260801-010). The operator already
   risk-accepted deferring this once (2026-08-01, phase 245 scoping); nothing
   about real-provider usage volume has changed since (host-cli was only
   activated for deep-verify/code-review in PR #351, the same day).

**Two more constraints the review surfaced, both binding on whatever revisits
this later:** ledger-routed finding text is `redactSecrets`'d and truncated
to 80 chars (`finding-routing.ts:143`), so `SUMMARY.json` — not the
ledger — is the corpus of record for any future analysis; and this repo's
tests are `mock`-only by house rule, so no CI suite can ever exercise the
real drift failure mode — validating a future fix depends on operator
dogfooding with a real provider, not test coverage.

**A related, separate defect the review also found and verified:** a
refused settle and a later successful settle for the same draft both write
the identical `<draft>-SUMMARY.json` path, so a convergence re-loop's
attempt-1 findings are silently destroyed the moment attempt-2 succeeds
(`packages/core/src/services/settle.ts` — refused path ~778-781, success
path ~1148-1150). That is real, uninstrumented-related data loss, filed
separately as **rec-20260801-011** rather than folded into this phase's
scope — it is arguably the cheapest real source of genuine cross-settle
drift evidence (a reloop pair), which is exactly why it matters for this
decision's trigger below, but fixing it is its own unit of work.

## Acceptance Criteria

### AC-1: The decision is recorded durably and is queryable, not just prose in this file
Given rec-20260801-010 is `needs-decision` and has been `converted` to this
phase (terminal — CADENCE has no CLI path to unconvert a recommendation)
When phase 246 settles
Then `cadence decision add --rec rec-20260801-010` has recorded a decision
whose rationale states: (a) zero code-review findings have been persisted
across any settle to date (0/257 `SUMMARY.json` files, verified 2026-08-01),
(b) the correct next step once data exists is an **offline analyzer over the
accumulated SUMMARY.json corpus** (not in-loop telemetry, not fuzzy-matching
— both rejected above with reasons), and (c) the trigger for revisiting:
**at least 3 settles under a non-mock review provider have each persisted at
least 1 code-review finding** (3 chosen to match this repo's existing
convergence-attempt magnitude, `config.convergence.maxAttempts` default;
adjustable when first revisited, not binding).

## Constraints

- **No source code changes ship in this phase.** The evidence supports
  waiting, not building; shipping telemetry anyway to "do something" is the
  exact speculative-build this decision exists to avoid.
- **The pre-committed next step is an offline analyzer, not in-loop
  telemetry or fuzzy-matching.** Recorded here so a future session facing
  the same rec doesn't re-derive (or re-reject) the same three options from
  scratch.
- **`SUMMARY.json` is the corpus of record**, not the recommendation ledger
  (routed text there is redacted and truncated).
- **This decision cannot be validated by CI.** Its premise (no real-provider
  duplicates observed yet) can only be re-checked by an operator running
  real settles with a non-mock provider — the trigger in AC-1 is what that
  operator should watch for.

## Open Questions

  decision record and its stated trigger.
