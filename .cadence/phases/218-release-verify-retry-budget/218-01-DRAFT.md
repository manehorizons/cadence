# 218-01 — Give post-publish npm verification a patient retry budget

## Objective

`scripts/release-integrity.mjs`'s `verifyNpmPackages` retries `npm view
<pkg> version` via a shared `retry()` helper with a default of 3 attempts
and a 1s/2s linear backoff — ~3 seconds of total patience. This is far
shorter than npm's CDN can take to propagate a fresh publish: the v1.51.0
Release workflow run (30136637570, 2026-07-25) failed its "Create GitHub
Release and verify registry" step because `host-codex` still showed
`1.50.0` on npm 3 retries after publish, even though the publish itself
had already succeeded and all four packages were confirmed correctly live
moments later on independent re-check. The same `retry()`/`verifyNpmPackages`
pairing is also used pre-publish (`verifyNpmPublished`, to skip an
already-done publish) where a fast failure is correct — so the fix is not
a blanket timeout bump, it's a distinctly more patient budget for the
post-publish verification call specifically.

## Acceptance Criteria

### AC-1: Post-publish npm verification tolerates realistic CDN propagation delay without slowing down the pre-publish idempotency check
Given the Release workflow has just published all four packages to npm
When `runReleaseIntegrity`'s post-publish call to `verifyNpmPackages`
checks whether each package's live npm version matches the just-published
version, and one or more packages have not yet propagated to the npm CDN
edge node the check happens to hit
Then the check retries with a materially more patient budget than today's
~3 seconds (enough to tolerate realistic real-world propagation delay,
observed on 2026-07-25) before concluding a genuine mismatch, and only
throws once that patient budget is exhausted; When `verifyNpmPublished`
(the pre-publish idempotency check used by the "Publish to npm" workflow
step to decide whether to skip an already-done publish) runs, Then it
keeps its current fast-fail behavior — a package genuinely not yet
published still fails quickly, not after the new patient budget.

## Boundaries

- Do NOT modify the `retry()` helper's backoff algorithm (the `1000 * attempt` linear-delay formula) — only how many attempts it's given for the post-publish call.
- Do NOT change `verifyNpmPublished`'s effective attempts/timing — it must keep today's fast-fail behavior for the pre-publish idempotency check.
- Do NOT touch `.github/workflows/release.yml` or any step ordering — this phase is scoped entirely to `scripts/release-integrity.mjs` and its test file.
- Do NOT let any test actually wait real wall-clock seconds for a retry delay — use fake timers or an injectable delay seam.
- Do NOT add a new runtime dependency.
