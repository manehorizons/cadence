# 244-01 — Settle-time guard for global-CLI-shadowing-branch-build

## Objective

`cadence settle` silently writes a downgraded artifact (SUMMARY `schemaVersion: 1`,
no `assurance` record) when the process actually executing it is a
globally-installed `cadence` binary that predates this repo's own build,
rather than this checkout's `packages/core/bin/cadence.cjs` (rec-20260729-001,
confirmed on phases 233/234; phases 235/236/241/242 already avoid it by
convention, per dec-20260801-001). The two binaries report an **identical**
`--version` string (unbumped `package.json` on an unreleased branch matches
whatever is currently published), so version comparison cannot detect the
mismatch. This phase adds a narrow, realpath-based self-check — "is the
binary actually executing me located inside this repo's own git worktree,
given that this repo is recognizably the CADENCE monorepo itself" — that
fires a loud stderr notice (matching the existing `MOCK_FALLBACK_BANNER`
convention in `packages/core/src/verify/verifier-factory.ts`) and records
provenance on the written SUMMARY, so a mismatch is both visible live and
auditable after the fact. dec-20260801-001 already names the interim
procedural mitigation (settle via the local build explicitly); this phase is
the code-level guard, not a redesign of CLI resolution.

## Acceptance Criteria

### AC-1: 244-01/AC-1 — mismatch detection is a pure, unit-testable function
Given a candidate "running binary" realpath and a repo toplevel path (as
plain string arguments — no process/filesystem access inside the function
itself, per this repo's pure-core/impure-shell convention)
When the running binary's realpath does NOT sit inside the repo toplevel,
AND the repo toplevel is recognizably the CADENCE monorepo (has
`packages/core/bin/cadence.cjs` and `.cadence/` at its root)
Then the function reports a mismatch; when the binary path IS inside the
repo toplevel, or the repo isn't recognizably CADENCE's own monorepo, it
reports no mismatch — covering both the false-positive-avoidance case (a
normal consumer repo using a globally-installed `cadence` is NOT a
mismatch) and the true-positive case.

### AC-2: 244-01/AC-2 — settle prints a loud notice and records provenance on mismatch
Given the detector from AC-1 reports a mismatch during `cadence settle run`
When settle proceeds to write its SUMMARY
Then a banner (same shape/placement convention as `MOCK_FALLBACK_BANNER`,
a new named export alongside it or colocated per existing module
boundaries) is written to stderr via the existing injected `io.err` port
before settle completes, AND the written SUMMARY records the
resolved-binary-vs-repo-toplevel mismatch as an additive, optional field
(new Zod field on `SummaryZ` in `cadence-types`, `.optional()` —
pre-existing SUMMARYs must keep parsing) so the condition is auditable from
the artifact alone, without having watched stderr live.

### AC-3: 244-01/AC-3 — no behavior change on a matched (correct) invocation
Given `cadence settle run` executes via this repo's own local build (the
common/intended case — this very phase must be settled that way)
When settle runs
Then no mismatch banner is printed, the new SUMMARY field is absent (not
`null` — `exactOptionalPropertyTypes`, omit the key), and no other settle
output changes — full regression safety against existing settle golden
fixtures/tests.

## Boundaries

- DO NOT attempt to detect or fix already-published binaries retroactively
  (impossible — this guard only protects settles that run through code
  containing this fix, i.e. this build and future releases built from it).

  identical across the two binaries in the motivating case.
- DO NOT make the mismatch a hard refusal (settle should still complete) —
  loud notice + recorded provenance, matching this repo's "Quiet Fallback"
