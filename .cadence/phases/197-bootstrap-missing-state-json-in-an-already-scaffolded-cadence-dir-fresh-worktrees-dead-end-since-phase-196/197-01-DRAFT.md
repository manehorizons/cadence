# 197-01 — Bootstrap missing state.json in an already-scaffolded .cadence/ dir (fresh worktrees dead-end since phase 196)

## Objective

Phase 196 (issue #177) made `.cadence/state.json` gitignored and per-worktree.
That silently broke the two existing recovery paths for a `.cadence/` dir that
has no `state.json` yet (a fresh `git worktree`, or a fresh clone of a repo
that already has `.cadence/` committed): `cadence init` refuses outright
because `.cadence/` already exists, and `cadence onboard` — the command
explicitly built for "a repo that already has `.cadence/` committed" — reads
`state.json` for the project name but never creates it when absent, so it
exits 0 and points the user at `cadence progress`, which then throws
`NotInitializedError`. Every state-reading command dead-ends the same way.
Make `cadence onboard` bootstrap a fresh `state.json` (IDLE, no active
phase/draft) when one is missing, deriving the project name from the existing
`.cadence/PROJECT.md` header (not re-derived from `package.json`, which can
disagree with the name already recorded for the project — confirmed in this
very repo: root `package.json#name` is `cadence-monorepo`, but
`PROJECT.md`/state.json's recorded project name is `cadence`). Also correct
`cadence doctor`'s state-missing diagnostic, which currently suggests two
things that do not work ("run any cadence command to regenerate state" and
"or `cadence init`") — point it at the real fix instead.

## Acceptance Criteria

### AC-1: `cadence onboard` bootstraps a missing state.json
Given a `.cadence/` directory that is fully scaffolded (config.json,
PROJECT.md, ROADMAP.md, phases/) but has no `state.json` (the exact state of
a freshly created worktree or a fresh clone post-phase-196)
When `cadence onboard` runs
Then it creates a valid `state.json` (schemaVersion 1, loopPosition IDLE,
activePhase/activeDraft null, revision 0) with the project name read from
`.cadence/PROJECT.md`'s `# <name>` header, prints a clear notice that it
bootstrapped state (not a silent write), and a subsequent `cadence progress`
no longer throws `NotInitializedError`

### AC-2: `cadence onboard` leaves an existing state.json untouched
Given a `.cadence/` directory that already has a valid `state.json`
When `cadence onboard` runs
Then it does not overwrite or reset `state.json` (loop position, active
phase/draft, revision, and all other fields are unchanged) and behaves
exactly as before this fix (host-wire + verifier-readiness reporting only)

### AC-3: `cadence doctor` points at the working fix
Given a `.cadence/` directory with a missing `state.json`
When `cadence doctor` runs
Then its `state` check's fix suggestion names `cadence onboard` (the command
that now actually resolves the problem) instead of the current suggestion
("run any cadence command" / "or `cadence init`"), neither of which works

## Boundaries

- DO NOT touch `cadence init`'s refusal-on-existing-`.cadence/` behavior — a
  full re-init on top of a committed `.cadence/` dir should keep refusing;
  only the `onboard` path is being fixed.
- DO NOT change `emptyState()`'s shape or the `CadenceState` zod schema.
- DO NOT re-derive the onboard project name from `package.json` — this repo
  is the counterexample (`cadence-monorepo` vs the recorded `cadence`).
- DO NOT touch the ReDoS/`--filter-regex` regex-injection issue (#249) —
  that is separate, deferred to the next phase after this one lands.
- DO NOT refactor `init.ts`'s state-construction block beyond what's needed
  to keep `onboard.ts`'s bootstrap logic consistent with it (reuse
  `emptyState`/`SimpleStateBackend`, don't restructure `init.ts` itself).
