# 253-01 — Dependency override remediation

## Objective

Corrected premise: pnpm 9.12.0's pnpm.overrides mechanism is NOT broken — proven by git history (commits 5e8f2894 and a427a939 show lockfile resolutions moving in lockstep with override declarations) and by the fact CI always runs the real pinned 9.12.0 binary via packageManager; the misleading warning the original v1.55 handoff cited comes from a globally-installed newer pnpm launcher (e.g. v11.2.2) self-switching and printing a notice about its own irrelevant behavior before delegating to the pinned 9.12.0, which then applies the overrides correctly. The real, much smaller defect: override targets in package.json/pnpm-lock.yaml are stale (pinned below the current patched floor for fast-uri and brace-expansion's 5.x line), the brace-expansion 2.x resolved line has no override of its own at all, ip-address has no override at all, and nothing detects when a target drifts out of date. This phase refreshes the four override targets to their real patched floors, adds a missing ip-address override, adds a new detector that fails CI when any override target is unsatisfied by any resolved lockfile instance, and corrects the false narrative in place in docs/security/audit-exceptions.md and the tracked v1.55 handoff doc — it does NOT remove the existing overrides (they are load-bearing) and does NOT attempt any pnpm major-version upgrade (pnpm 11.0.0-11.0.8 has its own separate, worse override-ignoring regression).

## Acceptance Criteria



### AC-1: override targets refreshed to patched floors
Given the corrected remediation table (fast-uri >=3.1.5, brace-expansion 5.x line >=5.0.9, brace-expansion 2.x line >=2.1.4 as its own override, ip-address >=10.3.1 as a new override)
When package.json's pnpm.overrides and the regenerated pnpm-lock.yaml overrides block are inspected
Then every override key names the current patched floor, ip-address has a dedicated new override, and brace-expansion's 2.x line has an override distinct from the 5.x line's — no unversioned key that would wrongly force one line toward the other's target

### AC-2: every resolved instance satisfies its override target
Given the corrected overrides applied and pnpm-lock.yaml refreshed
When every resolved instance of fast-uri, brace-expansion (both the 2.x and 5.x lines), and ip-address in pnpm-lock.yaml is checked against its override's target range
Then every instance satisfies its target range — not just the first instance found, since brace-expansion resolves to two live instances

### AC-3: detector fails when an override target goes unsatisfied
Given the new lockfile-overrides detector (scripts/check-lockfile-overrides.mjs or equivalent)
When one override target is deliberately reverted to a stale value and the detector runs, then restored
Then the detector fails with a diagnostic naming the unsatisfied package, resolved version, and instance while reverted, and passes again once the target is restored

**As built (whole-branch review, 2026-08-05):** T5's evidence
(253-01-T5-EVIDENCE.md) found this AC's literal "reverted to a stale value"
phrasing does not by itself demonstrate a failure — lowering a target's
floor within the same major version is provably non-failing, since a
resolved version at or above the new (lower) floor still satisfies it. The
detector's two real failure branches, both demonstrated and unit-tested,
are: a **tightened** target above the resolved version (`unsatisfied`), and
a **removed/uncovered** override key for a resolved major-version line
(`unguarded-line`, the actual shape of this phase's original defect). The
detector genuinely has teeth; this note corrects the AC's example framing,
not its substance.

### AC-4: corrected lockfile is exercised by a real install and wired into CI
Given the corrected override targets and the new detector
When a clean pnpm install and a pnpm install --frozen-lockfile are run locally against the refreshed lockfile, and security.yml's audit job is inspected
Then both installs succeed locally (captured as task evidence, not a redundant unit-testable claim) and the audit job invokes the new detector on the same install path as the existing check-audit-exceptions.mjs step, so a regressed override target fails CI before reaching main — asserted by a workflow-content test; this phase's own 3-OS PR CI passing is the standard merge bar every phase already carries

### AC-5: audit-exceptions.md corrected in place
Given docs/security/audit-exceptions.md's line-33 prose asserting overrides are non-functional
When the doc is read after this phase's changes
Then line 33's prose no longer asserts overrides are non-functional and instead states the corrected mechanism (a globally-installed newer pnpm launcher warns about its own irrelevant behavior; the pinned 9.12.0 binary applies overrides correctly)

### AC-6: v1.55 handoff corrected in place
Given the tracked docs/handoffs/HANDOFF-v1.55-integrity-release.md's §4, §7 Phase A, and §14
When the doc is read after this phase's changes
Then each of §4, §7 Phase A, and §14 states the real defect (stale override targets, no drift detector, ip-address missing an override entirely) instead of the original false 'pnpm.overrides is broken' diagnosis
