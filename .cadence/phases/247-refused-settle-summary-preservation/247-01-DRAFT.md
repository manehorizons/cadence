# 247-01 — Preserve refused-settle findings: additive per-attempt SUMMARY sibling

## Objective

Fix two compounding gaps so a refused settle's findings actually survive:
first, `writeRefusedSettleSummary` never records the `codeReview`/
`securityAudit` findings that caused the refusal in the first place
(they're computed and merged into `acc` but silently dropped before the
write); second, even once recorded, a later settle attempt for the same
draft overwrites that record. Fix both — record, then protect.

## Acceptance Criteria

### AC-1: A refused settle records the findings that caused it
Given a settle refuses after `code-review` and/or `security-audit` ran and
accumulated findings into `acc` (regardless of which specific gate's
refusal triggered the write — an earlier gate may have passed only via
`--force`/`--allow-code-review-failure` while a later gate is what
actually refuses)
When `writeRefusedSettleSummary` runs
Then the written `refusedSummary` conditionally includes `codeReview`/
`securityAudit` (mirroring the success path's
`...(codeReviewFindings ? { codeReview: codeReviewFindings } : {})` shape
at `settle.ts:~1132` exactly), **and when (and only when) those findings
are non-empty** it also gets a `contentHash` computed the same way the
success path computes one (`settle.ts:~1146`) — closing the "refused
summaries aren't tamper-evident" gap independent review flagged, scoped
to exactly the case that needs it (a findings-bearing record worth being
tamper-evident) so it does not contradict the "no new keys on a
findings-free refusal" constraint below. A refused `build-test-must-pass`
settle with no code-review findings keeps producing the exact same output
as today, including the existing test at `settle.test.ts:1388` (which
already uses the `codeReviewFindingsOverride` test seam to inject
findings into a refused settle and passes without asserting an exact key
set) — that seam is the natural way to drive new tests for this AC.

### AC-2: A refused settle with findings additively preserves them in an immutable per-attempt sibling
Given a settle refuses **and** the now-recorded (AC-1) `codeReview` or
`securityAudit` findings are non-empty
When `writeRefusedSettleSummary` runs
Then it additionally writes an immutable sibling pair at
`.cadence/phases/<phase>/<draftId>-refused-<completedAt-slug>-SUMMARY-snapshot.json`
(and matching `.md`) — a name that deliberately does **not** end in
`-SUMMARY.json`/`-SUMMARY.md`, so `mcp/resources.ts`'s `readdir`+`endsWith`
discovery and `git/diff-strict.ts`'s `-SUMMARY\.json$` regex/pathspec never
pick it up — containing the identical `refusedSummary` content, and the
canonical `<draftId>-SUMMARY.json`/`.md` write is structurally unchanged
from AC-1's shape (existing tests keep passing unmodified; the sibling is
written after the canonical write completes, so a sibling-write failure
can never prevent the canonical record from landing). A refusal with no
findings (e.g. `build-test-must-pass` alone) writes no sibling.

### AC-3: Repeated refused attempts for the same draft never collide with each other
Given N settle attempts occur for the same draft, each refusing with
findings present
When each attempt writes
Then every prior sibling remains on disk untouched — `completedAt` is
produced via an injectable clock seam (mirroring `converge.ts`'s
`now?: () => string`) so tests can assert N distinct, deterministic
filenames rather than relying on real wall-clock spacing — and existing
readers of the canonical path continue reading only the single canonical,
most-recent SUMMARY, never a sibling.

## Boundaries

- Do NOT change `GATE_ORDER` or any gate's pass/refuse/bypass semantics —
  this phase is additive recording + preservation only.
- Do NOT modify `Summary`/`SummaryZ` schema — `codeReview`/`securityAudit`/
  `contentHash` already exist (used by the success path); this phase only
  populates them on the refused path too.
- Do NOT touch `converge.ts` / `ConvergentReviewHistoryEntry` / the
  code-review convergence sidecar (`<draftId>-CODE-REVIEW.json`) — the
  rejected alternative from the SPEC, out of scope.
- Do NOT add a sibling-cleanup or retention/pruning mechanism — explicitly
  deferred per the SPEC's Constraints.
- Do NOT write a sibling on the success path, or for a findings-free
  refusal — scope is refused-with-findings only.
