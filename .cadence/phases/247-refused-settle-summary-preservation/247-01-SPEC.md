# 247-01 — Preserve refused-settle findings: additive per-attempt SUMMARY sibling

## Objective

Fix two compounding gaps so a refused settle's findings actually survive:
first, `writeRefusedSettleSummary` never records the `codeReview`/
`securityAudit` findings that caused the refusal in the first place
(they're computed and merged into `acc` but silently dropped before the
write); second, even once recorded, a later settle attempt for the same
draft overwrites that record. Fix both — record, then protect.

## Context

**Revision note (2026-08-01).** The first draft of this SPEC assumed
`writeRefusedSettleSummary` already persists `codeReview`/`securityAudit`
findings and framed the whole problem as "a later attempt overwrites
them." An independent fresh-context review, verified against source
before accepting it, found that premise false: **`writeRefusedSettleSummary`
never received the findings at all**, on any attempt, ever — there was
nothing for a later attempt to overwrite. The real, more fundamental gap
comes first.

**Verified: `writeRefusedSettleSummary` drops `acc` entirely.**
`packages/core/src/services/settle.ts`: the function's signature (~751-759)
takes `gates` but not `acc`; its `Summary` literal (~761-777) has no
`codeReview`/`securityAudit` keys; its call site (~1357-1359) destructures
`const { acc, refused, gates } = await runSettleGates(ctx)` and passes only
`gates`, never `acc`, into the write. Meanwhile the code-review gate
returns `summaryPatch: { codeReview: identifiedFindings }` on **both** its
pass and refuse return paths (`gates/code-review.ts`), `registry.ts`'s
`mergeInto(acc, res)` applies that patch *before* the refuse short-circuit,
and the success path reads exactly this back out
(`codeReviewFindings = acc.codeReview`, `settle.ts:838`; spread
conditionally into the final `Summary` at ~1132). The refused path throws
all of that away. Same shape for `securityAuditFindings = acc.securityAudit`
(`settle.ts:839`).

**So the original framing had it backwards.** Every refused settle in this
repo's history has an empty-of-findings SUMMARY, findings or not — there
was never anything to lose to an overwrite because nothing was ever
written. This phase must first thread `acc.codeReview`/`acc.securityAudit`
into `writeRefusedSettleSummary` (mirroring the success path's conditional
spread exactly), and only then does the originally-reported
overwrite-by-a-later-attempt problem have real content to protect —
so the additive per-attempt sibling from the first draft is still the
right second half of the fix, now sequenced correctly behind the recording
fix.

**Why this still needs fixing now, not deferred like `dec-20260801-003`:**
unchanged from the first draft — the fix must land before real-provider
dogfooding begins, because the first genuine reloop pair (attempt-1-fails
/ attempt-2 pair under a non-mock provider) is exactly the evidence
`dec-20260801-003`'s trigger is waiting to observe, and it would otherwise
never even be recorded (gap 1), let alone survive a second attempt
(gap 2).

**Extending the shared convergence sidecar to carry finding text remains
rejected, now on stronger grounds.** `ConvergentReviewHistoryEntry` /
`runConvergentReview` (`packages/core/src/verify/converge.ts`) tracks
`{ at, pass, findingsCount, provider, model?, verdict, bypassed? }` per
attempt — a count, never finding text — and is shared across 4 call sites
(`plan-review`, `code-review`, `spec-approve` ×2). Independent review
found the "shared primitive" framing alone wasn't quite the reason (the
sidecar's `sidecarJson` is a plain `Record<string, unknown>` that
`code-review.ts` serializes itself, so a code-review-only field
technically wouldn't require touching the shared primitive) — the
load-bearing reason is that it isn't general: a `coverage` or
`build-test-must-pass` refusal writes a refused SUMMARY with no
code-review sidecar involved at all. Once gap 1 is fixed, there's a
sharper reason still: `SUMMARY` is where every gate's findings already
live uniformly (both `codeReview` and `securityAudit`), so a code-review-
specific side-channel would be the wrong shape regardless of feasibility.

**Verified: the sibling fix must be additive, not a path change.** Tests
assert the refused SUMMARY lands at the canonical path
(`packages/core/tests/services/settle.test.ts:370,713,1413`), and readers
include `packages/core/src/verify/phase-replay.ts`,
`packages/core/src/cli/commands/summary.ts`, `packages/core/src/mcp/resources.ts`
(discovers by `readdir` + `endsWith('-SUMMARY.json'|'-SUMMARY.md')` +
`.sort().at(-1)`), and `packages/core/src/git/diff-strict.ts`
(regex `([^/]+)-SUMMARY\.json$` + a `.cadence/phases/*/*-SUMMARY.json` git
pathspec, feeding `verify --changed`). Redirecting the canonical write
would break all four. The sibling naming below is safe against every one
of these **only because it does not end in the literal suffix
`-SUMMARY.json`/`-SUMMARY.md`** — this is a load-bearing constraint below,
not an accident to leave implicit.

**Naming and clock seam.** The sibling name derives from `completedAt`,
already computed. Independent review flagged that `completedAt` is
produced by an inline `new Date().toISOString()` with no injectable clock
(unlike `converge.ts`'s existing `now?: () => string` precedent) — making
"N attempts produce N distinct siblings" untestable deterministically, and
theoretically collidable if two attempts land in the same millisecond.

**Verified: the seam needs a real route from tests, not just a new
parameter on a private function.** `writeRefusedSettleSummary` is
module-private — `settle.ts` exports only `SettleArgs`,
`detectForeignCadenceBinary`, `resolveForeignBinaryFacts`, and
`settleService`, and every settle test drives `settleService(cwd, opts,
io)`. A follow-up review caught that adding `now?` to the private function
alone is unreachable from any test. The seam belongs on **`SettleArgs`**
(already the exported, test-facing options bag — same pattern as its
existing `verifier?: VerifierProvider` override) as an optional `now?: ()
=> string`, defaulting to `() => new Date().toISOString()` when absent,
and threaded to both `completedAt` computations — the refused path *and*
the success path, so the two stay symmetric rather than only one becoming
test-injectable.

**Scope refinement: sibling only when there's something to preserve.**
Independent review's git-history point: `.cadence/phases/**` is committed
under the single-commit settle convention, so an unconditional sibling on
every refusal (including e.g. a `build-test-must-pass` refusal with zero
review findings) would permanently commit an empty-of-findings file for
no reason. Scoping the sibling write to "only when `codeReview` or
`securityAudit` findings are present" both bounds growth to meaningful
cases and matches the sibling's actual purpose (preserving finding text),
without needing any cleanup mechanism.

## Acceptance Criteria

### AC-1: A refused settle records the findings that caused it
Given a settle refuses after `code-review` and/or `security-audit` ran and
accumulated findings into `acc` (regardless of which specific gate's
refusal triggered the write — an earlier gate may have passed only via
`--force`/`--allow-code-review-failure` while a later gate is what
actually refuses)
When `writeRefusedSettleSummary` runs
Then the written `refusedSummary` conditionally includes `codeReview`/
`securityAudit` (mirroring the success path's
`...(codeReviewFindings ? { codeReview: codeReviewFindings } : {})` shape
at `settle.ts:~1132` exactly), **and when (and only when) those findings
are non-empty** it also gets a `contentHash` computed the same way the
success path computes one (`settle.ts:~1146`) — closing the "refused
summaries aren't tamper-evident" gap independent review flagged, scoped
to exactly the case that needs it (a findings-bearing record worth being
tamper-evident) so it does not contradict the "no new keys on a
findings-free refusal" constraint below. A refused `build-test-must-pass`
settle with no code-review findings keeps producing the exact same output
as today, including the existing test at `settle.test.ts:1388` (which
already uses the `codeReviewFindingsOverride` test seam to inject
findings into a refused settle and passes without asserting an exact key
set) — that seam is the natural way to drive new tests for this AC.

### AC-2: A refused settle with findings additively preserves them in an immutable per-attempt sibling
Given a settle refuses **and** the now-recorded (AC-1) `codeReview` or
`securityAudit` findings are non-empty
When `writeRefusedSettleSummary` runs
Then it additionally writes an immutable sibling pair at
`.cadence/phases/<phase>/<draftId>-refused-<completedAt-slug>-SUMMARY-snapshot.json`
(and matching `.md`) — a name that deliberately does **not** end in
`-SUMMARY.json`/`-SUMMARY.md`, so `mcp/resources.ts`'s `readdir`+`endsWith`
discovery and `git/diff-strict.ts`'s `-SUMMARY\.json$` regex/pathspec never
pick it up — containing the identical `refusedSummary` content, and the
canonical `<draftId>-SUMMARY.json`/`.md` write is structurally unchanged
from AC-1's shape (existing tests keep passing unmodified; the sibling is
written after the canonical write completes, so a sibling-write failure
can never prevent the canonical record from landing). A refusal with no
findings (e.g. `build-test-must-pass` alone) writes no sibling.

### AC-3: Repeated refused attempts for the same draft never collide with each other
Given N settle attempts occur for the same draft, each refusing with
findings present
When each attempt writes
Then every prior sibling remains on disk untouched — `completedAt` is
produced via an injectable clock seam (mirroring `converge.ts`'s
`now?: () => string`) so tests can assert N distinct, deterministic
filenames rather than relying on real wall-clock spacing — and existing
readers of the canonical path continue reading only the single canonical,
most-recent SUMMARY, never a sibling.

## Constraints

- **Additive only.** No change to `GATE_ORDER`, no change to any gate's
  pass/refuse/bypass semantics. `SummaryZ`'s `codeReview`/`securityAudit`/
  `contentHash` fields already exist (used by the success path); AC-1 only
  populates them on the refused path too, using the identical existing
  shape. A refusal with no findings produces the exact same output as
  today (no sibling, and the summary gains no new keys).
- **Refused-path only for the sibling.** The success path does not need
  one: a successful settle is the final record for that draft, and the
  loop advances to a new `activeDraft` afterward, so there is no future
  overwrite to protect against on the success path.
- **Sibling name must never end in `-SUMMARY.json` or `-SUMMARY.md`.**
  Load-bearing against `mcp/resources.ts` and `git/diff-strict.ts`
  (both cited above) silently picking up a refused snapshot as if it were
  the canonical SUMMARY.
- **Filesystem-safe naming.** The `completedAt`-derived slug must not
  contain `:` (Windows path-illegal); replace `:`/`.` in the ISO timestamp
  with `-`. Example: `2026-08-01T21:39:22.923Z` →
  `2026-08-01T21-39-22-923Z`. CI runs Windows as a real matrix leg — not
  optional.
- **Bounded growth by construction.** Scoping the sibling to
  "findings present" (not every refusal) means a broken loop that refuses
  repeatedly on, say, `build-test-must-pass` alone accumulates zero
  siblings. A loop that repeatedly fails code-review does accumulate one
  small pair per attempt; accepted as-is, matching the first draft's
  reasoning — these are small, git-committed-but-inspectable files, not a
  runtime resource, and no cleanup mechanism is in scope for this phase.
- **Best-effort, never blocking, canonical-write-first.** Matches the
  existing precedent in this file exactly: the retro-digest block
  (`settle.ts:~1156-1170`) and phase 242's findings-routing block
  (`settle.ts:~1181-1218`) both wrap their side-effect in `try/catch` with
  an `io.err('note: ... — ${msg}\n')` notice on failure, never blocking or
  changing settle's exit code. The sibling write gets the same wrapper;
  the canonical write stays a bare `await` (as it is today) and always
  happens first, so a sibling-write failure can never mask or replace the
  canonical record.
- **Paired doc edits for the now-conditional refused-path `contentHash`.**
  Four existing statements assert or imply that only a normal-completion
  SUMMARY ever gets a content hash, and all four become stale the moment
  AC-1 ships: `packages/core/src/services/summary-verify.ts:15` (JSDoc),
  the user-facing string in `packages/core/src/cli/commands/summary.ts:168`,
  `docs/reference/commands.md:2567`, and `docs/concepts.md:183`. Per the
  repo's Doc Drift convention these are a paired edit with the code change,
  not a follow-up.
