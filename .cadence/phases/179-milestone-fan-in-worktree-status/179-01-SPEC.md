# 179-01 — Milestone fan-in: worktree status/reconciliation command

## Objective

External proposal (lumen2 session, grounded against cadence@05f1162/v1.37.0)
split the original idea into two independent halves — fan-out (provision N
sibling worktrees + emit N agent-prompt-shaped hand-off prompts) and fan-in (a
status/reconciliation command consuming phase 142's
`gatherHandoffCandidates`/`liveLoopPosition` to show which of a milestone's
parallel phases have settled). This SPEC is scoped to **fan-in only**
(Option C from the proposal): add a read-only command that maps a milestone's
phases to known sibling worktrees and reports each one's live loop position,
replacing N manual `cadence status` round-trips with one. Fan-out (Option A —
a new, side-effecting `cadence milestone worktrees` subcommand that runs `git
worktree add` on the operator's behalf) is explicitly deferred to a future
milestone pending its own cost/benefit pass; do not build it here. Full
writeup: ~/cadence-parallel-phase-worktree-agents-proposal.md

## Acceptance Criteria

### AC-1: Reconciliation command reports live loop position per milestone phase
Given a milestone with N phases that have each been provisioned in their own
sibling worktree and dispatched independently
When the operator runs the new status/reconciliation command against that
milestone id
Then it lists each of the milestone's phases with its owning sibling
worktree (if any) and that sibling's live loop position (via phase 142's
`gatherHandoffCandidates`/`liveLoopPosition`), so a phase whose position is
`IDLE` with itself as `activePhase` reads as settled/merge-candidate and a
phase still `BUILD`/`SPEC`/`DRAFT` reads as in-progress — without the
operator manually `cd`-ing into each worktree.

## Constraints

- Read-only: this command must not write `state.json`, transition the loop,
  or create/modify any worktree — it only reads sibling worktree state via
  existing primitives (`listSiblingWorktrees`, `gatherHandoffCandidates`).
- Fan-out (automated worktree provisioning + prompt generation) is out of
  scope for this SPEC — see Objective.
- Milestone touches documentation surfaces — spec/doc drift risk
  (`docs/reference/commands.md` + the `milestone` family's "read-narrow"
  framing need a paired update since this may be its first non-`propose`
  read command).

## Open Questions

- Command home: a new `cadence milestone status <id>` subcommand, or a
  `cadence doctor` check alongside the existing `worktree-phases` check?
  The proposal leans `milestone status` but doesn't lock it.
- Whether "these N phases are independent" needs any machine-checked
  signal here, or stays an operator judgment call (out of scope per the
  proposal, but worth confirming before DRAFT).
