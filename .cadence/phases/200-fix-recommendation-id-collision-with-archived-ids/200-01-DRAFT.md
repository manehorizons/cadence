# 200-01 — Fix: recommendation ID generation can reuse an archived ID

## Objective

`nextRecommendationId` (`packages/core/src/intelligence/store/ids.ts`) computes the next
same-day recommendation ID sequence number only from `ledger.recommendations` (the active
array), never `ledger.archived`. Once every recommendation created on a given day has been
archived (shipped/rejected/etc via `recommendation-archive.ts`), the active array has zero
entries under that day's prefix, so the counter resets to `001` and collides with the very
first recommendation ID issued that day — even though that ID remains permanently referenced
(evidence, assumptions, decisions, milestone links, commit messages, DRAFT files). Fix
`nextRecommendationId` to compute the max sequence number across both `ledger.recommendations`
and `ledger.archived`, closing GitHub issue #248. `RecommendationLedger` is the only one of the
four ledger types with an `archived` bucket (confirmed via `packages/types/src/intelligence.ts`)
— `nextEvidenceId`/`nextAssumptionId`/`nextIntelligenceDecisionId` are unaffected by design and
must not be touched.

## Acceptance Criteria

### AC-1: an already-archived same-day ID is never reissued
Given a recommendation ledger where every recommendation created on a given day has been moved
from `recommendations` into `archived` (leaving zero active entries under that day's prefix)
When a new recommendation is created on that same day
Then its assigned ID's sequence number is one greater than the highest sequence number found in
either `recommendations` or `archived` for that day's prefix — never a reused ID

### AC-2: non-collision behavior is unchanged
Given a recommendation ledger with active (non-archived) entries under the current day's prefix
When a new recommendation is created that same day
Then the assigned ID's sequence number is exactly one greater than the highest active sequence
number, matching pre-fix behavior

### AC-3: test suite passes
Given the fix and regression tests are in place
When `pnpm --filter @manehorizons/cadence-core test` runs
Then it exits successfully with no failing tests

## Boundaries

- DO NOT change `nextEvidenceId`, `nextAssumptionId`, or `nextIntelligenceDecisionId` — their
  ledgers have no `archived` bucket, confirmed via `packages/types/src/intelligence.ts`.
- DO NOT retroactively renumber or deduplicate IDs that already collided in existing project data.
- DO NOT change the archive/unarchive lifecycle itself, only the ID-generation function.
- DO NOT add CLI/UI messaging about collisions — this is a pure ID-generation correctness fix.
