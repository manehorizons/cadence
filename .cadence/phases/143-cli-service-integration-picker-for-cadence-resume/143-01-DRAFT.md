# 143-01 — CLI/service integration + picker for cadence resume

## Objective

Wire phase 142's `gatherHandoffCandidates` core into `cadence resume`'s CLI/service layer — a TTY-aware picker, `--list`/`--pick`/`--path`/`--local` flags, a `resume` config block, and a read-only sibling-resume path — while keeping today's single-worktree behavior byte-for-byte unchanged.

## Acceptance Criteria

### AC-1: single-candidate behavior is byte-identical to today
Given a repo with only a local resumable handoff (no siblings with candidates), or `resume.crossWorktree: false` in config, or the `--local` flag
When `cadence resume` runs
Then its output is byte-identical to the pre-phase-143 baseline — no candidate-gathering, no nudge, no menu

### AC-2: 2+ candidates nudges but still resumes local by default
Given a repo with a local candidate and one or more sibling worktrees that also have resumable handoffs, and `resume.autoList` at its default (`false`)
When bare `cadence resume` runs (no `--list`/`--pick`/`--path`)
Then it resumes the local candidate exactly as today plus prints one stderr nudge naming the candidate count and pointing at `--list`

### AC-3: --list renders all candidates without picking
Given 2+ handoff candidates across worktrees
When `cadence resume --list` runs
Then it returns/renders every candidate (menu text in text mode, full array under `--json`) and resumes nothing

### AC-4: --pick/--path resolve directly and skip the menu
Given 2+ handoff candidates
When `cadence resume --pick <n>` or `cadence resume --path <p>` runs
Then it resolves the named candidate directly, with no interactive prompt

### AC-5: sibling pick is read-only and clearly labeled
Given a `--pick`/`--list`-selected candidate whose `source` is `sibling`
When resume returns its result
Then the response carries a header naming the sibling's worktree path/branch and a "cd there to act on it" hint, local `state.session.lastHandoff` is never stamped to the foreign doc, and no file under either worktree's `.cadence/` is written (a before/after snapshot test asserts this)

### AC-6: --full on a sibling candidate skips live context recompute
Given a `--pick`ed sibling candidate combined with `--full`
When resume assembles its response
Then it returns the full doc text but `context` is `null` with a hint to `cd` and re-run `--full` there — `runContext` is never invoked against a foreign root

### AC-7: non-TTY never hangs; TTY prompts interactively
Given 2+ candidates and no `--pick`/`--path`
When `cadence resume --list` (or `resume.autoList: true`) runs in a non-TTY environment
Then it prints the candidate list and exits cleanly without blocking on input; in a TTY it prompts for a pick using the existing `resolveInteractivity` seam

### AC-8: resume config block is wired end-to-end
Given `.cadence/config.json`
When a project sets `resume.crossWorktree` or `resume.autoList`
Then both flow through to `cadence resume`'s behavior (AC-1/AC-2) and default to `{ crossWorktree: true, autoList: false }` when unset. (Schema-only, matching the `phaseGuard`/`handoff.retain`/`logging` precedent — those blocks are also absent from `config edit`'s wizard catalog and `config explain`'s field rows, which are curated to a different, smaller field set; `resume` need not appear there either.)
