# 290-01 — Packs Slice 1: manifest resolve and validate

## Objective

Add a PackManifest schema, a resolvePacks() resolver, and a cadence doctor check reporting whether each enabled pack resolves -- with zero behavioral effect on gate computation. Proves I-1/I-2/I-4a from docs/packs-design.md without touching gatesFor/effectiveGateSet's output for any existing fixture.

## Acceptance Criteria

### AC-1: PackManifest schema validates shape and id grammar, fail-closed
Given a Zod schema PackManifestZ added to packages/types/src/pack.ts
When a manifest object is parsed
Then a well-formed manifest (id matching the grammar ^@?[scope]/[name]$ -- bare cadence/name today, @scope/name reserved for third-party per dec-20260822-017, semver version, optional integrity/skillAudit.required/gates[].add/commands) validates; a manifest missing id/version, a non-grammar id, or any key outside this allowlisted shape is rejected -- the schema is .strict() (deliberately fail-closed; a future v2 field is a schema-version concern, not this slice's, per dec-20260822-018's additive-integrity precedent)

### AC-2: resolvePacks resolves local packs, never throws
Given config.packs.enabled lists pack ids and .cadence/packs/<id>/pack.json files exist, are missing, or are invalid on disk
When resolvePacks(repoRoot, config) is called
Then each enabled id resolves to {id, source:'local', manifest} on success or {id, source:'local', error:<reason>} on missing-file/invalid-JSON/schema-failure -- the function never throws for any single pack's failure and one pack's failure never blocks another's resolution

### AC-3: disabled wins over enabled on id collision
Given a pack id present in both config.packs.enabled and config.packs.disabled
When resolvePacks is called
Then that id is excluded from the resolved set entirely, per dec-20260822-024

### AC-4: cadence doctor reports resolved/unresolved packs at warning severity
Given zero or more enabled packs, some resolvable and some not
When cadence doctor runs
Then it emits a packs check reporting which enabled packs resolved and which didn't (with reason) at warning severity -- never error in this slice per dec-20260822-025's phase-1 behavior -- and reports ok with no warning when zero packs are enabled

### AC-5: doctor-check doc row and doc-content test for the new check
Given docs/reference/commands.md's doctor-check table and packages/core/tests/docs/cli-reference.test.ts's per-check test pattern (e.g. 268-01/AC-3, 277-01/AC-4 style)
When this slice ships
Then the table gains a packs row describing the check and its warning severity, and a new dedicated test (following the established per-check pattern, not a manual assertion) asserts the doc documents it

### AC-6: zero behavioral effect on gate computation, falsifiably proven
Given the full existing gatesFor/effectiveGateSet test suite
When this slice's changes are applied
Then (a) gatesFor and effectiveGateSet output is byte-identical for every existing fixture, and (b) a new structural test asserts no file under packages/core/src/gates/** or packages/core/src/services/** imports anything from packages/core/src/packs/** -- a falsifiable absence-of-coupling assertion, not a same-output check that would trivially pass against an empty implementation too

- Do NOT implement `'registry'`/`'remote'` source resolution -- local only in this slice.
- Do NOT implement `commands[]` doctor-checking -- Slice 4 (rec-20260822-012), stretch/optional.
