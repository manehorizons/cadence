# 223-01 — Content-hash provenance for SUMMARY.json

## Objective

Give SUMMARY.json a settle-time content hash and a `cadence summary verify` command, so a hand-edited settled artifact is detectable instead of rendering faithfully as if it were genuine. Scope is detection only (dec-20260726-001): no signing, no keys, no new settle-time gate — full cryptographic signing is deferred to rec-20260726-001, gated on the parked threat-model rec.

## Acceptance Criteria

### AC-1: settle records a content hash
Given a phase settles and SUMMARY.json is written
When `cadence settle run` completes
Then the written SUMMARY.json carries a `contentHash` field (algorithm + hex digest) computed over the settled content, and `summary render` displays it

### AC-2: tamper detection
Given a settled SUMMARY.json whose content is hand-edited after the fact (the stored `contentHash` is now stale relative to the content)
When `cadence summary verify <phase> <num>` runs against it
Then it reports a MISMATCH (non-zero exit) instead of silently treating the file as valid

### AC-3: pre-existing summaries degrade honestly
Given a pre-phase-223 SUMMARY.json with no `contentHash` field
When `cadence summary verify <phase> <num>` runs against it
Then it reports "no hash present — unverifiable" as a distinct outcome, not a false MATCH or a crash

## Tasks

### T1: Add the contentHash field to the Summary schema
- files: `packages/types/src/summary.ts`, `packages/types/tests/summary.test.ts`
- action: add an optional `contentHash: { algorithm: 'sha256', value: string }` field to `SummaryZ` (additive/back-compat per house convention — `.optional()`, existing SUMMARY.json fixtures keep parsing unchanged)
- verify: schema tests confirm both a record with and without `contentHash` still parse
- done: AC-1

### T2: Compute and attach the hash at settle time
- files: `packages/core/src/services/settle.ts`, `packages/core/src/render/summary-md.ts` (or wherever `renderSummaryMd` lives), `packages/core/tests/services/settle*.test.ts`
- action: after building the `summary` object and before the `atomicWriteJSON`/`atomicWriteText` pair at `settle.ts:649-651`, compute a sha256 hex digest over a canonical (stable-key-order) JSON stringification of `summary` — excluding the `contentHash` field itself — and attach it as `summary.contentHash` before both writes; render the hash (or a short prefix of it) in the human SUMMARY.md output. Export the canonicalization + digest function from a shared location (not inlined in `settle.ts`) so T3 imports the same logic instead of re-deriving it
- verify: a settle-run test independently recomputes the same canonical digest from the written SUMMARY.json's other fields and asserts it matches the stored `contentHash.value`
- done: AC-1
- depends: T1

### T3: Add `cadence summary verify <phase> <num>`
- files: `packages/core/src/cli/commands/summary.ts`, `packages/core/src/services/summary-render.ts` (or a new `summary-verify.ts` pure function alongside it), `packages/core/tests/cli/summary*.test.ts`
- action: a pure function reads the on-disk SUMMARY.json, recomputes the canonical digest the same way T2 did (same exclusion of `contentHash`), and returns one of MATCH / MISMATCH / NO_HASH; the CLI subcommand prints the verdict and exits non-zero only on MISMATCH (NO_HASH is a clean, non-failing "unverifiable" notice — this repo's "no silent fallback" rule from CLAUDE.md applies: NO_HASH must be loud, not swallowed)
- verify: unit tests cover all three verdicts, including a MISMATCH fixture built by hand-editing a settled SUMMARY.json's `taskResults` after the fact and leaving `contentHash` stale
- done: AC-2, AC-3
- depends: T2

## Boundaries

- DO NOT implement signing, keys, or any external trust root here — that is rec-20260726-001, explicitly deferred behind the parked threat-model rec (mil-rec-rec-20260712-016) per dec-20260726-001.
- DO NOT make settle itself refuse or gate on a hash mismatch of a *prior* phase's SUMMARY — this phase adds detection tooling only, not a new settle-time gate.
- DO NOT write the hash into `.cadence/state.json` or `STATE.md` — both are gitignored/per-worktree; the hash must live in the committed `SUMMARY.json` so a PR reviewer on a fresh checkout can verify it.
- DO NOT change the on-disk shape/meaning of any existing `Summary` field — `contentHash` is additive only.
