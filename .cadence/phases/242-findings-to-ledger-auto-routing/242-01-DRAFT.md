# 242-01 — Findings-to-ledger auto-routing

## Objective

Route code-review findings into the recommendation ledger at settle time, per the source design doc's §7.3 (docs/handoffs/cadence-phase0-assurance-kernel-review.md) and phase 236's ROADMAP.md 'As built' amendment. Each identified finding (one carrying the stable id phase 236 computes) becomes a Recommendation sourced as 'review' with a cadence-artifact Evidence entry pointing at the settle that raised it. Routing is keyed on Finding.id so a re-settle of an unchanged phase never mints a duplicate entry for the same finding, and one scout id covers a whole settle's batch of routed findings rather than one per finding. Findings without a stable id (security-audit findings, which do not have identity wired yet) are skipped, not force-routed. This is a settle-time writer only: no new gate, no GATE_ORDER change, no refusal semantics, and no disposition-mutation CLI (accept/waive/fix/supersede stays a follow-on phase's surface, per phase 236's own boundary).

## Acceptance Criteria

### AC-1: identified code-review findings route to the ledger
Given a settle whose code-review gate produced findings that carry a stable `id` (phase 236 identity)
When settle finalizes and writes the SUMMARY
Then each such finding is written to the recommendation ledger as a `Recommendation` with `source: 'review'`, linked to a `cadence-artifact` `Evidence` entry whose `path` is that settle's `<draftId>-SUMMARY.json` file path and whose `summary` text names the phase id, draftId, and SUMMARY `contentHash`

### AC-2: re-settling an unchanged phase does not duplicate ledger entries
Given a phase that was already settled once and had its findings routed
When the same phase is settled again with the same findings (same `Finding.id`s)
Then no new `Recommendation` is created for any finding whose id was already routed in a prior settle

### AC-3: findings without stable identity are deliberately excluded, not force-routed
Given a settle whose findings include at least one without a stable `id` (e.g. a security-audit finding, which does not have identity wired in yet)
When the routing step runs
Then that finding is excluded from routing without crashing or minting a ledger entry from a fabricated identity — this is expected, routine filtering rather than a failure (AC-5 governs failures), so it prints no stderr notice of its own

### AC-4: one scout id per settle batches its routed findings
Given a settle that routes two or more findings in the same run
When the routing step creates their `Recommendation` entries
Then all of them share one freshly-minted `scoutId` (the existing `scout-YYYYMMDD-HHMM` convention) rather than each finding minting its own

### AC-5: routing failures never block or fail settle, and are never silent
Given the routing step throws (e.g. a ledger write fails)
When settle runs to completion
Then settle still reports its normal success outcome and writes its SUMMARY, and a stderr notice naming the failure is printed (matching the existing `io.err('note: retro artifact failed to write — ...')` precedent in `finalizeAndCloseSettle`) — never a bare, silent `catch {}`

### AC-6: gate behavior is byte-for-byte unchanged
Given the full settle gate sequence
When this phase's changes are applied
Then `GATE_ORDER`, every gate's pass/refuse verdict, and existing refusal reasons are unchanged — this phase adds no gate and changes no outcome

### AC-7: findings that collide on identity within one settle merge, with the collision recorded
Given two or more findings in the same settle whose `Finding.id` is identical (rec-20260731-001's known collision: same file/anchor/severity/normalized-message, no occurrence discriminant)
When the routing step runs
Then they route as a single `Recommendation`, and that entry's evidence/summary explicitly records the occurrence count — never silently minting one entry with no trace of the collapsed duplicates, and never minting N separate entries for one id (`dec-20260731-001`)

## Boundaries

- DO NOT implement disposition mutation (accept / waive / fix / supersede) — that stays a follow-on phase's CLI surface, per phase 236's own boundary.
- DO NOT wire finding identity into security-audit findings in this phase — skip un-identified findings rather than inventing identity for them here (that is separate, undecided scope).
- DO NOT add a new gate or change `GATE_ORDER` — this is a settle-time writer, not a gate; no new refusal semantics.
- DO NOT let a routing failure block, refuse, or silently swallow its error — it must degrade the same way the existing retro-digest/auto-archive steps do, and it must always print a stderr notice on failure (AC-5).
- DO NOT touch `computeFindingId` / `finding-identity.ts`'s hash inputs to resolve rec-20260731-001 — per `dec-20260731-001`, the collision is resolved by merge-by-identity plus an occurrence count in the routed evidence, not by changing the identity hash.
- DO NOT reconcile the `dec-20260730-001` decision-id collision or any rec-id divergence between this arc and `main` — out of scope for this phase, tracked separately in the arc's handoff.
- DO NOT touch `GATE_ORDER`, coverage-gate scoping, or anything already shipped in phases 232–241 outside the ledger/recommendation-store/config files named above.
- DO NOT trust a green `coverage` gate on this arc branch at face value — it predates phase 239's phase-qualified AC-token scoping (rec-20260729-004; phase 239 landed only on `main`, not merged into this arc yet), so a bare `AC-N` token can be trivially satisfied by an unrelated past phase's test.
