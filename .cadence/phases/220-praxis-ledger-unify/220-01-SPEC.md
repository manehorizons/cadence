# 220-01 — Deepen the Praxis ledger into one module

## Objective

Replace the five subject ledgers' (recommendations, evidence, assumptions, decisions, milestones) independently hand-rolled read/write and id-minting logic with one shared module, so a fix or safeguard added for one subject (e.g. the Phase 219 cross-ledger id-collision check) applies to all five instead of needing to be re-patched per subject — while genuinely bespoke per-subject transition logic (recommendation promotion, archive/unarchive, decision supersession) stays subject-specific on top of the shared primitives rather than being forced into one generic shape it doesn't fit.

## Acceptance Criteria

### AC-1: One shared module backs read/write/id-minting for all five subjects
Given the five subject ledgers (recommendations, evidence, assumptions, decisions, milestones)
When any subject reads its ledger file, writes it back, or mints a new id
Then that path runs through one shared module rather than five independent hand-rolled implementations — each subject's existing read/write/mint functions keep their current names and signatures as thin wrappers over it, so the ~13 existing callers outside `store/` and `cli/commands/` (`services/settle.ts`, `draft-new.ts`, `milestone-propose.ts`, `progress.ts`, `spec-new.ts`, `doctor/run.ts`, `intelligence/context.ts`, `inspect.ts`, `recommend.ts`, `cli/commands/next.ts`, `retro.ts`, `intelligence.ts`) continue to work unchanged. Bespoke subject-specific transition logic (recommendation promotion, archive/unarchive, decision supersession) is explicitly NOT required to collapse into one generic transition function — see Constraints.

### AC-2: Cross-ledger id-collision safeguard applies to all four id-minting subjects
Given a dangling cross-reference in a related ledger — a recommendation id inside `evidence[].recommendationId`, an assumption id inside `recommendation.assumptionIds[]`, a decision id inside `recommendation.decisionIds[]`/`supersededBy`/`supersedes`, or an evidence id inside `recommendation.evidenceIds[]` — whose number is higher than the owning ledger's own current max
When a new recommendation, evidence, assumption, or decision record is minted
Then the new id is computed with the same cross-ledger-max safeguard Phase 219 added for recommendations, using the per-subject cross-reference source named above — milestones mint no sequence id at all (their ids are cluster-derived, `mil-grp-<slug>`/`mil-rec-<recId>`) and are out of this AC's scope entirely

### AC-3: Milestones ledger reaches parity with the other four in reconcile/audit/stats
Given a milestone whose `recommendationIds[]` includes an id that exists in neither the recommendations ledger's live nor archived array (a milestone referencing a merely-archived, still-recoverable recommendation is NOT a broken reference — archived is recoverable via `unarchive`)
When `cadence intelligence audit` runs
Then it reports the broken reference as a new `orphan-milestone` finding kind alongside the existing eight (`AUDIT_KINDS`, `--filter-kind` validation, and `render-intelligence-audit.ts`'s section order all include it); `cadence intelligence reconcile`'s result (including its `--json` shape) and `computeIntelligenceStats`/`render-intelligence-stats.ts` include milestones alongside the other four subjects; and `docs/reference/commands.md` is updated in the same commit — both the "4 intelligence ledgers" count (3 occurrences) and the "eight finding kinds" list (which needs a ninth) currently go stale otherwise

### AC-4: One shared list/filter pipeline serves recommendation, decision, and assumption CLI commands
Given the `--sort-by`, `--filter-regex`, and `--filter-regex-flags` options exposed by `cadence recommendation list`, `cadence decision list`, and `cadence assumption list`
When a user passes any of them, or an invalid combination
Then all three commands validate through one shared pipeline parameterized by each subject's own sort-key set and command name — regex/flag validation and error wording are identical modulo the `<subject> list failed:` prefix and each subject's own allowed sort-key list, rather than three independently maintained copies of the validation logic

### AC-5: Existing on-disk ledgers keep reading correctly
Given the current `.cadence/intelligence/*.json` ledger files in this repo (and in any project already using CADENCE)
When the deepened module reads them
Then every existing record parses to a deep-equal value under the current schema — additive-only, no migration step required

### AC-6: Ledger writes stay byte-stable and mode-parity holds
Given a ledger file with no logical change to make
When the deepened module writes it back
Then the output is byte-identical to the pre-refactor writer (property order and formatting unchanged, so `cadence intelligence reconcile` remains byte-idempotent as documented), and `milestones.json` is written with the same `{ mode: 0o600 }` the other four ledger files already receive (currently missing — `store/milestones.ts`'s writer omits it)

## Constraints

- Additive, backward-compatible schema changes only (repo convention) — no migration script, no breaking format change to existing `.cadence/intelligence/*.json` files.
- `decayState` derivation logic (fresh/aging/stale/superseded/contradicted/needs-revalidation) is out of scope — flagged as a related but separate gap in the architecture review, not part of this deepening.
- MCP/CLI service parity (rec-20260725-004) is a separate phase, not bundled into this one.
- `packages/core/src/services/settle.ts`'s own internal multi-concern refactor (a separate recommendation, rec-20260725-007) is out of scope — but `settle.ts` is one of ~13 read-only consumers of the per-subject ledger functions and must keep working unchanged via the preserved thin-wrapper signatures (see AC-1).
- `intelligence/milestone.ts` (milestone clustering + its `applyTransition`) is IN boundary — its transition logic informs the shared module's design and its audit/reconcile/stats hookup is required by AC-3.

**Shared module shape** (resolved design decision, revised after adversarial review found the first sketch didn't fit the real code):

- A `SubjectLedgerSpec<TRec, TLedger, TStatus, TAction, TPayload>` descriptor in a new `packages/core/src/intelligence/store/ledger.ts`, consumed by generic functions (`readLedger`, `writeLedger`, `mintId`) — data + pure functions only, all I/O stays in the generic module (pure core / impure shell).
- `records`/`withRecords` operate on a `{ live, archived }` shape, not a flat array, to accommodate recommendations' two arrays (`recommendations` + `archived`) — other subjects leave `archived` empty and unused.
- **Recommendations + evidence form one composite write unit and keep their existing paired writer.** `writeIntelligenceLedgers` (`store/io.ts`) atomically writes both files and renders `RECOMMENDATIONS.md` from all four non-evidence ledgers read off disk — it stays as-is on top of the shared read/write primitives rather than becoming two independent `writeLedger` calls. `renderMd` (where a subject has one) receives a sibling-ledger bundle (`{ rec, ev, as, dec, mil }`), not just its own ledger.
- `idMint` (optional; `prefix` + `ownIds` + `crossRefIds`) is **omitted entirely for milestones** — see AC-2. Per-subject `crossRefIds` sources: recommendation ← `evidence[].recommendationId`; evidence ← `recommendation.evidenceIds[]`; assumption ← `recommendation.assumptionIds[]`; decision ← `recommendation.decisionIds[]` + `supersededBy`/`supersedes`.
- **Generic `transitions` (`allowed`/`next` + a `guard(ledger, target, payload) → string | null` hook, an optional `patch?(record, payload) → TRec` hook for the optional-key add/delete `exactOptionalPropertyTypes` forces — e.g. decision's `delete updated.supersededBy`) is used only where it actually fits** (assumptions; decisions' straightforward transitions, with the supersession cycle-walk living in `guard`; milestones, whose `applyTransition` result carries an optional `warning` field the generic result type must support). **Recommendation promotion (`applyRecommendationPromotion`) and archive/unarchive stay bespoke, subject-specific functions built on the shared read/write primitives — they are explicitly NOT required to fit the generic `transitions` shape**, since promotion's target status is caller-supplied and gated by `PROMOTABLE_FROM` plus sanctioned exceptions rather than a simple `action → next` lookup, and archive/unarchive move a record between the `live`/`archived` arrays rather than changing a status field in place.
- `notFound` (optional; defaults to a generic message) — recommendations keeps its nearest-id-suggestion formatter (`buildRecommendationNotFoundMessage`).
- `milestones.json`'s missing `{ mode: 0o600 }` write flag is fixed as part of AC-6 (not filed as a separate follow-up) — confirmed still missing at `store/milestones.ts`'s writer vs. the other four writers in `io.ts`; add the missing case to `store/io.test.ts`'s existing platform-guarded mode assertions.
