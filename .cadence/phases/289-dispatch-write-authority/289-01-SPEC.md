# 289-01 — Dispatch write authority: read-only mode is structurally enforced

## Objective

A sub-agent instructed to be read-only must be structurally unable to mutate the intelligence ledger — not merely told not to by the dispatch packet's prose prohibition.

## Acceptance Criteria

### AC-1: Read-only mode refuses ledger mutation
Given read-only mode is active
When `cadence decision add` (and each other ledger-mutating subcommand) runs
Then it exits non-zero with a message naming the mode and the blocked operation, and the ledger file's content hash is unchanged.

### AC-2: The read-only investigation commands keep working unchanged
Given read-only mode is active
When `cadence context handoff`, `cadence recommend`, `cadence inspect`, `cadence recommendation list`, and `cadence next` run
Then each succeeds unchanged, including writing its own derived `.md`/`.json` output. Verified pre-build: none of these five commands' code paths import any store write function (`writeIntelligenceLedgers`, `writeIntelligenceDecisionLedger`, `addIntelligenceDecision`, `runDecisionTransition`, `writeAssumptionLedger`, `addAssumption`, `runAssumptionTransition`, `writeMilestoneLedger`, `runIntelligenceReconcile`, `rerenderRecommendationsMdIfPresent`) — confirmed by an empty grep across all five.

### AC-3: Byte-identical when the mode is inactive
Given the mode inactive (the default, and every existing invocation)
When any command runs
Then behavior is byte-identical to pre-change. Capture fixtures first.

### AC-4: Refusal proven inside a real dispatched child, not just in-process
Given a real dispatched sub-agent with the mode active
When it attempts a ledger write
Then the write is refused inside the child process — proven by an actual dispatch, not unit test alone.

### AC-5: Refusal isn't CLI-surface-only
Given enforcement bound at the store's write functions (D-AH)
When a ledger mutation is attempted by importing the service directly rather than via the CLI
Then it is still refused.

### AC-6: The packet text doesn't overclaim
Given this phase's scoping finding (the mechanism is session-scoped-during-the-window, not fully process-isolated to the child — see Decisions)
When the dispatch packet's prose is updated to describe read-only enforcement
Then it states the mechanism accurately (env-scoped, store-layer refusal) and does not claim isolation stronger than what AC-4/AC-5 actually prove.

## Decisions (pre-resolved by investigation — see `dec-20260822-012` et al. and this session's re-derivation)

- **D-AH — enforcement layer: option 1, the store's write functions** (`packages/core/src/intelligence/store/*.ts`'s ten write entry points), not `atomicWriteText`. Re-derived CMD-C: **28** `atomicWriteText` call sites (not 27 — `packages/core/src/intelligence/milestone.ts:478`, `runMilestoneExport`, was missing from the original handoff's table). **Correction (found during T1's independent review, not accepted at first pass):** the original note here wrote this off as "fine to stay blocked via whatever layer is chosen" — that was wrong. `runMilestoneExport` writes `.cadence/intelligence/exports/<id>/SPEC.md` to disk via `mkdir`+`atomicWriteText` *before* calling the guarded `writeMilestoneLedger` — so under `CADENCE_READ_ONLY=1`, pre-fix, the export file was created successfully and only the subsequent ledger write refused. A real, CLI-reachable mutation would have survived read-only mode. Fixed as part of T1: `assertNotReadOnly('runMilestoneExport')` added as the function's first statement, closing the gap before any I/O runs. CMD-D re-confirmed: the read-only commands (`context`, `recommend`, `inspect`) reference none of the eleven now-guarded write entry points — clean separation.
- **D-AI — scope: ledger only**, not state.json or phase artifacts. Re-verified: none of `context.ts`, `recommend.ts`, `inspect.ts` write `.cadence/state.json` or `STATE.md` — their only `atomicWriteJSON`/`atomicWriteText` calls target their own derived output (`context/<scope>.json`/`.md`, `RECOMMEND.md`/`recommend.json`, `STRATEGY.md`/`inspection.json`).
- **D-AJ — scoping seam: `.claude/settings.json`'s `env` block, with a corrected mechanism.** Empirically tested this session (three live probes against a dispatched sub-agent, using a throwaway `CADENCE_SCOPING_TEST_20260822` key):
  1. **Env does propagate to a subsequently-dispatched sub-agent**, confirming `dec-20260822-012`. A key added to `.claude/settings.json`'s `env` block mid-session was visible in a freshly-dispatched child's `process.env` and shell env.
  2. **Changing an existing key's value propagates live** — a second dispatch after editing the value saw the new value.
  3. **Deleting the key does NOT un-set it** for the remainder of the session — a third dispatch, made *after* the key was removed from the file entirely, still saw the stale value. This held for both the orchestrator's own shell and a freshly-dispatched child.
  4. **Setting the value to an explicit empty string DOES clear it live** — a dispatch after that saw an empty value.

  **Conclusion: the mechanism is a live add/update merge, not a live remove/sync.** The scoping recipe must be "write the active value before dispatch, write an explicit falsy/off value after" — never "delete the key after." A delete-based revert is silently ineffective for the rest of the session. This is a correction to the handoff's literal "set before dispatch and removed after" phrasing and must be called out explicitly in the implementation and the packet text (AC-6).

  **This does not achieve true per-dispatch isolation** in one respect: since the same settings.json `env` block is process-wide, the *orchestrator's own* environment also picks up the value (observed directly in the orchestrating session's own Bash tool). A dispatch sequence of "turn on, dispatch, turn off" is safe only if the orchestrator does not attempt its own ledger writes *between* turning the mode on and turning it back off. That's an achievable discipline for a dispatch call (which is synchronous from the orchestrator's perspective), so option 1 remains viable, but it is session-scoped-during-the-window, not process-isolated-to-the-child — the packet/docs must say so accurately (AC-6).
- **D-AK — packet text**: update it in this phase (not deferred) to state read-only enforcement accurately given the D-AJ finding above — it may name the mechanism (env-scoped, store-layer refusal) but must not claim isolation stronger than what's proven.
- **D-AL — settle.ts's silent catch (found by two rounds of the settle-time deep-verify gate, not by build-time review) is a real AC-1 gap and is fixed in-phase, reversing this SPEC's original plan to defer it.** `cadence settle`'s best-effort advance of a converted recommendation to `settle-pending` (`runAdvanceConvertedToSettlePendingForPhase`, `packages/core/src/services/settle.ts:~1507-1516`) sat behind a bare `try{}catch{}` predating this phase, with no stderr notice on failure — unlike its sibling block ~40 lines above. T1's guard now makes that call throw under `CADENCE_READ_ONLY`, and the bare catch swallowed it: settle would exit 0 while silently failing to advance the rec, which is a real "ledger mutation attempt succeeds/fails silently" gap under AC-1's general wording ("read-only mode refuses ledger mutation"), even though `cadence settle` is not one of AC-1's named example subcommands. First pass (whole-branch review's finding) was handled by filing `rec-20260822-004` and documenting the gap in `commands.md`, judging settle.ts out of this phase's declared boundaries. The settle-time deep-verify gate (host-cli provider, real) refused AC-1 on this same basis twice, including citing the doc note itself as evidence the gap was known and unfixed — that repetition, from an independent gate rather than a single reviewer's opinion, is the signal that out-of-boundary deferral was the wrong call here. Fixed by mirroring the sibling block's pattern (`io.err` notice naming the failure), added to T1's `files:` (`settle.ts` plus `tests/services/settle-ship-ref.test.ts`) rather than left as a separate phase, since the fix is a two-line, success-path-inert addition to code T1 already made newly reachable. `rec-20260822-004` is promoted to `shipped` in this phase's settle rather than left open describing already-fixed code.
- **D-AM — AC-3 amended: `packet.ts`'s rendered text is out of its byte-identity scope.** AC-3 ("byte-identical when inactive... any command runs") and AC-6 (packet prose must change to add the `CADENCE_READ_ONLY` paragraph, unconditionally, whether or not the mode is active) are in direct tension as originally worded — no test can satisfy both simultaneously, since AC-6 mandates exactly the kind of output change AC-3's literal text forbids. This was a plan-time wording gap, not a build defect: the settle-time deep-verify gate caught it twice (`packet.test.ts`'s fixture re-pin, read as an AC-3 violation both times). Resolved as an "As built" amendment to AC-3's Then clause, scoping byte-identity to guarded write entry points and CLI commands and excluding `packet.ts`'s dispatch-prompt text, which AC-6 governs instead. The AC-3 id and its existing SATISFIED coverage are unaffected — this is a text clarification, not new test-writing.
- **D-AO — third revisit to T1: `writeLedger` itself (`packages/core/src/intelligence/store/ledger.ts:63`) was unguarded, found by a real `code-review` gate during D-AN's settle (HIGH severity).** `writeLedger` is the shared low-level primitive under all four subject-specific guarded wrappers (`writeIntelligenceLedgers`, `writeAssumptionLedger`, `writeIntelligenceDecisionLedger`, `writeMilestoneLedger`) — each wrapper calls `assertNotReadOnly` with its own operation name before reaching `writeLedger`, but `writeLedger` itself is exported and directly importable from `ledger.js`, with nothing structurally stopping a caller that imports it directly (bypassing all four wrappers) from mutating any ledger while `CADENCE_READ_ONLY` is set. Verified before fixing: grepped every call site repo-wide — today only the four wrappers and `ledger.test.ts`'s own unit tests call it, so no current caller exploits the gap, but the surface itself contradicted AC-1's "structurally refused at the write layer" claim. Fixed by adding `assertNotReadOnly('writeLedger')` as the function's own first statement (defense-in-depth; a no-op on all four existing call paths, which already guard earlier with more specific messages) — the same shape as T1's original `runMilestoneExport` fix. New direct-import test added to `ledger.test.ts` (which already imports `writeLedger` directly for its own generic-primitive tests, using a fake "widget" subject spec). Operator-approved explicitly ("Yes, authorized to fix and re-settle") before this revisit, since it surfaced only after D-AN's `--force` settle had already completed once.
- **D-AN — settled with `--force`, operator-approved, over a third deep-verify refusal judged empirically false.** After D-AL/D-AM's fixes, a third `settle run --auto --deep` pass (host-cli, real provider) refused AC-2 ("only `context handoff` is cited as exercised") and AC-3 ("cited tests cover only decision add and milestone writing") — both with zero AC-2/AC-3-relevant edits since round 1 (AC-2 passed) and round 2 (AC-3's replacement tests already existed and were unchanged into round 3). Falsified directly: `grep -n "289-01/AC-2:\|289-01/AC-3:" packages/core/tests/intelligence/read-only-mode.test.ts` shows all five AC-2-tagged tests (`context handoff`, `recommend`, `inspect`, `recommendation list`, `next`) and seven AC-3-tagged tests (`decision add`, `recommendation add`, `recommendation list`, `decision supersede`, `assumption add`, `assumption validate`, `milestone propose`, `intelligence reconcile`) present and passing — contradicting both round-3 claims verbatim. Investigated the mechanism before concluding it was verifier unreliability rather than a code bug: `packages/core/src/verify/anthropic-verifier.ts`'s `formatUserMessage` sends every `VerifyTestRef` with no slicing/sampling, and the phase's cumulative diff (~49KB) is well under `verifier.diffCapBytes`'s 256KB default, ruling out truncation as the cause. Filed `rec-20260822-005` (with this investigation as evidence, `ev-20260822-013`) recommending the deep-verify gate not hard-block on a single unreplicated LLM verdict — e.g. require agreement across repeated calls, or surface verdict drift on unchanged evidence as a distinct signal from a genuine regression. Reported the full three-round history and this specific falsification to the operator; settled with `--force` on their explicit instruction ("Do it — settle with force"), not unilaterally. Per the assurance-record design (D-Z era; see `packages/core/src/gates/assurance-record.ts`'s comment on `hasErrorSeverityBypass`), this phase's assurance grade is capped at `mixed` and cannot read `strong` — the real verifier's (disputed) objection is preserved in `SUMMARY.json`'s `deepVerify` field and the bypass is recorded in `gateBypasses`/rendered in `SUMMARY.md`, not hidden.

## Red-fixture proof (pre-build baseline — the failure this phase closes)

Verified in a throwaway scratch repo (`cadence init`), 2026-08-22: `CADENCE_READ_ONLY=1 cadence decision add --title ... --rationale ...` **succeeded** and wrote a new decision to `.cadence/intelligence/decisions.json`, exit 0. No code path today reads `CADENCE_READ_ONLY` (or any other signal) before a ledger mutation — confirmed by grep across `packages/core/src/intelligence/` and `packages/core/src/dispatch/` (zero non-comment hits for read-only/readOnly/READ_ONLY in any write path). This is the pre-change baseline AC-1 must invert.
