# 289-01 — Dispatch write authority: read-only mode is structurally enforced

## Objective

A sub-agent instructed to be read-only must be structurally unable to mutate the intelligence ledger. Enforce a `CADENCE_READ_ONLY` env-gated refusal at the intelligence store's write entry points (D-AH), leave the three read-only investigation commands (`context`, `recommend`, `inspect`) and `recommendation list`/`next` untouched (D-AI/AC-2), document the settings.json env-scoping mechanism accurately including its add/update-live-but-delete-sticky quirk (D-AJ), and update the dispatch packet's prose to claim only what's actually enforced (D-AK/AC-6).

## Acceptance Criteria

### AC-1: Read-only mode refuses ledger mutation
Given read-only mode is active (`CADENCE_READ_ONLY` set to a truthy value)
When `cadence decision add` (and each other ledger-mutating subcommand: `assumption add`, `assumption transition`, `decision`'s transition path, `milestone` ledger writes, `recommendation`'s ledger-affecting subcommands, `reconcile`) runs
Then it exits non-zero with a message naming the mode and the blocked operation, and the ledger file's content hash is unchanged.

### AC-2: The read-only investigation commands keep working unchanged
Given read-only mode is active
When `cadence context handoff`, `cadence recommend`, `cadence inspect`, `cadence recommendation list`, and `cadence next` run
Then each succeeds unchanged, including writing its own derived `.md`/`.json` output (`context/<scope>.json`/`.md`, `RECOMMEND.md`/`recommend.json`, `STRATEGY.md`/`inspection.json`).

### AC-3: Byte-identical when the mode is inactive
Given the mode inactive (the default, and every existing invocation, `CADENCE_READ_ONLY` unset)
When any command runs, ledger-mutating or not
Then behavior (exit code, stdout, ledger file contents) is byte-identical to pre-change, for
every guarded write entry point and CLI command **except** `packages/core/src/dispatch/packet.ts`'s
rendered dispatch-prompt text — AC-6 requires that text to change (to add the `CADENCE_READ_ONLY`
paragraph) regardless of whether the mode is active, so it is out of AC-3's byte-identity scope by
design; see the SPEC's Decisions section for the amendment record. Fixtures captured before the
guard is wired in.

### AC-4: Refusal proven inside a real dispatched child, not just in-process
Given a real dispatched sub-agent (via the `Agent` tool, `--execution dispatch`) with `CADENCE_READ_ONLY` set in `.claude/settings.json`'s `env` block before dispatch
When it attempts a ledger write (e.g. `cadence decision add`)
Then the write is refused inside the child process, proven by capturing the child's actual exit code/output — not a unit test standing in for it.

### AC-5: Refusal isn't CLI-surface-only
Given enforcement bound at the store's write functions
When a ledger mutation is attempted by importing e.g. `addIntelligenceDecision` directly (bypassing the CLI's `decision add` command entirely) with `CADENCE_READ_ONLY` set
Then it is still refused with the same guard, proving the CLI isn't the only enforcement point.

### AC-6: The packet text doesn't overclaim
Given the D-AJ finding that env-block scoping is live-add/update but not live-delete, and that the orchestrator's own environment also sees the value once set
When `packages/core/src/dispatch/packet.ts`'s forbidden-actions prose is updated
Then it accurately describes read-only mode as an available, real enforcement mechanism (naming `CADENCE_READ_ONLY`) without claiming a stronger isolation guarantee (e.g. "fully removed after the dispatch") than what AC-4 actually proves.
