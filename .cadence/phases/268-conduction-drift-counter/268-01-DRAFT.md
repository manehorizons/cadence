# 268-01 — Conduction drift counter

## Objective

cadence doctor's conduction-reachability (phase 251) answers a point-in-time capability question ('can this repo conduct a real finding') but nothing answers the trend question ('has it, lately'). That gap is exactly how 263 settles accumulated under mock with zero escalation in the v1.54 audit. Derive a read-only streak counter from the SUMMARY corpus (consecutive settles with no non-mock verifier identity in provenance), surface it in cadence doctor/status, and escalate severity by streak length.

## Acceptance Criteria

### AC-1: Read-only streak counter derived from the SUMMARY corpus
Given the settled-phase SUMMARY.json corpus under `.cadence/phases/**`
When a read-only, best-effort utility walks it in chronological order
Then it returns the count of consecutive most-recent settles with no non-mock provider identity in `assurance.verifierRollup`, degrading to indeterminate (never throwing) on missing or malformed data, consistent with the phase-208 `phase-freshness` best-effort precedent

### AC-2: DoctorSeverity gains an `indeterminate` rung, all existing consumers unaffected
Given `packages/core/src/doctor/model.ts`'s `DoctorSeverity` type (`'ok' | 'warning' | 'error'`) per `dec-20260810-005`
When it is extended to `'ok' | 'warning' | 'error' | 'indeterminate'`
Then `DoctorReport.ok`'s roll-up boolean, the `fail()` helper family, `packages/core/src/doctor/fix.ts`'s fix-planner classification, and `packages/core/src/cli/commands/doctor.ts`'s CLI/JSON rendering + exit code all handle the new rung explicitly (not via a fallthrough default); `indeterminate` keeps `ok: true` in the roll-up (matching `warning`'s existing treatment, consistent with O.5's warning-not-refusal posture — neither rung fails the repo's exit code), and every pre-existing doctor check's rendered output and exit-code behavior is byte-for-byte unchanged (regression-tested)

### AC-3: Streak surfaced in doctor and status
Given the streak counter from AC-1 and the `indeterminate` rung from AC-2
When `cadence doctor` or `cadence status` runs
Then the current streak value and a human-readable explanation appear in their output, non-blocking — an indeterminate counter renders as `indeterminate` severity with explanatory text, never silently as `ok`

### AC-4: Severity escalates by streak length against a provisional threshold
Given a streak length and a threshold of 3 (borrowed from `dec-20260801-003`'s `config.convergence.maxAttempts` default per `dec-20260810-004`, explicitly marked provisional in both code and rendered output)
When the streak reaches or exceeds the threshold
Then `cadence doctor`'s severity for this check escalates one rung — `ok` → `warning` at threshold; `indeterminate` is orthogonal to this ladder and is never itself escalated by streak length — and this never blocks or refuses a settle (O.5); it is a warning only, with no new refusal path added anywhere in the settle pipeline

### AC-5: Counter is correct against a fixture corpus
Given a fixture SUMMARY.json corpus with a known, hand-computed streak (including a case with a non-mock entry resetting it, and a case with missing/malformed `verifierRollup` data)
When AC-1's counter runs against the fixture
Then its returned streak value matches the hand-computed expectation exactly, including the indeterminate-degrade case
