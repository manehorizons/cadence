# 221-01 — Give the MCP surface real "one engine" parity with the CLI

## Objective

Close three confirmed CLI/MCP parity gaps: `cadence_recommendation_promote`
silently drops the CLI's `--ref` provenance, the milestone-propose
"newly-proposed" predicate is copy-pasted in two files (already caused one
whole-branch-review-caught bug), and `next`/`verify`/`explain` already have
the right `(args, io) -> CommandResult` service shape but are stranded in
`cli/commands/` where MCP cannot reach them.

## Acceptance Criteria

### AC-1: `cadence_recommendation_promote` carries shipped-ref provenance like the CLI does
Given a recommendation is being promoted to `status=shipped` via the
`cadence_recommendation_promote` MCP tool with a `ref` argument supplied
When the tool runs
Then the resulting recommendation's `shippedRef` field is set to the given
value — matching `cadence recommendation promote <id> --status=shipped --ref
"<text>"` — and supplying `ref` when the target status is not `shipped` is
rejected with the same refusal message the CLI already gives, not silently
ignored

### AC-2: The "any newly-proposed milestone" predicate has one definition, not two
Given `cli/commands/milestone.ts`'s `propose` action and
`services/milestone-propose.ts`'s `milestoneProposeService` both need to
detect "did this run produce zero newly-proposed milestones"
When either call site runs after a `milestone propose`
Then both invoke one exported predicate — no two independent
`ledger.milestones.some((m) => m.status === 'proposed')` literals — so a
future change to "newly proposed" semantics cannot fix one call site and
silently leave the other stale

### AC-3: `cadence_next` and the verify/explain MCP tools exist with CLI parity
Given `next.ts`'s `nextService`, `verify.ts`'s `runVerifyCoverage` /
`runVerifyPhase`, and `explain.ts`'s `runExplain` already use the
`(repoRoot, args, io: CommandIO) => Promise<CommandResult>` shape every
other MCP-backed service uses, but live in `cli/commands/` where
`mcp/tools.ts` cannot import them
When that logic is relocated into (or re-exported from) `services/next.ts`,
`services/verify.ts`, and `services/explain.ts`
Then `mcp/tools.ts` registers MCP tools backed by those service modules
(one tool for next, one per verify subcommand, one for explain) producing
output/exit-code parity with their CLI counterparts for the same repo
state, and `docs/mcp.md`'s tool table lists all of them

## Boundaries

- Do NOT change the on-disk shape of `Recommendation`, `MilestoneLedger`, or any other persisted ledger schema.
- Do NOT touch the `handoff`/`resume`/`doctor` MCP services — confirmed during SPEC to already delegate cleanly to a single shared core with no drift; out of scope.
- Do NOT attempt a repo-wide "every CLI command must have a services/ twin" refactor or a general architecture-lint rule — scope is exactly AC-1/2/3 above.
- Do NOT change any CLI-facing output, flag names, or exit codes for `next`/`verify`/`explain`/`recommendation promote`/`milestone propose` — this phase adds MCP parity and removes duplication, it does not change existing CLI behavior.
