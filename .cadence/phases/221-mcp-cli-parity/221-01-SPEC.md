# 221-01 — Give the MCP surface real "one engine" parity with the CLI

## Objective

Close three confirmed CLI/MCP parity gaps in the Praxis-adjacent surfaces — a
silently-dropped `--ref` field, a copy-pasted eligibility predicate that has
already drifted once, and three CLI-only service functions MCP structurally
cannot reach — so the "one engine, three surfaces" thesis holds for these
call paths instead of being two independently-maintained implementations.

## Acceptance Criteria

### AC-1: `cadence_recommendation_promote` carries shipped-ref provenance like the CLI does
Given a recommendation is being promoted to `status=shipped` via the
`cadence_recommendation_promote` MCP tool with a `ref` argument supplied
When the tool runs
Then the resulting recommendation's `shippedRef` field is set to the given
value — matching what `cadence recommendation promote <id> --status=shipped
--ref "<text>"` already produces via the CLI — and supplying `ref` when the
target status is not `shipped` is rejected with the same
"`shippedRef (--ref) is only valid when promoting to shipped`" refusal the
CLI already gives, not silently ignored.

### AC-2: The "any newly-proposed milestone" predicate has one definition, not two
Given `cli/commands/milestone.ts`'s `propose` action and
`services/milestone-propose.ts`'s `milestoneProposeService` both need to
detect "did this run produce zero newly-proposed milestones" (to decide
whether to print the empty-result enrichment)
When either call site runs after a `milestone propose`
Then both invoke one exported predicate (not two independent
`ledger.milestones.some((m) => m.status === 'proposed')` literals) — so a
future change to what counts as "newly proposed" cannot fix one call site
and silently leave the other stale, which is exactly the class of bug a
prior whole-branch review already caught here once (see the existing
comment in `services/milestone-propose.ts`).

### AC-3: `cadence_next`, `cadence_verify`, and `cadence_explain` exist as real MCP tools
Given `next.ts`'s `nextService`, and the equivalent verify/explain command
logic in `cli/commands/verify.ts` / `cli/commands/explain.ts`, already use
the `(repoRoot, args, io: CommandIO) => Promise<CommandResult>` shape every
other MCP-backed service uses, but are defined inside `cli/commands/` where
`mcp/tools.ts` cannot import them without reaching across the CLI/MCP
boundary
When the corresponding logic is relocated into (or re-exported from)
`services/next.ts`, `services/verify.ts`, and `services/explain.ts`
Then `mcp/tools.ts` registers `cadence_next`, `cadence_verify`, and
`cadence_explain` tools backed by those service modules, each producing
output/exit-code parity with its CLI counterpart for the same repo state,
and `docs/mcp.md`'s tool table lists all three alongside their CLI
equivalents.

## Constraints

- Do not change the on-disk shape of `Recommendation`, `MilestoneLedger`, or
  any other persisted ledger schema — this phase is a code-organization and
  drift-closing fix, not a data-model change.
- Do not touch `handoff`/`resume`/`doctor` MCP services — investigation
  during SPEC confirmed those three already delegate cleanly to a single
  shared core (`runHandoff`/`runResume`/`runDoctor`) with no behavior
  divergence; the recommendation that seeded this phase overstated the gap
  there specifically, and re-touching working code is out of scope.
- Do not attempt a repo-wide "every CLI command must have a services/ twin"
  refactor or a general architecture-lint rule in this phase — scope is the
  three confirmed gaps above (AC-1/2/3). A broader convergence sweep, if
  wanted, is a separate future recommendation.

## Open Questions

  authoring (exact file/line evidence in the phase's originating
  recommendation and this session's research), not speculation.
