# 226-01 — Centralize gate bypass and seal policy in the settle driver

## Objective

Close three drifts around `gates.sealed`: `docs/reference/config.md` names only
2 of the 3 gates that actually consult `isGateSealed` (stale since
`boundary-scan` shipped in Phase 156), the remaining ~8 bypassable gates
(`plan-review`, `security-audit`, `deep-verify`, `interactive-verdict`,
`code-review`, `draft-read`, `structural-verifier`, `per-task-verify`) decide
their own bypass semantics with no declared policy or seal support, and
`registry.ts`'s per-gate provenance only records *why a gate was skipped* for
`test-coverage`'s bypass — not `build-test-must-pass`'s or `boundary-scan`'s.

## Acceptance Criteria

### AC-1: docs/reference/config.md lists every gate that consults gates.sealed
Given `docs/reference/config.md`'s `gates.sealed` section currently states
"only two gate ids currently check `gates.sealed`" (naming `test-coverage`
and `build-test-must-pass` only)
When `boundary-scan` (`packages/core/src/gates/boundary-scan.ts`) already
calls `isGateSealed(ctx, 'boundary-scan')`
Then the doc names all three (`test-coverage`, `build-test-must-pass`,
`boundary-scan`), and a doc-content test in
`packages/core/tests/docs/` asserts the doc's sealed-gate list is a superset
of every gate file that actually imports `isGateSealed` — so a future gate
that adds seal support without a doc update fails the same way the
command-reference/config-schema doc-sync tests already do.

### AC-2: A single declared bypass-flag naming policy governs every bypassable gate
Given bypass flags today are ad hoc per gate file (`--force` used generically
across `build-test-must-pass`/`coverage`/settle-level blocked-AC bypass,
`--allow-<gate>-failure` / `--allow-<verb>` used inconsistently elsewhere:
`--allow-missing-coverage`, `--allow-failing-build`,
`--allow-boundary-scan-failure`, `--allow-plan-review-failure`,
`--allow-spec-review-failure`, `--allow-ui-spec-review-failure`,
`--allow-per-task-failure`, `--allow-verifier-failure`,
`--allow-code-review-failure`, `--allow-security-audit-failure`)
When the policy is written down once (e.g. in `docs/concepts.md`'s gate
matrix section or a new `gates/README.md`): `--force` bypasses
build-correctness gates only, every other gate's dedicated
`--allow-<gate>-failure` flag is its sole bypass, and any gate id may be
added to `gates.sealed` to refuse both
Then each of the ~10 existing bypassable gates is audited against that policy
and any gate whose flag doesn't already match the documented naming
convention is either renamed (with a changeset) or the doc explicitly
carves out the exception and why.

### AC-3: Bypass provenance is recorded uniformly across all sealed-eligible gates
Given `runSettleGates` in `packages/core/src/gates/registry.ts` only special-
cases `gate === 'test-coverage' && res.flags?.coverageBypassed === true` to
record a `'bypassed via --allow-missing-coverage'` skip reason — a settle run
that bypasses `build-test-must-pass` or `boundary-scan` still shows
`status: 'ran'` in the SUMMARY's gate provenance, not `'skipped'` with a
bypass reason
When `build-test-must-pass` and `boundary-scan` gates surface their own
bypass state through `GateResult.flags` the same way `coverage.ts` does
Then `runSettleGates` records a matching `'bypassed via --allow-failing-build'`
/ `'bypassed via --allow-boundary-scan-failure'` skip reason for those two
gates as well, and a settle's `SUMMARY.json` `gateBypasses`/provenance trail
faithfully reflects every bypass that occurred, not just `test-coverage`'s.

## Constraints

- Do NOT change gate *behavior* (which flags bypass which gate, what sealing
  blocks) — this phase is about documentation accuracy, a declared policy,
  and provenance-recording parity, not new bypass/seal semantics.
- Touches `docs/reference/config.md` and possibly `docs/concepts.md` —
  doc-drift risk if the gate matrix changes again before this lands; keep the
  doc-content test as the enforcement backstop per CLAUDE.md's Doc Drift
  failure mode.
- `registry.ts` changes must preserve `runSettleGates`'s existing return
  shape (`RunGatesResult`) — only the `skipReason` string content changes for
  the two newly-covered gates, not the provenance array's structure.

## Open Questions

- Does AC-2's audit surface any gate whose current flag naming is load-
  bearing enough (e.g. already documented in `docs/reference/commands.md` or
  relied on by existing scripts) that renaming it needs a deprecation window
  instead of a straight rename?
- Should `gates.sealed` gain seal support for any of the other ~8 gates as
  part of this phase, or is that explicitly out of scope (matching the
  milestone's own "documentation + policy + provenance" framing, not "expand
  sealing")?
