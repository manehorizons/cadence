# 226-01 — Centralize gate bypass and seal policy in the settle driver

## Objective

Close three drifts around `gates.sealed`: `docs/reference/config.md` (and, as
discovered while drafting, `docs/concepts.md`'s "Gate bypass reference
summary") name only 2 of the 3 gates that actually consult `isGateSealed`,
and are additionally missing bypass-flag rows for `build-test-must-pass` and
`boundary-scan` entirely — stale since `boundary-scan` shipped in Phase 156.
The remaining ~8 bypassable gates (`plan-review`, `security-audit`,
`deep-verify`, `interactive-verdict`, `code-review`, `draft-read`,
`structural-verifier`, `per-task-verify`) decide their own bypass semantics
with no declared naming policy. `registry.ts`'s per-gate provenance only
records *why a gate was skipped* for `test-coverage`'s bypass — not
`build-test-must-pass`'s or `boundary-scan`'s.

## Acceptance Criteria

### AC-1: docs list every gate that consults gates.sealed, completely and accurately
Given `docs/reference/config.md` states "only two gate ids currently check
`gates.sealed`" (naming `test-coverage`/`build-test-must-pass` only) and
`docs/concepts.md`'s "Gate bypass reference summary" table (a) makes the same
two-gate claim in its `gates.sealed` callout and (b) is missing table rows
for `--allow-failing-build` and `--allow-boundary-scan-failure` entirely
When `boundary-scan` (`packages/core/src/gates/boundary-scan.ts`) already
calls `isGateSealed(ctx, 'boundary-scan')`
Then both docs name all three gates (`test-coverage`, `build-test-must-pass`,
`boundary-scan`) wherever `gates.sealed` is discussed, `docs/concepts.md`'s
bypass table gains the two missing rows, and a new doc-content test in
`packages/core/tests/docs/` asserts the doc's sealed-gate list is a superset
of every gate file that actually imports `isGateSealed` — so a future gate
that adds seal support without a doc update fails the same way the existing
command-reference/config-schema doc-sync tests already do.

### AC-2: A single declared bypass-flag naming policy governs every bypassable gate
Given bypass flags today are ad hoc per gate file (`--force` used generically
across `build-test-must-pass`/`coverage`/settle-level blocked-AC bypass,
`--allow-<gate>-failure` used for most gates, `--allow-missing-coverage` /
`--allow-failing-build` using an `--allow-<verb>` shape instead) with no
written-down convention explaining the split
When the policy is written down once in `docs/concepts.md` (near the existing
"Gate bypass reference summary"): `--force` is the generic override for
build-correctness gates only, every other gate's dedicated
`--allow-<gate>-failure` flag is its sole bypass, `--allow-<verb>`-shaped
flags (`--allow-missing-coverage`, `--allow-failing-build`) are the accepted
naming variant specifically for the two original sealed-eligible gates
(pre-dating the `--allow-<gate>-failure` convention), and any gate id may be
added to `gates.sealed` to refuse both forms
Then each of the ~10 existing bypassable gates is checked against that policy
in the DRAFT retro / PR description, and any gate whose flag doesn't match is
either flagged for a follow-up rename (recommendation, not done in this
phase — see Open Questions) or the doc explicitly carves out the exception
and why, with no source-level renames in this phase.

### AC-3: Bypass provenance is recorded uniformly across all three sealed-eligible gates
Given `runSettleGates` in `packages/core/src/gates/registry.ts` only special-
cases `gate === 'test-coverage' && res.flags?.coverageBypassed === true` to
record a `'bypassed via --allow-missing-coverage'` skip reason — a settle run
that bypasses `build-test-must-pass` or `boundary-scan` still shows
`status: 'ran'` in the SUMMARY's gate provenance, not `'skipped'` with a
bypass reason
When `build-test-must-pass` and `boundary-scan` gates surface their own
bypass state through `GateResult.flags` the same way `coverage.ts` already
does (`boundary-scan.ts`'s existing `bypassed` local at line 62 just needs to
flow into the returned flags)
Then `runSettleGates` records a matching `'bypassed via --allow-failing-build'`
/ `'bypassed via --allow-boundary-scan-failure'` skip reason for those two
gates as well, and a settle's `SUMMARY.json` gate-provenance trail faithfully
reflects every bypass that occurred, not just `test-coverage`'s.

## Boundaries

- DO NOT change which flags bypass which gate, or what sealing blocks — this
  phase is documentation accuracy, a declared policy, and provenance-
  recording parity only.
- DO NOT rename any existing `--allow-*` flag in this phase, even if AC-2's
  audit flags one as non-conformant — renames are a breaking CLI change and
  belong in a follow-up recommendation with their own changeset, not folded
  in here silently.
- DO NOT add `gates.sealed` support to any of the other ~8 gates — expanding
  sealing is explicitly out of scope (see Open Questions in the SPEC).
- DO NOT touch `docs/reference/commands.md` or the command-registration
  tests — no CLI surface changes in this phase.
