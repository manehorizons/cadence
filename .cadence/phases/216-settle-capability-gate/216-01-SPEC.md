# 216-01 — Close the trust envelope: gate the SETTLE capability class in MCP serve

## Objective

`packages/core/src/mcp/tools.ts` classifies `cadence_settle` as capability
class `SETTLE` but its `run()` is never wrapped with `gatedRun` — unlike
`cadence_draft_approve`/`cadence_spec_approve` (`APPROVAL_BYPASS`), an MCP
call to `cadence_settle` executes immediately with no trust-envelope check.
`enforceApprovalBypassGrant` (phase 181) is already tool-agnostic and the
`cadence mcp trust grant/revoke/list` CLI already accepts `SETTLE` as a
gated class (`mcp-trust-grant.ts`'s `GATED_CLASSES`) — the remaining step is
wiring `cadence_settle`'s `run` through the existing `gatedRun` wrapper, the
same pattern already proven for the two `APPROVAL_BYPASS` tools.

## Acceptance Criteria

### AC-1: cadence_settle is gated by the trust envelope
Given an MCP client calls `cadence_settle`
When no valid trust grant exists for `cadence_settle` (missing, def-hash
mismatch, version mismatch, or expired — the same four checks
`enforceApprovalBypassGrant` already applies to the `APPROVAL_BYPASS` tools)
Then the call is refused with a reason naming which envelope check failed,
`settleService` never runs, and no `state.json`/`SUMMARY.{json,md}` write
occurs and the loop position is unchanged; When a valid, matching,
unexpired trust grant for `cadence_settle` exists (issued via
`cadence mcp trust grant --tool cadence_settle` on a real terminal)
Then the call proceeds to `settleService` exactly as it does today (no
change to a granted caller's behavior).

## Constraints

- Reuse `enforceApprovalBypassGrant`/`gatedRun` as-is — both are already
  generic over `ToolDef`, not `APPROVAL_BYPASS`-specific in implementation
  (only in current doc comments and the phase-181 DRAFT boundary that
  deferred this). Do not fork a parallel enforcement path for `SETTLE`.
- Do not change `cadence_settle`'s `inputSchema`, description text (beyond
  documenting the new grant requirement, matching how
  `cadence_draft_approve`/`cadence_spec_approve` document theirs), or its
  `CapabilityClass` value — it stays `SETTLE`.
- Do not touch the CLI `cadence settle` command path — this phase gates the
  MCP tool surface only, exactly as phase 181 scoped `APPROVAL_BYPASS`.
- Zero-runtime-dependency bias applies (`CLAUDE.md`) — no new dependency;
  this is pure wiring of existing machinery.
- Update stale doc comments/tests that assert `cadence_settle` is "left
  ungated this phase" (`tools.ts` header comment, `enforce.ts` doc comment,
  `tools-capability-class.test.ts`'s `SETTLE class` test) to reflect the new
  reality — the phase-181 DRAFT boundary line itself is historical record
  and stays untouched (`CLAUDE.md`'s "The .keel Cleanup" / Freshen Reflex
  principle: don't rewrite past-phase artifacts).

## Open Questions

- None — this is a scoped extension of already-designed, already-tested
  machinery; no new design decisions are required.
