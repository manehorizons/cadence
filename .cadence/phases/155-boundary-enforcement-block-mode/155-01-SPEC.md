# 155-01 — Boundary enforcement block mode, including subagent edits

## Objective

DRAFT declares `files:` per task and `Boundaries` per phase, but pre-tool-edit
checks (`packages/core/src/checks/boundary.ts`) only ever emit a `warn`
severity — there is no way today to make an out-of-boundary edit actually
refuse. Add a top-level `boundaryEnforcement: 'warn' | 'block'` config
(default `warn`, back-compat; overridable per-phase via DRAFT frontmatter,
mirroring the existing `profile` override), where `block` mode refuses an
out-of-boundary edit at edit time, wherever the host surfaces the touched
files before the write lands (`ctx.raw.files`).

**Explicitly out of scope for this phase:** a settle-time diff scan that
catches boundary violations edit-time interception cannot see (e.g. subagent
edits, which today only bump `state.session.subagentSpawns` and are invisible
to `handlePreToolEdit`). A prior review of this SPEC found that mechanism
rests on a false premise — CADENCE anomalies are informational-only and never
block settle (`packages/types/src/anomaly.ts:8-11`); building it correctly
requires a genuine new settle-refusal path, an unscoped diff enumeration with
a defined base ref, and an ignore-list for `.cadence/**` self-writes (settle's
own artifact writes would otherwise self-trip the scan). That is real,
separate design work, tracked as a follow-on recommendation rather than bolted
onto this phase.

## Acceptance Criteria

### AC-1: warn mode is unchanged (back-compat)
Given `boundaryEnforcement` is unset or `"warn"`
When a file outside the active draft's declared `files:` is edited
Then `handlePreToolEdit` behaves exactly as today (notifies via
`anomaly-notify`, never returns `ok: false`) and settle's anomaly collection
still reports it as a `warn`-severity `files-outside-boundary` event.

### AC-2: block mode refuses out-of-boundary edits at edit time
Given `boundaryEnforcement === "block"`, an active draft/phase, at least one
task declares a non-empty `files:` list, and the host provides `ctx.raw.files`
for the pending edit
When a file outside the union of declared `files:` is about to be written
Then `handlePreToolEdit` returns `{ ok: false, blockMessage }` naming the
undeclared file, and the edit does not proceed.

### AC-3: no active draft/phase never blocks
Given `boundaryEnforcement === "block"` but `state.activeDraft` or
`state.activePhase` is unset (mirrors the existing guard at
`handlers.ts:51`)
When any file is edited
Then `handlePreToolEdit` returns `{ ok: true }` unchanged — block mode never
fires without a declared boundary to enforce.

### AC-4: empty declared-files set fails open, not closed
Given `boundaryEnforcement === "block"` and the active draft's tasks declare
zero files in total (an empty union)
When any file is edited
Then `handlePreToolEdit` returns `{ ok: true }` — block mode must never block
100% of edits as a side effect of a DRAFT that omits `files:`; enforcement
requires an explicit non-empty allow-list.

### AC-5: per-phase override via DRAFT frontmatter
Given a project-level `boundaryEnforcement: "block"` default
When a DRAFT's frontmatter declares its own `boundaryEnforcement: "warn"`
(mirroring how `profile` already overrides per-phase per
`packages/types/src/plan.ts:31` / `parse/draft-parser.ts:102`)
Then the phase-level value wins for that phase's edits.

## Constraints

- `warn` stays the default; existing `boundary.test.ts` / hook-handler tests
  must keep passing unmodified.
- `boundaryEnforcement` is a **top-level** config field (like `phaseGuard` /
  `gates` / `resume`), not nested under `hooks:` — `hooks` today is
  boolean-only gate toggles, and this value is read by more than the hook
  layer once the settle-time follow-on lands.
- Reuse the existing `files-outside-boundary` anomaly type: give
  `runBoundaryCheck` an optional `severity` parameter defaulting to `'warn'`
  (no consumer filters on severity today — `status.ts` only displays the
  event), so `boundary.test.ts` needs no changes for AC-1.
- Edit-time blocking only fires where the host actually surfaces
  `ctx.raw.files` before the write lands — hosts/subagent paths that can't be
  intercepted at edit time are explicitly NOT claimed as covered by this
  phase; that gap is the settle-time follow-on's job, not this one's.
- Precedence with `config.hooks.preToolUseBuildGate` (a separate, unrelated
  gate on loop position, not declared files): the boundary block check runs
  first in `handlePreToolEdit`'s existing order (lines 51-90 before line 91)
  and returns immediately on refusal; document this ordering rather than
  reshuffling it.

## Open Questions

- When a single edit event's `ctx.raw.files` contains multiple files and more
  than one is out-of-boundary, does `block` mode refuse on the first
  violation found, or collect and name all violators in one `blockMessage`?
  (`runBoundaryCheck` today emits one event per file — the planner should
  pick one behavior and note it doesn't need to change the underlying loop.)
