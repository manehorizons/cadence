# 148-01 — settle run --ship-ref shortcut

## Objective

Close issue #134: an opt-in `cadence settle run --ship-ref "<text>"` flag that,
when the settling phase has a `converted` recommendation pointed at it,
promotes that recommendation straight to `shipped` (with `shippedRef` set to
the given text) instead of the default `settle-pending` advance. Reuses the
existing, tested `converted → shipped` transition
(`applyRecommendationPromotion` / `runRecommendationPromotion` in
`packages/core/src/intelligence/store/recommendations.ts`) — no new
transition logic, just a new caller into it from
`packages/core/src/services/settle.ts` (~line 508-526, alongside the existing
`runAdvanceConvertedToSettlePendingForPhase` call) and a
`--ship-ref <text>` flag in `packages/core/src/cli/commands/settle.ts`
(follow the `--verifier` flag's wiring pattern in that file as the template).

## Acceptance Criteria

### AC-1: --ship-ref promotes straight to shipped
Given a phase with a `converted` recommendation whose `convertedToPhaseId`
is that phase
When the operator runs `cadence settle run --ship-ref "PR #NNN" --auto`
Then the recommendation ends up with `status: shipped` and
`shippedRef: "PR #NNN"` in `.cadence/intelligence/recommendations.json` (not
`settle-pending`), and settle stdout prints a line naming the id and the
shipped transition (e.g. `recommendation <id> moved to shipped (--ship-ref)`)

### AC-2: default settle behavior is unchanged without the flag
Given the same phase/recommendation setup as AC-1
When the operator runs `cadence settle run --auto` with no `--ship-ref`
Then the recommendation advances to `settle-pending` exactly as it does on
`main` today (byte-for-byte existing behavior — regression guard)

### AC-3: --ship-ref is a safe no-op with nothing to ship
Given a phase with no `converted` recommendation pointed at it
When the operator runs `cadence settle run --ship-ref "PR #NNN" --auto`
Then settle still completes successfully (exit 0) and prints no
shipped-recommendation line — mirrors the existing best-effort behavior of
the settle-pending path when there is nothing to advance

### AC-4: implementation is covered by tests
Given the feature implementation is complete
When `packages/core/tests/services/settle-*.test.ts` (or a new
`settle-ship-ref.test.ts`) and the CLI parse tests run
Then AC-1, AC-2, and AC-3 are each covered by a passing test that asserts on
real recommendation-ledger state, not just an exit code

## Tasks

- files: `packages/core/src/cli/commands/settle.ts`, `packages/core/src/services/settle.ts`
- action: add `--ship-ref <text>` to the `settle run` command (reject empty
  string same as other text flags), add `shipRef?: string` to the
  `SettleArgs` interface, thread it through to the service call
- verify: `cadence settle run --help` shows the new flag
- done: (scaffolding for AC-1)

### T2: Promote converted recs to shipped when --ship-ref is set
- files: `packages/core/src/services/settle.ts`
- action: in the post-summary recommendation-advance block (~line 508-526),
  branch on `args.shipRef`: when set, call `runRecommendationPromotion(cwd,
  rid, { status: 'shipped', shippedRef: args.shipRef })` for each `converted`
  rec targeting `settledPhase` (same filter `runAdvanceConvertedToSettlePendingForPhase`
  already uses) instead of calling the settle-pending advance; keep the whole
  block best-effort (try/catch, never blocks settle) like the existing code
- verify: manual settle run against a fixture with a converted rec shows
  `shipped` + `shippedRef` in the ledger afterward
- done: AC-1, AC-2, AC-3

### T3: Tests

- verify: `pnpm --filter @manehorizons/cadence-core test` passes

## Boundaries

- DO NOT change the default (`--ship-ref` omitted) settle-pending behavior.
- DO NOT duplicate the `converted → shipped` transition logic — call the
  existing `runRecommendationPromotion` seam.
- DO NOT touch the MCP `cadence_settle` tool's argument surface in this phase
  unless it already forwards other `SettleArgs` fields 1:1 today — if it
  does, mirror `shipRef` there for parity (check
  `packages/core/src/mcp/tools.ts`); if it doesn't already forward
  comparable flags, leave MCP parity as an explicit follow-up rather than
  scope-creeping this phase.
