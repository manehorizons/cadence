# 219-01 — Cross-check evidence.json in recommendation id-minting

## Objective

Make recommendation id-minting immune to a dangling `evidence.json` row silently colliding with a newly minted recommendation id, and add a `cadence doctor` check that surfaces such orphaned evidence rows so future drift is caught immediately instead of surviving unnoticed.

## Acceptance Criteria

### AC-1: id-minting cross-checks evidence.json
Given an evidence ledger entry references a `recommendationId` with no matching entry in `recommendations.json` (an orphaned/dangling row)
When `cadence recommendation add` mints a new recommendation id for the same date prefix
Then the minted id is strictly greater than both the max existing `recommendations.json` id and the max `recommendationId` referenced by `evidence.json` for that date prefix, so it can never collide with the orphaned row

### AC-2: doctor flags orphaned evidence rows
Given the evidence ledger contains a row whose `recommendationId` has no matching entry in `recommendations.json` (active or archived)
When `cadence doctor` runs
Then it reports the orphaned evidence row as a diagnostic finding, naming the evidence id and the missing recommendation id

## Constraints

- Do not change the recommendation/evidence id format (`rec-YYYYMMDD-NNN` / `ev-YYYYMMDD-NNN`)
- The doctor check must be best-effort — degrade to no finding on any read error, never throw (matches existing doctor check conventions)
