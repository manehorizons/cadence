# 293-01 — packs slice 4 -- doctor-checked commands declaration

## Objective

cadence doctor gains a new check that verifies each enabled pack's declared commands[] entries (slash-command names, per docs/packs-design.md line 86) exist in CADENCE's registered slash-command set. Doctor-checked only, never enforced -- no Gate entry, no DELTAS cell, no refusal path -- matching D-AP's explicit exclusion of commands from anything gate-shaped. The registered set is derived from Object.keys(COMMAND_GUIDANCE) (@thomas-powers-jr/cadence-types, already a core dependency), which this phase also pins as invariant-equal to the host-toolkit COMMANDS catalog's .name list so the check's authority never silently drifts from what actually installs as a slash command.

## Acceptance Criteria

### AC-1: doctor flags a pack declaring an unknown command
Given a repo with an enabled pack whose `pack.json` `commands` array names at least one string that is not a key of `COMMAND_GUIDANCE` (`@thomas-powers-jr/cadence-types`)
When `cadence doctor` runs
Then it reports a new check (`pack-commands`) at `severity: 'warning'` naming the pack id and every unrecognized command string, with `fixId: null`, and `DoctorReport.ok` stays `true` (warning never flips `ok` — matches `checks.every(c => c.severity !== 'error')` in `packages/core/src/doctor/model.ts`)

### AC-2: clean and degraded paths report ok, not warning
Given any of: zero enabled packs, an enabled pack whose `commands` field is absent (`.optional()` on `PackManifestZ`), an enabled pack whose every declared command matches a real `COMMAND_GUIDANCE` key, or a repo whose config fails to load
When `cadence doctor` runs
Then the check reports `ok`/`pass` in every case — branching on the **resolved** pack count (not `config.packs.enabled.length`), so an id present in both `enabled` and `disabled` (disabled wins, D-AQ) is excluded before the check ever runs, and a config-load failure degrades to `pass('pack-commands', ...)` exactly like `checkPacks`'s existing `catch`, never the `indeterminate` rung

### AC-3: the registered-command-set invariant is pinned by a test
Given the check's authority for "does this command exist" is `Object.keys(COMMAND_GUIDANCE)`
When the equality of that set against `COMMANDS.map(c => c.name)` (the actual installed-slash-command catalog in `packages/host-toolkit/src/routing.ts`) is asserted in a test
Then the two sets match exactly, so a future command added to one catalog but not the other is caught immediately rather than letting `pack-commands` silently pass or falsely warn

### AC-4: implementation is covered by tests and the docs pairing is kept in sync
Given the feature implementation is complete
When the relevant tests run and `docs/reference/commands.md`'s doctor-check table plus `docs/packs-design.md` §7 are read
Then AC-1/AC-2/AC-3's behavior is covered and passing, the new `pack-commands` row is documented in `docs/reference/commands.md` alongside the existing `packs` row, and `docs/packs-design.md` §7 marks Slice 4 landed
