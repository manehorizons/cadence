# 101-01 — Recommendation archive core + manual commands

## Objective

Add soft-archival of recommendations: a second `archived` array in the ledger, pure
`archiveRecommendation`/`unarchiveRecommendation` move-transforms, their impure `run*`
wrappers, and the manual CLI commands `recommendation archive`/`unarchive`/`list
--archived` — recoverable move-aside, no deletion (v1.24 phase 1 of 3).

## Acceptance Criteria

### AC-1: Ledger gains a backward-compatible `archived` array
Given an existing `recommendations.json` with **no** `archived` key
When the ledger is parsed via `RecommendationLedgerZ`
Then it parses successfully with `archived` defaulting to `[]` (no migration needed).

### AC-2: Recommendation gains archive-provenance fields
Given the `RecommendationZ` schema
When a rec is live (in `recommendations`)
Then `archivedAt` and `archiveReason` are absent; and the schema accepts an
`archivedAt` (ISO datetime) + `archiveReason` (`manual|shipped|rejected|converted-settled`)
on an archived rec.

### AC-3: `archiveRecommendation` moves a live rec into `archived`
Given a ledger with a live rec `R` (in `recommendations`)
When `archiveRecommendation(ledger, R.id, 'manual', now)` is applied
Then `R` is removed from `recommendations`, appended to `archived` with
`archivedAt=now` + `archiveReason='manual'`, and every other live rec and every
pre-existing archived rec is preserved unchanged.

### AC-4: `archiveRecommendation` rejects unknown / already-archived ids
Given a ledger
When `archiveRecommendation` is called with an id absent from `recommendations`
(unknown, or already in `archived`)
Then it returns `{ ok: false, error }` naming the id, and the ledger is untouched.

### AC-5: `unarchiveRecommendation` restores an archived rec
Given a ledger with rec `R` in `archived`
When `unarchiveRecommendation(ledger, R.id, now)` is applied
Then `R` returns to `recommendations` with `archivedAt`/`archiveReason` cleared, is
removed from `archived`, and `updatedAt=now`; an id absent from `archived` returns a
typed error and leaves the ledger untouched.

### AC-6: Existing transforms preserve the `archived` array
Given a ledger holding one or more archived recs
When any pre-existing transform runs — `addRecommendation`,
`applyRecommendationTransition`, `applyRecommendationPromotion`,
`deriveRecommendationLinks` — and the ledger is written
Then the `archived` array survives the round-trip intact (no silent drop).

### AC-7: `run*` wrappers persist atomically
Given a repo with an intelligence store
When `runRecommendationArchive(root, id, reason)` then
`runRecommendationUnarchive(root, id)` run
Then each persists via `writeIntelligenceLedgers` (single atomic JSON write +
RECOMMENDATIONS.md re-render), and a reload reflects the change.

### AC-8: Manual `archive` / `unarchive` CLI commands
Given the CLI
When `cadence recommendation archive <id>` runs on a live rec
Then the rec is archived with `archiveReason='manual'` and a confirmation prints;
`unarchive <id>` restores it; an unknown/ineligible id exits non-zero with a clear
message (no stack trace).

> **Deviation (build):** dropped the planned `--reason <text>` flag. `archiveReason`
> is an enum (`manual|shipped|rejected|converted-settled`); there is no free-text note
> field, so a `--reason` flag would be a no-op or expose the phase-102 auto-reasons to
> manual misuse. Manual archive records `manual`. A free-text `archiveNote` is YAGNI
> (revisit if a real need appears).

### AC-9: `list --archived` shows the archive; default list excludes it
Given a ledger with both live and archived recs
When `cadence recommendation list` runs
Then only live recs are listed (archived never leak in), with a footer hint of the
archived count; and `cadence recommendation list --archived` lists the archived recs
(both `terminal` and `json` formats).

## Boundaries

- DO NOT add auto-archive wiring (promote/reject/settle hooks) or the
  `recommendations.autoArchive` config — that is **phase 102**. This phase is the
  storage model + manual surface only.
- DO NOT hard-delete: `unarchive` must fully restore. No purge command.
- DO NOT render archived recs into the active `RECOMMENDATIONS.md` body (they live in a
  separate array and naturally fall out of the existing render; keep it that way).
- DO NOT touch `applyRecommendationPromotion`'s status/terminal rules — archival is
  orthogonal to status here.
