# 156-01 — Settle-time boundary diff scan (blocking)

## Objective

Follow-on to phase 155's edit-time `boundaryEnforcement: 'block'`, which
cannot see a violation that never passes through the host's pre-tool-edit
hook — most notably a subagent-driven edit (`handleSubagentResult` only bumps
`state.session.subagentSpawns`, never checks touched files against the
boundary). Add a new **`boundary-scan`** settle gate: a genuine
settle-refusal path (CADENCE anomalies are informational-only and never block
settle today — `packages/types/src/anomaly.ts:8-11` — so this cannot be
built as "just another anomaly") that enumerates files touched by the whole
phase via an **unscoped** git diff (not `ctx.touchedFiles`/`ctx.diff()`,
which are scoped to the *declared* files and can structurally never surface
an out-of-boundary file — confirmed at `services/settle.ts:232,287`), ignores
`.cadence/**` self-writes, and refuses settle when a file outside the active
draft's declared `files:` union is found — but only when
`effectiveBoundaryEnforcement(config, draft) === 'block'`.

## Acceptance Criteria

### AC-1: new self-guarded gate, correctly no-opped in provenance
Given the `Gate` enum gains `'boundary-scan'`, `GATE_REGISTRY` registers it
as `{ impl: runBoundaryScanGate, selfGuarded: true }` (mirroring
`deep-verify`/`interactive-verdict`'s shape at `gates/registry.ts:43-52`),
and `SELF_GUARD_PREDICATES` (`gates/registry.ts:87-90`) gains
`'boundary-scan': (ctx) => effectiveBoundaryEnforcement(ctx.config, ctx.draft) === 'block'`
When `effectiveBoundaryEnforcement(ctx.config, ctx.draft)` resolves to
anything other than `"block"`
Then the gate is invoked (selfGuarded bypasses the `gateSet.gates.includes`
check) and its impl returns `{ outcome: 'pass' }` immediately as a no-op, AND
the phase-140 gate-provenance table records it as `status: 'skipped'` (not
`'ran'`) — omitting the `SELF_GUARD_PREDICATES` entry would silently
mislabel every default-config (`warn`-mode) settle's `SUMMARY.gates` from
this phase forward. `ALWAYS_FIRE`/`DELTAS` in `gates/engine.ts` are NOT
modified, since this gate's sole trigger is `boundaryEnforcement`, orthogonal
to tier/profile (unlike `deep-verify`, whose predicate also ORs in gate-set
membership — this gate has no such OR branch).

### AC-2: unscoped enumeration with a loud (not silent) fallback when the base ref is unavailable
Given a phase whose current branch diverged from `<phaseGuard.integrationRef>`
(default `"main"`)
When the `boundary-scan` gate runs
Then it enumerates the union of (a) committed-since-divergence files via
`git diff --name-only <merge-base> HEAD` and (b) working-tree
modified/added/untracked files via `git status --porcelain
--untracked-files=all`, both through the existing best-effort `gitBestEffort`
helper (`git/worktrees.ts:21`) — NOT `ctx.touchedFiles` or `ctx.diff()`, both
of which are pre-scoped to the declared `files:` set and can never contain
an outsider (`services/settle.ts:232,287`). The merge-base is computed
against `origin/<integrationRef>` first; if that ref doesn't resolve (no
remote, shallow clone — the common case on a CI runner, exactly where
`block` mode is most likely to be armed), fall back to a **local**
`<integrationRef>` (e.g. `main`) merge-base instead of silently returning
empty. Only when BOTH resolution attempts fail does enumeration (a) degrade
to empty — and in that case the gate emits a visible `ctx.io.err` notice
("boundary-scan: could not resolve a base ref against `<integrationRef>` —
committed-file scan skipped, only working-tree changes were checked")
rather than passing with no signal at all. (b) never depends on a remote and
always runs. Porcelain lines are parsed per their documented format: strip
the 2-character status code + 1-space prefix; for `R`/`C` (rename/copy)
entries, which render as `R  <old> -> <new>`, take only the destination
(post-`-> `) path — matching `git diff --name-only`'s own default (renames
on) behavior of reporting the destination path.

### AC-3: `.cadence/**` self-writes are ignored
Given the enumeration from AC-2 includes paths under `.cadence/**` (settle's
own DRAFT/PROGRESS/SUMMARY/state.json/STATE.md writes, and this very phase's
own SPEC/milestone-export artifacts)
When the boundary-scan gate filters the enumeration
Then every `.cadence/**` path is dropped before comparison against declared
`files:` — settling THIS phase (or any phase) in `block` mode must not
self-trip on CADENCE's own bookkeeping.

### AC-4: refuses on a real out-of-boundary file, passes otherwise
Given `boundaryEnforcement` resolves to `"block"`, the AC-2/AC-3 filtered
enumeration contains at least one file outside the union of the active
draft's declared `files:`, and the declared `files:` union is non-empty
(mirrors phase 155 AC-4's fail-open rule — an empty declared set means there
is no boundary to enforce)
When `cadence settle run` executes the `boundary-scan` gate
Then it returns `{ outcome: 'refuse' }`, `ctx.io.err` names every offending
file, and settle halts before writing SUMMARY — distinct from today's
`files-outside-boundary` anomaly, which only warns and never halts anything.
A deleted or modified out-of-boundary file counts as an offender the same as
an added one; a rename is judged on its destination path only (per AC-2) —
renaming a declared file to an undeclared path is a violation, renaming an
already-undeclared file is not a *new* one.

### AC-5: bypassable and sealable, with a SUMMARY audit trail on bypass
Given a refusing `boundary-scan` gate
When the operator passes `--force` or the new `--allow-boundary-scan-failure`
flag (mirroring `--allow-security-audit-failure`'s pattern in
`gates/security-audit.ts`)
Then settle proceeds past the refusal, and the `summaryPatch` records
`boundaryScan: { offenders: string[] }` (a new optional `SummaryZ` field,
mirroring how `securityAudit`'s findings survive a bypass) so a forced
violation still leaves an audit trail — UNLESS `"boundary-scan"` is listed
in `config.gates.sealed` (`isGateSealed`, `gates/types.ts:250`), in which
case neither flag has any effect, mirroring
`test-coverage`/`build-test-must-pass`'s sealed behavior.

## Constraints

- `boundaryEnforcement` unset or `"warn"` must produce ZERO behavior change:
  the gate is a complete no-op (back-compat with every existing settle test),
  correctly reported as `skipped` per AC-1.
- Do not reuse `ctx.touchedFiles`/`ctx.diff()`/`collectGitDiff`/
  `collectDiffForCodeReview` for the enumeration — they are declared-files-
  scoped by construction (`services/settle.ts:232,287`) and cannot serve
  AC-2's purpose no matter how they're called.
- Reuse `gitBestEffort` (`git/worktrees.ts:21`) rather than a new raw
  `execFileSync` call — same best-effort, never-throws contract the
  phase-collision guard already relies on. It uses `execFile` (no shell), so
  file paths with spaces/special characters are not an injection risk.
- The new gate must be a normal `GateImpl` (`(ctx: SettleContext) =>
  Promise<GateResult>`) living in `gates/boundary-scan.ts`, registered in
  BOTH `GATE_REGISTRY` (a missing entry is a compile error) AND `GATE_ORDER`
  (a plain array with NO compile-time totality check — omitting it there
  compiles fine but the gate silently never runs; do not rely on the
  registry catching this), placed early/cheap — no external services,
  network, or subprocess beyond local git — similarly to
  `structural-verifier`/`test-coverage`.
- `--allow-boundary-scan-failure` must be threaded through all four sites
  the existing `--allow-security-audit-failure` flag touches: the CLI
  `.option(...)` registration (`cli/commands/settle.ts`), `SettleOpts`
  (`gates/types.ts:148-162`), the `ctx.opts` conditional-spread block
  (`services/settle.ts:249-262` — the site most easily missed: an omission
  here means the flag parses but never reaches the gate), and the settle
  command's own args type.
- Do not touch `packages/core/src/notify/collect.ts`'s existing
  `files-outside-boundary` anomaly emission (settle's warn-only detection,
  sourced from `progress.tasks[*].touchedFiles` telemetry) — that stays
  exactly as-is; this gate is an independent, additional refusal path, not a
  replacement.
- `git status --porcelain` already omits `.gitignore`d paths by default (they
  only surface with an explicit `--ignored`), so no additional exclude list
  beyond `.cadence/**` (AC-3) is needed for e.g. an un-gitignored
  `node_modules`.
- **Known scoping limitation, accepted rather than solved here:** the
  merge-base enumeration covers everything committed since the branch
  diverged from `<integrationRef>`, not just this phase's own commits. A
  branch carrying multiple phases, or commits made directly on the
  integration branch, can surface a *prior* phase's files as false-positive
  offenders of the *current* phase. `block` mode's committed-file scan
  assumes one-phase-per-branch-since-integration-ref; this is a real
  limitation to document (e.g. in `docs/reference/config.md`), not a bug to
  fix in this phase.
- This phase's own DRAFT must declare every file it actually touches (the
  new gate impl, registry/engine/types wiring, the new CLI flag's four
  threading sites, and the SummaryZ field) — if this phase settles with its
  own `boundaryEnforcement: block` frontmatter override (to dogfood the new
  gate), an incomplete `files:` declaration will cause it to self-refuse.
