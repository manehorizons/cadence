# 137-01 — Refusal trio: concrete next-move everywhere

## Objective

Three small surfaces break CADENCE's "always name a concrete next move"
pattern: (a) `cadence progress` in BUILD emits an unrunnable compound command
(`cadence build task <id> ... OR cadence settle run ...`) instead of the
actual first-pending task id; (b) `draft approve` on a missing DRAFT.md dumps
a raw ENOENT-flavored message instead of a clean guarded refusal (like `spec
approve` already does); (c) `settle run` out of position names no next step
at all. Close rec-20260701-007 / audit finding F10 by fixing all three.

## Acceptance Criteria

### AC-1: BUILD-state progress names the first pending task, or settle
Given loopPosition=BUILD with an active draft
When `cadence progress` (or `--json`) runs
Then if any task is not yet recorded (per PROGRESS.json), the command is
`cadence build task <firstPendingId> --status=DONE`; if every task is
recorded, the command is `cadence settle run --auto`. No compound/OR command
is ever printed. Best-effort: if the draft/progress files can't be read, fall
back to today's message rather than blocking.

### AC-2: draft approve on a missing DRAFT.md gives a clean guarded refusal
Given `<phase>/<id>-DRAFT.md` does not exist
When `cadence draft approve <phase> <num>` runs
Then it prints `draft approve refused: <path> not found.` (mirroring `spec
approve`'s existing guard) and exits 1 — no raw Node fs error text

### AC-3: settle run out of position names the actual next step
Given loopPosition is not BUILD (or no active draft/phase)
When `cadence settle run` runs
Then the refusal message still contains the existing
`settle run requires loopPosition=BUILD` text (loop-violation anomaly
plumbing depends on it — unchanged) AND additionally names the concrete next
command (the same one `cadence progress` would print for the current state)

## Constraints

- (a) and (c) both reuse the existing pure `nextAction` (`progress.ts`) as the
  single source of truth — no duplicated per-state hint logic.
- (c) must not change the anomaly-emission path: `LoopViolationError` +
  `emitLoopViolation(cwd, err, 'settle.run')` still fire, and the existing
  `loop-violation.test.ts` assertions (stderr matches
  `/settle run requires loopPosition=BUILD/`, one anomaly event with
  `context.source === 'settle.run'`) must keep passing unmodified.
- (b) mirrors `spec-approve.ts`'s exact guard shape (`existsSync` check +
  `... refused: <path> not found.` + exit 1) — no behavior change to any
  other draft-approve gate.
