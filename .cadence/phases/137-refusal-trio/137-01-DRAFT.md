# 137-01 — Refusal trio: concrete next-move everywhere

## Objective

Three small surfaces break CADENCE's "always name a concrete next move"
pattern: (a) `cadence progress` in BUILD emits an unrunnable compound command
(`cadence build task <id> ... OR cadence settle run ...`) instead of the
actual first-pending task id; (b) `draft approve` on a missing DRAFT.md dumps
a raw ENOENT-flavored message instead of a clean guarded refusal (like `spec
approve` already does); (c) `settle run` out of position names no next step
at all. Close rec-20260701-007 / audit finding F10 by fixing all three.

## Acceptance Criteria

### AC-1: BUILD-state progress names the first pending task, or settle
Given loopPosition=BUILD with an active draft
When `cadence progress` (or `--json`) runs
Then if any task is not yet recorded (per PROGRESS.json), the command is
`cadence build task <firstPendingId> --status=DONE`; if every task is
recorded, the command is `cadence settle run --auto`. No compound/OR command
is ever printed. Best-effort: if the draft/progress files can't be read, fall
back to today's message rather than blocking.

### AC-2: draft approve on a missing DRAFT.md gives a clean guarded refusal
Given `<phase>/<id>-DRAFT.md` does not exist
When `cadence draft approve <phase> <num>` runs
Then it prints `draft approve refused: <path> not found.` (mirroring `spec
approve`'s existing guard) and exits 1 — no raw Node fs error text

### AC-3: settle run out of position names the actual next step
Given loopPosition is not BUILD (or no active draft/phase)
When `cadence settle run` runs
Then the refusal message still contains the existing
`settle run requires loopPosition=BUILD` text (loop-violation anomaly
plumbing depends on it — unchanged) AND additionally names the concrete next
command (the same one `cadence progress` would print for the current state)

## Tasks

### T1: BUILD progress names the first pending task id
- files: `packages/core/src/progress.ts`, `packages/core/src/services/progress.ts`,
  `packages/core/tests/cli/progress.test.ts`
- action: add `build?: { firstPendingTaskId: string | null }` to
  `NextActionHints`. In the BUILD case of `nextAction`: if the hint is
  present with a string id, emit `cadence build task <id> --status=DONE`; if
  present with `null` (all tasks recorded), emit `cadence settle run --auto`;
  if the hint is absent (I/O failed), keep today's compound fallback message.
  `progressService` computes the hint (best-effort) by parsing the active
  draft's `## Tasks` via `parseDraftMd`, reading `PROGRESS.json` if present,
  and returning the first task id (in draft order) with no entry in
  `progress.tasks`, or `null` if every task has an entry.
- verify: `pnpm --filter @manehorizons/cadence-core test -- cli/progress`
- done: AC-1

### T2: draft approve guards a missing DRAFT.md
- files: `packages/core/src/services/draft-approve.ts`,
  `packages/core/tests/cli/draft-approve-gate.test.ts`
- action: add an `existsSync(path)` guard before `readFile`, mirroring
  `spec-approve.ts`'s `if (!existsSync(specPath)) { io.err(...); return
  { exitCode: 1 }; }` shape, message: `` `draft approve refused: ${path} not
  found.\n` ``.
- verify: `pnpm --filter @manehorizons/cadence-core test -- cli/draft-approve`
- done: AC-2

### T3: settle run names the next step on a position refusal
- files: `packages/core/src/services/settle.ts`,
  `packages/core/tests/cli/loop-violation.test.ts`
- action: where `settleService` currently throws
  `LoopViolationError('settle run requires loopPosition=BUILD with an active
  draft', ...)`, instead construct the error, compute
  `nextAction(state)` (imported from `../progress.js`), print
  `` `settle run failed: ${err.message} Next: ${action.command}\n` `` (keeping
  the existing message text intact for the loop-violation regex), call
  `emitLoopViolation(cwd, err, 'settle.run')`, and return `{ exitCode: 1 }`
  directly (no throw — `state` is in scope here, avoiding a closure issue
  with the outer catch).
- verify: `pnpm --filter @manehorizons/cadence-core test -- cli/loop-violation`
- done: AC-3

## Boundaries

- DO NOT change any other gate/refusal path in `draft-approve.ts` or
  `settle.ts`.
- DO NOT change `LoopViolationError`'s shape or `emitLoopViolation`'s
  signature.
- DO NOT change `PROGRESS.json`'s schema — read-only in `progressService`.
