# 234-01 — Kernel / verifier / consumer boundary, lint-enforced

## Objective

Name the kernel / verifier / consumer split — already ~80% built and unnamed — as a
published contract, route every verifier-backed gate through it, and add a lint rule that
fails the build on an internal-import violation, with zero `GATE_ORDER` changes and no
change to any gate's pass/refuse semantics.

## Acceptance Criteria

### AC-1: The boundary is named as a single published contract
Given the three roles are unnamed and the verifier injection boundary is fragmented across
`VerifierPorts` (`gates/types.ts` — `deep`, `codeReview`, `securityAudit`),
`DraftVerifierPorts` (`gates/draft-types.ts` — `planReview`), `BuildVerifierPorts`
(`gates/build-types.ts` — `perTask`), and two ungoverned direct factory imports in
`services/spec-approve.ts:9,11`
When the boundary is named as a published contract
Then one contract module declares the `kernel` / `verifier` / `consumer` roles and the
verifier contract, and it is the only surface a verifier is resolved through.

### AC-2: All seven verifier-backed gates satisfy it with zero special cases
Given the five gates named in §6 Slice 2 (`code-review`, `plan-review`, `spec-review`,
`security-audit`, `ui-spec-review`) plus the two the doc omits but which are equally
verifier-backed (`deep-verify` via `VerifierPorts.deep`, `per-task-verify` via
`BuildVerifierPorts.perTask`)
When each is wired to the published contract
Then all seven satisfy it with no per-gate special-casing inside the contract's own
definition, and `spec-review` / `ui-spec-review` are resolved through a port rather than
importing `selectSpecReviewVerifier` / `selectUiSpecReviewVerifier` directly in
`services/spec-approve.ts`.

### AC-3: The lint rule fails on a deliberately introduced internal import
Given the rule is registered in `eslint.config.js`
When a verifier module imports a kernel internal instead of the published contract
Then `pnpm lint` exits non-zero and names the offending import path, proven by a committed
test that asserts the failure — not by manual observation alone.

### AC-4: Gate order and gate semantics are unchanged
Given hard constraint §9.5 ("no `GATE_ORDER` changes during Slice 2")
When the boundary work lands
Then `GATE_ORDER` is unchanged, no gate's pass/refuse semantics change, and the existing
suite passes with no test loosened to accommodate the refactor.

### AC-5: Settled artifacts still read and re-settle equivalently
Given hard constraint §9.2 (every existing settle artifact must still read correctly)
When a previously settled phase is re-settled after the boundary lands
Then the verdict and SUMMARY are equivalent to before, and existing SUMMARY files still
parse.

## Constraints

- No `GATE_ORDER` changes; no gate pass/refuse semantic changes (§9.5, §6 Slice 2).
- No package moves, no per-plugin versioning, no third-party plugin story, no distribution
  work. One version, one release, monorepo (§6 Slice 2).
- Behavior-preserving throughout: this names and enforces a boundary that already exists,
  in the same spirit as the core→host arrow.
- Zero-runtime-dependency bias: prefer ESLint built-ins (e.g. `no-restricted-imports`
  zones) over standing up a custom-rule package, unless the built-in genuinely cannot
  express the constraint.
- **Tripwire T3 (binding, from §8).** If the extraction runs beyond a couple of focused
  sessions, **revert** — overrun is the diagnosis, not a schedule problem: it means this is
  a rewrite wearing a refactor's clothes and the "already 80% built" premise was wrong.
  Record the outcome in the SUMMARY if it trips.
- Out of scope (Slice 3): `CodeReviewInput` criteria-anchoring, the anchor ladder, finding
  identity, ledger routing.

## Open Questions

- **Q1 — Contract home. RESOLVED by measurement:** the contract lives in core, not
  `@manehorizons/cadence-types`. All seven verifier input/result types (`CodeReviewInput`,
  `CodeReviewResult`, `PlanReviewInput`, `SpecReviewInput`, `SecurityAuditInput`,
  `UiSpecReviewInput`, `VerifyInput`) are defined under `packages/core/src/verify/`; hoisting
  the contract into types would drag them along, which is a package move and forbidden by
  §6 Slice 2. Target: a new `packages/core/src/contracts/` module.
- **Q2 — Which gates count. RESOLVED (operator, 2026-07-28): all seven.** §6 Slice 2 names
  five, but `deep-verify` and `per-task-verify` are equally verifier-backed; excluding two
  verifier-backed gates from a "zero special cases" contract is itself a special case. AC-2
  is written against seven. This widens the diff relative to the doc's literal wording —
  watch it against tripwire T3.
- **Q3 — Rule mechanism. RESOLVED (agent judgment): try the built-in first.** Attempt
  `no-restricted-imports` zones, which need no new infrastructure and honor the repo's
  zero-runtime-dependency bias. Escalate to a custom ESLint rule only if the built-in cannot
  express the constraint, and record the escalation in the SUMMARY if it happens.
- **Q4 — spec-approve normalization. RESOLVED (operator, 2026-07-28): in scope.**
  `services/spec-approve.ts:9,11,51,150` currently reaches past the boundary entirely.
  Leaving it lint-exempted would ship the contract with a hole in exactly the place the rule
  is meant to catch, so `spec-review` / `ui-spec-review` get real ports here.
