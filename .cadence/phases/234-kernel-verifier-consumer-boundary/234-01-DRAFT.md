# 234-01 — Kernel / verifier / consumer boundary, lint-enforced

## Objective

Name the kernel / verifier / consumer split — already ~80% built and unnamed — as a published contract in `packages/core/src/contracts/`, route all seven verifier-backed gates through it (including `spec-review` / `ui-spec-review`, which today bypass ports entirely via direct factory imports in `services/spec-approve.ts`), and add a lint rule that fails the build on an internal-import violation, with `GATE_ORDER` and every gate's pass/refuse semantics unchanged.

## Acceptance Criteria

### AC-1: The boundary is named as a single published contract
Given the verifier injection boundary is fragmented across `VerifierPorts` (`gates/types.ts`), `DraftVerifierPorts` (`gates/draft-types.ts`), `BuildVerifierPorts` (`gates/build-types.ts`), and two ungoverned direct factory imports in `services/spec-approve.ts`
When the boundary is named as a published contract
Then `packages/core/src/contracts/` declares the `kernel` / `verifier` / `consumer` roles and a generic verifier-port contract, and that module is the only surface through which a verifier **type** is named.

> **As built (2026-07-28) — AC text amended, operator-approved.** The clause above originally read "*and that module is the only surface through which a verifier is resolved*." That over-claimed relative to the design source: `docs/handoffs/cadence-phase0-assurance-kernel-review.md` §6 Slice 2 asks only to "name the three roles as published contracts" and "add a lint rule failing the build when a verifier package imports kernel internals rather than the published contract" — it never requires `contracts/` to be the *resolution* surface, and architecturally it should not be. Verifier **resolution** legitimately happens by direct `verify/*-factory.ts` import at four composition roots (`services/settle.ts`, `gates/build-context.ts`, `gates/draft-context.ts`, and this phase's own `services/spec-approve-ports.ts`); two independent reviewers judged that placement correct, and `contracts/` re-exports only the `VerifierProvider` *type* from `verifier-factory.js` — never a `select*` function — so it is structurally incapable of being the resolution surface. What did ship, and is mechanically enforced by T4's lint rule, is that `contracts/` is the only surface through which a verifier **type** is named: zero direct imports of the seven verifier-family modules remain anywhere in `packages/core/src` outside `verify/` and `contracts/`.
>
> Separately, `done:` originally credited AC-1 to T1 alone, which overstated T1's evidence — T1 delivers the module, but T4's lint rule is what enforces the "only surface" clause. T4 now also carries `done: AC-1`. The first issue was surfaced by the whole-branch review, the second by the independent T1 review.

### AC-2: All seven verifier-backed gates satisfy the contract with zero special cases
Given `code-review`, `plan-review`, `spec-review`, `security-audit`, `ui-spec-review`, `deep-verify`, and `per-task-verify`
When each is wired to the published contract
Then all seven are expressed in terms of the published port type with no per-gate special-casing inside the contract's own definition, and `spec-review` / `ui-spec-review` are injected through a port rather than importing `selectSpecReviewVerifier` / `selectUiSpecReviewVerifier` directly.

### AC-3: The lint rule fails on a deliberately introduced internal import
Given the boundary rule is registered in `eslint.config.js`
When a verifier module imports a kernel internal instead of the published contract
Then lint exits non-zero and names the offending import path, asserted by a committed test that runs ESLint over a fixture containing the violation.

### AC-4: Gate order and gate semantics are unchanged
Given hard constraint §9.5 forbids `GATE_ORDER` changes in this slice
When the boundary work lands
Then `GATE_ORDER` is unchanged in content and order, no gate's pass/refuse outcome changes, and the existing suite passes with no test loosened to accommodate the refactor.

### AC-5: Settled artifacts still read and re-settle equivalently
Given hard constraint §9.2 requires every existing settle artifact to keep reading correctly
When previously settled SUMMARY artifacts are parsed and an unchanged phase is re-settled
Then they parse without error and the re-settle verdict is equivalent to the pre-refactor verdict.

## Boundaries

- DO NOT change `GATE_ORDER` — not its contents, not its order (hard constraint §9.5).
- DO NOT change any gate's pass/refuse semantics; this slice is behavior-preserving.
- DO NOT move packages, add per-plugin versioning, add a third-party plugin story, or do any distribution work.
- DO NOT hoist verifier types into `@manehorizons/cadence-types` — that is a package move.
- DO NOT add a runtime dependency; prefer ESLint built-ins over a new custom-rule package.
- DO NOT touch Slice 3 scope: `CodeReviewInput` criteria-anchoring, the anchor ladder, finding identity, or ledger routing.
- DO NOT loosen an existing test to make the refactor pass.
- TRIPWIRE T3 (binding): if this extraction runs beyond a couple of focused sessions, revert rather than push through, and record the outcome in the SUMMARY.
