# 189-01 — cadence onboard: one-command setup for the 2nd-Nth teammate

## Objective

Add a `cadence onboard` command for a developer who clones a repo that
already has `.cadence/` committed by a teammate: it performs only the
per-machine setup bits (install host hooks, report provider/API-key
readiness) instead of re-running the full `cadence init` scaffold, which
would refuse because `.cadence/` already exists. Pair it with a
init-generated `CONTRIBUTING.md` snippet so the path is discoverable by the
next teammate. Keep the host-hook-install logic that `cadence init --full`
and `cadence onboard` both need in one shared module instead of duplicated
spawn logic.

## Acceptance Criteria

### AC-1: `cadence onboard` sets up an already-initialized repo
Given a repo with `.cadence/` already committed (e.g. cloned from a
teammate) and host hooks not yet installed locally
When the developer runs `cadence onboard`
Then it installs the host hooks (same mechanism `cadence init --full`
uses), reports the existing project name and gate profile read from
`.cadence/`, reports provider/API-key readiness (present/missing, no
secrets printed), and does not touch `.cadence/config.json` or
`state.json`.

### AC-2: `cadence onboard` refuses cleanly when there is nothing to onboard onto
Given a repo with no `.cadence/` directory
When the developer runs `cadence onboard`
Then it exits non-zero with a message directing them to `cadence init`
instead, matching the existing refuse+suggest pattern (no scaffolding, no
partial side effects).

### AC-3: `cadence init` seeds a discoverable onboarding pointer
Given `cadence init` completes (default or `--full`) in a repo without a
`CONTRIBUTING.md`, or with one that lacks the managed block
When init finishes
Then a managed block (merge-idempotent, matching the `writeClaudeMd`
merge-managed-block pattern) is written into `CONTRIBUTING.md` telling the
next contributor cloning the repo to run `cadence onboard`; a second
`cadence init --claude-md`-style regeneration does not duplicate the block.

## Boundaries

- DO NOT have `cadence onboard` write, scaffold, or mutate
  `.cadence/config.json` or `.cadence/state.json` — it is read-only against
  existing CADENCE state; only host-hook installation and stdout/stderr
  output are side effects.
- DO NOT have `cadence onboard` call `cadence activate` or write provider
  API keys anywhere — it only reports readiness (present/missing), never
  handles or persists secrets.
- DO NOT modify this repo's own root `CONTRIBUTING.md` as part of building
  the init-time snippet feature — the managed block is for repos that
  `cadence init` scaffolds (consumer projects), not for CADENCE's own
  hand-authored contributing doc.
- DO NOT duplicate the host-adapter spawn logic between `init.ts` and
  `onboard.ts` — both must call the T1 shared module.
- DO NOT expand scope to Codex-host-specific onboarding flows beyond what
  the existing `maybeWireHost` dual-host (Claude Code / Codex) logic
  already covers.
