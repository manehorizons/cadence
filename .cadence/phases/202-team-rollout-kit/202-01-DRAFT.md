# 202-01 — Team rollout kit

## Objective

Give teams a way to see CADENCE gate/settle results in PR review via a new deterministic summary-rendering subcommand, plus documented rollout guidance for adopting CADENCE across a team without replacing existing CI or human review.

## Acceptance Criteria

### AC-1: PR reviewers can see gate/settle results without reading raw JSON
Given a phase has been settled and its SUMMARY.json committed
When a reviewer runs `cadence summary render <phase> <num>`
Then it prints a deterministic, human-readable rendering of gate outcomes and per-AC status suitable for pasting into a PR description or comment, without needing to open SUMMARY.json by hand

### AC-2: malformed or missing SUMMARY.json is handled deliberately
Given a phase directory with no SUMMARY.json, or one that fails schema validation
When `cadence summary render` is run against it
Then it refuses loudly with a clear stderr message naming the problem, rather than crashing or printing a blank/garbled summary

### AC-3: a documented rollout path exists for adopting CADENCE as a team
Given a team wants to start using CADENCE across multiple contributors
When they follow the new rollout documentation
Then they can find guidance covering shared conventions (PR template usage of `cadence summary render`, what reviewers should check, how gate bypasses are surfaced to the team) that does not require replacing their existing CI or code-review process

## Tasks

### T1: Implement `cadence summary render <phase> <num>`
- files: `packages/core/src/cli/commands/summary.ts`, `packages/core/src/cli/index.ts`
- action: read a phase's SUMMARY.json, validate it against the existing SUMMARY schema, and render a deterministic human-readable text/markdown rendering of gate outcomes and per-AC status to stdout
- verify: running the command against a real settled phase's SUMMARY.json prints correct, deterministic output
- done: AC-1

### T2: Refuse loudly on missing/malformed SUMMARY.json
- files: `packages/core/src/cli/commands/summary.ts`
- action: detect a missing SUMMARY.json or one failing schema validation and print a clear stderr refusal naming the problem instead of crashing or emitting a partial render
- verify: running against a phase directory with no SUMMARY.json, and against a deliberately corrupted one, both produce the documented refusal message and a non-zero exit code
- done: AC-2
- depends: T1

### T3: Add tests for `cadence summary render`
- files: `packages/core/tests/cli/summary-render.test.ts`
- action: cover the happy path (real settled-phase fixture) and the missing/malformed SUMMARY.json edge cases from T1/T2
- verify: `pnpm --filter @manehorizons/cadence-core test -- summary-render` passes
- done: AC-1, AC-2
- depends: T1, T2

### T4: Write team rollout documentation
- files: `docs/team-rollout.md`, `docs/reference/commands.md`
- action: document the PR-review workflow (using `cadence summary render` in a PR description/comment), shared team conventions, and how gate bypasses are surfaced to reviewers; register the new command in the command reference
- verify: `docs-command-count.test.ts` / command-reference doc-content tests still pass with the new command listed
- done: AC-3
- depends: T1

## Boundaries

- DO NOT scaffold or touch a CI gate workflow generator (`cadence init --ci` / rec-20260709-003) — explicitly out of scope for this phase.
- DO NOT auto-post to PRs or add a GitHub Actions dependency — `cadence summary render` is a plain CLI command the operator/reviewer runs by hand or wires into their own CI, not an automated poster.
- DO NOT introduce a new public API shape without documenting it in the ACs.
- DO NOT leave the missing/malformed-SUMMARY.json refusal behavior implicit or silent.
