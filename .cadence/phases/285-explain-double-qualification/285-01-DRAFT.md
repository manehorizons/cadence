# 285-01 — explain double qualification

## Objective

`cadence verify coverage --explain` must never silently produce a token that cannot match, and must never report NOT SATISFIED at exit 0 because the caller's argument was rewritten wrong. Under verification.coverageScheme: 'phase-qualified', passing an already-qualified --explain argument (e.g. 282-01/AC-4) currently causes the active draft's qualifier to be prepended a second time, producing a search token that can never match, silently and at exit 0. Per D-X (rec-20260816-001), the fix normalizes an already-qualified argument to its bare form and prints a stderr notice, matching the existing Quiet Fallback precedent a few lines above in the same function (the no-active-draft degraded path). The bare scheme is untouched; D-Y (files: glob expansion) is out of scope -- that is Phase I, a separate phase.

**As-built amendment (whole-branch review):** the same invariant cuts both ways, and T2's independent review found the opposite-direction failure the original Objective wording didn't anticipate -- a naive unconditional strip of an already-qualified argument down to an empty string (`--explain '<Q>/'`, nothing after the slash) produces a false SATISFIED at exit 0 via an empty-pattern match, which is a *worse* silent failure than the double-qualification bug this phase set out to fix. The shipped fix (AC-1) refuses this case outright rather than searching it; see T2's own As-built amendment below for the reproduction and fix.

## Acceptance Criteria

### AC-1: An already-qualified --explain token is normalized with a loud notice, never silently double-qualified
Given verification.coverageScheme: 'phase-qualified', an active draft `<Q>`, and `--explain <Q>/AC-N` (a token the caller already qualified)
When `cadence verify coverage --explain` runs
Then it does not search for `<Q>/<Q>/AC-N`; per D-X (option 3), it strips the leading `<Q>/` prefix, searches using the bare `AC-N` form (qualified once, exactly as `--explain AC-N` would be), and writes a stderr notice naming both the original argument and the bare form actually used. If stripping the prefix would leave an empty search token (`--explain <Q>/` with nothing after the slash), the command refuses with a non-zero exit and a message naming the problem, rather than searching an empty pattern -- `explainAcCoverage`'s `\b${acId}\b` degrades to matching every word boundary on an empty string, which would silently report `satisfied: true` for a search that searched nothing at all, a failure in the opposite (falsely-satisfied) direction from the bug this AC exists to fix, and the worse one to ship

### AC-2: The correct bare --explain AC-N path is byte-identical to pre-change
Given the same phase-qualified setup and the correct bare `--explain AC-N`
When the command runs
Then stdout and JSON output are byte-for-byte identical to a vitest snapshot committed before this phase's fix lands (`toMatchSnapshot()`, not a re-observed assertion), and no stderr notice is printed; the committed `.snap` file has an empty `git diff` after T2

### AC-3: The bare scheme is untouched, proven with a discriminating fixture
Given verification.coverageScheme: 'bare' and an `--explain` argument that looks qualified (contains `/` and matches state's `activeDraft`, which `bare` must never read)
When the command runs
Then the result is byte-for-byte identical to a vitest snapshot committed before this phase's fix lands, `satisfied` is `true` (the literal argument matched the literal token verbatim), `expectedQualifier` is `undefined`, and no qualifier-related stderr notice is printed -- note `satisfied` alone does not discriminate a leak here (a bare AC suffix still matches as a `\b`-bounded substring of the qualified-looking compound token), so the real signal a regression would trip is `expectedQualifier` becoming defined (`bare` never computes it) or the committed snapshot diverging

### AC-4: JSON shape and CoverageExplainResult are unchanged
Given --json and any of the scenarios above (bare arg, correct qualified arg, already-qualified arg)
When the command runs
Then the JSON output's key set matches CoverageExplainResult's own field list exactly, derived from source rather than hand-copied, in every scenario; only the acId value (when normalization occurred) and the stderr/exit surface differ; explainAcCoverage's exported signature and the CoverageExplainResult interface in packages/core/src/verify/coverage.ts are not edited by this phase

### AC-5: Docs state the bare-form contract under both schemes
Given docs/reference/commands.md's verify -> coverage --explain documentation
When phase 285 lands
Then it explicitly states --explain takes the bare AC-N form under both schemes, and documents that an already-qualified argument under phase-qualified is normalized to its bare form with a stderr notice rather than silently producing an unmatchable token
