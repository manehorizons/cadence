# 286-01 — Boundary glob expansion

## Objective

A `files:` entry containing a wildcard must match the files it describes, in
both `warn` and `block` mode. Today `runBoundaryCheck` (`packages/core/src/
checks/boundary.ts`) compares `declaredFiles` to `touchedFiles` via exact
`Set` membership — no glob library is in `packages/core`'s dependencies, so a
declared entry like `.changeset/*.md` can never match anything. Under
dispatch-scoped `block` mode (phase 280) this produces a hard refusal on
correctly-scoped work; phase 281's T6 already hit the `warn`-mode version live
(declared `.changeset/*.md`, wrote exactly that file, got a
`files-outside-boundary` anomaly anyway). Per dec-20260821-001 (D-Y): reuse
the existing `globToRegExp`/`toMatcher` from `packages/core/src/verify/
coverage.ts:655` (extracted to a shared module, no new dependency), scoped to
wildcard-containing entries only so literal declarations keep today's exact
behavior; a wildcard entry that matches zero touched files gets a new,
separate, warn-only anomaly that cannot reach any block-mode refusal path.

## Acceptance Criteria

### AC-1: A wildcard `files:` entry matches the file it describes
Given a declared `files:` entry `.changeset/*.md` and a touched file
`.changeset/foo.md`
When `runBoundaryCheck` runs
Then no `files-outside-boundary` anomaly is emitted for that file. The glob
follows the existing `globToRegExp` semantics verbatim: `*` matches within a
single path segment (`[^/]*`), so `.changeset/*.md` matches `.changeset/
foo.md` but does **not** match `.changeset/nested/foo.md` or `.changeset/
foo.md.bak`.

### AC-2: A literal declared entry's boundary-check output is unchanged
Given a declared entry containing no `*` and the same declared/touched-file
scenarios already exercised by the *existing* boundary test suite
(`checks/boundary.test.ts`, `cli/build-task-boundary.test.ts`, `gates/
boundary-scan.test.ts`, `hooks/handlers-boundary-block.test.ts`)
When `runBoundaryCheck` (or a caller built on it) runs
Then it emits exactly the same `AnomalyEvent[]` it always has — proven by
explicit, hand-written `toEqual()` expectations (not `toMatchSnapshot()`,
whose capture-order a static read of the tree cannot establish) covering
each suite's existing literal-declaration scenarios, and by the literal
matching path (`literalDeclared.has(normFile)`, the same `Set.has` on the
same `norm()` closure as before) being structurally unreachable from the new
wildcard-matcher code — wildcard entries are filtered into a separate array
before the literal check ever runs, so the literal path cannot be affected by
this phase's changes by construction, independent of test provenance.

### AC-3: An undeclared file still refuses in `block` mode, wildcard or not
Given a touched file matching no declared entry — literal or wildcard — when
the check runs in `block` mode, then it still refuses and names the file.
Proven with an adversarial fixture combining a wildcard declaration
(`.changeset/*.md`) that correctly matches one touched file
(`.changeset/foo.md`) alongside a second, genuinely undeclared touched file
in the same run — the second file must still produce a `files-outside-
boundary` anomaly at `severity: 'error'` and drive `blockRefusal` in
`services/build-task.ts` exactly as today.

### AC-4: The matcher is the existing in-repo glob compiler, no new dependency
Given `packages/core` has no glob/minimatch/micromatch dependency today, and
`globToRegExp`/`toMatcher` live as module-local functions in
`packages/core/src/verify/coverage.ts`
When the boundary check (`checks/boundary.ts`) needs glob matching for
wildcard `files:` entries
Then it reuses the same two functions, extracted verbatim into a new shared
module (`packages/core/src/util/glob.ts`) and imported by both
`coverage.ts` and `checks/boundary.ts` — not duplicated — and
`packages/core/package.json`'s `dependencies` + `devDependencies` key set is
asserted, by a test reading the file live, to be byte-unchanged; no
glob/minimatch/micromatch dependency is added.

### AC-5: A zero-match wildcard warns; a zero-match literal stays silent
Given a declared entry containing `*` that matches **zero** touched files
(per dec-20260821-001, D-Y)
When the boundary check runs
Then a new, additive `AnomalyType` (`boundary-pattern-unmatched`) is emitted
at a **hardcoded** `severity: 'warn'` — it ignores the caller's requested
`severity` and can never appear at `'error'` — returned from a **separate**
new function (`findUnmatchedBoundaryPatterns`), never merged into
`runBoundaryCheck`'s existing `AnomalyEvent[]` return, and wired into exactly
one call site (`services/build-task.ts`) as an advisory stderr notice that
does **not** feed `blockRefusal`. The other three `runBoundaryCheck` call
sites (`hooks/handlers.ts`'s pre-edit block, `gates/boundary-scan.ts`,
`notify/collect.ts`) are untouched by this AC.
Given a **literal** declared entry that matches zero touched files instead
When the boundary check runs
Then nothing is emitted — the common case (a task declaring 3 files and
touching 2 of them) stays silent exactly as today. Proven with a test
asserting the new anomaly is absent from the array `services/build-task.ts`
uses to compute `blockRefusal`, even when `boundaryEnforcement` resolves to
`block`.

**Follow-up filed, not fixed here (T3, independent-reviewer finding):** the same review confirmed a real, latent limitation — `build-task.ts`'s `declaredFiles` is the union of *all* tasks' `files:` in a draft, while `touchedFiles` passed to `findUnmatchedBoundaryPatterns` is only the current task's delta (earlier tasks' already-touched files are subtracted). In a multi-task draft where an earlier task already satisfied a wildcard pattern it declared, recording a *later* task re-triggers a spurious `boundary-pattern-unmatched` advisory for the earlier task's already-matched pattern. Confirmed non-issue for phase 286-01's own build (T1/T2/T3's `files:` lists contain no `*` entries), and it is warn-only noise, never a refusal — but the reviewer correctly noted it reintroduces exactly the "noise on nearly every task" class dec-20260821-001 scoped wildcard-only detection to avoid, just for wildcard-declaring multi-task drafts specifically. Filed as a recommendation (see report) rather than expanded in this phase, per the Boundaries below and to avoid scope creep on an already-landed, independently-reviewed design.

## Boundaries

- Do NOT change when the boundary check runs — phase 280's seams (which call sites invoke `runBoundaryCheck` and when) stand unchanged; only `build-task.ts` gains the new advisory call.
- Do NOT change `boundaryEnforcement` defaults or its resolution logic (`gates/engine.ts`'s `effectiveBoundaryEnforcement`).
- Do NOT add a new runtime dependency — the existing `globToRegExp`/`toMatcher` extraction is the only matcher used.
- Do NOT merge the new `boundary-pattern-unmatched` anomaly into `runBoundaryCheck`'s existing return array, and do NOT wire it into `hooks/handlers.ts`, `gates/boundary-scan.ts`, or `notify/collect.ts` — those three call sites gate on `events.length` today, and mixing the new type in would let a zero-match wildcard trigger a hard block-mode refusal, which is the exact class of bug this phase exists to avoid, not introduce.
- Do NOT make a literal (non-wildcard) declared entry warn on zero matches — that is today's normal, common, silent case and must stay silent.
- Do NOT implement `--explain` double-qualification (rec-20260816-001) — that shipped separately as phase 285.
