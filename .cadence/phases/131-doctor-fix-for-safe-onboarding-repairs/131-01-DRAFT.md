# 131-01 — doctor --fix for safe onboarding repairs

## Objective

Give `cadence doctor` a `--fix` mode that applies safe, deterministic,
in-process repairs for the mechanically-fixable findings and reports what
changed — converting diagnosis into momentum. `--fix --wire-host` additionally
re-runs the host install for host-wiring findings (explicit opt-in, since it
spawns the host package and writes into `.claude/`); `--fix --dry-run` previews
without writing. No prompts anywhere — agent/non-TTY-safe by construction (the
v1.29 lesson). Safety comes from the *classification* of each repair, not a
confirmation gate. Source: rec-20260619-004. Design:
`docs/superpowers/specs/2026-06-26-doctor-fix-design.md`.

Fix classification (the 9 existing checks):
- **auto** (plain `--fix`): `git-hooks` → `git config core.hooksPath .githooks`;
  `state` *STATE.md-missing branch only* → regenerate `STATE.md` from valid
  `state.json`.
- **wire-host** (`--fix --wire-host`): `host-hooks`, `host-commands` → spawn
  `cadence-host-claude-code install` (deduped to one run).
- **manual** (never auto-applied): `node`, `initialized`, `state`(corrupt json),
  `worktree-phases`, `verification-readiness`, `handoff-retention` — reported as
  guidance using each check's existing `remediation`.

## Acceptance Criteria

### AC-1: pure planner classifies fixable findings
Given a `DoctorReport` with a mix of passing and failing checks
When `planFixes(report)` runs
Then the returned plan includes only non-ok checks, each classified as
`auto` / `wire-host` / `manual` per the design table (driven by a new
`fixId` tag on the check, not by parsing detail strings)

### AC-2: `--fix` applies the in-process auto repairs and re-checks
Given a repo whose `git-hooks` (`core.hooksPath` unset) and/or `state`
(`STATE.md` missing) checks are failing
When `cadence doctor --fix` runs
Then `core.hooksPath` is set to `.githooks` and `STATE.md` is regenerated from
the valid `state.json` (without rewriting `state.json`), the checks are re-run,
and the post-fix state is reported

### AC-3: `--dry-run` previews without writing
Given fixable findings exist
When `cadence doctor --fix --dry-run` runs
Then nothing is written (`core.hooksPath` and `STATE.md` are untouched) and the
planned actions are printed

### AC-4: host repairs are gated and deduped
Given the `host-hooks` and `host-commands` checks are both failing
When `cadence doctor --fix --wire-host` runs
Then the host install subprocess is invoked exactly once (deduped by `fixId`);
and when run as plain `cadence doctor --fix` those repairs are reported as
not-applied rather than executed

### AC-5: manual findings stay guidance; non-interactive; JSON carries the plan
Given `manual`-class findings (e.g. `verification-readiness`, `worktree-phases`)
When `cadence doctor --fix` runs
Then they are never auto-applied — reported as guidance with their existing
remediation — the command issues no prompt (non-TTY-safe), and
`cadence doctor --fix --json` includes the fix plan and applied-fix outcomes

## Boundaries

- DO NOT modify the 9 checks' diagnostic logic — they stay read-only; the only
  change is the additive `fixId` tag.
- DO NOT add a `cadence repair` command, auto-set `handoff.retain`, add an MCP
  check/repair, or add an interactive confirmation mode (all explicitly out).
- DO NOT let any repair throw out of the command — every repair is best-effort
  and reported.
- DO NOT have `core` import host code — host install is reached only via the
  existing subprocess-spawn helper.
- DO NOT rewrite `state.json` when regenerating `STATE.md`.
