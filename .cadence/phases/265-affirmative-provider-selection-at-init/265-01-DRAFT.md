# 265-01 — Affirmative provider selection at init

## Objective

Make cadence init present the verifier provider choice explicitly and record it as a retrievable intelligence-ledger decision, so no repo can run indefinitely under an inherited default without the operator having made or seen that choice -- without requiring a real provider (D-B) or breaking any non-interactive init path.

## Acceptance Criteria

### AC-1: Interactive prompt presents explicit choice
Given a session where a prompter is available (real TTY stdin, or CADENCE_PROMPTER_SCRIPT set for scripted testing of this same prompt logic) and no --verifier-provider flag, no --activate/--full flag given
When init resolves the verifier provider before writing config.json
Then it runs the prompt logic (real readline on a real TTY, scripted answers when CADENCE_PROMPTER_SCRIPT is set) asking the operator to choose explicitly among mock, anthropic, local, host-cli, with mock presented as a legal, unshamed, first-class option rather than silently defaulted past

### AC-2: Non-interactive paths never hang
Given init runs with no prompter available (non-TTY stdin AND CADENCE_PROMPTER_SCRIPT unset), or an explicit --verifier-provider/--activate/--full flag is given (which always wins over prompting, even under a TTY)
When init resolves the verifier provider
Then it completes without prompting or hanging -- an explicit flag is honored outright, and the no-flag/no-prompter case silently resolves to mock (D-B: never coerced to a real provider) -- --dry-run's InitPlan also reports what would happen (prompt vs explicit vs default-mock) without ever writing a decision

### AC-3: Selection recorded as a ledger decision
Given any completed init run -- interactive, explicit-flag, or defaulted-mock
When the verifier provider is resolved (scope defaults to deep-verify-only, same default activate's non-interactive --provider path uses; the interactive prompt may additionally ask an activate-style "apply to every verifier gate?" follow-up to widen scope to all)
Then addIntelligenceDecision records the choice (provider + scope) in .cadence/intelligence/decisions.json WITHOUT a recommendationId (rec-20260808-006 only exists in this repo's own ledger; passing it would throw unknown recommendation in a consumer repo), so the record is retrievable via cadence decision list even though config.json alone was already sufficient to infer the provider

### AC-4: Consequence message is profile-conditioned, not a blanket claim
Given the resolved verifier provider and the resolved gate profile (resolveGateProfile's output) at init time
When the plain-language consequence is composed for display and for the decision rationale
Then it correctly distinguishes the auto-profile case (per gates/engine.ts DELTAS and dec-20260808-004: code-review and security-audit never fire under auto profile at any tier, so assurance.overall: strong is unreachable regardless of provider) from the standard/strict-profile case (a real provider is a necessary but not automatically sufficient condition, since tier still gates which review gates fire) -- derived from gates/engine.ts and deriveAssuranceRecord, never asserted from memory -- and a test proves the message differs correctly between an auto-profile init and a strict-profile init

### AC-5: onboard does not gain a prompt
Given cadence onboard run against a repo whose .cadence/ already carries a recorded provider selection, or one that predates this phase and carries none
When onboard runs, TTY or not
Then it continues to only report existing verifier readiness via assessReadiness -- exactly today's behavior -- and never prompts for a provider choice, verified against the phase 246 onboard semantics (readOnboardProject / bootstrapMissingState) with a regression test asserting no prompter is invoked for provider selection

- DO NOT modify `onboard.ts` -- T4 only adds a regression test proving its existing no-prompt behavior holds.

- DO NOT pass `recommendationId: 'rec-20260808-006'` (or any id) to `addIntelligenceDecision` -- that recommendation exists only in this repo's own ledger; passing it would throw `unknown recommendation` in every consumer repo that runs `cadence init`.
