# 165-01 — Host-CLI headless verifier provider

## Objective

Add a 4th verifier provider (`host-cli`) that authenticates by shelling out to the user's already-installed, already-authenticated host CLI (`claude` / `codex`) in headless mode, so independent AC verification works without a separately configured `ANTHROPIC_API_KEY`.

## Acceptance Criteria

### AC-1: host-cli provider produces schema-valid verdicts
Given `verification.provider` (or a per-family provider slice) is set to `host-cli` and the configured host CLI binary is installed and authenticated
When a verification gate runs (e.g. deep-verify)
Then the provider spawns the host CLI in headless/non-interactive mode with the per-AC prompt, parses its output into a schema-valid verdict via the shared repair-retry harness (AC-4), and returns the same verdict shape the `local`/`anthropic` providers return today.

### AC-2: Loud, non-blocking fallback when the host CLI is unavailable
Given `host-cli` is selected but the configured binary is not found on PATH or is not authenticated
When the verifier factory resolves the provider
Then it falls back to `mock` with the same stderr warning banner pattern used by `anthropic`/`local` today (never a silent fallback, never a hang waiting on interactive auth — this covers the CI/non-interactive case from rec-20260710-006).

### AC-3: No new HostAdapter surface
Given the existing `HostAdapter`/`HostCapabilities` contract (`packages/types/src/host.ts`)
When the `host-cli` provider is implemented
Then it adds zero new fields/methods to `HostAdapter`/`HostCapabilities` — the provider lives entirely in `packages/core/src/verify/`, spawning the CLI binary directly the same way `local-client.ts` calls an arbitrary HTTP endpoint (core-imports-host is never touched).

### AC-4: Repair-retry harness is shared, not duplicated
Given `local-client.ts`'s existing JSON-extraction + schema-repair-retry logic (`extractJson`, `safeJson`, the retry loop)
When the `host-cli` provider needs to coerce host-CLI stdout into a schema-valid verdict
Then that logic is factored into a shared, transport-agnostic module used by both `local` and `host-cli` (the only new transport-specific code is the subprocess spawn/capture, mirroring `callOnce`'s fetch call).

## Constraints

- No new required env var — provider selection lives in the existing `verification.provider` config slice; add `'host-cli'` to the `VerifierProvider` union in `verifier-factory.ts`.
- Must not require any change to `HostAdapter`/`HostCapabilities` — binary discovery/spawn stays entirely inside core's verify module (see AC-3).
- Tests must not depend on a real `claude`/`codex` binary being installed — stub the subprocess transport; the suite stays offline/deterministic per the "Live-Provider Test" convention (mock only).
- Must not hang in CI/non-interactive environments waiting on interactive host-CLI auth — falls back per AC-2 instead.

## Open Questions

- Which flag reliably produces machine-parseable JSON per host CLI in headless mode — `claude -p --output-format json` vs. `codex exec` (or equivalent) — needs a quick spike against both real binaries before committing to exact spawn args.
- Binary-discovery strategy: fixed `which claude`/`which codex` PATH lookup, or an explicit override (e.g. `CADENCE_HOST_CLI_BIN`) for non-standard installs?
- Per-AC vs. per-gate-run batching (rec-20260710-004): start per-AC (matches today's provider call shape, simplest) and revisit batching only if spawn latency proves to be a real problem in practice — is that deferral acceptable for this slice?
- Quota-transparency guardrail (rec-20260710-006 — surfacing that verification now consumes the user's host-CLI subscription quota): in scope for this slice, or an explicit follow-up phase?
