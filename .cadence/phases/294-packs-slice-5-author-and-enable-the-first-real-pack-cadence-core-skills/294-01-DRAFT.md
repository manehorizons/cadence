# 294-01 — packs slice 5: author and enable the first real pack (cadence/core-skills)

## Objective

Slices 1-4 (phases 290-293) built the entire packs mechanism -- manifests resolve and validate, skillAudit.required unions with per-requirement provenance, gates[].add unions into effectiveGateSet, and declared commands[] are doctor-checked -- but no pack has ever existed: `.cadence/packs/` does not exist, `config.packs.enabled` is empty, and `skillAudit.provenance` reads `[]` in all four packs phases' own settle artifacts. This phase authors and enables CADENCE's own pack, `cadence/core-skills`, producing the first live pack resolution against a real manifest in a real settle. Investigation (D-AV) found the mechanism's telemetry precondition is currently broken in this repo -- `.claude/settings.json`'s `PostToolUse` hook array is missing the `Skill`-tool matcher that `install.ts` generates, so `state.skillAudit.invoked` never populates and `runSkillAuditCheck` would hard-refuse any settle that declared a `skillAudit.required` entry. The manifest therefore declares only `commands[]`; the empty-provenance consequence of that choice is itself proven and recorded as AC-3, not hidden.

## Acceptance Criteria

### AC-1: the real manifest resolves
Given `.cadence/packs/cadence/core-skills/pack.json` authored with `id: "cadence/core-skills"`, a `version`, and a `commands` array (no `skillAudit`, no `gates`)
When `resolvePacks` runs against a config enabling `cadence/core-skills` and the real repo root (not a tempRepo fixture)
Then it returns a single success entry `{ id: 'cadence/core-skills', source: 'local', manifest }` whose `manifest` deep-equals the file's actual parsed contents

### AC-2: doctor is clean against the enabled pack
Given the pack enabled in `.cadence/config.json`
When `cadence doctor` runs (proven both by a unit test calling `checkPacks`/`checkPackCommands` against the real repo root, and by real `cadence doctor` command output)
Then the `packs` check reports the pack resolved and the `pack-commands` check reports no warning -- every declared command is a real key of `COMMAND_GUIDANCE`

### AC-3: a commands-only pack leaves no skillAudit trace (the honest negative result)
Given the manifest deliberately omits `skillAudit.required` (D-AV: the host's Skill-tool `PostToolUse` matcher is unregistered in this repo, confirmed by reading `.claude/settings.json` against `packages/host-claude-code/src/install.ts`'s `matched(SKILL_TOOL_MATCHER)` registration and by a synthetic hook payload proving the handler itself is correct; `runSkillAuditCheck` in `packages/core/src/checks/skill-audit.ts` hard-refuses, severity `error`, when `config.telemetry.skillInvocations` is true and a required skill was never invoked)
When `runSkillAuditCheck` runs against the resolved `cadence/core-skills` pack
Then `requiredWithProvenance` (the array `state.skillAudit.provenance` is recorded from) contains zero entries with `source: 'pack:cadence/core-skills'` -- proving a commands-only pack produces no provenance entry in any settled `SUMMARY.json`, replacing this phase's originally-hypothesized "first non-empty provenance array" outcome with a recorded negative finding

### AC-4: disabled wins over enabled
Given `cadence/core-skills`'s id present in both `packs.enabled` and `packs.disabled`
When `resolvePacks` runs against the real manifest file
Then it is not resolved (empty result) -- D-AQ's disabled-wins rule exercised against a real manifest, not only a fixture

### AC-5: a malformed copy fails closed
Given a deliberately malformed copy of the real manifest (an unrecognized top-level key added)
When it is parsed through `PackManifestZ`
Then it fails with a specific Zod validation reason -- `.strict()` proven against a real file's shape, not only a fixture

### AC-6: the design doc gains Slice 5
Given `docs/packs-design.md` §7's slice plan ends at Slice 4
When this phase settles
Then §7 gains a Slice 5 entry in the same shape as Slices 1-4 (objective + acceptance) and the §3 status banner reflects Slice 5 landed
