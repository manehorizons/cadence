# 113-01 — One onboarding front door + guided Next: rail

## Objective

Make `cadence start` the single, unambiguous onboarding front door (with
`cadence quickstart` reframed as the post-init "where am I / what's next" map),
and give every onboarding command a closing `Next:` line so the first session
is a guided rail with no dead-ends.

Decision (locked, rec-20260617-007): **`start` = the door, `quickstart` = the
map.** v1.27 "onboarding breeze" fixed the `init` sub-path but not the
top-level door; this closes that gap. Copy/UX-only except one small `doctor`
code change.

## Acceptance Criteria

### AC-1: README leads with one front door
Given the README Quickstart section
When a newcomer reads the "New to CADENCE?" guidance
Then `cadence start` is presented as the single entry point and the co-equal
"(or `cadence quickstart` for a read-only map)" phrasing is gone — `quickstart`
is instead described as the post-init map ("once set up, … where you are + next
moves").

### AC-2: doctor ends with a Next: line
Given `cadence doctor` finishes a run
When its human-rendered output is produced
Then it ends with exactly one `Next:` line — pointing at the first problem's
remediation when any check is non-ok, else at `cadence progress` — sourced from
a pure, unit-tested helper. (`--json` output is unchanged.)

### AC-3: docs/quickstart.md opens with a driver fork
Given the docs Quickstart page
When a reader starts it
Then the top presents a 3-way "how are you driving CADENCE?" fork (terminal /
Claude Code / MCP) so host users branch immediately instead of finishing the
CLI-only path first.

### AC-4: start and quickstart cross-reference their roles consistently
Given the rendered output of `cadence start` and `cadence quickstart`
When each points at the other
Then `start` is named as the action front door and `quickstart` as the
read-only map, with no "go run the other one" loop (each points onward, not in a
circle).
