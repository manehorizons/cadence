# 134-01 — cadence progress --json

## Objective

Add `--json` to `cadence progress` so agent/MCP callers get the same
structured `{ command, reason }` payload the service already returns,
instead of having to regex the two rendered text lines — closing
rec-20260701-004 / audit finding F4 (the loop-write/progress commands are
the one gap in an otherwise `--json`-covered CLI).

## Acceptance Criteria

### AC-1: --json emits the structured payload instead of rendered text
Given any loop state
When `cadence progress --json` runs
Then stdout is a single JSON object `{ command, reason }` (parseable via
`JSON.parse`) and the rendered `Next:`/`Reason:` text lines are not printed

### AC-2: default (no flag) behavior is unchanged
Given any loop state
When `cadence progress` runs without `--json`
Then stdout is unchanged — the existing `Next: ...` / `Reason: ...` two-line
rendering

### AC-3: --json composes with every loop position
Given IDLE, DRAFT, BUILD, and SETTLE-adjacent states
When `cadence progress --json` runs in each
Then the JSON payload's `command` field matches what the non-JSON `Next:`
line would have said for that same state

## Constraints

- Mirror the existing `recommendService`/`recommend --json` pattern
  (`packages/core/src/services/recommend.ts`) — no new JSON shape invented.
- No change to `progressService`'s return value (`data: { command, reason }`
  already exists); this is a CLI-flag + output-branch change only.

## Open Questions

- None — reproduced directly in the 2026-07-01 audit (evidence
  ev-20260701-004): `cadence progress --json` currently exits 1 with
  "unknown option".
