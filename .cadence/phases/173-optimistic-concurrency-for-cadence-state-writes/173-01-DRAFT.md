# 173-01 — Optimistic concurrency for cadence state writes

## Objective

Prevent lost updates when two cadence state writers (CLI commands, hooks, or the MCP server) race on .cadence/state.json in the same checkout, by adding an optimistic-concurrency revision check to SimpleStateBackend.commit(), the single write choke point every writer already shares.

## Acceptance Criteria

### AC-1: Backward-compatible schema
Given an existing state.json file written before this phase, with no revision key at all
When it is parsed by the updated CadenceStateZ schema
Then it parses successfully with revision defaulting to 0, and emptyState() also includes revision: 0

### AC-2: Stale write refused
Given two independent readers have read the same on-disk state.json revision in the same checkout
When one of them commits successfully and the other then commits based on its now-stale read
Then the second commit is refused with StateConflictError naming both revisions, and the on-disk file is left as the first writer left it

### AC-3: Sequential same-object commits do not self-conflict
Given a single command reads state once and calls commit() twice in a row on that same in-memory object (e.g. handlePostToolEdit's two independent write branches)
When the first commit() call succeeds
Then the second commit() call also succeeds without throwing, because state.revision was bumped in place by the first call

### AC-4: Bootstrap write unaffected
Given no state.json exists yet at the target .cadence directory
When commit() is called
Then it writes successfully without any revision comparison, since there is nothing on disk to conflict with

### AC-5: Force bypass warns loudly
Given a caller holds a state object whose revision is stale relative to disk
When commit(state, { force: true }) is called
Then it overwrites unconditionally and writes a stderr warning naming both revisions

## Boundaries

- Do NOT add a lock file, PID/process-identity tracking, or signal handling — the design deliberately rejected the lock-based approach during spec review (see docs/superpowers/specs/2026-07-12-cadence-write-lock-design.md).
- Do NOT thread a `--force-commit` CLI flag through any command in this phase — the `force` option is backend-level only for now (explicit scope decision made during planning); CLI wiring is deferred to a future phase if the default refuse-and-retry recovery proves insufficient in practice.
- Do NOT change `renderStateMd`/`STATE.md`'s rendered content — the design does not require surfacing `revision` in the human-readable view.
- Do NOT add a runtime dependency (e.g. a file-locking package) — the mechanism is pure in-process comparison logic, zero-runtime-dependency bias applies.
- Do NOT modify `atomic-write.ts` — the existing atomic temp-file+rename write path is reused unchanged.
