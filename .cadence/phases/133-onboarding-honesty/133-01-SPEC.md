# 133-01 — doctor git-hooks check: verify dir before flagging/fixing

## Objective

Fix `cadence doctor`'s `git-hooks` check and `--fix` repair so a missing
`.githooks/` directory is reported not-applicable instead of `warning`, and so
`--fix` never overwrites a pre-existing custom `core.hooksPath` (e.g. a Husky
`.husky` setup) — closing rec-20260701-002 / audit finding F2.

## Acceptance Criteria

### AC-1: missing .githooks/ is not-applicable, not a warning
Given a git repo whose `.githooks/` directory does not exist on disk
When `cadence doctor` runs the `git-hooks` check
Then the check reports `pass`/not-applicable (not `warning`), and `doctor --fix`
does not classify it as an `auto` fix

### AC-2: a pre-existing custom hooksPath is never auto-overwritten
Given a git repo with `core.hooksPath` already set to a non-`.githooks` custom
value (e.g. `.husky`)
When `cadence doctor --fix` runs
Then the `git-hooks` repair is classified `manual` (not `auto`) and no `git
config` write is made, so an existing Husky-style setup is left untouched

### AC-3: the happy path is unchanged
Given a git repo with `.githooks/` present and `core.hooksPath` unset (or
already `.githooks`)
When `cadence doctor` / `cadence doctor --fix` runs
Then behavior is unchanged from today (warn + auto-fix to `.githooks` when
unset; pass when already `.githooks`)

## Constraints

- No new config knob — this is a correctness fix to the existing `git-hooks`
  check (`packages/core/src/doctor/run.ts`) and fix classification
  (`packages/core/src/doctor/fix.ts`), not a new feature.
- Must not change behavior for the common case (no `.githooks` dir doesn't
  exist in most consumer repos today's exact wording — new wording only for
  the two corrected paths above).
