## As built (post-settle amendment, 2026-08-06)

This phase settled clean (`assurance.overall: strong`, both `code-review`/`security-audit` ran with `provider: host-cli`) but two things drifted from the plan above during Thomas's live conduction run, both caught by real (non-mock) code-review calls, not anticipated at DRAFT-authoring time:

- **AC-1's actual verification shape differs from the Given/When/Then above.** T2's test went through two more real-provider-caught revisions after T1 closed AC-1: (1) a hard assertion that `seeded-defect.ts` always trips both detectors broke the moment step 5 overwrote it in place with the fixed counterpart's content -- a real code-review call flagged the test itself as broken; (2) the fix that followed (asserting the two detectors merely agree with each other) was too weak -- it passed even with *neither* seeded defect present, which a second real code-review call also caught. The design that actually shipped: a synthetic sample (built via string concatenation, not a literal credential-shaped string, to avoid the same self-trigger risk) validates the detector regexes independent of live disk content; `seeded-defect.fixed.ts` (never mutated) keeps a hard "trips neither" assertion; and `seeded-defect.ts` is asserted to always be in exactly one of two legitimate states -- byte-identical to the fixed counterpart, or genuinely tripping both detectors -- never a third, silently weaker state. Verified adversarially (fixed state passes, vulnerable state passes, a hand-sabotaged "neither defect" state correctly fails) before the final settle.
- **The counting claim in AC-2/Boundaries above ("only step 5's clean settle counts toward `dec-20260801-003`'s revisit trigger") is wrong and should not be trusted.** `dec-20260801-003`'s actual trigger text: "at least 3 settles under a non-mock review provider (anthropic/local/host-cli) have each persisted at least 1 code-review finding." That is a settle-level count of *any* persisted code-review finding, not "the one clean settle" -- and the clean settle (step 5, `256-02-SUMMARY.json`) itself carries exactly one MEDIUM finding (see below), so even the framing of "the clean settle has zero findings" underlying the original boundary was factually wrong. Counted directly from this phase's persisted artifacts: `256-02-refused-2026-08-06T04-21-23-042Z` (2 findings), `...T04-33-37-866Z` (2), `...T04-43-22-653Z` (3), `...T05-08-23-709Z` (1), `...T05-13-30-388Z` (2), and the final `256-02-SUMMARY.json` (1) -- **six** real, non-mock settles each persisting >=1 code-review finding, all under `provider: host-cli`. This phase alone exceeds `dec-20260801-003`'s 3-settle threshold; the trigger's literal numeric condition is met. Whether the *content* of those six is actually useful drift-analysis data (several are repeat invocations against unchanged vulnerable content, which may not be independent signal) is exactly the question the decision's own planned "offline analyzer over the accumulated SUMMARY.json corpus" exists to answer -- not asserted here. See `ev` added to `rec-20260801-010` for the pointer; revisiting `dec-20260801-003` itself is a separate, future decision, not made by this phase.
- **A real, non-blocking gap in the deleted runbook, for the record since the file itself is gone:** the final clean settle's own MEDIUM code-review finding (on `CONDUCTION-RUNBOOK.md:180`) correctly identified that Step 3's "if it comes back clean instead of refused: STOP" contingency branch never routed back through Step 6 (revert `securityAudit.provider` to `mock`) -- so taking that branch would have left the repo's baseline config invalid.
