# 281-01 — Close the cadence done bypass hole

## Objective

Route `cadence done <id>` through `buildTaskService` so the documented shortcut for `build task <id> --status=DONE` carries identical guarantees — per-task-verify and the record-time boundary/redundancy check — to the command it claims to be a shortcut for.

## Acceptance Criteria

### AC-1: done refuses like build task when per-task-verify would refuse
Given a phase whose per-task-verify gate would refuse task T1
When `cadence done T1` runs
Then it refuses with the same exit code and message as `cadence build task T1 --status=DONE`, and PROGRESS.json is unmutated.

### AC-2: done refuses like build task under a block-mode boundary breach
Given `boundaryEnforcement` resolving to `block` and a working-tree file outside T1's declared `files:`
When `cadence done T1` runs
Then it refuses and names each stray file, matching `build task`'s refusal exactly.

### AC-3: done records identically to build task in warn mode
Given `warn` mode
When `cadence done T1` runs
Then it records the outcome and populates `touchedFiles` identically to `build task --status=DONE`.

### AC-4: existing done behavior is unchanged when none of the three inherited gates would refuse
Given a repo where none of the three gates `done` now inherits from `buildTaskService` would refuse — per-task-verify, the record-time boundary/redundancy check, and the pre-existing (phase 58) unknown-task-id guard
When `cadence done T1` runs
Then observable behavior (exit code, stdout line, PROGRESS row) is unchanged from pre-change — proven by the existing `tests/cli/done.test.ts` cases still passing, with the one case that named an undeclared task id (an incidental fixture choice, never actually valid — `build task` against the same undeclared id has refused since phase 58) corrected to use a declared id instead. (As-built amendment, D-N2/`dec-20260815-006`: the unknown-task-id guard was not identified at SPEC-authoring time; discovered when T4's build reproduced it.)

Also: given `cadence done` is invoked outside BUILD (a `LoopViolationError`), the emitted `anomaly-notify` `loop-violation` event's `context.source` remains `'build.done'`, distinct from `build task`'s `'build.task'` tag, matching `packages/core/tests/cli/loop-violation.test.ts`'s pre-existing, unmodified assertion. (As-built amendment, D-N3/`dec-20260815-007`.)

### AC-5: docs state done's gate parity and the bypass path, and the repo's own roadmap/milestone records reflect this phase
Given `docs/reference/commands.md`'s `done` section
When a reader looks up what gates `done` carries and how to bypass a refusal
Then it states that `done` carries the same gates as `build task --status=DONE` — per-task-verify, the record-time boundary/redundancy check, and the unknown-task-id guard (exit 2) — and names `build task` (with `--allow-per-task-failure` / `--allow-boundary-breach`) as the path for bypass flags, per decisions D-N (dec-20260815-005) and D-N2 (dec-20260815-006); and given `tests/docs/phase271-record-integrity.test.ts`'s roadmap-currency drift check, when this phase's own directory is on disk, then `.cadence/ROADMAP.md` and `.cadence/MILESTONES.md` each carry a Phase 281 entry so the drift check passes.

## Constraints

- No change to `buildTaskService` itself.
- No new flags on `done` beyond what exists today (`--notes`) — D-N chose the true-alias option, not flag passthrough.
- No touching `recordTaskOutcome` directly.
- `tests/cli/done.test.ts`'s existing cases must keep passing unmodified (they exercise the "neither gate refuses" path — no declared `files:`, no dispatch, default mock verifier).

## Open Questions

- None — D-N (dec-20260815-005) already resolved the alias-vs-passthrough question and its user-visible-refusal consequence.
