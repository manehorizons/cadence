# 240-01 — doctor verification-readiness checks every verifier seam, not just deep-verify

## Objective

Close #331: `verification-readiness` credential-checked only the deep-verify seam,
so `cadence doctor` reported `ok` while a sibling seam configured to a real
provider without credentials was guaranteed to downgrade to mock at call time.

## Acceptance Criteria

### AC-1: a downgrading sibling seam is reported, not blessed
Given `verifier` on `host-cli` (healthy, credential-free) and `specReview` on `anthropic` with no `ANTHROPIC_API_KEY`
When `cadence doctor` runs
Then `verification-readiness` is `warning`, not `ok`, and its detail/remediation names `specReview` and the provider that will downgrade

### AC-2: every affected seam is named, not just the first
Given two or more seams configured to a real provider whose credentials are absent
When the check runs
Then each offending seam is named in `VERIFIER_SEAMS` order

### AC-3: no new false positives
Given a seam on `mock` (announces itself) or on `host-cli` (no required credential by design)
When the check runs
Then neither is treated as a downgrade, and a fully credentialed config still reports `ok`

### AC-4: existing deep-verify behaviour is unchanged
Given the pre-existing all-mock, missing-key, Claude-Code-session, and `.env`-discovery cases
When the check runs
Then each returns exactly the severity and wording it did before, the deep-verify branches taking precedence over the new one

### AC-5: the configured-provider partition is untouched
Given `seamsReal` / `seamsMock`, which partition by configured provider name
When `assessReadiness` runs
Then their contents are unchanged and the new information is carried by a separate `seamsDowngraded` field

### AC-6: docs state the real contract
Given `docs/reference/commands.md`'s doctor-check table and `docs/providers.md`
When they describe `verification-readiness`
Then they say it covers every seam, since both previously documented the deep-verify-only contract

## Boundaries

- DO NOT change `seamsReal`/`seamsMock` semantics — existing tests assert they partition by configured provider name, which is a legitimate separate question.
- DO NOT escalate this check to `error`, and DO NOT make any previously-passing credentialed config warn.
- DO NOT flag `host-cli` seams: `credsPresent` returns true for them by design, since the binary's existence is checked lazily at spawn.
- DO NOT change the mock-fallback behaviour itself in `verify/verifier-factory.ts` — the downgrade is deliberate; only its visibility is in scope.
- DO NOT take on the two follow-ons filed under #331 (moving `MOCK_FALLBACK_BANNER` into the factory; reporting a mock-downgraded review as `skipped` rather than `ran` via phase 232's `verifierIdentity`) — separately scoped.
