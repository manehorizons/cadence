# 60-01 — Host-adapter contract + authoring guide

## Objective

Make the today-implicit Claude-Code host-adapter contract explicit as a lean,
versioned `HostAdapter` type (+ Zod) in `cadence-types` that `host-claude-code`
provably conforms to, and publish a "write your own adapter" guide on the docs
portal — without adding a second adapter or speculative capability flags.

## Context

A host adapter is defined today only implicitly, by what `host-claude-code`
exports: a `HostCapabilities` descriptor (`packages/types/src/host.ts`), an
event map (`mapEvent`: host event → `AbstractEvent`), payload extraction
(`extractPayload`/`ExtractedPayload`), an install surface (`installHooks`,
`installCommands`), and host-internal plumbing (`shim`/`routeHookEvent`,
`locate-self`/`resolveLocalPaths`). `AbstractEvent` already has a Zod schema
(`AbstractEventZ`); `HostCapabilities` does not, and there is no unifying
`HostAdapter` type or version constant. This phase closes that gap. It is the
documentation-and-contract slice of the deferred v1.5.0 multi-host milestone —
the "re-introduce a host-adapter contract" scope item — explicitly **minus**
"first second adapter" (gated on real user pull) per **DESIGN.md D11**.

## Acceptance Criteria

### AC-1: A typed `HostAdapter` contract exists, derived from real needs
Given `cadence-types` is the pure data layer
When the contract is added
Then a `HostAdapter` interface (or equivalent typed surface) exists in
`cadence-types` capturing the core-facing adapter surface — `capabilities`,
`mapEvent`, `extractPayload`, and the install entry points — modeled on
`host-claude-code`'s actual exports, with no capability fields that
`host-claude-code` does not itself use.

### AC-2: `HostCapabilities` gains schema parity
Given `AbstractEvent` already ships a Zod schema (`AbstractEventZ`)
When capabilities are formalized
Then a `HostCapabilitiesZ` Zod schema exists and `claudeCodeCapabilities`
parses/validates against it (asserted by a test).

### AC-3: The contract is versioned
Given "stable/versioned" is the rec's explicit ask
When the contract is published
Then an `ADAPTER_CONTRACT_VERSION` constant is exported from `cadence-types`
and the authoring guide cites it as the stability anchor.

### AC-4: `host-claude-code` provably conforms
Given the existing adapter is the reference implementation
When the contract lands
Then `host-claude-code` conforms to `HostAdapter` at compile time
(`satisfies`) **and** a test asserts the assembled adapter matches the contract
(capabilities validate, mapped events are within `AbstractEventZ`).

### AC-5: The authoring guide is published on the docs portal
Given the rec targets community adapter authors
When the guide ships
Then a "write your own adapter" page is published in the docs portal, its route
registered in `website/scripts/routes.mjs` (sync-docs link-checker passes), and
it walks the full contract with `host-claude-code` as the worked example
(event map, payload extraction, capabilities, install/shim/locate-self
responsibilities).

### AC-6: Existing behavior is unchanged
Given this is additive (types + docs)
When the phase completes
Then `host-claude-code` runtime behavior is byte-identical (all prior host +
core tests stay green; no engine changes).

## Constraints

- **D11 (amends D5):** this is a *documented capabilities contract*, NOT
  bespoke-adapter pluralism. MCP (`cadence mcp serve`, phase 58) is the chosen
  reach-path for non-Claude-Code surfaces.
- **No second adapter.** The ROADMAP activation gate ("no second adapter
  without a real user for it") still holds — this phase ships zero new host
  packages.
- **Leaner successor, not speculative flags.** The contract is derived from
  what `host-claude-code` actually needs (event map + payload + install/shim/
  locate-self), not re-inflated `HostCapabilities` speculation.
- **Engine stays host-unaware.** The host-agnostic-engine anchor is not
  inverted; adapters keep translating lifecycle → abstract events.
- **`cadence-types` stays pure.** Contract is types + Zod schema + a version
  constant only — no logic, no I/O.
- **Docs portal route discipline.** Register the new page in
  `website/scripts/routes.mjs`, or the `sync-docs` link-checker breaks the Docs
  workflow.

## Open Questions

- Contract version format: integer (`1`) vs semver string (`"1.0.0"`)?
  Leaning integer — the contract is coarse-grained and breaking-only.
- Are `shim`/`locate-self` (`RouteResult`, `LocalPaths`) part of the typed
  `HostAdapter` surface, or documented-only as host-internal plumbing? Leaning
  documented-only: the typed contract covers the core-facing surface
  (capabilities/mapEvent/extractPayload/install); shim + locate-self are
  host-internal responsibilities the guide describes but the type does not pin.
