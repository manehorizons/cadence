# 140-01 — SUMMARY gate provenance

## Objective

Record per-gate ran/skipped provenance and per-AC evidence class in SUMMARY, so a settle's PASS verdicts are auditable instead of opaque.

## Acceptance Criteria

### AC-1: SUMMARY.json records per-gate ran/skipped provenance
Given a successful settle run
When SUMMARY.json is written
Then its `gates` array records a `ran` or `skipped` (+ reason) status for
every one of the 8 settle-dispatched gates, in `GATE_ORDER`

### AC-2: acResults rows carry an evidence class
Given a settle run that produces `acResults[]`
When SUMMARY.json is written
Then each `acResults[]` row carries an optional `evidence` field set to the
strongest real evidence class found for that AC — `ai-verified`, `executed`,
`assertion`, `mention`, or `unverified`

### AC-3: mock-provider deep-verify never yields ai-verified evidence
Given `settle run --deep` (or any deep-verify path) using the `mock`
verifier provider
When per-AC evidence is derived
Then no AC's evidence class is ever `ai-verified` — it falls through to that
AC's test-coverage evidence instead

### AC-4: SUMMARY.md renders gate provenance and evidence tags
Given a written SUMMARY.json with `gates`/`evidence` data
When SUMMARY.md is rendered
Then it includes a `## Gate provenance` section (one line per gate) and an
evidence tag next to each AC line, plus deep-verify token usage when present

### AC-5: pre-phase SUMMARY records remain backward compatible
Given a SUMMARY.json/SUMMARY.md record written before this phase (missing
the `gates`/`evidence` fields)
When it is parsed or rendered by the updated code
Then it still parses and renders unchanged
