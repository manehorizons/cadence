# 176-01 — Audit trail for settle gate throws

## Objective

Make `runSettleGates` catch any exception thrown by a gate impl and normalize it into a `refuse` `GateResult`, so every gate outcome — including a raw throw — flows through the existing refusal path that already writes a SUMMARY, instead of escaping uncaught to `settle.ts`'s outer catch (~line 654), which prints stderr and exits 1 with no SUMMARY at all.

## Acceptance Criteria

### AC-1: Throwing gate produces an audited SUMMARY
Given any settle gate impl in `GATE_REGISTRY` (e.g. `build-test-must-pass`) throws during its invocation in `runSettleGates`
When `cadence settle run` executes and that gate is reached
Then the driver catches the exception, records a `gates` provenance entry with `status: 'refused'` and a `reason` containing the thrown error's message, `runSettleGates` returns `refused: true`, and `settle.ts`'s existing refusal branch (~line 393-421) persists `SUMMARY.json`/`SUMMARY.md` — loop state (`activeDraft`/`loopPosition`) is left untouched, same as any other gate refusal, and the process exits 1.

### AC-2: Non-throwing gate behavior is unchanged
Given no gate impl throws
When `cadence settle run` executes across a mix of passing and normally-refusing gates
Then gate provenance, accumulator merging, and SUMMARY output are byte-identical to pre-change behavior (regression safety for the existing `registry.test.ts` / `registry-coverage.test.ts` / `registry-logging.test.ts` suites).

## Tasks

### T1: Normalize gate-impl throws to a refuse outcome
- files: `packages/core/src/gates/registry.ts`
- action: In `runSettleGates`, wrap the `const res: GateResult = await entry.impl(ctx);` call (~line 141) in try/catch. On catch, build a synthetic `GateResult` (`{ outcome: 'refuse', reason: `${gate}: threw — ${message}` }`), log it (`log.warn('gate threw', { gate, error: message })`), push a `{ gate, status: 'refused', reason }` provenance entry, and `return { acc, refused: true, gates }` — mirroring the existing refuse branch already below it (lines 143-147) so it reuses the same accumulator/provenance/SUMMARY machinery security-audit's internal try/catch already benefits from.
- verify: Add a test in `packages/core/tests/gates/registry.test.ts` using the `deps.registry` test seam to inject a gate impl that throws; assert `refused === true`, the last `gates` entry has `status: 'refused'` and a `reason` containing the thrown message, and no exception propagates out of `runSettleGates`.
- done: AC-1

### T2: Regression-guard existing pass/refuse flows
- files: `packages/core/tests/gates/registry.test.ts`
- action: Confirm (adding a case if none exists) that a normal pass-through run and a normal in-band `refuse` (a gate returning `{ outcome: 'refuse' }` without throwing) still produce identical `gates` provenance and `acc` merging after the try/catch wrap.
- verify: `pnpm --filter @manehorizons/cadence-core test -- gates/registry` (or the workspace's equivalent test command) green.
- done: AC-2

## Boundaries

- DO NOT touch `security-audit.ts`'s existing internal try/catch — it already normalizes its own throws; this phase only closes the gap for the other 8 gates via the shared driver.
- DO NOT change `GateResult`/`GateImpl` types in `gates/types.ts` — the synthesized refuse result must fit the existing `{ outcome: 'refuse', reason? }` shape.
- DO NOT change `settle.ts`'s refusal-handling block (~lines 393-421) — it already does the right thing once `refused: true` reaches it; this phase only ensures a throw reaches it that way.
- DO NOT add a `finally` block or resource-cleanup logic beyond the try/catch — no gate impl currently holds a resource across its single `await entry.impl(ctx)` call that needs one.
