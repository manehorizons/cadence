# 249-01 — Post-gate refusal SUMMARYs + finding-durability ledger closeout

## Objective

Extend phase 247's refused-SUMMARY writer (`writeRefusedSettleSummary`) to
the three post-gate `settle.ts` refusal families that still exit 1 with no
SUMMARY at all — AC derivation, anomaly/skill-audit, and evidence-floor —
so every refusal with a resolved draft/gate context leaves a record
identical in shape to the gate-loop refusal family phase 247 already
hardened, while durably closing out the finding-durability ledger
bookkeeping (`rec-20260731-010`, `rec-20260712-006`) that motivated this
arc.

## Context

**This phase's DRAFT input document
(`docs/handoffs/cadence-phase249-draft-input.md`) is stale on one load-bearing
point: T1/T2 are not still-pending work.** Verified live before drafting
(the guard checks the document itself specifies): `cadence decision list
--filter-rec rec-20260731-010` already returns `dec-20260802-003` ("Ledger
routing stays finalize-only on refusal..."); `cadence recommendation show
rec-20260731-010` already shows `status: deferred` with 2 evidence entries
and 1 linked decision; `cadence recommendation show rec-20260712-006`
already shows `readiness: ready-for-cadence-spec` with 2 evidence entries.
All three match the document's own AC-1 assertions for T1/T2 verbatim. This
work landed in local commits `7e487102`/`75403970` the night before the
draft-input document was written, but — this is the actual gap the document
was reacting to, just misdiagnosed — those commits were never pushed to
`origin/main`, so from a durability standpoint the bookkeeping might as
well not have existed. Landed via a pre-phase housekeeping PR (#359,
squash-merged as `9d561fbd`) before this worktree branched, specifically so
phase 249 starts from a base where the ledger state is real, not
tribal knowledge in one checkout. **T1/T2 below are therefore verify +
reconcile tasks, not the document's original create/mutate commands** —
re-running the original `decision add`/`recommendation promote` commands
verbatim would mint a duplicate decision and re-promote already-terminal
recommendations. The anti-skip contract's own idempotency-guard clause
(§3: "a guard firing is a report-back event, not a silent skip")
anticipates exactly this outcome.

**AC-1's `intelligence audit` clause, as originally sketched, is not just
unsatisfiable but a moving target — a raw count is the wrong shape
entirely.** `cadence intelligence audit` currently reports 148 issues (up
from the 145 `rec-20260802-003` documented at filing time). Independent
review + root-cause investigation during this SPEC's authoring found why:
`computeIntelligenceAudit` (`packages/core/src/intelligence/store/audit.ts`)
builds its valid-rec-id set from `recommendations[]` only and never
consults `archived[]` — so a decision/evidence entry whose rec is
*legitimately archived* (not lost, not deleted) is flagged as an orphan
indistinguishable from a genuinely-vanished rec. `recommendation-promote.ts`'s
`autoArchive: true` default means **every phase that closes by promoting
its source rec to `shipped` — the single-commit settle convention's normal
path — immediately orphans that rec's own evidence entries.** This is not
a fixed historical backlog; it is an ongoing generator, and **this phase's
own required closing action (promoting `rec-20260712-006` to `shipped`)
will trigger it.** Filed as evidence on `rec-20260802-003`
(`ev-20260802-014`) rather than a new rec — same subject, and it directly
answers that rec's own open question ("lost commits or a reconcile bug?").
A count-based AC clause would therefore fail the instant this phase
completes its own mandated work — not a defect to route around with a
bigger number, but a sign the clause needs a different shape entirely. AC-1
below replaces the count with a stability check on the two specific recs
this phase touches, which holds regardless of active/archived status.

**Verified: the three in-scope families need zero signature widening.**
`settleService` (`packages/core/src/services/settle.ts:1397-1526`) holds a
single `acc: SettleAccumulator` (from `runSettleGates(ctx)`, `~1457`) and a
single `gates: GateProvenance[]` in scope for its entire body, both
computed once, before any of the three in-scope refusal points are
reached:

- **AC derivation** (`deriveSettleAcResults`, refusal at `~961`, called
  from `settleService` at `~1460`): runs after the gate loop, so `gates` is
  already computed; the function itself already receives `acc` as a
  parameter, so `acc.codeReview`/`acc.securityAudit` are in scope at its
  own refusal point.
- **Anomaly/skill-audit** (`runAnomalyAndSkillAuditChecks`, refusal at
  `~1059`, called from `settleService` at `~1470`): the helper doesn't
  receive `acc`, but it doesn't need to — `settleService` itself still has
  `acc` (and `gates`) in scope at the call site.
- **Evidence floor** (`deriveEvidenceAndCheckFloor`, refusal at `~1153`,
  called from `settleService` at `~1487`): already receives `acc` directly
  as a parameter.

So the fix is not "thread payloads through each helper" — it is: at each
of the three `if (!result.ok) return result.result;` lines in
`settleService`, replace the bare return with
`return await writeRefusedSettleSummary(cwd, activePhase, state, draft,
progress, gates, acc.codeReview, acc.securityAudit, cadenceConfig,
foreignBinaryMismatch, now, io);` — the exact same writer, the exact same
`acc`, called from the orchestrator instead of from inside each helper.
None of `AcDerivationResult`, `AnomalyAndSkillAuditResult`, or
`EvidenceFloorResult` need a new field; none of `deriveSettleAcResults`,
`runAnomalyAndSkillAuditChecks`, or `deriveEvidenceAndCheckFloor` need a
new parameter. `writeRefusedSettleSummary`'s existing conditional
`contentHash`/snapshot-sibling behavior (phase 247) applies unchanged
because it is the same function, not a reimplementation.

**Verified: two existing tests assert the exact opposite of AC-2 and must
change, not just gain new assertions — later corrected to three during T4
(see As-built note below).** `packages/core/tests/cli/settle-auto.test.ts:106`
(`expect(existsSync(join(active.root, '.../01-01-SUMMARY.md'))).toBe(false);`)

(`expect(existsSync(summaryPath(active.root))).toBe(false);`) currently
assert that the AC-derivation and skill-audit refusals write no SUMMARY —
true today, false once AC-2 ships. These lines must flip from asserting
absence to asserting presence + shape as part of implementing AC-2; this is
not optional and not a suite regression, it is the test suite catching up
to the behavior change the phase exists to make. Checked exhaustively at
SPEC-authoring time (`grep -rniE "toBe\(false\)" packages/core/tests
--include=*.test.ts` filtered to SUMMARY-shaped paths): the evidence-floor
family (`settle.test.ts`'s `evidenceFloor` describe block, the
`AC-4/AC-1: refuses cadence settle run --auto...` test) has **no** existing
absence assertion to flip — it currently only checks `state.json`. That
family needs a **new** assertion added, not an existing one changed. A
third file, `packages/core/tests/mcp/trust/enforce.test.ts:401`, also
asserts SUMMARY absence but belongs to the out-of-scope precondition family
(a pre-`settleService` MCP-grant refusal) — unaffected by this phase.

## Constraints

- **Single refused-writer invariant preserved.** No fourth writer, no
  reimplementation of phase 247's conditional `contentHash`/sibling logic —
  route through the existing function.
- **No signature widening beyond what's proven necessary above.** If
  implementation discovers a call site genuinely lacks `acc`/`gates` in
  scope (contradicting this SPEC's verified read of `settle.ts`), that is a
  stop-and-reconcile moment against this document, not silent
  improvisation.
- **T1/T2 order.** Per the draft input's anti-skip contract: T1 and T2 must
  be DONE before any T3+ (scoping) or T4+ (implementation) work begins —
  even though T1/T2 are now verify-only, not create-only, the ordering
  still matters: it's the point where a stale assumption about ledger state
  would be caught before code changes compound it.
- **Non-goals (explicit, per the draft input's scope lock):**
  precondition/gate-set-resolution refusals stay silent by design (no
  resolved context to record); `rec-20260802-001`'s deep-verify
  registry-side gap is phase 250, not this phase; `rec-20260802-003`'s
  orphan-ledger cleanup (including the `archived[]`-blind-spot mechanism
  this phase's investigation added as evidence, `ev-20260802-014`) is a
  separate, already-filed recommendation — not resolved here; `rec-20260801-004`'s
  `shippedRef` "PR pending" cosmetic is left alone (no verified CLI path
  updates a ref on an already-shipped rec).
- **AC-1 has no code-behavior test coverage story — two pre-committed
  bypasses, not a settle-time discovery.** AC-1 asserts CLI-observable
  ledger state, not code behavior; no test can carry an `AC-1` assertion
  token. Phase 246 (also decision/ledger-only) precedent used only
  `--evidence-floor-bypass=AC-1:...` — but 246 was tier `quick-fix`, where
  `auto`'s gate-set deltas (`packages/core/src/gates/engine.ts`) omit
  `test-coverage` entirely, so the coverage gate never ran and needed no
  bypass. This phase is tier `standard`, where `auto`'s deltas *do* include
  `test-coverage` (verified directly against `engine.ts`'s `DELTAS` table),
  and that gate (`packages/core/src/gates/coverage.ts`) refuses the whole
  settle in assertion mode if *any* AC lacks a qualifying test reference —
  with only a blanket bypass available (`--allow-missing-coverage`, no
  per-AC flag, unlike evidence-floor). So this phase settles with **both**:
  `--evidence-floor-bypass AC-1:ledger-state verification via CLI show/list
  output, not code behavior — no test can carry this AC's token (phase 246
  precedent, tier difference required also bypassing test-coverage)` and
  `--allow-missing-coverage` (blanket — AC-2/3/4's real test coverage in T5
  is still verifiable by reading the test files directly; the gate itself
  can't check per-AC here, but the SUMMARY's per-AC evidence field still
  reports accurately). Decided now, not discovered at settle time.
- **Report-back item, not an AC:** after this phase's own settle promotes
  `rec-20260712-006` (per the single-commit settle convention's
  promote-and-ship step), re-run `cadence recommendation show` on both
  `rec-20260731-010` and `rec-20260712-006` and confirm both remain fully
  resolvable regardless of `archived[]` status. This is deliberately a
  report-back observation rather than an AC clause, because it can only be
  checked after the AC gate has already run (see AC-1).
- **`cadence intelligence audit`'s issue count is expected to increase when
  this phase settles — explained, not a regression.** Promoting
  `rec-20260712-006` to `shipped` auto-archives it
  (`recommendation-promote.ts`'s `autoArchive: true` default), which — per
  the `computeIntelligenceAudit` gap documented above — orphans its own
  evidence entries. A future reader of this phase's SUMMARY seeing the
  audit count tick up should not treat that as something phase 249 broke;
  it is `rec-20260802-003`'s documented mechanism firing exactly as
  expected.
