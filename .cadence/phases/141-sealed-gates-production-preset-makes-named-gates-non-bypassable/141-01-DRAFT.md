# 141-01 — Sealed gates: production preset makes named gates non-bypassable

## Objective

Let the `production` preset name gates that ignore `--force` and their own per-gate `--allow-*` flag, so the strictest posture is actually non-bypassable instead of "bypassable-but-logged."

## Acceptance Criteria

### AC-1: `gates.sealed` config field exists
Given a `.cadence/config.json`
When it is loaded through `CadenceConfigZ`
Then it accepts an optional `gates.sealed: string[]` field (gate ids) that
defaults to `[]`, and a config predating this phase (missing the field)
still parses unchanged

### AC-2: `production` preset seals `test-coverage` and `build-test-must-pass`
Given `cadence init --gate-profile production` (or the `production` preset
directly)
When the resulting config is inspected
Then `gates.sealed` is `['test-coverage', 'build-test-must-pass']`; the
`solo` and `team` presets are unchanged (`gates.sealed` stays `[]`)

### AC-3: sealed `test-coverage` ignores `--force` and `--allow-missing-coverage`
Given a settle run whose config has `'test-coverage'` in `gates.sealed`, and
an AC with no linked test
When `cadence settle run --force` or `--allow-missing-coverage` is run
Then the gate still refuses, and its refusal message states the gate is
sealed and cannot be bypassed (naming `gates.sealed`)

### AC-4: sealed `build-test-must-pass` ignores `--force` and `--allow-failing-build`
Given a settle run whose config has `'build-test-must-pass'` in
`gates.sealed`, and a configured `testCommand` that exits non-zero
When `cadence settle run --force` or `--allow-failing-build` is run
Then the gate still refuses, and its refusal message states the gate is
sealed and cannot be bypassed (naming `gates.sealed`)

### AC-5: unsealed behavior is unchanged
Given a config with `gates.sealed` empty, absent, or naming a different
gate
When the same `--force` / `--allow-missing-coverage` / `--allow-failing-build`
flags are used on `test-coverage` / `build-test-must-pass`
Then the existing bypass behavior (and its existing bypass-notice logging)
is byte-for-byte unchanged

## Boundaries

- DO NOT seal any gate other than `test-coverage` and `build-test-must-pass` in this phase — other gates' bypass posture is unchanged.
- DO NOT change what makes `test-coverage`/`build-test-must-pass` refuse in the first place (coverage detection, test-run semantics) — sealing only removes the bypass, it does not add new refusal conditions.
- DO NOT change the `solo`/`team` presets' `gates.sealed` (stays `[]`, matching current unsealed behavior).
