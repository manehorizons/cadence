# 255-01 — Make Security and CodeQL merge-blocking

## Objective

Add stable security-success and codeql-success aggregator status checks (mirroring ci-success's if:always()+needs-result pattern) so a red Security or CodeQL run on main actually blocks merge, closing the gap where required_status_checks.contexts is exactly ["ci-success"] today and a failing or skipped security/CodeQL job blocks nothing (rec-20260804-006); the branch-protection edit that makes the new contexts required is named as an explicit post-merge operator action, not automated in this phase.

## Acceptance Criteria

### AC-1: security-success aggregates secret-scan + audit (sbom excluded)
Given security.yml has no aggregator job and its three jobs (secret-scan, audit, sbom) post individually with no branch-protection wiring
When a security-success job is added to security.yml, following ci-success's if: always() + explicit needs.<job>.result string-comparison pattern, needing [secret-scan, audit] only -- sbom generates a CycloneDX compliance artifact via a network fetch, not a security verdict, so it is deliberately excluded from the gate
Then a deliberately-failing secret-scan or audit job causes security-success to fail, and a deliberately-skipped one also causes security-success to fail (skip != success)

### AC-2: codeql-success gives CodeQL a stable, non-matrix-derived required-check name
Given codeql.yml's analyze job reports its status under a matrix-derived context name (analyze (javascript-typescript)) that would silently stop reporting if the language matrix ever changes, per the same reasoning ci.yml:45-47 already documents for why ci-success exists as its own job
When a codeql-success job is added to codeql.yml needing [analyze] with the same if:always() + string-compare pattern
Then codeql-success reports under a name independent of the language matrix, and a deliberately-failing or deliberately-skipped analyze run causes codeql-success to fail

### AC-3: honest gate scope is documented, not just implemented
Given codeql-success gates on the analyze job completing, not on zero CodeQL alerts (CodeQL's analyze step does not fail by default on findings), while audit and secret-scan genuinely fail on undocumented high/critical advisories or leaked secrets
When this distinction is stated explicitly in a workflow comment and/or docs/security
Then no doc, workflow comment, or later SUMMARY overclaims that CodeQL findings now block merge -- only that the analysis job running to completion is required

### AC-4: security-ci.test.ts covers both new aggregators
Given packages/core/tests/docs/security-ci.test.ts already asserts security.yml and codeql.yml trigger config, and the 253-01 audit-job describe block is the established precedent for asserting a job's needs/step wiring by slicing the raw workflow text
When new describe blocks assert security-success's needs list, if: always(), and the string-compare-to-success pattern, and the same for codeql-success needing [analyze]
Then the test suite fails if either aggregator job is removed, loses an entry from its needs list, or drops the always()/string-compare pattern

### AC-5: branch-protection change named as an explicit, sequenced, non-automated operator task
Given main's required_status_checks.contexts is exactly ["ci-success"] today (confirmed live via gh api), and GitHub blocks a PR indefinitely on a required context that has never reported
When the DRAFT records, as its own task (not a side note), that adding security-success and codeql-success to branch protection's required contexts must happen only after this phase's PR merges to main and both jobs have reported at least once
Then the task text is unambiguous that this is a GitHub Settings operator action, not a cadence/CLI command, and states the merge-then-add ordering explicitly

## Boundaries

- Do NOT touch `ci.yml` or `ci-success` -- this phase adds new aggregator jobs to `security.yml` and `codeql.yml` only. Restructuring `security.yml`/`codeql.yml` into `workflow_call` reusable workflows invoked from `ci.yml` (the alternative "extend ci-success's needs" design) was considered and rejected: `needs:` only resolves within a single workflow file, so that path either duplicates every PR's security/CodeQL runs or strips their independent `push`/`pull_request` triggers, silently starts running them on `ci.yml`'s extra `feat/kernel-assurance-v2` trigger branch (which security.yml/codeql.yml deliberately don't target), and contradicts security.yml's own stated design note ("Keep new jobs additive, one per concern"). `workflow_run` was also considered and rejected as strictly worse. Do not revisit this path without re-litigating with the operator.
- Do NOT add `sbom` to `security-success`'s `needs` -- it is a compliance-artifact generation step (network fetch via `pnpm dlx @cyclonedx/cyclonedx-npm`), not a security verdict, and rec-20260804-006's intent is undocumented advisories and leaked secrets blocking merge, not SBOM-generation flakiness blocking merge.
- Do NOT modify GitHub branch protection settings via any script, API call, or `gh` command in this phase's BUILD tasks -- that is T5/AC-5's explicit, sequenced, post-merge operator action, not automated code.
- Do NOT modify `pnpm.overrides` targets or `audit-exceptions.md`'s exception rows beyond the honest-scope note added in T3 -- that content belongs to phases 253/254, already shipped.
- Do NOT touch `ci.yml`'s `feat/kernel-assurance-v2` trigger asymmetry -- unrelated to this phase's scope.
