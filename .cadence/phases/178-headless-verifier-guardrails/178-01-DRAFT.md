# 178-01 — Guardrails for headless-CLI verifier

## Objective

Harden the `host-cli` verifier provider (`packages/core/src/verify/host-cli-client.ts`,
`verifier-factory.ts`) against the three risks recorded in rec-20260710-006:
invisible consumption of the user's host-CLI subscription quota during
verification calls, an unguarded self-invocation path when cadence itself is
already running inside the same host CLI it would spawn headlessly, and a
subprocess hang in CI/non-interactive environments when the spawned process
never exits. Each guardrail is loud (stderr notice, matching the existing
`MOCK_FALLBACK_BANNER` / per-call warning style) and additive — none of the
existing per-call mock-fallback behavior for the already-handled failure
modes (`not-found`, `nonzero-exit`, `output-error`) changes.

## Acceptance Criteria

### AC-1: quota-transparency notice on first real call
Given the `host-cli` provider is selected for any verifier family
When a verification call is actually spawned (config selection alone does not count)
Then a stderr notice is emitted, once per process, stating that the call
consumes the host CLI's own subscription/usage quota rather than a
separately metered API key — mirroring `docs/providers.md`'s now-resolved
"Deferred: batching + quota transparency" gap

### AC-2: self-invocation is refused, not silently nested
Given cadence is itself running inside a headless/non-interactive session of
the same host-CLI family it would spawn (detected via that family's
documented session environment variable, e.g. `CLAUDECODE` for `claude`)
When the `host-cli` provider is selected and a call is attempted
Then the spawn is refused before any subprocess is created, a loud stderr
warning names the self-invocation risk, and the call falls back to `mock`
for that call — using the existing `wrapWithFallback`/`HostCliError`
fallback path rather than a second, parallel fallback mechanism

### AC-3: a hung subprocess times out instead of hanging forever
Given the spawned host-CLI subprocess never closes stdout or exits (the
"Known limitation" already documented in `docs/providers.md`)
When a configurable timeout elapses (env-discoverable via the existing
`discoverKey` seam, with a sane default; test-injectable so tests never
sleep for the real duration)
Then the subprocess is killed, `spawnCapture` rejects with a new
`HostCliError` (`reason: 'timeout'`), and the existing per-call
mock-fallback wrapper (`wrapWithFallback`) catches it exactly like any other
`HostCliError` today

## Tasks

### T1: Quota-transparency stderr notice
- files: `packages/core/src/verify/host-cli-client.ts`, `packages/core/tests/verify/host-cli-client.test.ts`
- action: emit a one-time-per-process stderr notice (reuse the existing `getLogger()`/warn-banner style, not a new ad hoc `console.log`) the first time `hostCliJSON` actually spawns a subprocess; do not warn on selection alone, and do not repeat the notice on subsequent calls in the same process
- verify: a test asserts the notice fires exactly once across multiple `hostCliJSON` calls in one process and never fires when the provider isn't `host-cli`
- done: AC-1

### T2: Self-invocation guard
- files: `packages/core/src/verify/host-cli-client.ts`, `packages/core/src/verify/verifier-factory.ts`, `packages/core/tests/verify/host-cli-client.test.ts`, `packages/core/tests/verify/verifier-factory.test.ts`, `packages/core/tests/verify/per-task.test.ts`, `packages/core/tests/verify/json-repair.test.ts`
- action: detect the running-inside-the-same-host-CLI-family condition via that family's session env var before spawning; on detection, throw/reject a `HostCliError` (new `reason: 'self-invocation'`) with a message naming the risk, so it flows through the existing `wrapWithFallback` mock-fallback path unchanged
- verify: a test sets the detection env var and asserts the call falls back to mock with the self-invocation warning instead of spawning; a test without the env var set proceeds to spawn normally (no false positives)
- done: AC-2
- **As-built amendment (2026-07-12, caught in T2 review):** detection via `CLAUDECODE` fires for *any* Claude-Code-spawned subprocess or IDE integrated terminal, not only genuine recursive `cadence`-spawns-`claude`-spawns-`cadence` nesting — this is this repo's own standard operator workflow (CLAUDE.md items 4-5, subagent-driven builds). Pre-existing `host-cli-client.test.ts` tests were pinned to `env: {}` to stay deterministic, but two other pre-existing suites that call `hostCliJSON`/`HostCliPerTaskVerifier` without pinning `env` (`per-task.test.ts`, `json-repair.test.ts`) started failing (5 tests total) when the suite runs from inside a Claude Code session — never in CI, which doesn't set `CLAUDECODE`, but real in this repo's own mandated re-verification workflow. Added those two files to T2's boundary to pin `env: {}` there too, matching the existing pattern, rather than leaving a silently-red suite under the repo's own standard invocation.

### T3: Subprocess spawn timeout
- files: `packages/core/src/verify/host-cli-client.ts`, `packages/core/tests/verify/host-cli-client.test.ts`
- action: add a configurable timeout around `spawnCapture` (env-discoverable default, test-injectable override) that kills the child process and rejects with `HostCliError({ reason: 'timeout' })` if the process neither closes stdout nor exits in time
- verify: a test with a fake `SpawnFn` that never closes/exits confirms the call rejects with `reason: 'timeout'` well within the test's own timeout budget (no real sleeping), and a test with a normally-closing fake process confirms no regression
- done: AC-3

- verify: doc text matches the shipped behavior (reviewed by hand; no existing doc-content test targets this file's prose)
- done: AC-1, AC-2, AC-3
- depends: T1, T2, T3

## Boundaries

- DO NOT wire a `host-cli` builder for any verifier family beyond the ones
  already wired (`per-task-verify`) — that is out of scope, tracked
  separately as "current scope: per-task-verify only" in `docs/providers.md`.
- DO NOT implement request batching — explicitly still deferred.
- DO NOT change the behavior or messages of the existing `not-found` /
  `nonzero-exit` / `output-error` fallback paths; only add the new
  `self-invocation` and `timeout` reasons alongside them.
- DO NOT add a new runtime dependency for the timeout (use `AbortController`/
  `setTimeout` + `child.kill()`, already available in Node).
