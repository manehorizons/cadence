# 245-01 — Finding-identity hash: drop anchor + severity volatility

## Objective

computeFindingId (packages/core/src/verify/finding-identity.ts) currently hashes anchor.kind, anchor.ref, and severity alongside file and normalized message. Both anchor and severity can legitimately change across settles for the same underlying defect: the DRAFT-amendment/anchor-earning workflow deliberately re-anchors a previously-gap finding (criteria-anchor-corpus.test.ts's own 'AC-5 round trip' proves this), and severity is live LLM classification under real providers. Either change currently mints a new id for an unchanged defect, which phase 242's ledger dedup (keyed on Finding.id) misses, minting a duplicate Recommendation. Narrow the identity hash to (file, normalized message) only, and fix deriveRoutingCandidates' intra-settle merge logic, which currently assumes severity is invariant within a matched-id group.

## Acceptance Criteria

### AC-1: identity is stable across anchor changes
Given the same file, severity, and message with two different anchors (anchor:{kind:'none'} and anchor:{kind:'ac',ref:'AC-1'})
When computeFindingId is invoked for both
Then it returns the identical id

### AC-2: identity is stable across severity changes
Given the same file, anchor, and message with two different severities ('medium' and 'high')
When computeFindingId is invoked for both
Then it returns the identical id

### AC-3: identity remains sensitive to file and message differences
Given two findings that differ only in file, or only in normalized message text
When computeFindingId is invoked for each
Then the two ids are different

### AC-4: AC-5 round-trip proves identity survives the anchor-earning workflow
Given criteria-anchor-corpus.test.ts's existing AC-5 round-trip scenario (same finding, DRAFT amended to add AC-1 coverage)
When the before and after anchored findings are compared
Then their id fields are asserted equal

### AC-5: routing-candidate merge no longer assumes severity is invariant within a matched group
Given two occurrences of the same finding id within one settle whose severities disagree
When deriveRoutingCandidates merges them into one routing candidate
Then the merged candidate takes the most severe of the group's severities
