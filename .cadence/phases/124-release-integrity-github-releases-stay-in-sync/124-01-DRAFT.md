# 124-01 — Release integrity: GitHub releases stay in sync

## Objective

Make the manual Release workflow finish the whole public release record, not just npm
and a tag. After a successful publish, GitHub must have a non-draft release for the
same `v<version>` tag, populated from the package changelog, and the workflow must
verify npm, tag, and GitHub release agreement before it exits green.

## Acceptance Criteria

### AC-1: release workflow creates or updates the GitHub Release
Given the Release workflow has published the public packages and pushed `v<version>`
When the release-integrity step runs
Then it creates or updates the GitHub Release for that exact tag with notes derived
from the core changelog and marks it as the latest release.

### AC-2: reruns are idempotent and mismatches fail loudly
Given the tag or release already exists
When the workflow is rerun for the same version
Then the step updates/validates the existing release instead of creating an
`untagged-*` draft; if npm, tag, or release metadata disagree, the step exits
non-zero with the exact mismatched package/tag/release named.

### AC-3: post-publish verification covers all public packages
Given the Release workflow published the package set
When the release-integrity verification runs
Then every non-private `@manehorizons/cadence-*` package under `packages/` is
checked on npm for the same version as `packages/core/package.json`, and the
remote `v<version>` tag plus GitHub Release metadata are checked too.

### AC-4: release docs define "done"
Given a maintainer follows the release process
When they read the release documentation
Then "done" explicitly means npm packages, git tag, GitHub Release, and latest
release marker all agree.

### AC-5: implementation is covered by focused tests
Given the feature implementation is complete
When the relevant unit/docs tests run
Then changelog extraction, package-version checks, release-note rendering, and
workflow wiring are covered without touching npm or GitHub.

## Tasks

### T1: Add release-integrity script
- files: `scripts/release-integrity.mjs`
- action: discover public packages, validate lockstep versions, extract the
  `packages/core/CHANGELOG.md` entry, create/update the GitHub Release, and verify
  npm/tag/release agreement.
- verify: script pure helpers are unit-tested without network access.
- done: AC-1, AC-2, AC-3, AC-5

### T2: Wire the Release workflow
- files: `.github/workflows/release.yml`
- action: run the script after the tag step on real publishes with `GH_TOKEN` and
  `NODE_AUTH_TOKEN` available; keep dry runs pack-only.
- verify: workflow wiring test asserts the script step and token environment.
- done: AC-1, AC-3, AC-5

### T3: Document release done-state
- files: `docs/release.md`, `docs/README.md`, `README.md`
- action: document the release checklist and the new GitHub Release automation.
- verify: docs mention npm + tag + GitHub Release + latest marker as the done bar.
- done: AC-4

## Boundaries

- DO NOT auto-publish a version from local developer machines.
- DO NOT make the dry-run workflow create tags or GitHub Releases.
- DO NOT add a new npm package or public CLI command for this internal release helper.
- DO NOT rely on long inline shell in the workflow when a tested helper is clearer.
