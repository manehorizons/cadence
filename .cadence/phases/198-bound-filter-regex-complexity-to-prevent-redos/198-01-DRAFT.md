# 198-01 — Bound --filter-regex complexity to prevent ReDoS

## Objective

Close issue #249 (CodeQL: ReDoS-shaped regex-injection) by rejecting pathological or oversized `--filter-regex` patterns before they are compiled with `new RegExp(...)` in `assumption.ts`, `decision.ts`, and `recommendation.ts`, with regression tests proving both the guard and that legitimate filter patterns keep working unchanged.

## Acceptance Criteria

### AC-1: oversized --filter-regex patterns are rejected before compilation
Given a `--filter-regex` value that exceeds a fixed maximum length
When `assumption list`, `decision list`, or `recommendation list` would otherwise compile it with `new RegExp`
Then the command exits non-zero with a clear stderr validation error and never calls `new RegExp` on the pattern

### AC-2: legitimate --filter-regex patterns are unaffected
Given a normal, previously-accepted `--filter-regex` value (simple literal, bounded character class, anchors, etc.)
When any of the three commands runs with that pattern
Then filtering behaves exactly as before the fix, with no output or exit-code drift

### AC-3: the guard is applied identically across all three commands
Given the same regex-safety bound
When `assumption.ts`, `decision.ts`, and `recommendation.ts` each handle `--filter-regex`
Then all three reject the same set of unsafe patterns — none is left unpatched

### AC-4: test suite passes
Given the fix and regression tests are in place
When the relevant test command runs
Then it exits successfully with no failing tests

- files: `packages/core/tests/cli/assumption.test.ts, packages/core/tests/cli/decision.test.ts, packages/core/tests/cli/recommendation.test.ts`
- action: add a failing regression test per command proving an overlong `--filter-regex` pattern is currently compiled/executed with no length guard
- verify: the new tests fail before the fix, for the expected reason (no guard present)
- done: AC-1

## Boundaries

- DO NOT add a new runtime dependency (e.g. a safe-regex library) without explicit operator sign-off — zero-runtime-dependency bias per `CLAUDE.md`.
- DO NOT change `--filter-regex`'s documented semantics for safe patterns (must remain backward-compatible with existing legitimate usage).
- DO NOT refactor `--filter-text`/`--filter-text-exact` handling or any other unrelated CLI filter logic while fixing this defect.
- DO NOT expand scope to MCP-tool exposure of these commands — issue #249 confirmed `--filter-regex` is not currently reachable via any MCP tool; that finding stands unless independently re-verified.
