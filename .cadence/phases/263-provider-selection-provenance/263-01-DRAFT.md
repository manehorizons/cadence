# 263-01 — Provider selection provenance (configured vs fallback vs empty-diff)

## Objective

Persisted gate provenance cannot currently distinguish a deliberately-configured provider from one that silently fell back to mock (at selection time in createVerifierFactory, or at call time in wrapWithFallback), nor from a real provider whose call structurally could not judge anything because its diff was empty -- three epistemically distinct states that today look identical or go unrecorded; this phase adds a providerSelection field populated at the single shared code path that already knows each answer, covering all seven verifier seams, without changing any provider identity string, the schema version, or any gate's pass/fail/refuse behavior.

## Acceptance Criteria

### AC-1: Selection-time fallback distinguishable from configured, across all seven seams
Given a gate configured for anthropic/local/host-cli whose prerequisite is missing at selection time (missing API key, missing local baseURL/model, or the family has no hostCli builder wired)
When createVerifierFactory falls through to spec.mock() at one of its three synchronous selection-time branches
Then the resulting verifier's result carries providerSelection: 'fallback', while a gate where mock (or a real provider) was the operator's actual configured choice carries providerSelection: 'configured' -- covering both the five settle-pipeline seams (deep-verify, per-task-verify, code-review, security-audit, plan-review; persisted in SUMMARY.json's gates[] via registry.ts) and the two cadence-spec-approve-only seams (spec-review, ui-spec-review; persisted via services/spec-approve.ts's untyped sidecar JSON -- <id>-SPEC-REVIEW.json / <id>-UI-SPEC-REVIEW.json, already carries provider/model today, confirmed via direct read, not governed by GateProvenanceZ)

### AC-2: Call-time fallback distinguishable the same way, with an explicit multi-call resolution
Given a gate configured for host-cli whose selection succeeds but a specific verifier call throws a HostCliError (binary missing, spawn failure, self-invocation guard)
When wrapWithFallback's Proxy delegates that call to the mock fallback
Then a gate run in which any verifier call fell back records providerSelection: 'fallback', even if other calls in that same run succeeded -- any-fallback-wins, not last-write-wins

### AC-3: Empty-diff non-empty-touchedFiles calls on code-review/security-audit are recorded as structurally unable to judge anything -- observation only
Given code-review or security-audit configured to a non-mock provider, with touchedFiles non-empty but ctx.diff() empty
When the gate runs exactly as it does today -- this phase does not change whether or when the provider call fires
Then persisted provenance for that gate records providerSelection: 'empty-diff' alongside its normal result; deep-verify and per-task-verify are unaffected (per-task-verify already surfaces empty diff via its own 'concerns' verdict) and spec-review/plan-review/ui-spec-review are out of scope (not diff-scoped)

### AC-4: Schema stays additive at the current version; historical corpus provably untouched; distinction queryable in one command
Given the 269+ historical SUMMARY.json records under .cadence/phases/
When providerSelection is added as an optional enum field with NO .default(...) (per the coverageScheme/coverageMode phase-239 precedent -- optional fields added after phase 232's schemaVersion 2 bump have never required a further bump) and cadence summary verify is run against every file
Then every historical record still parses and content-hashes identically, a regression test mirroring summary-coverage-scheme.test.ts's precedent fails if a .default() is ever added, and a single recorded command reports configured/fallback/empty-diff/absent counts across the whole corpus
