## Findings

| ID | Tag | Sev | What |
|----|-----|-----|------|
| **T1** | `works-as-designed` | — | Manual-approve gate: `n` refuses cleanly; the refuse path **leaves state untouched** (loop still DRAFT, re-runnable) — confirms ROADMAP 29.3 AC "refuse-and-leave-state-untouched"; `y` → BUILD. |
| **T2** | `ux` | MED | The y/n prompt shows only `[y/n]:`. Empty input and arbitrary garbage (`maybe`, `x`) are silently treated as decline and **consume one of 3 attempts with no "please answer y or n" feedback** — the user can't tell empty≠retry-forever, that garbage = decline, or how many attempts remain. A one-line "didn't understand — y or n (attempt 2/3)" re-prompt would remove the confusion. (`n` is decisive/immediate vs garbage gets retried — defensible but undocumented.) |
| **T3** | `ux` / robustness | MED | `cadence build task T1--status=DONE` (missing space, easy CLI typo) **silently recorded a task literally named `T1--status=DONE`** (`Recorded T1--status=DONE: DONE`) instead of erroring on an unknown task id. `build task` does not validate the id against the DRAFT's task list — a malformed/unknown id is accepted and recorded, masking the typo. Surprising; cost the user a confused retry. |
| **T4** | `ux` / correctness | MED (triage) | Interactive `skip` on **AC-2** let settle **succeed** (`Settled 01-01`) even though AC-2's task **T2 was never marked DONE** (only T1 was). `settle run --auto` refuses on a PENDING task; the interactive `skip` path appears to bypass that structural check ("skip falls through to other gates" — but no other gate caught the incomplete AC). Needs triage: is `skip` intended to mask a structurally-incomplete AC? If so, document it; if not, skip should still honor structural completeness or warn. |
| **T5** | `works-as-designed` | — | The interactive walker UI is clear and information-rich (separators, G/W/T, linked tests w/ line, touched files, pass→note / skip→no-note, echoed verdict). No friction. |
| **T6** | `works-as-designed` | — | Non-TTY refusal for both gates (approve, `settle --interactive`) — not re-driven; covered by prior session evidence (29.2 / F6): clear stderr, exit 1. |

## Headline / carry-forward

The TTY-positive paths **work and are well-presented** (T1, T5). Three actionable UX findings: **T2** (approve prompt gives no bad-input feedback / attempt count), **T3** (`build task` accepts an unvalidated task id — silently records typo'd ids), **T4** (interactive `skip` let settle pass an AC whose task never reached DONE — triage skip-vs-structural semantics). T3/T4 are the higher-value ones (real surprise / possible correctness gap). All deferred to a later remediation phase per the 29.1→29.7 pattern.

## REMEDIATION VERIFIED (Phase 29.8)

- **T2 — FIXED.** `askApproveVerdict` (draft.ts) now re-prompts unrecognized/empty input with `Please answer y or n (attempt N/3):` (1-indexed); explicit `y`/`n` still resolve on the first prompt; 3 unrecognized → refuse as before. Unit-tested via a recording prompter (`ask-approve-verdict.test.ts`).
- **T3 — FIXED.** `cadence build task <id>` now validates `<id>` against the active DRAFT's declared task ids; an unknown/typo'd id (incl. the `T1--status=DONE` missing-space case) errors `unknown task id "<id>" … Valid ids: …` exit 2 and records nothing (`build-task-validation.test.ts`). **Follow-up (carry-forward):** the `cadence block` / `needs-context` shortcuts call `recordTaskOutcome` directly and do **not** yet share this validation, so e.g. `cadence block BOGUS` can still ghost-record. Surfaced by the parity tests (now use declared ids). Tracked for a later small consistency phase — out of T3's `build task` scope.
- **T4 — FIXED.** Root cause was narrower than first stated: `settle run --interactive` *without* `--auto` skipped structural derivation entirely (`settle.ts` guard `if (opts.auto)`), so a skipped/unverdicted AC never blocked — the walker's "Skip falls through to other gates" was false without `--auto`. Guard widened to `if (opts.auto || interactiveRequested)`: when the walker runs, ACs not user-verdicted (explicit `--ac` / interactive pass/fail) are structurally derived and offenders refuse unless `--force`. Explicit/interactive pass/fail overrides unchanged. Tests: `settle-interactive.test.ts` T4 cases (skip + PENDING task → refuse; `--force` escapes).
- **T1/T5/T6 — unchanged** (works-as-designed).

All three actionable 29.3 findings closed. Shipped in Phase 29.8 (`29-tty-remediation/29-08`).
