# CADENCE Phase 39.7 — Lift the draft + build command gates — Design + Plan

> Seventh v1.3.0 phase, the heaviest. Extracts the four remaining inline
> enum gates — `coherence-check` (Phase 23.2), `approve` (24.1), `plan-review`
> (25.1 + 35.1 convergence) from `draft.ts`, and `per-task-verify` (24.2) from
> `build.ts` — into discrete `gates/*.ts` modules. **Bit-identical** at the CLI
> surface. After this, every enum gate except `anomaly-notify` has a discrete
> module (12/13), so the Phase 44.1 registry can be total.

## The contract problem (and the chosen shape)

The settle `GateImpl` is `(ctx: SettleContext) => Promise<GateResult>`, and
`SettleContext` is settle-bound (it carries `progress`, `touchedFiles`,
`coverage()`, `diff()`, settle verifiers, a `SettleAccumulator`). The draft/build
gates fire at **approve** and **task-record** time with different inputs and
outputs — they are NOT part of the settle dispatch. Forcing them through
`SettleContext` would be wrong.

**Chosen (operator-selected): separate contexts, shared `GateResult` shape.**
- New `gates/draft-types.ts` — `DraftGateContext` + `DraftGateImpl =
  (ctx: DraftGateContext) => Promise<GateResult>`.
- New `gates/build-types.ts` — `BuildGateContext` + `BuildGateImpl =
  (ctx: BuildGateContext) => Promise<GateResult<BuildProducts>>`.
- `GateResult` is generalized to `GateResult<P = SettleAccumulator>` so the
  per-task gate can carry a `PerTaskVerifyRecord` payload while settle and the
  draft gates keep the default `P` unchanged (no settle call-site churn —
  `GateResult` with no arg still means `GateResult<SettleAccumulator>`).
  `mergeInto` stays settle-only (draft/build routers read the single return
  directly; they don't accumulate).

Each gate reaches its collaborators (verifier, notifier, prompter, sidecar)
ONLY through `ctx` ports; the command router owns construction — exactly the
39.1 gate-collaborator policy, applied to two new surfaces.

### Reconciliation note for 44.1 (flagged, not resolved here)

These four gates fire in DRAFT/BUILD, never settle, so they carry
`DraftGateImpl`/`BuildGateImpl` types **distinct** from the settle `GateImpl`.
44.1's "registry total over `Gate` minus `anomaly-notify`" must therefore be a
registry over the **settle-dispatched subset**, not literally all 12 modules —
`GATE_ORDER` already implies a settle-specific ordering. 39.7 records this so
44.1 doesn't assume a single flat `Record<Gate, GateImpl>` spanning all surfaces.
The `registry-coverage` test's IMPLEMENTED bucket means "has a discrete
`gates/*.ts` module," which all 12 will; the settle-registry subset is a 44.1
refinement.

## Per-gate extraction

### coherence (`gates/coherence.ts`) — UNCONDITIONAL, bit-identical

`coherence-check` is an ALWAYS_FIRE gate but is **never** consulted via
`gateSet.gates.includes('coherence-check')` today — `draft check` and the
approve-time blocker check run `coherenceCheck` unconditionally. Per the settled
v1.3 decision (bit-identical except 39.2's operator-approved wiring), coherence
stays unconditional; wiring it to membership is explicitly OUT of scope.

Shared primitives, two consumers with different presentation (both reproduced
verbatim):
- `ctx.coherence()` — memoized `coherenceCheck(draft, state, projectMd)` on
  `DraftGateContext` (mirrors settle's `coverage()`); approve computes it once
  and reuses for the blocker refuse AND the later warn emit (today: line 271
  result reused at 466).
- `runCoherenceGate(ctx): GateResult` — approve-time blocker step: prints each
  blocker as `[BLOCK] <code>: <message>`, refuses (router sets `exitCode = 2`)
  when any block-severity issue exists.
- `emitCoherenceWarns(ctx, source)` — builds `coherence-warn` `AnomalyEvent`s
  for warn-severity issues and emits via `ctx.emit.coherenceWarn`, gated on
  `anomaly-notify` membership. `source` is `'coherence.check'` | `'coherence.approve'`.
- `printAllCoherenceIssues(result, io)` — the `draft check` presentation:
  `[BLOCK] code: msg` for blocks, `[WARN] [WARN] code: msg` for warns
  (the existing double-`[WARN]` is preserved — bit-identical).

`draft check` (a diagnostic command, not a gate-set member) is rebuilt on these
primitives: parse → `coherence: OK` short-circuit → print all → emit warns
(`coherence.check`, even when blocked) → `exitCode = 2` if blocked.

### approve (`gates/approve.ts`) — Phase 24.1 manual gate

`runApproveGate(ctx): GateResult`. Fires when `gateSet.gates.includes('approve')`
and `opts.approve !== false`. Builds the prompter via `ctx.prompter.create()`
(throws on non-TTY → refuse with the `manual-approve: <msg> Pass --no-approve …`
line), runs `askApproveVerdict` (kept exported — its own `ask-approve-verdict`
suite covers it), refuses on `no`. Soft-cap (DESIGN §4 M2, Phase 21.1) is NOT
the `approve` gate — it stays in the router as a pre-approve refusal.

### plan-review (`gates/plan-review.ts`) — Phase 25.1 + 35.1 convergence

`runPlanReviewGate(ctx): GateResult`, the heaviest. Fires on `plan-review`
membership. Reads prior attempts via the existing `ConvergenceSidecar` port
(reused from 39.4), runs `ctx.verifiers.planReview.verify({ draft })`, computes
`nextConvergence`, appends history + writes the sidecar (legacy 29.7 top-level
fields preserved byte-for-byte), and on `!pass` reproduces the three arms
exactly: bypass (`--allow-plan-review-failure`, emits unconverged when escalated,
`bypassed:true`) → fall through; reloop → refuse; escalate-no-bypass → emit
unconverged + refuse. Unconverged emission goes through
`ctx.emit.planReviewUnconverged` (the ROADMAP's `ctx.emitUnconverged`, named to
mirror `codeReviewUnconverged`).

### per-task-verify (`gates/per-task-verify.ts`) — Phase 24.2

`runPerTaskVerifyGate(ctx): GateResult<BuildProducts>`. Fires only on `DONE`
outcomes when `per-task-verify` is in the set. Parses the task's declared files,
diffs via a `ctx.diff(files)` port, runs `ctx.verifiers.perTask.verify`, and
returns `{ outcome, summaryPatch: { perTaskRecord } }`. Refuse path prints the
`per-task-verify refused: …` line + emits `per-task-fail` via `ctx.emit.perTaskFail`;
bypass path (`--allow-per-task-failure`) prints the proceed line + emits
`bypassed:true`. The router threads `perTaskRecord` into `recordTaskOutcome`.
Task-id validation (29.8), loop-violation handling, and status parsing stay in
the router.

## Decision Log

- **Generalize `GateResult<P>` over a build-specific result type.** Honors the
  operator's "shared `GateResult` shape" choice: same `{ outcome, summaryPatch?,
  flags? }` shape, payload parameterized. Default `P = SettleAccumulator` keeps
  every settle call site and the 8 existing gates untouched.
- **Coherence stays unconditional (not membership-wired).** Bit-identical is the
  v1.3 default; 39.2's wiring was a conscious operator exception. Wiring
  `coherence-check` to its (always-fire) membership is a separate, deferred call.
- **Soft-cap, task-id validation, loop-violation stay in the routers.** They are
  not named enum gates; pulling them into `gates/` would over-scope the phase and
  blur the gate/router boundary.
- **`DraftGateImpl`/`BuildGateImpl` are distinct from settle `GateImpl`.** They
  fire on other surfaces; conflating them would falsely imply settle dispatch.
  44.1's registry totality is over the settle subset — flagged above.
- **`ctx.coherence()` memoized like settle's `coverage()`.** Approve already
  computes `coherenceCheck` once and reuses it; the port preserves that single
  computation rather than re-running for the warn-emit step.
