# CADENCE Phase 44.1 — Engine-driven gate registry — Design + Plan

> The milestone endgame. Every settle enum gate is now a discrete `GateImpl`
> (39.1–39.7). Convert settle's hand-wired
> `if (gateSet.gates.includes(X)) { runXGate(ctx); mergeInto; halt-on-refuse }`
> sequence (settle.ts:343–441, ~100 LoC) into a single engine-driven dispatch:
> a `Record<SettleGate, GateEntry>` registry that a `runSettleGates(ctx)` driver
> walks in a canonical `GATE_ORDER`. This makes `gates/registry.ts` the one
> source of truth for *which* settle gates fire and *in what order* — instead of
> that order living implicitly in settle's call sequence. **Bit-identical at the
> CLI surface.**

## The two design subtleties (from research) that shape everything

### 1. Execution order ≠ matrix order → a `GATE_ORDER` constant is required

`gates/engine.ts` builds the effective set as `[...ALWAYS_FIRE, ...DELTAS]`
(matrix order). Settle executes in a *different*, hardcoded order (cheap→
expensive, so the first refusal is cheap). Observed settle execution order
(settle.ts:350–440):

1. `draft-read` → 2. `structural-verifier` → 3. `build-test-must-pass` →
4. `test-coverage` → 5. `interactive-verdict` → 6. `deep-verify` →
7. `code-review` → 8. `security-audit`

Iterating `effectiveGateSet().gates` in array order is therefore **not**
behavior-preserving. The driver must walk an explicit `GATE_ORDER: SettleGate[]`
constant (this exact 8-element sequence), not the gate-set array.

### 2. `deep-verify` + `interactive-verdict` are self-guarded (invoked unconditionally)

Six gates are membership-guarded in settle today
(`if (gateSet.gates.includes(g))`). But `deep-verify` and `interactive-verdict`
are called **unconditionally** (bare blocks, settle.ts:393–400, 406–413); their
trigger — `opts.deep`/`opts.interactive` **OR** membership — lives *inside* the
impl, which returns `{ outcome: 'pass' }` when not requested (deep-verify.ts:
10–14, interactive.ts:15–20). So `--deep` / `--interactive` can fire these gates
**without** the gate being in the set. A pure `GATE_ORDER ∩ gateSet.gates`
intersection would silently drop those flag-driven runs — a regression.

**Resolution:** each registry entry carries a `selfGuarded?: boolean`. The
driver invokes a gate iff `entry.selfGuarded || gateSet.gates.includes(gate)`.
`deep-verify` and `interactive-verdict` are the only `selfGuarded: true`
entries; they remain invoked-every-settle exactly as today (the impl no-ops
internally). This is the bit-identical choice. The alternative — promoting the
flags into the gate set so the driver is a clean intersection — would require
threading `opts` into `effectiveGateSet()` (which today takes only
state/config/draft) and is a larger, riskier change rejected here.

## Registry scope — settle-dispatched subset only (deviation from ROADMAP AC-1 text)

ROADMAP AC-1 says "`GATE_REGISTRY` is total over `Gate` minus `anomaly-notify`"
(12 gates). **This is corrected per the Phase 39.7 flag** (recorded in the
2026-05-30 handoff Key decisions): the registry covers ONLY the
**settle-dispatched** subset. The four 39.7 gates fire in DRAFT/BUILD, never
settle, and use different impl shapes (`DraftGateImpl`/`BuildGateImpl`), so they
cannot share this `GateImpl` registry:

| Excluded gate | Why | Where it lives |
|---|---|---|
| `coherence-check` | DRAFT (always-fire) | `gates/coherence.ts`, DraftGateImpl, dispatched in draft approve |
| `approve` | DRAFT | `gates/approve.ts`, DraftGateImpl |
| `plan-review` | DRAFT | `gates/plan-review.ts`, DraftGateImpl |
| `per-task-verify` | BUILD | `gates/per-task-verify.ts`, BuildGateImpl |
| `anomaly-notify` | not a dispatched gate — a post-gates notify predicate | inline in settle (collectAnomalies + notify) |

So the registry is total over an 8-member **`SettleGate`** type:

```ts
export type SettleGate = Exclude<
  Gate,
  'coherence-check' | 'approve' | 'plan-review' | 'per-task-verify' | 'anomaly-notify'
>;
```

`Record<SettleGate, GateEntry>` makes a missing entry a **compile error**
(exhaustive). This preserves AC-1's intent (totality enforced at the type level,
no gate silently un-dispatched) over the correct subset.

`checks/` modules (skill-audit 39.6, boundary 43.1) are not `Gate` enum members
and stay explicitly dispatched by settle, outside the registry — unchanged.

## Design — `packages/core/src/gates/registry.ts` (new)

```ts
import type { Gate } from '@cadence/types';
import type { GateImpl, GateResult, SettleAccumulator, SettleContext } from './types.js';
import { mergeInto } from './types.js';
import { runDraftReadGate } from './draft-read.js';
import { runStructuralVerifierGate } from './structural-verifier.js';
import { runBuildTestGate } from './build-test-must-pass.js';
import { runCoverageGate } from './coverage.js';
import { runInteractiveGate } from './interactive.js';
import { runDeepVerifyGate } from './deep-verify.js';
import { runCodeReviewGate } from './code-review.js';
import { runSecurityAuditGate } from './security-audit.js';

export type SettleGate = Exclude<
  Gate,
  'coherence-check' | 'approve' | 'plan-review' | 'per-task-verify' | 'anomaly-notify'
>;

interface GateEntry {
  readonly impl: GateImpl;
  /** Invoked unconditionally (impl self-guards on opts-OR-membership). Only
   *  deep-verify (--deep) + interactive-verdict (--interactive). */
  readonly selfGuarded?: boolean;
}

/** Total over SettleGate — missing an entry is a compile error. */
const GATE_REGISTRY: Record<SettleGate, GateEntry> = {
  'draft-read': { impl: runDraftReadGate },
  'structural-verifier': { impl: runStructuralVerifierGate },
  'build-test-must-pass': { impl: runBuildTestGate },
  'test-coverage': { impl: runCoverageGate },
  'interactive-verdict': { impl: runInteractiveGate, selfGuarded: true },
  'deep-verify': { impl: runDeepVerifyGate, selfGuarded: true },
  'code-review': { impl: runCodeReviewGate },
  'security-audit': { impl: runSecurityAuditGate },
};

/** Canonical settle EXECUTION order (≠ matrix order). The driver walks this. */
export const GATE_ORDER: SettleGate[] = [
  'draft-read',
  'structural-verifier',
  'build-test-must-pass',
  'test-coverage',
  'interactive-verdict',
  'deep-verify',
  'code-review',
  'security-audit',
];

export interface RunGatesResult {
  readonly acc: SettleAccumulator;
  readonly refused: boolean;
}

/** Drive the settle gate sequence. First refusing gate halts (it already wrote
 *  its own stderr); the caller sets exitCode. Bit-identical to settle.ts:343–441. */
export async function runSettleGates(ctx: SettleContext): Promise<RunGatesResult> {
  const acc: SettleAccumulator = { flags: {} };
  for (const gate of GATE_ORDER) {
    const entry = GATE_REGISTRY[gate];
    if (!entry.selfGuarded && !ctx.gateSet.gates.includes(gate)) continue;
    const res: GateResult = await entry.impl(ctx);
    mergeInto(acc, res);
    if (res.outcome === 'refuse') return { acc, refused: true };
  }
  return { acc, refused: false };
}
```

## Settle rewrite (settle.ts)

Replace the 343–441 dispatch block (~100 LoC) with:

```ts
const { acc, refused } = await runSettleGates(ctx);
if (refused) { process.exitCode = 1; return; }

const coverageBypassed = acc.flags.coverageBypassed === true;
const interactiveVerify = acc.interactiveVerify;
const deepVerify = acc.deepVerify;
const verifierFailure = acc.flags.verifierFailure;
const codeReviewFindings = acc.codeReview;
const securityAuditFindings = acc.securityAudit;
```

Drop the eight `runXGate` imports + the local `acc`/`mergeInto` plumbing; import
`runSettleGates` instead. **`interactiveRequested`** (settle.ts:389–392) stays a
settle local — it is consumed by the downstream AC-merge finalizer
(settle.ts:467), not by gate dispatch, so it is finalizer input, not control
flow. (It is the documented seam between the interactive gate and the finalizer
today; leaving it untouched keeps the change scoped to dispatch.) This is the
only `'interactive-verdict'` literal left in settle, and it is in a data
derivation, not the gate control flow — satisfying AC-2's "no gate name
hardcoded in settle's control flow."

**Why moving the `const x = acc.y` reads after the loop is safe:** gates receive
only `ctx` (never `acc`); no gate reads another gate's accumulator contribution
(research confirmed "no shared mutable state"). The interleaved `const`s in the
current block (coverageBypassed, interactiveVerify, …) are pure post-gate reads,
so collapsing them to after the driver returns is behavior-preserving.

## Tests (TDD)

1. **Order snapshot (AC-3):** a driver run over a ctx whose gateSet includes all
   8 gates, with each impl stubbed to record its name, asserts invocation order
   === `GATE_ORDER`.
2. **Membership gating:** a gate absent from `gateSet.gates` is skipped — EXCEPT
   `deep-verify`/`interactive-verdict`, which run even when absent (selfGuarded),
   reproducing `--deep`/`--interactive` without membership.
3. **First-refuse halts (AC-5):** a mid-order gate returning `refuse` stops the
   loop; later gates never invoked; `refused: true`; `acc` carries prior merges.
4. **Exhaustiveness (AC-1):** `GATE_ORDER` covers exactly `Object.keys
   (GATE_REGISTRY)` (set-equal); type-level totality is enforced by the
   `Record<SettleGate, …>` annotation (a missing key fails typecheck).
5. **`mergeInto` wiring:** a gate's `summaryPatch`/`flags` land in `acc`.

Plus the full existing settle E2E suite (every `cli/settle-*` + gate tests) must
pass unchanged — the real bit-identical proof at the CLI surface.

## ACs (reconciled)

1. `GATE_REGISTRY` is total over **`SettleGate`** (Gate minus the four
   draft/build gates and `anomaly-notify`) — missing an entry is a compile
   error. *(Corrected scope per the 39.7 flag; see "Registry scope" above.)*
2. Settle dispatches by walking `GATE_ORDER`; no gate name appears in settle's
   gate **control flow** (the lone `interactive-verdict` literal that remains is
   a finalizer data derivation, not dispatch).
3. Firing order matches the pre-44.1 execution sequence (snapshot-tested).
4. Adding a future settle gate = add the enum member + a `GATE_ORDER` entry + a
   `GATE_REGISTRY` entry; settle.ts is untouched.
5. Behavior bit-identical at the CLI surface (full settle E2E suite green).
