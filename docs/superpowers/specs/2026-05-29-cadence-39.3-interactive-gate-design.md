# CADENCE Phase 39.3 — Lift the interactive AC-walker into `gates/interactive.ts` — Design + Plan

> Third v1.3.0 phase. Extracts the Phase 16 `--interactive` per-AC walker from
> `settle.ts` into `gates/interactive.ts` against the 39.1 contract. **Pure
> extraction — bit-identical** (back to 39.1/draft-read discipline; no behavior
> change, unlike 39.2's two newly-wired gates). Adds the **prompter port** the
> 39.1 success-criterion predicted ("39.3 needs a prompter port").

## Summary

The interactive walker (`settle.ts:305–378`) is the most entangled gate: it
constructs a `Prompter` (scripted via `CADENCE_PROMPTER_SCRIPT`, else
`StdinPrompter` with a non-TTY refusal), runs `walkAcsInteractively`, refuses on
any non-overridden `fail` verdict, and **produces `interactiveVerify`** which
the post-loop AC-merge finalizer (`settle.ts:647–717`) consumes. Extraction:

- New `gates/interactive.ts` exposing `runInteractiveGate: GateImpl`. It returns
  `{ outcome, summaryPatch: { interactiveVerify } }` — `interactiveVerify` is
  already a `SettleAccumulator` field (39.1), so the accumulator is unchanged.
- New **prompter port** on `SettleContext`: `prompter: { create(): Prompter }`.
  The scripted-vs-stdin construction (incl. the env seam) moves into the
  settle-side adapter; the gate calls `ctx.prompter.create()` inside a try/catch
  and refuses (same `interactive: <err>` stderr) when it throws (non-TTY).
- `SettleOpts` gains `interactive?: boolean`.
- `settle.ts` keeps `interactiveRequested` as a local (the AC-merge finalizer at
  `:671` reads it) and bridges `const interactiveVerify = acc.interactiveVerify`
  exactly as 39.1 bridged `deepVerify`/`verifierFailure`.

## Bit-identical notes

- **stdout preserved.** `walkAcsInteractively` writes AC rendering to
  `process.stdout` by default; the gate calls it with no `write` opt, so that
  output is byte-for-byte preserved. Refusal/`interactive:` lines stay on stderr
  via `ctx.io.err`.
- **Shared coverage scan.** The inline walker called `scanTestCoverage` a second
  time; the gate uses `ctx.coverage()` (memoized, 39.1) instead — same Map,
  same result, now shared with the coverage/deep gates. Behaviour-equivalent.
- **Refuse-and-halt + verdict order** identical: per-`fail` lines then the
  summary line, `process.exitCode = 1` at the driver.

## Decision Log

- **Prompter as a `create()` factory port, not a ready `Prompter`.** Construction
  can fail (non-TTY) and that failure is a gate refusal with specific stderr;
  modelling it as `create()` inside the gate keeps the refuse-and-halt inside the
  gate (testable) while the env/TTY policy stays in the settle adapter. Rejected:
  injecting an already-built `Prompter` (the throw path couldn't be a GateResult).
- **Gate uses `ctx.coverage()`, not a fresh scan.** Realises the 39.1
  memoization intent (walker was the 3rd independent scan). Bit-identical Map.
- **`interactiveRequested` stays a settle local.** The AC-merge finalizer needs
  it independently of whether the gate produced verdicts; it is a pure function
  of `opts`+`gateSet`, computed once in settle. Not threaded through GateResult.
